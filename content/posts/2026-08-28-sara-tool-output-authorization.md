도구 증강 에이전트는 신뢰할 수 없는 Observation(웹페이지, 이메일, 검색 결과)에서 파일 ID 같은 런타임 정보를 얻어 후속 호출을 구체화해야 해서, 외부 콘텐츠를 차단하면 정상 작업 능력까지 같이 무너짐. SARA가 이 딜레마를 역할 분리로 풀었음. 원문은 [arXiv:2608.27146](https://arxiv.org/abs/2608.27146).

1. 결과부터. GPT-4o-mini와 Gemini-2.5-Flash-Lite로 AgentDojo·AgentDyn 4개 설정에서 Agent-only의 공격 성공률(ASR) 15.79-33.28%가 SARA 적용 후 0.06-0.63%로 떨어졌고, 공격 하 작업 완수율(UA)은 Agent-only 기준 이상을 유지했음. 보안을 얻으려 유틸리티를 버리는 트레이드오프를 피한 게 핵심 성과임.

2. 위협 모델이 명확함. 신뢰 대상은 사용자 요청, 도구 스키마, SARA 런타임, 실제 도구 실행기임. 불신 대상은 모든 도구 Observation의 자연어 내용과 구조화 필드임. 공격 목표는 Observation에 삽입된 지시가 사용자가 인가하지 않은 실제 외부 효과(발송, 권한 변경, 거래)를 유발하는 것임. 단순 데이터 의존은 보호 대상에서 제외해서 오보호를 피함.

3. 구성 요소 다섯 개임. 첫째, 인가 계약 K = Contract(U)로 각 항목을 (효과 유형, 허용 연산, 대상 범위, 정적 인자)로 표현함. K는 과제 수준의 권한 상한이고 런타임 정보는 기존 권한을 구체화할 수만 있음. 상한을 못 넘게 하는 설계임.

4. 둘째, 맥락 격리 Action Probe임. Observation을 받아 행동 유도 의미 존재 여부를 STATIC/ACTIONABLE으로 판정하고, 도구 수준 액션 발자국과 (도구, 인자 경로, 정규화 값) 형태의 인자 근원 앵커를 뽑음. 셋째, ACTIONABLE이 한 번이라도 관측되면 트레이토리가 EXPOSED로 전환되고 액션 오리진은 후속 도구 단계를 건너 지속됨. 한 번 오염된 근원은 사라지지 않는다는 추적 원칙임.

5. 넷째, 감사된 실행 이력임. 허가되어 성공한 호출만 기록하고 증거 능력을 DATA_ONLY(패스트패스, 인자 값으로만 사용)와 GOAL_BOUND(실행 체인·인자 바인딩 판정 참여)로 구분함. 다섯째, No-History-Promotion임. 액션 유도 근원이 부여된 인자가 실행 이력에 재등장하더라도 그 재등장만으로 오리진이 소멸되거나 실행 권한으로 승격되지 않게 함. 실행 이력을 통한 권한 세탁을 차단하는 장치인데, 이게 실무적으로 제일 값진 아이디어임.

6. 실행 경계 심사. 후보 호출은 K, 오리진 집합, 실행 이력을 근거로 목표 지지·실행 체인 지지·인자 수준 지지를 모두 충족해야 실행됨. 부작용 없는 조회 호출은 Probe 발자국과 중복되는 경우만 심사하고 나머지는 패스트패스라서 비용도 관리됨.

7. CaMeL과의 비교가 흥미로움. CaMeL은 ASR 0.11-0.28%로 더 낮지만 정상 작업 비용이 큼. Agent-only 대비 정상 작업 감소폭이 SARA는 5.79-11.82%p인데 CaMeL은 15.94-39.71%p임. 보안 강도와 유틸리티 보존의 균형에서 SARA가 실무 친화적이라는 결론이 나옴. Spotlighting은 ASR 22.97%가 잔존하고 Tool Filter·IPIGuard는 ASR은 낮지만 UA가 43-45%로 무너짐.

8. 백본 일반화. Llama3.1-8B, Llama3.3-70B, Qwen2.5-14B, Qwen3-32B에서 AgentDojo 기준 Llama3.1-8B만 4.02%에서 1.64%로 떨어지고 나머지는 0.03% 이하임. 소형 백본에서 잔여 ASR이 관측되는 건 Probe의 의미 판별이 모델 용량에 부분 의존한다는 뜻임. 논문이 완전한 의미 판별을 가정하지 않고 오심사 통과를 방어 실패로 정직하게 계산하는 것도 신뢰 포인트임.

9. 내 하네스에 적용할 것 세 가지. 첫째, 각 과제 시작 시 인가 계약(허용 효과 유형과 대상 범위)을 명시적으로 선언하고, 실행 전에 호출이 그 계약 안에 있는지 코드로 검사함. LLM의 판단이 아니라 코드 심사가 경계를 소유하는 구조임. 둘째, 외부 콘텐츠에서 온 인자에는 출처 태그를 붙이고, 그 태그가 실행 이력을 거쳐도 권한으로 승격되지 않게 함. No-History-Promotion의 원칙을 그대로 이식하는 것임. 셋째, 부작용 있는 호출(발송, 삭제, 결제)만 전수 심사하고 조회는 패스트패스로 비용을 관리함.

10. 문제제기. 에이전트와 실행기 사이에 런타임 배치가 필요해서 API형 에이전트 서비스에 끼워넣기 어려울 수 있고, 사용자 요청·도구 스키마·실행기의 무결성을 신뢰해야 한다는 전제가 있음. 그리고 Probe 자체가 LLM이라 완벽한 의미 판별은 아니라는 한계를 논문도 인정함.

11. 결론. 인젝션 방어의 정답은 입력을 차단하는 게 아니라 실행 경계에서 권한 근거를 심사하는 것임. "이 호출을 승인할 권리가 어디서 왔는가"를 코드가 물을 수 있는 구조가 있으면, Observation이 아무리 오염돼도 무단 효과는 실행 단계에서 막힘.
