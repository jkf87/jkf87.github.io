과학 소프트웨어를 LLM 에이전트가 학습할 수 있는 실행 환경으로 바꾸는 인프라가 나옴. ScienceIDE(arXiv:2609.19134). 저자들이 "과학 경험 병목" 해결이라고 부르는 문제의 정체가 명확함. 과학 코드는 돌아가기만 하면 끝이 아니라 수치 오차 허용 범위와 도메인 관례까지 맞아야 진짜 성공이라서 기존 코딩 벤치마크로는 학습 경험을 만들 수 없다는 것. 흐름 시뮬레이션에서 랜덤 시드 때문에 결과가 흔들리면 점별 오차 비교로는 정상 실행과 결함을 구분 못 하니까 모멘트·분포·보존량 같은 관측 가능량을 비교하는 합격 정책을 따로 설계해야 함.

1. 핵심 구조가 세 가지임. 전문가가 모듈 경계와 합격 기준을 고정하면 에이전트가 코드를 고치거나 구현해서 시뮬레이션을 돌림. 검증자가 컴파일 후 실제 과학 시뮬레이션을 실행해 보상을 계산해서 보상 자체가 검증 가능한 RL 설정이 됨. 그 경험으로 Qwen3.5-4B/9B를 학습시키니 과학 코드 수리 성적이 크게 오르고 일반 코딩·추론 벤치마크로도 전이됨. 등록된 태스크가 64개 환경 27개 코드베이스에서 2,812개. PLUTO, Athena++, MITgcm 같은 실제 연구 코드가 환경임.

![ScienceIDE 기술 개요](/images/2026-09-17-scienceide-scientific-code-agent-environments/fig-2-p4.png)

2. 가장 중요한 설계가 공식 테스트를 "캘리브레이션된 검증"으로 컴파일하는 과정임. 모듈별로 공식 유닛/회귀 테스트와 예제를 조사하고 노미널 실행과 변형 초기조건 실행을 비교해 수치 민감도를 측정함. 그리고 각 검증에 "어떤 과학적 편향을 걸러내는지"를 설명하는 warrant를 붙임. 검증이 왜 존재하는지 감사할 수 있게 하는 것. 그리고 "제안은 넓게, 증명은 실행으로" 원칙. AI가 만든 변환 후보가 태스크가 되려면 결함 주입 기준으로 정상 witness와 결함 baseline이 실행 결과에서 실제로 갈라지는 behavioral contrast를 보여야 함. 논문과 레포를 모아놨다고 학습 환경이 되는 게 아니라는 주장의 근거가 이 검증 절차임.

![태스크 검증 구조](/images/2026-09-17-scienceide-scientific-code-agent-environments/fig-5-p8.png)

3. 벤치마크 결과를 읽는 법이 instructive함. ScienceIDE-Hard 85개 태스크(수리 52 + 구현 33)에서 성공 조건이 코드 실행이 아니라 프라이빗 과학 기준과의 수치 합치. 15개 모델을 1시간 예산으로 돌려서 Claude Fable 5.1이 67.1%로 최상위. 근데 저자가 정직하게 상위권 순위가 통계적으로 확정되지 않았다고 명시함. Opus와 Astra의 반복 구간이 겹침. 그리고 예산이 순서를 바꿈. 10분 시점에서는 Astra가 49.6%로 Fable(25.9%)을 크게 앞서는데 약 31분에서 역전됨. 비용도 Fable이 태스크당 추정 7달러 수준으로 모델에 따라 몇 배 차이. 벤치마크 숫자만 보고 모델을 사는 관행에 대한 반례 자료임.

![ScienceIDE-Hard 결과](/images/2026-09-17-scienceide-scientific-code-agent-environments/fig-7-p10.png)

4. RL 파트가 핵심 기여임. 검증자가 에피소드 끝에 시뮬레이션을 돌려 점수를 주므로 보상이 outcome-only. 수십 턴, 수만 토큰짜리 트랙토리에 끝에 한 번 보상이 오는 구조라 일반 RL보다 훨씬 어려움. 구현 디테일이 실무적임. 롤아웃은 vLLM(고처리량 배칭 추론을 위한 오픈소스 LLM 서빙 엔진), 학습은 veRL 기반 커스텀 PSRL 트레이너, 에피소드 실행은 harbor 컨테이너. 롤아웃 GPU와 학습 GPU를 분리해 병렬로 돌리고 token-level truncated importance sampling(오래된 롤아웃 데이터의 영향을 현재 정책과의 확률 차이에 비례해 잘라내 보정하는 기법)으로 1-step staleness를 보정. 그리고 예산 초과로 잘린 에피소드의 토큰을 마스킹하니 학습이 안정화됨. 잘린 에피소드를 0보상으로 그대로 쓰면 "열심히 시도한 긴 에피소드"가 억제되는 문제가 생김. 결과는 30스텝 만에 LAPS 0.357 → 0.857, MITgcm-biogeo 0.286 → 0.571. 트렁케이션 비율도 39.5% → 6.6%로 감소해서 정책이 "죽어라 오래 시도하다 끊기는" 에피소드를 "검증자 판정까지 도달하는" 에피소드로 바꾼 것.

5. SFT 결과는 전이가 균일하지 않다는 점까지 데이터로 보여줌. 검증된 시연 트랙토리로 Qwen3.5 계열을 SFT하니 PLUTO-Dust 수리 보상이 0.0000 → 0.3333, LAPS 0.3125 → 0.5000이고 일반 벤치마크도 BBH Word Sorting +33.6pp, HumanEvalFix JS +10.98pp 등 15개 매칭 비교에서 개선. 단 HumanEvalFix Python(9B)은 86.11 → 77.78로 하락한 사례도 있음. 과학 경험이 만능이 아니라 검증 가능한 경험을 잘 만들면 학습이 된다는 게 정확한 읽기임.

![SFT 벤치마크 전이](/images/2026-09-17-scienceide-scientific-code-agent-environments/fig-10-p14.png)

6. 내 해석. 이 논문의 실제 기여는 모델이 아니라 환경 구축 방법론임. 2,812개 태스크라는 숫자보다 "전문가 합의를 실행 가능한 검증으로 컴파일하는 절차"가 재사용 가능한 자산이라는 점이 더 오래 남을 것. 이 구조는 과학 도메인뿐 아니라 사내 레거시 코드와 검증 시트에도 그대로 적용 가능함. 검증 가능한 기준이 이미 존재하는 도메인, 그러니까 수치 시뮬레이션 코드, 데이터 파이프라인 회귀 테스트, 계산 결과 허용 오차가 문서화된 시스템에서 전문가 합의 → 실행 검증 → 태스크 팩토리 구조를 돌려볼 수 있음. 이식 체크리스트는 이렇게음. 첫째, 우리 도메인의 합격 기준을 실행 가능한 검증으로 컴파일할 수 있는가. 둘째, 각 검증에 warrant, 즉 걸러내는 편향의 설명을 붙일 수 있는가. 셋째, 후보 태스크가 behavioral contrast를 실제 실행으로 증명하는가. 넷째, 잘린 에피소드의 토큰을 마스킹하는 처리를 학습 파이프라인에 넣었는가.
