에이전트 성능은 모델만큼 하네스가 결정함. ToFu는 MIT 라이선스 오픈소스 하네스인데, Claude Code보다 평균 28.4% 적은 토큰으로 SWE-bench Verified(실제 GitHub 이슈를 재현해 고치는 코딩 벤치마크 중 사람이 검증한 문제 세트)에서 더 높은 성능을 냈음. 토큰 절감이 곧 비용 절감이라는 점에서 실무적으로 훑어볼 가치가 충분함.

1. 문제의식은 세 개임. 단순한 인사에도 수천 토큰을 태우는 토큰 비효율, 영어 중심 LLM 구조 때문에 비영어권 사용자가 받는 페널티, 그리고 상용 하네스가 서버 측에서 조용히 바뀌어 연구 재현성이 없는 블랙박스 문제임.

2. 구조는 6개 모듈임. UI, 오케스트레이션 코어, 모델 추상화 레이어, 도구 런타임, 상태·지식, 컨텍스트 관리. 오케스트레이션 코어가 planner-worker-critic 루프를 명시적으로 돌리는 게 특징이고, 도구 런타임이 MCP(Model Context Protocol, 도구·데이터 소스를 표준 프로토콜로 에이전트에 연결하는 규격) 어댑터로 Overleaf, GitHub, Notion 등을 붙임.

![ToFu 아키텍처](/images/2026-07-18-tofu-white-box-agent-harness/fig-2-p3.png)

3. 핵심은 3계층 컨텍스트 압축임. 제1계층은 도구 출력 크기 인식 예산화. 검색 결과나 명령어 출력 같은 대용량 결과를 외부화하고 컴팩트한 미리보기로 대체함. 근데 소스코드 파일 읽기는 보수적으로 처리함. 잘라내면 에이전트가 다시 읽으러 와서 오히려 비용이 늘기 때문임.

4. 제2계층은 캐시 인식 마이크로 압축임. 최근 도구 결과는 보존하고 오래된 대용량 출력과 이미지는 플레이스홀더로 바꿈. 결정론적 규칙 기반이라 LLM 호출이 추가로 안 들고, 프롬프트 캐시 재사용을 무효화하지 않게 설계됐음. 캐시를 깨는 압축은 절감이 아니라 이중 지출이라는 판단임.

5. 제3계층은 쿼리 인식 의미적 압축임. 컨텍스트 한계에 다다르면 경량 모델이 오래된 대화를 현재 쿼리 기준으로 요약함. 중요한 턴은 고해상도, 유용한 턴은 압축, 무관한 터은 제거, 진행 중인 턴은 무조건 보존임. 보수적→적극적 순서로 단계 적용하는 게 핵심임.

6. 결과 숫자. 세 백본(opus 4.6, GLM 5.1, DeepSeek-v4-pro) 평균 Pass@1(한 번의 실행으로 과제를 성공할 확률)이 Claude Code 대비 +3.8%p, OpenCode 대비 +8.7%p. 토큰 사용량은 최대 43.6%까지 감소함. 더 많은 계산이 더 나은 성능을 보장하지 않는다는 걸 데이터로 보여줌.

7. 다국어는 translate-then-reason로 풂. 비영어 입력을 영어로 번역해 추론하고 원래 언어로 역번역함. 코드 블록은 보호 마커로 감쌈. 10개 언어 테스트에서 평균 2.5%p 향상. 단순하지만 모델의 영어 구조적 강점을 그대로 활용하는 접근임.

![다국어 강화 성능](/images/2026-07-18-tofu-white-box-agent-harness/fig-3-p6.png)

8. 메모리 설계도 실용적임. 구조화된 Markdown 레코드에 메타데이터를 붙이고 검색은 BM25(단어 일치 기반의 고전 검색 랭킹 함수)임. Dense embedding 대신 BM25를 고른 이유는 기술 메모리(라이브러리 이름, 에러 메시지, API)에서 정확한 용어 매칭이 더 잘 되기 때문임. 프로젝트별 메모리와 전역 메모리를 분리해서 재사용과 로컬 규칙을 둘 다 보존함.

9. 재미있는 건 ToFu가 Claude Code를 호출 가능한 도구로 쓸 수 있다는 점임. 하네스 위에 하네스를 얹는 메타 구조. 에이전트 생태계가 조합 가능(composable)해지는 방향을 보여주는 사례임.

10. 실무 채점. 우리가 돌리는 장기 자동화 작업에서 당장 베낄 것은 압축 3계층임. 도구 출력은 미리보기로 외부화, 캐시를 깨지 않는 규칙 기반 치환, 컨텍스트 한계 근처에서만 의미적 요약. 이 순서를 지키는 것만으로 토큰 청구서가 달라짐.

11. 근데 무조건 따라 하면 안 되는 부분도 있음. 코드 파일은 잘라내면 재읽기 비용이 발생한다는 걸 스스로 밝혔듯이, 압축은 대상별로 손익을 계산해야 함. 그리고 검증이 SWE-bench 중심이라 다른 도메인에서 같은 절감율이 나온다는 보장은 없음.

12. 그래도 이 논문의 메시지는 분명함. "어떤 LLM을 쓰느냐"만큼 "어떻게 감싸느냐"가 성능과 비용을 결정함. 화이트박스 하네스가 공개돼 있으니 자기 파이프라인의 컨텍스트 관리를 벤치마킹해볼 기준점으로 쓰면 됨.
