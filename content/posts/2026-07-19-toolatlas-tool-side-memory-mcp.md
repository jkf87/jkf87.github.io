MCP가 표준화되면서 같은 도구 서버를 수많은 에이전트가 부르는 세계가 됐음. 근데 각 에이전트는 도구를 시도하고, 실패하고, 다시 배움. 같은 실수를 수십 번 반복하는 셈임. ToolAtlas는 이 문제를 도구 경험을 공급자 쪽에 저장하는 걸로 풀었음.

1. 기존 방식인 에이전트 측 메모리엔 구조적 한계가 둘 있음. 첫째, 일반화 딜레마. 에이전트 A가 배운 도구 사용법은 A의 워크플로우와 액션 포맷에 얽혀서 B는 재사용 못 함. 둘째, 역량 맹목성. 메모리는 과거 태스크가 닿은 영역만 기록해서, 도구가 할 수 있지만 한 번도 안 쓴 기능과 조합 가능성이 영원히 빈칸으로 남음.

2. ToolAtlas의 발상 전환은 도구 메모리 그래프를 공급자가 한 번 구축하면 모든 하위 에이전트가 재사용하게 하는 것임. 도구 지식이 도구와 함께 사는 구조임.

![에이전트 측 메모리의 두 한계](/images/2026-07-19-toolatlas-tool-side-memory-mcp/fig-1-p1.png)

3. Stage 1은 부트스트래핑임. 도구 사양과 웹 사용 예시로 시드 태스크를 만들고, 각 태스크를 N회 독립 실행해서 검증기가 성공/실패를 라벨링함. 여기서 에이전트 중립적인 도구-근거 흔적을 추출해 초기 그래프를 만듦.

4. Stage 2가 차별점임. 수동적 궤적 수집이 아니라 그래프의 빈칸을 능동적으로 찾음. 외향 탐색은 아직 안 테스트한 경계 조건에 프로브를 생성하고, 내향 탐색은 미포착 기능과 도구 간 조합을 발굴함. 프로브를 실제로 실행해서 검증된 결과를 그래프에 다시 씀.

![ToolAtlas 파이프라인](/images/2026-07-19-toolatlas-tool-side-memory-mcp/fig-2-p4.png)

5. 그래프는 3개 레이어임. Tool-Trace Graph는 과거 실행의 중립적 흔적, Tool-Capability Graph는 기능·경계·공동 사용 엣지, Tool-Strategy Graph는 반복되는 오케스트레이션 원칙. 추론 시점엔 가벼운 내비게이터가 태스크에 맞게 관련 영역을 단계 확장하며 가이드를 만듦. 정적 top-k 검색이 아니라는 게 포인트임.

6. 결과. MCPMark와 MCP-Universe, 8개 MCP 서비스, 3개 백본(GPT-5.4, mini, Grok-4)에서 전 조합 향상. Grok-4는 pass@1 +21.61%. 약한 모델일수록 향상 폭이 큼. 도구 지식이 모델 능력을 대신 보완해주는 구조라 그럼.

7. 제일 실무적인 수치는 토큰임. 3.55M 토큰으로 Vanilla의 4.44M보다 적게 쓰고 최고 성과를 냄. 추론 토큰 20% 절감은 그대로 비용 절감임.

![토큰 대비 성능](/images/2026-07-19-toolatlas-tool-side-memory-mcp/fig-3-p8.png)

8. 교차 이전 검증이 이 논문의 설득력임. 학습 환경과 다른 인스턴스에서 baseline들은 Vanilla보다 55~77포인트 낮게 과적합됐는데 ToolAtlas는 pass@1 +24.16%. 메모리를 구축한 에이전트(SwitchAct)와 다른 에이전트(ReAct, CodeAct)로 바꿔도 +14~17% 향상이 유지됨. 에이전트 중립 저장이 실제로 작동한다는 증거임.

9. Ablation에서 Tool-Capability Graph를 빼니 -9.18%/-14.19%로 제일 크게 무너짐. 도구 중심 메모리 조직이 핵심이고, 기능 탐색이 경계 탐색보다 기여가 큼. 그래서 그래프의 빈칸을 능동적으로 메우는 게 중요했던 것임.

10. 실무 채점. 우리 인프라에 그대로 대입됨. 도구 래퍼나 MCP 서버를 자체 운영 중이라면, 호출 로그를 에이전트 세션에 버리지 말고 도구 단위로 축적하는 것. 성공/실패 검증이 붙은 실행 흔적을 도구 스키마 옆에 두면 새 에이전트·새 모델이 바로 검증된 지식에서 시작함.

11. 특히 모델을 자주 바꾸는 운영에서 이득이 큼. 모델 교체마다 도구 사용 노하우가 초기화되는 구조라면, 도구 쪽 지식은 모델과 무관하게 유지되니까. 약한 모델을 비용 때문에 쓰는 구간일수록 효용이 커지는 것도 실험과 일치함.

12. 한계도 보여야 함. 평가가 8개 서비스로 제한적이고, API가 바뀌면 재검증 메커니즘이 필요함. 그리고 공유 메모리라 오염(poisoning) 방지를 위한 접근 제어가 실배포 필수임. 도구 지식이 하나 오염되면 모든 하위 에이전트로 퍼지는 구조라 신뢰 문제가 에이전트보다 커짐.

13. 그래도 방향은 맞다고 봄. 도구 서버가 하나이고 에이전트가 여럿인 세계에서 도구 지식의 소유권은 도구에 있어야 함. 도구 문서를 정적 스펙에서 살아있는 메모리로 바꾸는 작업이 다음 단계임.
