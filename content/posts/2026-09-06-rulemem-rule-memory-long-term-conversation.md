장기 대화 에이전트의 메모리를 사실 저장소가 아니라 규칙 저장소로 만든 연구가 나옴. 검색 실패와 추론 실패를 분리해서 다룬다는 점이 실용적이라 정리함. 원문은 [arXiv:2609.03915](https://arxiv.org/abs/2609.03915).

1. 기존 메모리의 실패 지점부터. 사실 암기 방식(MemGPT, Mem0, LangMem, 대화에서 뽑은 사실을 임베딩으로 저장해 검색하는 메모리 시스템들)은 표면 유사도로 꺼내니 질문과 증거가 어휘적으로 멀면 검색 자체가 실패함. 사실 조직화 방식(Zep, A-MEM, 사실을 그래프로 연결해 두는 메모리 시스템들)은 그래프로 연결하지만 규모가 커지면 노이즈가 늘고 유효한 전제를 LLM이 스스로 추론해야 해서 논리 사슬이 끊기거나 환각이 생김.

![사실 메모리 vs 규칙 메모리](/images/2026-09-06-rulemem-rule-memory-long-term-conversation/figure1-paradigms.png)

2. 예시가 직관적임. "왜 Alice가 회의에 안 왔지?"라는 질문엔 "absent"라는 단어가 없음. "Alice가 휴가를 예약했다"는 기록에서 "여행 계획이 있으면 약속된 일정에 참석 못할 수 있다"는 규칙을 유도해야 답이 나옴. 사실 메모리로는 이 질문에 도달할 수 없다는 것.

![](/images/2026-09-06-rulemem-rule-memory-long-term-conversation/gifs/sherlock-deduction.gif)

3. RuleMem은 3단계로 돌아감. 첫째, 대화에서 (주체, 관계, 객체, 시각) 4원조 사실을 뽑고 그래프에서 경로를 샘플링해 같은 관계 패턴을 공통 규칙으로 유도함. 이때 고유명사를 [Person] 같은 타입 placeholder로 치환해 일반화함. 규칙은 자연어 Horn 절 — 전제들의 conjunct이 결론 하나로 가는 형식인데 형식 논리의 엄격함과 자연어의 유연함을 같이 씀.

![RuleMem 프레임워크](/images/2026-09-06-rulemem-rule-memory-long-term-conversation/figure2-framework.png)

![](/images/2026-09-06-rulemem-rule-memory-long-term-conversation/gifs/those-are-the-rules.gif)

4. 둘째가 검증임. LLM에 규칙을 뽑게 하면 과잉 일반화와 환각 규칙이 기본으로 나옴. 그래서 규칙 몸통을 조건으로 줬을 때 결론의 perplexity(언어모델이 문장을 예측할 때 느끼는 혼란도, 낮을수록 자연스러운 문장으로 보는 지표)가 얼마나 감소하는지(내부 일관성)와 실제 사실 증거가 결론을 지지하는지(외부 일관성)를 결합해 RPC 점수로 필터링함. 규칙 생성 후 검증 게이트를 다는 구조는 앞서 정리한 Recuris·PoisonedEvolution과 같은 원칙임.

5. 셋째가 규칙 기반 QA임. 활성화된 규칙의 몸통(전제)을 검색 쿼리로 써서 의미상 멀어도 논리적으로 관련된 사실을 회수함(Guided Recall). 그리고 질문+규칙+증거를 구조화해 생성하는데 규칙이 대전제, 사실이 소전제 역할을 함(Explicit Reasoning). RAG(검색 증강 생성, 검색한 문서를 근거로 답을 생성하는 방식)가 소전제만 공급한다는 지적이 이 논문의 핵심 프레임임.

6. 결과는 LoCoMo(긴 기간의 일상 대화를 여러 세션으로 기록해 둔 장기 대화 벤치마크)에서 Accuracy 78.05로 14개 baseline 평균보다 27.47점 높음. Multi-hop 82.43. Guided Recall을 붙이면 모든 프레임워크에서 검색률이 0.56→0.79로 +41.1%. Ablation에서 규칙 추상화를 빼면 baseline 수준으로 떨어지고 RPC를 빼면 오류 규칙이 연역을 방해해 성능이 저하됨 — 규칙화와 검증 둘 다 필요하다는 것.

![LoCoMo 결과 분석](/images/2026-09-06-rulemem-rule-memory-long-term-conversation/figure3-analysis.png)

7. 필자 적용 포인트. 블로그 파이프라인의 축적 로그도 같은 구조로 바꿀 수 있음. 파일별 성공/실패 기록을 그대로 쌓는 게 사실 암기라면, "특정 템플릿 구조의 글은 게이트에서 자주 걸린다" 같은 규칙으로 유도해 두면 다음 배치 계획과 검색 쿼리 양쪽에 쓸 수 있음. 규칙은 amortized 자산이라 매 쿼리 LLM 감독하는 것보다 싸다는 관점도 그대로 적용됨. 단 규칙 유도 후 perplexity 기반 검증을 달아야 오류 규칙이 추론을 오염시키지 않는다는 게 이 논문의 부속 교훈임.

8. 문제제기. 자연어 Horn 절에 형식적 변수 통일이 없어 오매칭 위험을 LLM 필터로만 막음. LoCoMo가 일상 대화 중심이라 도메인 지식 QA에서의 규칙 유도 품질은 미검증이고 RPC threshold도 경험적 튜닝이 필요함.

9. 남는 결론. 긴 대화형 제품(비서, CS 봇)의 메모리 설계에서 사실 그래프 다음 단계는 규칙 뱅크임. 검색 쿼리와 추론 대전제를 같은 자산에서 꺼내 쓴다는 설계는 구조가 단순해서 바로 이식할 수 있다는 게 이 논문의 실무적 매력임.
