"파서 하나 만들어 줘"라고 던지면 에이전트가 뭘 물어봐야 할까. 포맷, 에러 처리, 엣지 케이스. 바이브 코딩의 현실은 이렇게 요구사항이 불완전한 채 시작함. 근데 기존 벤치마크는 SWE-bench든 HumanEval이든 요구사항이 이미 완전하게 주어진 세계에서 채점했음. ICAE-Bench(모호한 요구사항에서 출발해 대화로 제약을 복원하게 하고 숨겨진 테스트로 채점하는 코딩 에이전트 벤치마크, 480과제·12언어)는 모호한 요구사항에서 출발해 대화로 제약을 복원하고 블랙박스 테스트(내부를 안 보여주고 입력-출력만 맞는지 확인하는 채점)로 채점하는 구조를 만듦. 결과가 뼈아픔. 최고 모델도 38%대임.

1. 과제 설계가 공들여져 있음. 실제 오픈소스 저장소에서 출발해 원본 코드의 동작에서 상세 PRD(제품 요구사항 문서)와 블랙박스 테스트를 추출함. 그다음 PRD에서 선택한 제약을 일부러 숨겨서 흐릿하게 만듦. 숨겨진 정보는 User Agent Data에 보관하고, 정답 코드와 테스트만 뺀 런타임 보존 Docker 이미지(필요한 라이브러리·설정은 그대로 들어있는 격리 실행 환경)를 만듦. 480개 과제에 12개 언어. 모호도도 L1(핵심 동작만), L2(제약 일부 복원), L3(대부분 유지), GroundPRD(완전 명시)로 단계를 나눔. User Agent는 자유롭게 답하는 LLM이 아니라 벤치마크가 작성한 기록에서만 답변함. 새 요구사항 발명과 정답 유출을 막는 통제임.

![ICAE-Bench 개요](/images/2026-07-28-icae-bench-interactive-coding-agent-evaluation/fig-1-p1.png)

2. 결과. Claude-Opus-4.8 Overall 38.2%, GPT-5.5 37.2%. Public 케이스(보이는 예시)는 각각 48.5%, 50.3%를 통과하는데 Hidden 케이스(숨겨진 엣지)에서는 35.5%, 32.8%로 떨어짐. 보이는 동작은 재현하지만 숨겨진 제약에서 무너진다는 패턴이 숫자로 드러남. Design 점수는 전 모델에서 5.5~12.1%. 돌아가는 코드는 만들어도 설계 품질은 기대 이하라는 것.

![PRD 모호도 수준별 Overall 합격률](/images/2026-07-28-icae-bench-interactive-coding-agent-evaluation/fig-6-p8.png)

3. 제일 중요한 발견은 "질문을 많이 한다고 잘하게 되지 않는다"임. 제약 커버리지를 높여도 합격률이 비례해서 오르지 않음. 병목은 정보 획득이 아니라 정보 활용임. User Agent에서 들은 제약을 컨텍스트에 보존하고, 구현 결정에 연결하고, 검증까지 이어가는 일관성 루프가 부족한 것. 그리고 GroundPRD(완전 명시)가 여전히 강한 상한선. 대화로 요구사항을 복구한 수준은 완전 명시에 못 미침. 어설프게 대화로 풀어주는 것보다 명세를 잘 써주는 게 아직 낫다는 뜻임.

4. 실행 환경 실험이 실무에 와닿음. 사고 모드를 켜면 Gemini-3.1-Pro가 26.7% → 36.6%로 10포인트 상승. 숙고는 실제로 도움이 됨. 근데 의존성을 더 제공하니 GLM-5.1이 37.4% → 28.4%로 하락함. 파일 수 191%, LOC 674% 폭발. 도구가 많아지면 복잡한 설계를 시도하다가 실패 지점만 늘어나는 것. 더 많은 도구가 더 나은 결과를 내지 않는다는 게 에이전트 환경 설계의 기본 상수로 다시 확인됨.

5. 프레임워크 효과도 있음. Claude Code가 OpenHands보다 안정적이고 파일 관리·도구 오케스트레이션에서 유리함. 그리고 실행 가능한 Public 케이스(예시 입출력)를 제공하는 게 정확도 향상으로 이어짐. 에이전트가 그걸 테스트로 써서 검증 루프를 만들 수 있기 때문. "예시를 문서로 주지 말고 실행 가능한 형태로 줘라"는 실무 지침이 나오는 대목임.

6. 내 결론은 이렇게임. 첫째, 바이브 코딩을 믿되 상한선을 알 것. 흐릿한 지시로 시작하면 최고 모델도 4할이다. 중요한 제약은 처음부터 명세에 써주는 게 이기는 글임. 둘째, 에이전트가 물어보는 질문에 성실히 답하는 것만으론 부족함. 답한 제약이 구현에 반영됐는지 추적해야 함. 나온 코드에서 제약이 빠졌는지 점검하는 게 사람의 몫. 셋째, 실행 가능한 예시 케이스를 주면 검증 루프가 생겨서 실제로 정확도가 오름. 넷째, 의존성과 도구는 필요한 만큼만. 풍부한 환경이 오히려 실패를 부름.

7. 남는 과제도 분명함. Design 점수가 전 모델 낮다는 건 동작하는 코드와 좋은 코드의 간극이 여전하다는 것. 그리고 요구사항-구현-검증의 일관성 루프를 유지하는 능력은 컨텍스트 크기 문제가 아니라 하네스 아키텍처 문제라는 지적. 다음 경쟁이 "코드를 잘 짜는 것"이 아니라 "요구사항을 끝까지 살려내는 것"이라는 방향 제시에 동의함.
