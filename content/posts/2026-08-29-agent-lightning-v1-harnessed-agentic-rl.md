에이전트 RL에서 "누가 환경 루프를 소유하나"라는 질문을 뒤집은 프레임워크가 v1.0으로 정식화돼서 정리함. Microsoft가 낸 것이고 후속 프레임워크들이 이미 따라간 방향이라 기준점 가치가 큼. 원문은 [arXiv:2608.17528](https://arxiv.org/abs/2608.17528).

1. 구조 전환이 핵심임. 기존 agentic RL은 트레이닝 엔진이 환경 루프를 직접 돌리고 하네스는 배포 시점 실행 장치였음. harnessed agentic RL은 하네스가 환경 상호작용 루프를 직접 소유하고 RL 트레이너는 LLM 요청-응답 쌍만 관찰함. 배포에 쓰는 하네스를 그대로 학습에 쓴다는 뜻이라 학습-배포 간극이 원천적으로 사라짐.

![Agent Lightning 구조: 하네스가 루프를 소유](/images/2026-08-29-agent-lightning-v1-harnessed-agentic-rl/agl-lite-controller.png)

2. 이 전환이 왜 어려운지 다섯 가지 난제로 정리돼 있음. 하나의 롤아웃이 여러 LLM 호출로 나뉘면 토큰 경계가 어긋나는 재토큰화, 호출 묶음 처리(sample merging), 이점 계산, loss 정규화, 스케줄링이 전부 새로 생김. 하네스가 멀티에이전트·서브에이전트·핸드오프까지 포함하면 롤아웃 하나가 동적 샘플 여러 개로 확장되니 당연함.

3. 설계 부품 세 가지가 실무적임. API Gateway는 하네스가 그대로 붙는 접점으로 롤아웃과 가중치 업데이트가 한 GPU 풀을 시분할 공유하게 조율함. Rollout Controller는 Kubernetes 잡/로컬 프로세스 실행 상태를 조정함. 그리고 샘플 수가 롤아웃마다 다를 때 롤아웃 단위 이점 + 롤아웃 단위 정규화 조합이 검증에서 가장 안정적이었다는 것 — 이건 다른 프레임워크 설계에도 적용되는 교훈임.

4. 성능 숫자가 임팩트를 말함. 코드 약 3,500줄, 학습 데이터 6K 예제만으로 Qwen3.5-9B의 SWE-bench Verified를 41.8→56.4%로 +14.6포인트. 동기식 대비 collocated async로 약 2배 속도에 GPU도 덜 씀. 코딩 외에 명령 이행·검색 에이전트 학습 다이내믹스도 같이 보고해서 도메인 일반성도 챙김.

5. 생태계 맥락도 중요함. 원래 Agent Lightning이 제안한 LLM 엔드포인트 프록시 방식을 verl Uni-Agent, AReaL 2.0, slime, Polar 같은 후속 프레임워크가 따라감. v1.0은 그 접근에 이름을 붙이고 재현 가능한 파이프라인으로 만든 버전임. 앞서 정리한 Molt(단일 백엔드·가독성 우선)와 이 논문(하네스 소유권 우선)이 같은 문제를 다른 축에서 푸는 셈이라 같이 읽으면 지도가 완성됨.

6. 필자 관점. 직접 훈련을 안 해도 관점 하나는 바로 쓸 수 있음. 학습-배포 동일성 원칙임. 파이프라인을 개선할 때 실험용 변형과 실배포 변형이 어긋나면 개선 효과가 실전에서 증발하는데, 하네스가 루프를 소유하면 그 간극이 없다는 것. 필자의 마이그레이션 파이프라인도 개선 실험을 실배포 하네스 위에서 돌리는 게 원칙이 됨.

7. 문제제기. 6K 예제라는 저비용 설정이 SWE-bench 도메인 기준이라 다른 도메인에서 같은 효율이 나올지는 확인이 필요함. 그리고 하네스가 복잡할수록 샘플 병합·스케줄링 난제가 커져서, 표면적 단순함이 실제 구현 난이도를 그대로 반영하진 않음.

8. 남는 결론. 에이전트 RL의 다음 표준 다툼에서 "하네스 소유권"이 축이 됐다는 게 이 논문의 위치임. 배포 하네스를 그대로 학습 환경으로 쓰는 구조는 이미 업계 수렴형이니, 프레임워크를 고를 때 이 축을 기준으로 보는 게 순서임.
