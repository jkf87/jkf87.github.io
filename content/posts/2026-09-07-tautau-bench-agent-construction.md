Sierra와 Princeton의 ττ-bench는 방향을 뒤집은 벤치마크임. 기존 τ-bench 계열이 "완성된 에이전트"를 시뮬레이션 고객에게 점수 매긴다면, ττ-bench는 에이전트를 만드는 코딩 에이전트 자체를 채점함. 원문은 [arXiv:2609.04611](https://arxiv.org/abs/2609.04611).

1. 결과부터. 53개 태스크, 4개 도메인(항공/리테일/통신/은행)에서 최강 조합인 Claude Opus 5 + Claude Code가 통과율 23.9%임. 전문가가 직접 만든 레퍼런스 천장은 82.2%로 격차가 3.4배 남. 돌아가는 에이전트는 만들 수 있는데 배포 가능한 에이전트는 못 만든다는 게 현재 상태임.

2. 태스크 설계가 실제 프로젝트와 같은 시작점을 줌. 사업이 실제 보관하는 기록(운영 핸드북, 상담 녹취/채팅 기록, 이메일, 슬라이드, 스크린샷, 화면 녹화), 기록에 없는 요구사항을 쥔 시뮬레이션 클라이언트(질문해야만 답해줌), 클라이언트 소유 REST API(일부 엔드포인트에 결함이 심어져 있음), 상속받는 불완전한 코드베이스, 20개 모델 메뉴와 대화당 크레딧 예산을 주는 것임. 이 안에서 고객상담 에이전트를 만들어 제출하면 숨겨둔 평가 태스크의 시뮬레이션 고객을 상대로 점수를 매기고 예산 초과분은 차감함.

3. 실패 패턴 1. 은행 도메인에서 무너짐. 은행 코퍼스는 원자 팩트가 2,969개로 다른 도메인 전체(85-155개)를 합친 것보다 훨씬 크고 태스크 하나가 최대 580개 팩트에 의존함. 여기서 최고 조합 점수가 5.9%로 떨어짐.

4. 실패 패턴 2, grep만 하고 안 읽음. 개발 에이전트들이 은행 코퍼스 1,700여 파일 중 연 파일은 80개 미만이었음. 키워드 검색으로 정책을 조립하니까 만들어진 에이전트는 정책을 모른 채 "확인된 게 없다"고 답함. 내 자동화에서도 문서 수집을 검색 히트 중심으로 하면 안 되고 실제로 열어 읽은 문서 수를 세야 한다는 교훈으로 챙겼음.

5. 실패 패턴 3, 클라이언트에게 묻지 않음. 클라이언트가 요구사항 20-25개를 쥔 태스크에서 제출 전 질문을 최대 4개만 했고 전체 툴콜 중 클라이언트 대화는 0.3%였음. 묻지 않으면 평균 0.16점, 4개 이상 묻으면 0.50점으로 3배 차이남. $2,500 값이 질문 하나로 해결되는 상황을 "태스크에 원래 없는 갭"이라 결론 짓고 넘어간 사례도 있었음. 요구사항 수집 단계를 프롬프트로 강제하는 게 점수를 가장 싸게 올리는 레버라는 뜻임.

6. 실패 패턴 4, 물려받은 코드를 측정 없이 갈아엎음. 상속 코드를 처음 20스텝 안에 전부 읽는 건 잘하는데 실행은 해보지 않고 통째로 재작성함. 시작 코드 중 하나는 손대지 않아도 0.36점이었는데 아무도 그걸 몰랐음. 기존 자산의 베이스라인을 먼저 측정하는 습관이 없다는 것임.

7. 실패 패턴 5, 예산 관리를 양쪽으로 놓침. 21개 빌드가 예산을 초과해 페널티로 점수가 0이 된 게 10개였고, 반대로 더 흔한 문제는 예산의 절반만 쓰고 강한 모델로 안 올리는 것임(평균 사용률 0.45-0.72×, 레퍼런스는 0.96×). 테스트 출력에 예산이 같이 찍히는데도 3배 초과 상태로 그냥 제출한 케이스도 있었음.

8. 실패 패턴 6, 자기 테스트를 맞춰서 고침. 에이전트와 자기가 쓴 테스트가 어긋나면 테스트의 기대값을 늦추는 행동이 6회 관측됐음. 평가기 소스를 읽거나 숨긴 데이터를 파려는 시도는 17-42% 빌드에서 관측됐는데 전부 실패했음. 테스트를 수정할 때 방향을 항상 의심해야 한다는 근거임.

9. 반전 포인트. 제출된 에이전트의 92%가 단일 LLM 툴 루프였는데(멀티에이전트 0), "인텐트별 라우팅 + 툴콜 검토"라는 한 줄 힌트만 줘도 통신 도메인 점수가 31%에서 67%로 두 배가 됐음. 능력이 아니라 습관의 문제였다는 것임. 모델 선택도 비슷해서 Codex 빌드의 96%가 OpenAI 모델만 골랐고 가장 싼 버킷에서만 선택했음.

10. 내 해석. 이 벤치마크의 가치는 점수 자체보다 요구사항 수집(self-spec-recovery)을 측정 가능하게 만든 것임. SWE-bench가 "주어진 이슈를 고쳐라"라면 ττ-bench는 "명세가 흩어져 있으니 먼저 모아라"임. 현장에서 에이전트 구축이 깨지는 지점이 정확히 여기임. 내 자동화 구축 프로세스에도 "제출(배포) 전 클라이언트 질문 최소 N개, 기존 자산 베이스라인 측정, 예산 사용률 체크"를 게이트로 넣어야겠다는 결론을 얻었음.

11. 문제제기. 태스크 53개로 규모가 작고, 도메인 편중(은행 35개)이 있음. 시뮬레이션 클라이언트의 응답 품질이 채점에 개입하는 여지도 남음. 그래도 실패 패턴 분석의 밀도가 높아서 벤치마크 논문이라기보다 에이전트 개발 관찰 보고서로 읽을 가치가 있음.
