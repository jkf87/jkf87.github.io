모델 가중치를 고정한 채 에이전트가 자기 실행 데이터를 근거로 자기 하네스를 반복 개선하는 루프가 나옴. Shanghai AI Lab의 [Self-Harness](https://arxiv.org/abs/2606.09498). 하네스 자동 개선을 검토 중인 사람에게 절차가 참고가 돼서 정리함.

1. 배경. 하네스(시스템 프롬프트, 도구, 메모리 정책, 오류 복구 절차)는 사람 전문가가 손으로 만들어서 새 모델 등장 속도를 못 따라감. 모델마다 실패 패턴이 달라서 효과적인 하네스 설계는 본질적으로 모델별 최적화 문제. 그리고 강한 외부 모델에게 고치게 하는 접근은 비싸고 프론티어 모델엔 쓸 선생이 없음 — 그래서 개선 대상 모델 자신이 제안자 역할까지 맡는 내부 루프를 제시함.

2. 3단계 루프. Weakness Mining — 실행 트레이스의 실패를 (최종 실패 원인, 행동의 인과적 지위, 추상 메커니즘) 세 성분이 정확히 일치할 때만 클러스터링. 타임아웃끼리 묶는 겉핥기 분류를 피하고 같은 하네스 개입으로 해결 가능한 실패만 모으는 것. Harness Proposal — 같은 모델이 제안자로 호출돼 K개의 상호 배타적 최소 수정을 병렬 생성, 감사 기록 동반. Proposal Validation — 승격 규칙은 Δ held-in ≥ 0, Δ held-out ≥ 0, max > 0. 어느 한쪽이라도 떨어지면 거절.

3. 숫자. 벤치마크 3개 × 모델 3종 = 9개 조합 전부에서 held-in/held-out 동시 상승(held-in은 개선에 쓴 과제군, held-out은 평가용으로 미리 떼어둔 과제군). 최대 +132%(Qwen3.5, AppWorld 22.5% → 52.2%; AppWorld는 API로 여러 앱을 조작하는 에이전트 벤치마크). Terminal-Bench-2.0(터미널 명령 과제 벤치마크)에서 Qwen3.5는 18.0% → 36.7%로 2배 이상.

4. 패턴 하나 — 약한 모델일수록 개선 폭이 큼. Qwen3.5-35B-A3B는 세 벤치마크에서 +104~132%. 초기 하네스가 최소 구성이라 약한 모델이 하네스 없이 잃는 점수가 컸다는 해석. Harness-Bench의 "약한 모델일수록 하네스 의존이 크다"와 정확히 같은 방향임.

5. 패턴 둘 — 채택된 수정은 작고 감사 가능함. 아티팩트 조기 생성, 도구 호출 50회 후 리다이렉트, 스키마 준수, 루프 브레이커, 셸 세션 간 변경사항 영속화 같은 것들. GLM-5/AppWorld는 null 완료 의미론, 진척 확인 알림, 페이지네이션 소진 규칙 세 개로 44.4% → 85.0%. 거창한 재설계가 아니라 최소 수정의 누적이라는 것.

6. 트레이스 사례가 생생함. 초기 하네스의 Qwen3.5는 extractor 스크립트를 만든 뒤 덮어쓰기 실패를 반복하다가 파일을 지우고 종료해 검증에 실패. 수정된 하네스는 툴 에러 시 시스템 프롬프트가 개입해 아티팩트를 재생성하고 검증자가 요구하는 파일을 남긴 채 종료. 모델은 그대로인데 행동이 바뀐 것.

7. 설계의 뼈대는 증거 파이프라인임. 실패 서명 클러스터 → 최소 수정 → 회귀 게이트. "수정 제안 생성"이 능력이 아니라 이 파이프라인이 효과의 핵심이라는 것 — 증거 번들이 구체적 수정 처방을 포함하지 않는 것도 평가자와 제안자를 분리하는 장치임. 격리 안 하면 제안자가 자기 실패를 자기 입맛대로 해석함.

8. 이건 하네스 진화 평가 연구(AI2·UW)의 과적합 비판에 대한 응답 구조이기도 함. held-out 분리, 이전 수정 이력 제공으로 반복 제안 방지, 회귀 게이트. Evo-Bench의 "하네스 민감도 선별"과 Skill-α의 "롤백 보상"이 하나로 묶인 형태임.

9. 여기서 문제제기. 논문이 스스로 명시함 — 이건 고정 벤치마크에서의 유계 하네스 수정 실험이지 열린 자기개선이 아님. 채택된 수정이 벤치마크 특화 실패 패턴을 반영할 수 있고, 검증자·트레이스 품질에 의존하며, 더 위험도가 높은 하네스 변경에는 패스율 비회귀를 넘어서는 승격 게이트가 필요하다고 저자들이 직접 씀.

10. 실무 적용. (1) 실행 트레이스에서 반복 실패를 원인·인과·메커니즘 삼중으로 클러스터링할 것 — 표면 증상으로 묶으면 잘못된 수정이 나옴. (2) 수정은 최소 단위로 나누고 감사 기록을 남길 것. (3) 승격은 held-in/held-out 둘 다 비회귀일 때만. (4) 하네스 수정과 모델 교체를 분리해서 생각할 것 — 가중치 고정 하에 하네스만 개선하는 실험이 모델 업그레이드 판단의 베이스라인이 됨.

11. 결론. 모델이 같아도 하네스가 바뀌면 행동이 바뀌고 성적이 오름 — 그 개선을 모델 스스로 하게 만든 것. 근데 효과의 원천이 제안 생성이 아니라 실패 클러스터링과 회귀 게이트라는 것 — 자동화의 우위는 생성이 아니라 증거 파이프라인에서 나온다는 결론임.
