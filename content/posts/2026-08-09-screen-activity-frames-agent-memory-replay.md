에이전트 메모리는 "사용자가 한 말"은 기억하는데 "사용자가 한 일"은 기억을 못 함. 그래서 컴퓨터를 쓰는 에이전트가 매번 똑같은 루틴을 다시 유추하느라 토큰을 태움. [이 논문](https://arxiv.org/abs/2608.05784)은 화면 캡처 스트림을 결정론적 코드만으로 에이전트 메모리로 컴파일하는 파이프라인을 제안함. 핵심은 모델을 컴파일 경로에서 완전히 빼는 것. 결과가 깔끔해서 정리함.

1. 배경. 화면 캡처 자체는 상용화돼 있음. Microsoft Recall, OpenAI Chronicle, ActivityWatch가 다 캡처함. 근데 하루 치 캡처가 약 2,000줄의 스냅샷 행이 되고 이걸 그대로 에이전트에 넣으면 126,812 토큰이 나옴. LLM으로 요약하면 되는데 요약은 실행마다 결과가 달라지고 존재하지 않는 활동을 지어냄. 원시 검색은 토큰 과다, LLM 요약은 비결정론적·환각 위험이라는 딜레마임.

2. 해법은 활동 프레임(activity frame)이라는 컴파일 단위임. 하나의 관심 구간으로, 애플리케이션과 사이트가 고정된 시간 구간. 프레임에 app, site, 시작-종료 시각, 지속시간, 타입드 페이지 레퍼런스(검색어, 프로필 등), 입력 통계(키 수, 클릭 수), 그리고 원시 행을 가리키는 증거 포인터가 들어감. 전부 코드로 계산됨. 세그먼테이션 규칙도 세 개의 상수로 정의됨. 프레임 갭 상한 90초, 90초 이상 입력 없으면 세션 종료, 20초 미만 잠깐 이탈은 인접 프레임에 병합. 튜닝이 아니라 캡처 주기에서 도출한 값이라는 것.

![측정 계층과 추론 계층 분리](/images/2026-08-09-screen-activity-frames-agent-memory-replay/fig-1-p3.png)

3. 브라우저 프레임은 URL을 파싱해서 46종의 타입드 페이지 레퍼런스(profile, search, repo, pull_request, email, ai_chat 등)를 만들고 매칭 안 되면 도메인과 함께 제네릭으로 떨어짐. 타입 시스템에서 데이터 손실이 없음. 그리고 2티어 구조가 이 설계의 정수임. 측정 티어는 결정론적 코드가 만들고, 추론 티어(태스크 라벨, 프로젝트 클러스터)는 선택적인데 네임스페이스, 신뢰도 태그, 증거 링크 세 가지를 강제함. 추론 티어를 통째로 삭제해도 측정 티어는 유효한 문서로 남음. 이 경계가 메모리 공격에 대한 방어가 됨. 증거 포인터로 기계적 재검증이 가능하고 추론 라벨이 사실처럼 위장할 수 없음.

4. 숫자가 전부를 말함. 하루 치 원시 JSON 126,812 토큰이 활동 프레임 문서로 34,815(3.6배), 컴팩트 컨텍스트 블록으로 1,469(86배)로 줄어듦. 86배 압축 블록은 시스템 프롬프트에 매번 넣을 수 있을 만큼 작음. QA 정확도는 64개 질문으로 독립 SQL 오라클과 비교해서 활동 프레임 블록이 98.4%. 반면 LLM 요약은 80.4%에 지속시간을 2.9배 부풀리고 존재하지 않는 야간 세션을 지어냈음. 그리고 결정론적 블록을 읽으면 미드티어 모델(Sonnet)이 프론티어 모델과 동일한 정확도를 냄. 좋은 표현이 모델 차이를 없애는 것.

![토큰 비교](/images/2026-08-09-screen-activity-frames-agent-memory-replay/fig-4-p6.png)

5. 재현성도 완벽함. 하루 전체 컴파일에 68밀리초. 같은 데이터를 두 번 컴파일하면 타임스탬프 제외 바이트 단위로 동일한 문서가 나옴. 요약은 매 실행마다 다른 결과를 냄. 내 하루가 어떻게 쪼개져 있는지도 보여줌. 43일 치 컴파일로 17,514개 프레임, 중앙값 0.5분, 68%가 1분 미만. 근데 서브-1분 프레임의 52%는 단일 스냅샷 통과라 실질 중앙값은 0.9분으로 인터럽션 연구의 기존 결과와 일치함.

6. 실무적으로 제일 유용한 건 루틴 오버헤드 비율 R임. 에이전트가 같은 루틴을 다시 유추하는 비용을 컴파일된 리플레이로 나눈 값인데, 가드 플랜 기준 중앙값 60배, 최소 스크립트 기준 343배. 즉 반복 루틴을 스크립트로 컴파일해두는 게 매번 유추시키는 것보다 수십~수백 배 싸다는 것. 근데 위임 가능한 재발률은 9.0%(시간 홀드아웃 예측 7.7%)로 전체 액션의 일부임. 웹 재방문률 40~58%와 혼동하면 안 되는데, 재방문이 전부 위임 가능한 작업은 아니라는 것. 무엇을 자동화할지 고를 때 실측 기반으로 골라야 한다는 교훈임.

7. 라이브 리플레이 증명도 인상적임. 2단계 루틴을 실제 브라우저에서 실행하는데 양쪽 스텝 모두 접근성 트리로 그라운딩되고 실행 시 모델 토큰 0건. 그리고 같은 플랜을 다른 페이지에서 실행하면 아무것도 매칭되지 않아서 안전하게 실패함. 컴파일된 기억이 틀린 곳에서 억지로 실행되지 않는다는 것. 이 "안전한 실패"가 리플레이 시스템의 필수 조건임.

8. 이 원칙은 화면 캡처가 아니라도 적용됨. 내 로그, 세션 히스토리, 작업 기록을 LLM으로 요약해서 메모리를 만들지 말고 결정론적 코드로 구조화된 문서를 만들고 LLM은 그걸 읽기만 하게 하는 것. 요약은 유창한 문장 뒤에 환각을 숨기는데, 컴파일은 증거 포인터로 검증 가능함. 그리고 추론 결과는 사실과 별도 티어에 신뢰도 태그를 달아두는 것. 참고로 구현에는 MCP 서버가 포함돼서 MCP 지원 에이전트에 6개 도구로 노출되고 전부 로컬에서 돌아감. 입력 내용(타이핑 텍스트)은 기본 제외라는 프라이버시 처리도 감안돼 있음.

9. 한계는 명확함. 단일 사용자 51일 코퍼스, 캡처 엔진별 어댑터 필요, 측정 티어는 의도를 모름(프로필 뷰 2건은 보고하지만 "영업 활동"은 아님), 화면 머무름이 주의와 같지 않음(입력 없는 구간이 45%). 그래도 결론은 유효함. 메모리의 신뢰성은 요약의 유창함이 아니라 재현성과 증거 링크에서 나오고, 그건 코드가 LLM보다 잘함.
