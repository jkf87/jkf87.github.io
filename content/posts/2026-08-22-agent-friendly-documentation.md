문서 개선 예산을 어디에 쓸지 실측 데이터로 답한 연구가 나옴. 코딩 에이전트가 실제로 무슨 문서를 읽는지 추적한 결과가 통념과 정반대였다는 것. 원문은 [arXiv:2608.20195](https://arxiv.org/abs/2608.20195).

1. 측정 설계부터. 실제 에이전트 코딩 세션 트랜스크립트 557개(이벤트 94,813개)와 에이전트가 연 풀리퀘스트 33,097개를 분석함. 문서 상호작용 총 3,033건, 세션의 56.7%가 최소 한 번은 문서를 읽거나 고침. 관측은 저장소 내 파일 기반이라 외부 브라우저 문서는 안 보인다는 범위가 명시돼 있음.

2. 핵심 결과는 문서 유형 분포임. 에이전트 인스트럭션 파일(AGENTS.md, CLAUDE.md)이 35.4%, 에이전트 워킹 노트(계획, thoughts/, 검증 로그)가 25.1%. 합쳐서 60.5%가 에이전트 전용 파일임. 반면 API 레퍼런스는 1.3%, 트러블슈팅 가이드는 0.4%. 인스트럭션 파일이 API 레퍼런스의 약 27배 상호작용을 받음. 문서 리서치 전통은 API 레퍼런스 품질이 중심이었는데 에이전트 소비자의 행동은 정반대라는 것.

3. "문서 읽고 곧바로 코드 수정" 그림도 기각됨. 문서 읽기 직후 코드 수정으로의 전이 확률이 0.002 — 읽기 1,328회 뒤 바로 고친 건 3번. 대신 문서 읽기 뒤엔 추가 문서 읽기(0.270)나 추론(0.245)이 이어짐. 문서 소비는 연쇄적이지 행동 촉발적이지 않다는 것.

4. 검증 쪽 결과가 더 흥미로움. 문서를 읽은 직후엔 오히려 테스트 실행(리프트 0.23)과 빌드(0.15)가 줄어듦. 그리고 문서를 기준으로 코드를 검증한 명시적 사례가 0건이었음. 문서는 검증 자원으로 안 쓰이고 있다는 것.

5. "막히면 문서" 통념도 지지 안 됨. 문서 상호작용의 70.2%는 자기 주도, 실패 유발은 7.5%. 실패 에피소드 2,034건의 첫 복구 행동 중 문서 읽기는 5.4%뿐이고 코드 다시 읽기(31.0%)와 같은 행동 재시도(19.9%)가 압도적임.

6. 방향성도 비대칭임. PR의 41.5%가 문서를 변경해서 문서가 입력이자 출력이긴 한데, 순서가 관측되는 경우 코드가 먼저인 게 82.5%. 문서가 코드를 안내하는 게 아니라 코드 변경 뒤에 따라오는 기록에 가깝다는 것.

7. 저자들이 세운 모델도 데이터로 정정됨. 인간 정보 탐색 연구의 선형 여정(발견→해석→적용→검증→갱신)을 가정했는데 검증·에스컬레이션 스테이지가 관측 0건이고 마지막 단계인 갱신이 1,401건으로 최대. 대신 상담 이엽(읽고 또 읽으며 추론으로 빠짐)과 생산 이엽(문서를 쓰고 고침)이 느슨하게 결합된 구조라는 결론임.

8. 필자 적용 포인트. 이 블로그 자동화도 똑같음. 필자 파이프라인에서 에이전트가 실제로 의존하는 문서는 AGENTS.md, 스킬 파일, 진행 로그이지 API 문서가 아님. 그래서 문서 투자 우선순위는 이렇게 됨 — 첫째, 인스트럭션 파일의 정확성과 명확성. 둘째, 자기완결적이고 로컬 검색 가능한 구조(링크 따라가기보다 한 파일에 다 있게). 셋째, 워킹 노트를 유지보수 표면으로 인식해서 주기적 정리. 이 세 가지가 API 레퍼런스 다듬기보다 앞섬.

9. 문제제기. 관측이 저장소 내 파일로 한정돼서 외부 문서 소비가 안 보임. 그리고 실행 가능한 문서(docstring, 스키마 계약)만 검증을 관측 가능하게 만들 수 있다는 건 가설 단계임. 그래도 부정 결과를 부록에 안 묻고 정면으로 보고하는 태도가 신뢰를 줌.

10. 남는 결론. 에이전트 친화적 문서 담론의 상당 부분이 직관 위에 서 있었는데 이 논문이 행동 데이터를 올려놓음. 다음 문서 개선 예산은 API 레퍼런스보다 AGENTS.md부터 점검하는 순서로 쓰는 게 데이터와 맞음.
