에이전트에 스킬을 추가하면 평균 패스율은 오름. 근데 그 평균 안에서 이미 풀리던 작업이 무너지고 있음. [Sentient Labs의 Regression Tax 논문](https://arxiv.org/abs/2607.22520)이 5,832회 실험으로 이 부작용을 정량화했는데, 스킬 회귀가 전체 이득의 59%를 상쇄했다는 게 핵심 숫자임. 스킬을 아무리 쌓아도 순효과가 잘 안 크는 이유를 세 가지 메커니즘으로 분해함. 내가 매일 스킬을 만들어 붙이는 입장에서 이건 무시 못 할 이야기라 정리함.

1. 실험 구성부터. OpenCode·MiniMax-M2.7, Codex·GPT-5.4-mini, Claude Code·Sonnet 4.6 세 스택(에이전트 하네스와 모델의 조합)에 스킬 없음, Anthropic 생성, OpenAI 생성, 연구진 자체 스킬 네 조건을 갖다 대고 오피스 자동화 벤치마크 두 개를 돌림. 스킬은 전부 같은 네 단계로 만듦. 베이스라인 실행, 궤적 분석으로 실패 신호 추출, 메타 스킬 크리에이터로 생성, 재평가. 공정한 비교임.

2. 첫 번째 통로가 가장 놀라움. **스킬 설명 삼투**임. 스킬 본문이 한 번도 실행되지 않았는데도, 시스템 프롬프트에 스킬 이름과 설명이 존재하는 것만으로 에이전트 행동이 바뀜. 관세율 이동평균 계산 작업에서 스킬 없이 정답을 내던 모델이 스킬 라이브러리를 추가하자 세 라이브러리 모두 똑같이 틀린 값을 냈음. 스킬은 단 한 번도 호출되지 않았는데 설명 속 "revised", "customs"라는 단어가 입력 해석 자체를 바꿔버린 것. 검색이나 마스킹 같은 호출 기반 선택으로는 절대 감지 못 하는 채널임. 설명이 항상 컨텍스트에 남아 있으니까.

3. 두 번째는 **그라운딩 전위**임. 스킬 본문이 실행되면 스킬이 제시하는 절차가 에이전트가 올바르게 읽고 있던 입력을 덮어씀. 회귀 81건 중 59건, 72.8%가 여기 해당했음. 대표 사례가 1934년과 1946년 공공지출 차이 계산인데, 베이스라인은 549와 407을 정확히 읽어 142를 냈는데 스킬 추가 후 네비게이션 스킬이 잘못된 수치 949로 유도해 542를 반환함. 산술은 맞았는데 입력이 스킬에 의해 밀린 것. 계산 능력 문제가 아니라 읽기가 오염된 것임.

4. 세 번째는 **검증 전위**임. 스킬이 에이전트가 원래 하던 출력 검증을 억제하거나 대체함. 절대 백분율 변화 작업에서 스킬 없이 정확히 +4.815를 내던 게 스킬 추가 후 부호가 바뀐 -4.816이 나옴. 크기는 정확했는데 "절댓값"이라는 요구사항 확인이 스킬 절차에 묻혀 생략된 것. 그리고 SpreadsheetBench(스프레드시트에 들어갈 수식을 만들어 셀 계산을 맞추게 하는 오피스 자동화 벤치마크)에서는 663개 실패 formula 중 226개가 사실상 이미 정답이었는데 셀에 계산된 값만 보고 수식 자체는 안 보는 value-only 채점기가 못 알아본 것이었음. 실행 기반 재채점만 넣어도 패스율이 67%대에서 78%대로 뜀.


5. 이 세 통로를 관통하는 구조적 통찰이 하나 있음. 에이전트 파이프라인은 입력 읽기(그라운딩), 절차(메서드), 출력 확인(검증) 세 단계인데, 기존 스킬은 압도적으로 메서드만 지원함. 근데 잔존 실패를 분석해보면 실패는 양 끝단에 몰려 있음. 오피스 벤치마크의 거의 모든 실패가 잘못된 표, 잘못된 연도, 잘못된 정의를 읽은 입력 단계 실패였고 산술은 정확했음. 즉 스킬이 가장 잘 지원하는 단계가 가장 적게 실패하는 단계인 것. 스킬 효과가 제한되는 근본 원인임.

6. 평균의 함정도 숫자로 보여줌. 같은 +5% 개선이라도 새로 10개 풀고 0개 망가뜨린 라이브러리와 새로 15개 풀고 10개 망가뜨린 라이브러리는 전혀 다른 거래임. 실제 데이터에서 Sonnet 4.6의 Anthropic 라이브러리는 이득이 가장 적었지만(10개) 회귀도 가장 적어(2개) 순효과 +8로 1위였음. 많이 푸는 라이브러리일수록 더 많이 망가뜨리는 패턴이 흔했다는 것. 스킬 평가는 이득과 회귀를 분리해서 보고해야 한다는 게 결론임.

7. 통계적 엄격함도 인상적임. 18개 동시 비교에 Bonferroni 보정(여러 통계 검정을 한꺼번에 할 때 유의성 기준을 검정 수만큼 엄격하게 낮춰 우연에 의한 유의해 보임을 걸러내는 다중 비교 보정)을 걸었더니 살아남은 유의미한 효과는 Claude Code·Sonnet 4.6의 SpreadsheetBench 3건뿐이었음. 즉 대부분의 겉보기 스킬 개선은 노이즈와 구별이 안 된다는 것. "스킬 넣었더니 좋아진 것 같다"는 수준의 판단으로 스킬 라이브러리를 운영하면 노이즈를 정책으로 삼는 것과 같음.

8. 실무 지침 네 개로 압축됨. 첫째, 스킬 평가는 이득과 회귀를 분리 보고할 것. 둘째, 스킬 본문 없이 설명만 컨텍스트에 넣은 조건을 별도로 테스트해서 삼투를 측정할 것. 셋째, 스킬에는 절차보다 그라운딩 정보(어떤 표를 읽어야 하는지)와 검증 로직(출력을 어떻게 확인하는지)을 담을 것. 넷째, 실행 가능한 출력 검증을 스킬에 포함시킬 것. 226개 회복 가능 실패가 보여주듯 구체적인 체크 하나가 퍼센트 포인트 단위로 돌아옴.

9. 내 스킬 작성 습관에 바로 대입해봄. 지금까지 스킬을 "이렇게 해라"는 절차서 중심으로 썼는데, 앞으로는 앞부분에 "이 작업에서 입력은 무엇이고 어디서 읽는다"와 뒷부분에 "완료를 이렇게 검증한다"를 필수 항목으로 넣어야 함. 그리고 스킬 설명 문구가 실행과 무관하게 행동을 바꾼다는 사실 때문에, 설명의 단어 선택 자체를 회귀 테스트 대상으로 봐야 함. 스킬 추가 전후로 기존 작업 로그를 돌려보는 것. 이게 59%의 세금을 줄이는 방법임.

10. 결론은 이렇게 됨. 신뢰성은 절차의 정교함이 아니라 입력을 정확히 읽고 출력을 검증하는 능력에서 나옴. 스킬도 같은 원칙을 따라야 함. 스킬을 많이 쌓는 게 실력이 아니라, 스킬이 다른 능력을 덮어쓰지 않게 통제하는 게 실력임.
