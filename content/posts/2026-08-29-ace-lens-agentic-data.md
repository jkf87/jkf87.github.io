에이전트 훈련 데이터를 만들 때 판단 기준은 양이 아님. 이 서베이(arXiv 2608.27260)가 주장하는 핵심 과제는 단순히 더 많은 데이터를 생성하는 게 아니라 유효하고 정보량 있고 중복 없는 경험을 계속 배분하는 것. agentic RL이든 하네스 최적화든 자기 진화든 "어떤 경험을 샘플해 학습시킬 것인가"는 피할 수 없는 질문인데, 이 논문이 그 질문에 공통 언어를 줌.

1. 첫 기여는 데이터 인자화임. 도메인마다 제각각인 에이전트 데이터를 하나의 객체 d = (E, q, τ, v)로 묶음. E는 환경 명세로 도구 생태계, 실행 환경, 시뮬레이터까지 포함. q는 상태를 가진 과제 신호. τ는 액션이 실제 관찰과 상태 변화를 만들어내는 상호작용 실현. v는 선택적 검증기로 성공 신호를 판정. API 호출, 저장소 과제, GUI 데모, 시뮬레이터 롤아웃처럼 겉모습이 달라도 전부 이 네 조각으로 환원됨. 일반 instruction 합성과의 차이도 여기서 나옴. 지시문-응답 쌍이면 충분한 일반 합성과 달리 에이전트 데이터는 액션이 관찰과 상태 변화로 이어져야 유효하기 때문.

![](/images/2026-08-29-ace-lens-agentic-data/fig-2-p7.png)

2. 평가 렌즈가 ACE임. Accuracy는 접지되고 내부적으로 일관된 데이터의 지지 집합을 만드는 조건. 서베이가 관찰한 흐름은 룰/모델/휴먼 계층 검사 → 제약 기반 구성 → 실행·상태 기반 검증 → 피드백 기반 수리와 선별적 허입으로 이어짐. 규칙 검사에서 실행 기반 검증으로 무게중심이 옮겨가는 중이라는 게 요점. Complexity는 절대값이 아니라 선언된 학습자와 실행 설정 대비 학습 부담임. 같은 과제도 모델에 따라 쉽거나 어려움. divErsity는 표면 변형을 넘어선 환경·과제·행동 전반의 커버리지와 중복 제어. 재조합, 탐색 기반 발견, 섭동·반사실 변형이 그 수단임. Accuracy가 지지 집합을 만들고 그 안에서 Complexity와 divErsity가 분포를 설계한다는 구분이 깔끔함.

3. 생성 패러다임이 두 갈래로 정리됨. Forward는 환경을 만들고 과제를 정의하고 롤아웃을 돌려 데이터를 얻는 순방향. Reverse는 관찰이나 결과에서 역방향으로 과제와 상호작용을 구성함. 관찰·결과 데이터는 있는데 과제 정의가 없을 때 데이터를 늘리는 길임. 내 경험과 대조하면 합성 데이터를 만들 때 이 두 갈래 중 어느 쪽인지 명시하지 않으면 논의가 자꾸 어긋났음. 이 이분법은 자체 데이터 파이프라인 설계를 설명할 때도 바로 쓸 수 있는 어휘임.

![](/images/2026-08-29-ace-lens-agentic-data/fig-3-p8.png)

4. 왜 관련 있는가. 스케일링, 데이터 소스, 훈련 체제, 적응 학습 전반이 ACE 관점에서 재정리될 수 있다는 게 저자들의 결론. CalibForge에서 봤던 "솔버 행동으로 난이도 캘리브레이션"이 Complexity 축의 사례고, 실패 궤적을 버리지 않는 연구들이 Accuracy의 피드백 기반 수리 축에 속함. 흩어져 있던 개별 연구들을 같은 좌표에 놓아주는 서베이의 전형적인 가치가 있음.

![](/images/2026-08-29-ace-lens-agentic-data/table-1-p9.png)

5. 내 해석. 실무에서는 v(검증기)와 Complexity 보정이 제일 먼저 무너짐. 검증기 없이 롤아웃을 쌓으면 성공 신호가 오염됨. 라벨이 없는 것처럼 보이는 게 아니라 틀린 라벨로 학습되는 게 제일 나쁨. 그리고 학습자 크기를 무시한 난이도 설정은 쉬운 데이터만 대량 생산함. CalibForge가 측정했듯 전부 통과하는 태스크는 학습 가치가 0에 가까움.

6. 실무 이식은 이렇게임. 첫째, 자체 에이전트 데이터 파이프라인을 (E,q,τ,v) 네 조각으로 문서화할 것. 특히 v를 "선택적"으로 두지 말고 필수 스키마로 만들 것. 둘째, 데이터 품질 논의를 ACE 세 축으로 나눠서 할 것. "데이터가 더 필요하다"는 말을 정확도 문제인지 복잡도 문제인지 다양성 문제인지로 분해하면 다음 행동이 달라짐. 셋째, 난이도는 대상 모델을 지정하고 측정할 것. 모델 바꾸면 난이도 분포를 다시 재야 함. 넷째, 다양성은 표면 변형(워딩 바꾸기)이 아니라 환경·과제·행동 커버리지로 관리할 것. 중복 제어 지표를 데이터셋 대시보드에 상시 올려둘 것.
