에이전트가 느린 이유 중 하나는 LLM 생성과 툴 실행이 한 줄로 직렬로 묶여 있다는 것임. LLM이 툴 콜을 내보내면 툴이 끝날 때까지 GPU는 기다림. PASTE는 이 직렬 루프를 깨는 서빙 시스템임. 과거 트레이스에서 반복 툴 호출 패턴을 학습해 LLM이 생성 중일 때 다음 툴 호출을 예측 실행함. 평균 태스크 완료 시간 43.5% 감소, p99 테일 지연 최대 55.4% 감소임.

1. 문제의 크기부터. 논문이 측정한 deep research, 코딩, AI-for-Science 워크로드에서 툴 실행이 에이전트 E2E 지연의 45~57%를 차지함. 이 비용은 직렬 경로 위에 그대로 노출돼서 LLM 생성을 아무리 빠르게 만들어도 안 줄어듦. 그래서 이 논문의 최적화 대상은 토큰 수준 지연이 아니라 태스크 수준 E2E 지연임.

![지연 분해](/images/2026-08-25-paste-speculative-tool-execution/fig-3-p3.png)

2. 관찰이 출발점임. 실제 에이전트 트레이스엔 반복 서브워크플로우가 있음. search 다음에 visit, edit 다음에 run test, grep 다음에 file_editor 같은 패턴임. 성공한 file_editor 호출의 55% 뒤에 터미널 실행이 따라오고 웹 방문의 95%에서 URL이 앞선 search 출력의 부분문자열임. 다음 툴 이름뿐 아니라 인자까지 이전 관찰에서 복사되는 경우가 많아서 LLM이 콜을 내기 전에 실행 가능한 형태로 예측할 수 있음.

![반복 패턴](/images/2026-08-25-paste-speculative-tool-execution/fig-2-p1.png)

3. 구조는 세 컴포넌트임. Pattern Analyzer가 과거 트레이스에서 반복 제어 흐름과 암묵적 데이터 흐름을 마이닝해 현재 세션 상태에서 구체적인 미래 툴 호출을 만듦. Tool Speculation Scheduler가 예측 실행을 승인하고 확정될 때까지 결과를 격리하고 정식 호출의 우선순위를 보장함. LLM-Tool Co-Scheduler가 툴이 끝난 세션이 LLM 엔진으로 몰려 들어갈 때 진입 속도를 조절함.

4. 세 번째가 제일 재밌는 부분임. 툴을 아무리 빨리 끝내도 돌아온 세션들이 한꺼번에 LLM에 몰리면 GPU가 병목이 돼서 이득이 사라짐. 논문이 실험으로 확인함. 툴 실행만 2배 빠르게 하고 LLM 스케줄러를 그대로 두니 고부하에서 툴 쪽 이득이 LLM 감속에 흡수됐고 최악의 경우 베이스라인보다 느려졌음.

![부하 민감도](/images/2026-08-25-paste-speculative-tool-execution/fig-5-p4.png)

5. 부하 스케일링 데이터가 이 주장을 뒷받침함. 동시 세션 1개에서 192개로 늘릴 때 LLM 생성 시간은 17배 이상 늘어나는데 툴 실행 시간은 거의 변하지 않음. 그래서 양쪽을 같이 스케줄해야 한다는 게 결론임. 병렬화는 한쪽 최적화가 아니라 시스템 설계라는 것임.

6. 안전성 설계가 신뢰의 핵심임. 예측 실행 결과는 격리됨. LLM이 실제로 같은 호출을 내보낼 때만 재사용되거나 승격되고 틀리면 버려짐. 예측은 정식 세션 상태에 아무것도 append하지 않고 부작용이 있는 툴은 정책과 샌드박싱으로 걸러짐. 틀린 예측이 있어도 외부 관찰 가능한 동작이 안 바뀌는 lossless 구조임.

![lossless 구조](/images/2026-08-25-paste-speculative-tool-execution/fig-8-p7.png)

7. 숫자 리뷰. Top-1 예측 정확도는 최대 27.8%밖에 안 됨. 근데 여러 후보를 동시에 걸어두면 되는 구조라 전체 히트율은 93.8%까지 올라감. 요청의 97%가 1배 이상 빨라졌고 최악의 경우에도 베이스라인과 비슷함. 예측이 빗나갔을 때 손해가 작다는 게 이득의 조건임.

8. 내 해석. 이 논문의 예측 부분이 특별히 똑똑한 건 아님. 패턴 매칭에 가깝고 Top-1도 27.8%임. 그럼에도 43.5%가 나온 건 시스템 설계 덕분임. 예측이 틀려도 잃을 게 없는 lossless 구조를 만들고, 히트율을 후보 수로 보완하고, 툴 쪽 이득이 GPU 쪽에서 새어나가지 않게 상호 스케줄링한 것. 숫자는 설계가 만든 것임.

9. 실무 채점. 에이전트 하네스를 만드는 입장에서 챙길 점 두 가지임. 첫째, 에이전트 트레이스의 반복 패턴은 메모리·압축 소스이기도 하고 지연시간 최적화의 소스이기도 함. 실행 로그를 버리지 말고 패턴화해둘 것. 둘째, 툴 병렬화를 넣을 때는 LLM 쪽 재진입 스케줄링을 같이 설계할 것. 한쪽만 고치면 고부하에서 이득이 사라짐.

10. 그리고 구현 비용이 낮다는 점. 에이전트 쪽 TypeScript 5k 줄 + vLLM 훅 Python 2k 줄이고 vLLM 소스코드는 건드리지 않음. 서빙 스택 교체 없이 붙일 수 있는 접근이라 자체 운영 환경에 적용 검토의 장벽이 낮음.

11. 한계. 예측이 잘 통하는 건 반복 패턴이 뚜렷한 워크로드라는 조건임. 탐색적이고 비반복적인 작업 비중이 크면 히트율이 떨어질 것임. 그리고 vLLM 기준 측정이라 다른 서빙 스택에서 같은 이득이 나온다는 보장은 없음.

12. 그래도 방향은 분명함. 서빙 최적화의 대상이 토큰 처리량에서 태스크 수준 E2E 지연으로 옮겨가고 있다는 것. 에이전트 시대의 서빙 시스템은 LLM 엔진만 빠르면 안 되고 툴 실행과의 공동 스케줄링까지 책임져야 한다는 결론임.
