에이전트 메모리에서 검색기가 과거 트레이토리(궤적, 에이전트가 과제를 수행하며 남긴 실행 기록 전체)를 잘 찾아와도 그걸 지금 쿼리에 맞게 다시 쓰는 단계가 따로 있고 병목은 거기에 있음. QCR 논문(arXiv:2608.12847)이 그 재사용 단계만 분리해서 측정하는 프레임워크를 만들었고, 테스트용 최소 구현인 QCR 노트로 평균 62.3% Success, Full Trajectory 대비 +10.7pt, 온라인 토큰 48.9% 감소를 냈음. WebArena(실제 사이트를 본뜬 가상 웹에서 과제를 수행하는 벤치마크)·WorkArena(기업 업무 웹 앱 과제 벤치마크)·AppWorld(일상 앱 조작 과제 벤치마크)의 2,391개 타깃 인스턴스로 평가함.

1. 설계 가설이 명확함. 메모리가 쌓이면 저장과 검색은 잘 되는데, 찾아온 기록을 변경된 타깃에서 쓰는 일이 새 병목이 된다는 관찰임. 사용자가 바뀌고 엔티티 ID가 바뀌고 환경 상태가 바뀐 타깃에서 과거 기록은 그대로 못 씀.

![설계 가설](/images/2026-08-15-qcr-query-conditioned-reuse-agent-trajectories/fig-1-p1.png)

2. 통제 평가 설계가 튼튼함. 후보 검색, 타깃 상태, 모델, 디코딩, 도구 예산을 전부 고정하고 에이전트에 전달되는 지원물만 바꿈. 오프라인에 검증된 과거 트레이토리를 뱅크에 저장하고, 온라인에 검색기가 상위 5개 후보를 반환하고, 공통 랭커가 하나를 고르고, 메모리 조건만 "같은 기록을 어떻게 변환해서 넘길지"로 차이를 둠.

3. 벤치마크도 목적에 맞게 새로 만듦. 검증된 소스 트레이토리 하나에서 최대 4개 타깃 변형을 생성하되 워크플로는 유지하고 엔티티·사용자·레코드 ID·파일 경로·날짜 같은 바인딩 값을 다른 발산 수준으로 교체함. 소스당 평균 3.84개 변형. 절차는 같고 값이 다른 상황에서 메모리가 실제로 도움 되는지를 측정할 수 있음.

![평가 파이프라인](/images/2026-08-15-qcr-query-conditioned-reuse-agent-trajectories/fig-2-p4.png)

4. QCR은 검색 뒤에 딱 하나의 연산을 끼워 넣음. 선택된 소스 트레이토리를 타깃 쿼리와 초기 관찰에 조건지어 짧은 노트로 재작성하는 것. 필드는 네 개임. 워크플로 불변식(소스와 타깃이 공유하는 절차), 재획득 바인딩(타깃에서 반드시 새로 확인할 값), 적용 조건(재사용 가능 조건과 거절 조건), 검증 가드레일(제출 전 확인 항목)임.

5. 작성 규칙이 엄격함. 과거 식별자·경로·사용자·날짜·도구 출력은 전부 소스 쪽 증거로만 취급하고 과거 바인딩을 타깃에 복사하는 걸 금지함. 노트는 검색 집합보다 확실히 짧아야 하고 타깃 정답을 누설하면 안 됨. 이 규칙들이 효용의 본체임.

6. 종단 결과. 세 벤치마크 전부에서 QCR이 최고임. WebArena 31.5→54.7, WorkArena 36.6→60.4, AppWorld 47.1→71.8. Full Trajectory는 토큰을 가장 많이 쓰면서(18.4k) 성능은 QCR보다 낮음. QCR은 API 호출도 가장 적음(16.7회). Milestone 완수율도 전 구간 최고임.

7. 선택 진단이 이 논문의 논리적 뼈대임. 상위 5개 후보의 재사용 커버리지는 97.8%로 충분한데 검색기 top-1의 정확도는 78.9%에 그침. 그래서 후보 설명을 다시 읽어 판정하는 요약 리랭커를 넣으니 재사용 가능 메모리 정확도 94.8%가 나옴.

![리랭커 효과](/images/2026-08-15-qcr-query-conditioned-reuse-agent-trajectories/fig-3-p7.png)

8. 그리고 종단 Success가 검색기 top-1 56.1%, 리랭커 선택 62.3%, 오라클 선택(정답 후보를 미리 알려주는 이상적 선택) 64.1%임. 리랭커가 오라클과 1.8pt 차이까지 감. 선택 문제는 거의 풀렸고 남는 격차는 사용 쪽에서 난다는 근거임. "검색 품질을 올리는 것"이 아니라 "찾은 걸 조건화해서 넘기는 것"이 다음 병목이라는 주장이 숫자로 뒷받침됨.

9. 트레이토리 길이 효용. Full Trajectory는 히스토리가 길어지면 효용이 +18.4pt에서 +2.9pt로 떨어짐. QCR도 줄긴 하는데 아주 긴 구간에서도 +13.2pt를 유지함. 유지율로는 15.8% vs 60.3%임.

10. 결정적인 결과는 바인딩 시프트 표임. 바인딩이 안 바뀌면 통째 주입도 +26.9pt로 쌈. 근데 대규모 시프트에서는 +2.2pt로 거의 사라짐. QCR은 +20.1pt를 유지함. 유지율 8.2% vs 67.9%의 차이임.

11. 실패 유형도 측정됨. 대규모 시프트에서 stale-binding 에러(소스 값이 타깃 관찰과 충돌하는 상태로 반복)가 Full Trajectory 46.9%에서 QCR 10.9%로 낮아짐. 올바른 재바인딩 비율은 31.7%→77.8%로 오름. 방법이 시프트를 없애는 게 아니라 낡은 소스 값이 현재 증거를 밀어내는 속도를 줄이는 것이라는 게 저자들의 표현임.

12. 실무 채점. 우리가 트레이토리나 스킬 카드를 쌓는 시스템이라면 세 가지를 바로 적용함. 첫째, 카드에 "이 값은 타깃에서 다시 얻어라" 필드와 거절 조건을 명시할 것. 둘째, 재사용 전에 쿼리 조건화 단계를 하나 끼워 넣을 것. 셋째, 컨텍스트 예산이 빠듯한 로컬 에이전트에서는 토큰 48.9% 절감이 곧 비용 절감임. 성능과 비용이 같은 방향으로 움직이는 흔치 않은 케이스임.

13. 그리고 요약이 아니라 조건화가 본체라는 교훈. Generic Summary는 대규모 시프트에서 +5.3pt에 그침. 그냥 짧게 줄이는 것과 타깃 쿼리에 맞게 다시 쓰는 것은 다른 연산임. 메모리 압축을 "요약"으로 처리하던 습관을 고칠 지점임.

14. 한계. QCR은 재사용 가설 검증용 최소 구현이지 보편적으로 최적인 메모리 스키마를 주장하는 게 아님. 4필드 자체가 구현 선택이고, 길이 분석도 등록된 구성에서의 측정이라 길이만 분리한 인과 실험은 아님.
