LLM 에이전트가 내는 액션은 에러 없이 조용히 실패하는 경우가 핵심 위험임. Look Before You Leap 논문은 셸 명령과 코드 편집 두 가지 액션에 대해 실행 전 결정론적 검증을 걸면 얼마나 막을 수 있는지 측정했음. 원문은 [arXiv:2609.11957](https://arxiv.org/abs/2609.11957).

1. 문제 정의. 에러가 나는 실패(clean failure)는 복구 가능함. 근데 에러가 안 나는 실패(silent failure)는 관측으로는 절대 발견되지 않음. 그럴듯한 결과를 내면서 조용히 틀리는 경로가 실제로 존재한다는 것임. 논문의 제안은 액션의 올바른 효과를 실행 전에 구성으로 고정하는 것임. 검증기는 확실하지 않을 때 판단 대신 기권하면 됨.

2. 셸 명령 검증. 벤치마크 구성이 특이함. 유효 명령은 tldr(커맨드라인 도구 사용법 요약 문서 모음) 코퍼스에서 뽑고 무효 명령은 존재하지 않는 바이너리·잘못된 문법·잘못된 옵션으로 변이해서 만듦. 검증기가 검사하는 규칙으로 벤치마크를 만들면 자기합격만 측정하게 되니까 검증기와 독립적인 행동 오라클(정답을 별도 절차로 확정해주는 판정 기준)로 무효성을 확정한 게 핵심임. 9,930개 명령·482개 도구에서 무효 명령 95.8% 검출(위양성 10.0%)임.

![실험 설계](/images/2026-09-14-look-before-you-leap-pre-action-verification/fig-1-p4.png)

3. 검증기는 세 가지 검사를 돌림. bash -n 문법 검사, which 바이너리 존재 검사, --help에서 추출한 플래그 집합 대조임. 서브커맨드 인식이라 git commit 플래그와 git 플래그를 분리 처리함. 문법·바이너리 검사는 위양성 0의 오라클-정확 코어고 전체 오류의 절반을 잡음. 플래그 검사는 헬프텍스트 커버리지(91.1%)에 제한되고 모든 위양성이 여기서 나옴.

4. 코드 편집 결과가 제일 극명함. 640개 편집·224개 파일로 apply 단계만 분리해서 측정했는데 콘텐츠 앵커 포맷(search/replace, unified diff, 즉 찾을 텍스트 내용 자체를 기준으로 위치를 찾는 편집 형식)은 실패해도 깨끗하게 실패하고 위치 앵커 포맷(라인 번호, 함수명)은 조용히 실패함. 라인 번호 편집은 1줄 밀림 perturbation(입력을 살짝 바꿔보는 교란)에서 99.1% 파일을 손상시킴. 함수명 편집은 12.7% 확률로 엉뚱한 함수를 수정함. 반면 unified diff는 자기 컨텍스트를 독립적으로 검증하니까 퍼지 0이든 2이든 조용한 실패가 0임.

![](/images/2026-09-14-look-before-you-leap-pre-action-verification/gifs/corroded-pipe-repair.gif)

5. 멀티헝크 편집의 분화도 흥미로움. SR-fuzzy(대충 일치하는 텍스트도 찾아주는 search/replace 변형)는 단일 편집에선 2.3%로 안전한데 헝크가 늘며 앵커가 짧아지면 조용한 실패율이 39.3%까지 치솟고 기각률이 0이라 전부 복구 불가로 감. requests 라이브러리 재현에서도 같은 패턴이 유지돼서 모델 문제가 아니라 포맷 자체의 문제임.

6. 배포 가능한 가드가 실무 산출물임. Selective grounding은 셸 명령용 2단계 게이트로 R 0.958(검출률, 전체 무효 명령 중 잡아낸 비율) @ FPR 0.070(위양성률, 정상 명령을 잘못 걸린 비율)을 운영점으로 잡음. Robust-Apply는 포맷 비의존 메타어플라이어로 최소 앵커 크기, 유사도 상한, 차등을 충족할 때만 패치를 커밋하고 애매하면 거부함. 8,320회 시행 중 조용한 오적용 1건(0.01%)임. 확실하지 않으면 적용을 거부하는 정책이 조용한 실패를 복구 가능한 실패로 바꾸는 것임.

![](/images/2026-09-14-look-before-you-leap-pre-action-verification/gifs/measure-twice-cut-once.gif)

7. 두 모달리티의 공통 구조가 깔끔하게 정리됨. 오라클-정확 코어(문법+바이너리, exact 매칭)가 있고 커버리지에 제한된 부분(플래그 추출, 퍼지 매칭)이 나머지 적용률을 사면서 유일한 오류원이 됨. 위험한 표현은 정확히 콘텐츠 검증이 불가능한 것들임. 참조에 없는 플래그, 앵커 없는 라인 번호·함수명은 맞는 대상과 틀린 대상을 구분 못 하니까 조용히 실패함.

8. 내 하네스에 바로 적용한 것. 첫째, 편집 인터페이스에 라인 번호 포맷을 쓰고 있다면 이 논문을 근거로 search/replace나 unified diff로 바꾸는 걸 진지하게 검토해야 함. 내 자동화는 이미 search/replace 기반이라 안심했지만 멀티헝크일 때 앵커 최소 길이 검사를 추가해야 한다는 과제를 얻었음. 둘째, 셸 명령 실행 전에 문법·바이너리·플래그 검사를 마이크로초-밀리초 비용으로 붙임. 모델 호출 0회로 위험의 절반 이상을 없앨 수 있다는 게 비용 대비 효과의 승부임.

9. 확장 원칙도 챙겨감. 파일 연산은 경로 존재·쓰기 가능 확인, API 호출은 스키마 검증 후 확실할 때만, DB 쓰기는 커밋 전 제약 검사. 설계 질문은 항상 같음. 위반 시 확실히 틀리다는 걸 증명할 수 있는 오라클-정확 속성이 있고 액션을 매칭할 콘텐츠 앵커가 있는가.

10. 문제제기. bash -n은 불완전한 조각을 거부하고 which는 alias·셸 함수·세션 PATH를 못 봄. 실제 모델 출력 프루빙이 42개 명령·9개 편집으로 가벼워서 실제 에러 분포에 대한 검출률은 아직 추정 안 된다고 논문도 인정함. 그리고 self-refine은 에러가 관측된 뒤의 수정이고 pre-action 검증은 관측 자체가 안 되는 조용한 실패를 다룬다는 구분이 있어서 둘을 조합하는 게 정답임.

11. 결론. 조용한 실패는 사후 검증으로 못 잡음. 실행 전에 정적 검증과 기권 정책을 넣어야 복구 가능한 실패로 바뀜. 검증 비용은 마이크로초에서 밀리초 수준이고 모델 호출이 없다는 점이 이 접근의 승부수임.
