컴퓨터 사용 에이전트(CUA)가 클릭만으로 일하는 비효율을 하이브리드 인터페이스로 푼 연구가 나옴. 작은 모델이 언제 CLI로 전환할지 배우는 것만으로 큰 폭이 오른다는 결과라 정리함. 원문은 [arXiv:2609.05374](https://arxiv.org/abs/2609.05374).

1. 문제 정의가 명확함. OSWorld(실제 운영체제 안에서 파일 편집·앱 조작 등 컴퓨터 사용 과제를 수행시켜 성공률을 측정하는 벤치마크) 같은 벤치마크에서 CUA는 대부분 GUI 좌표 클릭만 씀. 명령어 한 줄로 될 작업을 클릭 수십 번으로 하니 궤적이 길어지고 장기 워크플로에서 무너짐.

![](/images/2026-09-08-cua-universe-hybrid-gui-cli/gifs/mouse-clicking-come-on.gif) 반대로 CLI 특화 에이전트는 시각 상태·레이아웃에 접근 못 해서 인터페이스 상태 의존 태스크에 약함. 본질적 과제는 오케스트레이션 — 같은 앱 상태를 공유하면서 GUI와 CLI 전환 시점을 결정하는 능력이라는 것.

2. 파이프라인이 3단계임. App-Forge가 데스크톱 앱 16종(Blender, GIMP, OBS 등)을 재현 가능한 VM으로 변환하고 CLI 서피스를 발견·래핑·생성함. Task-Weave가 시드 파일 기반 연산 조합으로 하이브리드 태스크를 합성하고, Path-Steer(롤아웃 중 비효율적 클릭 경로를 CLI 호출로 갈아끼우는 경로 안내 기법)가 효율적 경로로 롤아웃을 스티어링해 검증 궤적 4,923 에피소드를 수확함. 앱 설치는 Codex, 태스크 합성은 Kimi K2.5, 성공 판정은 VLM 저지(스크린샷을 보고 과제 완수 여부를 채점하는 비전-언어 모델 심판)가 0.75 이상만 통과시키는 역할 분담임.

![CUA-Universe 개요](/images/2026-09-08-cua-universe-hybrid-gui-cli/fig-1-p2.png)

![](/images/2026-09-08-cua-universe-hybrid-gui-cli/gifs/code-rain-terminal.gif)

3. 학습은 RL이 아니라 검증 궤적 기반 SFT(교사가 만든 성공 예시를 정답지로 넣고 지도학습으로 파인튜닝하는 방식)임. Qwen3.5-9B에 LoRA(가중치 전체가 아니라 저랭크 행렬만 덧붙여 학습해 메모리·비용을 아끼는 파인튜닝 기법)를 얹었고 8×A100 2일. 교사의 성공 궤적 상단만 학습해서 학생이 교사 평균을 넘는 STaR/ReST 계열(모델이 생성한 성공 궤적을 다시 학습 데이터로 재활용해 스스로를 올리는 자기개선 방법) 효과로 설명함.

4. 결과는 같은 9B 베이스 대비 스코어 약 3배(0.189→0.582). 교사 Kimi K2.5(0.522)를 초과했고 스텝 -37%, 토큰 -60%(643K→255K). OSWorld 244태스크에서는 GUI-only 23.4% → GUI+CLI 40.2%로 이전에 실패하던 41개 태스크를 해결함. 핵심 대조는 학습 안 된 타 모델은 CLI를 줘도 +3~8개에 그친다는 것 — 전환 능력이 학습되어야만 이득이 된다는 뜻임.

![GUI+CLI 하이브리드 평가 결과](/images/2026-09-08-cua-universe-hybrid-gui-cli/fig-4-p6.png)

5. 일반화 결과도 흥미로움. 학습 시 앱 전용 CLI만 썼는데 미학습 MCP(도구와 데이터 소스를 표준 규격으로 에이전트에 연결해 주는 프로토콜) 인터페이스(158개 도구)에서도 SR 20.90→28.69%, 도구 사용 정확도 2.2배. "언제 도구로 전환할지"의 학습이 도구 종류를 넘어 이전된다는 것.

![메인 테이블](/images/2026-09-08-cua-universe-hybrid-gui-cli/table-1-p6.png)

6. Path-Steer ablation(해당 구성요소만 빼고 돌려보는 제거 실험)이 설계 근거를 줌. CLI 접근을 유지한 채 경로 안내만 빼면 수용률과 스코어가 다 떨어지고 태스크당 비용이 늘어남. 백본을 바꿔도 같은 패턴이라 이득이 모달리티 스티어링에서 온다는 결론임. 그냥 CLI를 열어주는 게 아니라 하이브리드 경로를 스티어링해야 데이터 품질이 오른다는 것.

7. 필자 적용 포인트. 브라우저 자동화 중심 파이프라인에도 같은 원칙이 적용됨. 화면 조작으로 되는 일을 셸·API 호출로 줄일 수 있는지 먼저 판단하는 계층을 두는 것. 필자 작업도 파일 편집은 전부 CLI로 하고 브라우저는 최후 수단으로만 쓰는데, 이 논문의 숫자가 그 설계가 왜 옳은지 정량 근거가 됨 — 스텝과 토큰이 동시에 줄고 성공률은 오름.

8. 문제제기. 코드·데이터가 release 예정 상태로 미공개라 재현 검증이 아직 불가함. CUA-Verse 8개 앱이 학습 도메인과 앱이 겹치고, 3D/공간 앱(Blender 0.398)은 여전히 약함. 채점이 GPT-5.4 VLM 저지에 의존하는 것도 오차 원인임.

9. 남는 결론. CUA의 다음 격차는 모델 크기가 아니라 인터페이스 선택 능력임. CLI 전환을 배운 9B가 못 배한 큰 모델들을 앞서는 구조이고, 환경 구축 + 검증 궤적 수확이라는 지루한 파이프라인이 그 능력을 만든다는 게 이 논문의 실무 교훈임.
