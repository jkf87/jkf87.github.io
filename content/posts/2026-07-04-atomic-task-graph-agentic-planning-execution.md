에이전트 성능이 안 나올 때 대부분은 모델을 바꾼다. 근데 이 논문은 제어 구조만 바꿔서 7B 모델을 GPT-4급으로 끌어옸다. 업무자동화 에이전트 설계에 바로 쓸 수 있는 지점이 많아서 정리함.

1. 배경은 익숙함. ReAct 스타일 에이전트는 관찰→추론→행동을 한 줄짜리 텍스트 궤적으로 쌓음. 한 단계 삐끗하면 그 오류가 뒤까지 전파되고, 실패하면 처음부터 다시 계획해야 함. 긴 업무 자동화 파이프라인일수록 이 문제가 치명적임.

2. 문제의 본질은 선형성임. 실제 업무는 비선형적임. "PDF에서 데이터 추출"과 "메일 초안 작성"은 서로 독립적인데 선형 궤적에서는 순차적으로 밖에 못 돌림. 느린 도구 하나가 전체를 붙잡음.

3. Atomic Task Graph(ATG)의 조치는 단순함. 작업을 원자적 도구 호출 단위까지 재귀적으로 분해하고, 입력-출력 의존성을 DAG로 명시하는 것. [논문](https://arxiv.org/abs/2607.01942) 하나만 참고하면 됨.

4. 핵심 설계 원칙은 세 개임. 첫째, 부모 노드의 인터페이스를 보존하며 분해. 둘째, 독립 브랜치는 병렬 실행하고 실행 전 가벼운 사전 검증을 돌림. 셋째, 오류가 나면 그래프 진화 이력으로 원인을 국소화해서 최소 서브그래프만 수리함.

5. 국소 수리가 실무 포인트임. 선형 구조에서는 중간 실패 시 전역 재계획이 필요함. ATG는 검증된 노드는 보존하고 영향 받은 노드만 교체함. 크롤링 파이프라인에서 특정 사이트만 막혔을 때 전체 재시작하지 않는 것과 같은 원리임.

6. 컨텍스트 관리도 구조로 해결함. 재귀 분해가 깊어질수록 각 노드가 보는 맥락이 좁아짐. 환각의 주 원인인 컨텍스트 과부하가 자연스럽게 줄어듦. 프롬프트 엔지니어링이 아니라 설계로 환각을 줄이는 접근임.

7. 숫자가 인상적임. Mistral-7B 기준 ALFWorld에서 ReAct 6.57 → ATG 55.73. WebShop 14.63 → 62.75. Llama-3-8B에서는 62.93, 67.85, 58.76. GPT-4+ReAct(41/64/66)조차 일부 지표에서 넘어섬.

8. 실행 단계도 줄어듦. ALFWorld 31.4 → 18.4 스텝, ScienceWorld 47.4 → 29.7 스텝. 약 33-42% 감소임. 비용이 스텝 수에 비례하는 실무 환경에서는 성능보다 이게 더 큰 절감임.

9. 사전 검증 단계는 실행 전 "생각해보기"임. 누락된 단계, 무효한 의존성, 도구 불일치를 실제 실행 전에 잡아냄. 벤치마크별로 위험한 계획의 18.9-27.4%를 사전 감지했고 정밀도는 74% 이상이었음.

10. 여기서 문제제기. 이 결과가 좋다고 내 파이프라인에 바로 갖다 붙이긴 어려움. 논문은 도구 공간이 사전에 정의된 환경(ALFWorld, WebShop, ScienceWorld)에서만 검증됨. 개방형 도구 탐색, 실제 API 장애, 인증 만료 같은 현실 변수는 안 다룸.

11. 근데 방향은 맞음. 실무에서 에이전트 실패의 대부분은 모델이 멍청해서가 아니라 구조가 취약해서임. 어느 단계가 실패했는지 알 수 없고, 재시도하면 전체를 다시 돌리고, 독립 작업도 순차로 돌리는 구조. ATG의 DAG+국소 수리는 이 세 문제에 대한 직접적 답임.

12. 적용은 점진적으로 할 만함. 당장 DAG 프레임워크를 안 갖다 놔도, (1) 작업을 원자 단위로 쪼개고 (2) 의존성을 명시하고 (3) 실패 시 검증된 결과를 재사용하는 것. 이 세 가지는 기존 파이프라인에 즉시 반영 가능한 원칙임.

13. 재귀 분해의 비용도 짚어야 함. 분해 깊이만큼 LLM 호출이 늘어남. 논문은 실행 스텝 감소로 상쇄된다고 주장하지만, 실제로는 분해 비용과 재시도 절감의 손익을 자기 워크로드로 계산해봐야 함.

14. 소형 모델 활용 전략에도 시사점이 있음. 로컬 7-8B 모델로 에이전트를 돌리고 싶다면, 모델 능력을 키우는 대신 제어 구조를 정교하게 만드는 편이 훨씬 저렴함. 백본 무관성도 확인됨 — Mistral, Gemma, Llama-3 모두 일관된 개선.

15. 결론은 이거임. "더 큰 모델"이 아니라 "더 나은 구조"가 에이전트 성능의 실무적 레버임. 특히 비용에 민감한 업무자동화에서는 모델 업그레이드보다 DAG 기반 계획-실행 통합이 먼저임. 근데 구조 개선은 검증된 벤치마크 환경과 실제 운영 환경의 격차를 항상 염두에 둬야 함.
