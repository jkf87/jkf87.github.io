지식노동 에이전트가 겪는 흔한 실패 하나를 정면으로 다룬 논문이 나옴. 검색한 파일, 수정한 파일, 제출한 파일이 서로 다른 버전인 경우가 있다는 것. 원문은 [arXiv:2608.18050](https://arxiv.org/abs/2608.18050).

1. 문제 구조가 실감남. 코딩 에이전트는 repo 체크아웃이라는 단일 상태를 검색·수정·테스트가 공유하는데, 문서 작업 에이전트는 다름. 검색은 파싱된 인덱스(마크다운 변환본)에서, 수정은 원본 파일(xlsx, docx)에서, 검토는 또 다른 시점 diff로, 제출은 또 다른 상태로 함. 한 버전에서 열 정의를 읽고 다른 버전을 수정해서 근거와 안 맞는 결과물을 내놓는 식임. 논문은 이걸 명시적 계약 부재로 지목함.

![](/images/2026-08-19-stagedworkspace-versioned-workspace/gifs/wait-james-franco.gif)

2. 해법은 세 가지 뷰를 하나의 상태에 묶는 것임. 현재 네이티브 파일(Wt), 원본 경로와 콘텐츠 해시로 태깅된 파싱 레코드(Ct), 시작 상태와의 diff(Δt). 파일이 바뀌면 해시가 달라지고 해당 파싱 레코드는 stale 마킹 후 재파싱됨. 이 규칙 하나로 grep이나 벡터 검색이 옛 버전 증거를 지금 정보처럼 내놓는 걸 막음.

![StagedWorkspace 구조](/images/2026-08-19-stagedworkspace-versioned-workspace/fig-2-p4-1.png)

3. 동기화 순서도 단순함. 툴 배치 끝나면 샌드박스를 워크스페이스로 동기화, 해시 스캔으로 바뀐 파일 식별, 안 맞는 파싱 레코드만 재파싱 큐에 넣기, diff 보고 후 제출. 변경 이력은 저널로 남고 승격·롤백 가능. 코딩 에이전트의 repo 계약을 문서 작업으로 옮긴 것이라는 요약이 정확함.

![](/images/2026-08-19-stagedworkspace-versioned-workspace/gifs/archive-file-retrieval.gif)

4. 결과가 큼. 미 재무부 PDF 697개짜리 OfficeQA Pro에서 Gemini 3.1 Pro가 29.3→63.9%로 +34.6점. GPT-5.4도 +8.3점. 프론티어 밖 모델일수록 동기화로 복구되는 폭이 큼 — 즉 강한 모델은 상태 꼬임을 부지런함으로 상쇄하고 있었다는 뜻임. 컨설팅·법률 480과제 APEX에서도 GPT-5.4 Nano가 16.9→25.0%로 오르며 Opus 4.7 레퍼런스를 넘음.

![OfficeQA Pro 결과](/images/2026-08-19-stagedworkspace-versioned-workspace/fig-4-p10-2.png)

5. 절제 실험이 인과를 깔끔하게 분리함. 모델·프롬프트·파서·검색기·그레이더·예산을 고정하고 뷰만 바꿨더니 파싱 뷰 제거 시 OfficeQA +8.3~12.1점 손해, 네이티브 뷰 제거 시 APEX 루브릭 +4.7~9.2점 손해. 태스크에 따라 병목 뷰가 다르니 둘 다 동기화해서 주는 게 최적점임.

6. 제출 전 diff 노출 실험도 실무적임. 파일 추적은 동일하게 두고 diff 도구 노출만 바꿨는데 GPT-5.4 Mini가 +8.5점. diff가 의미론적 정확성을 보장하진 않지만 제출 전에 의도와 실제 수정을 비교할 기회를 줌. 약한 에디터일수록 효과가 큼. 필자 파이프라인의 "완료 선언 전 외부 검증" 원칙과 같은 방향이 숫자로 확인된 것임.

7. 필자 적용 포인트. 블로그 마이그레이션도 파싱된 원문 읽고, 재작성 파일 쓰고, 게이트가 검사하는 구조라 똑같은 위험이 있음. 진행 파일(mig-progress)과 원문 캐시에 콘텐츠 해시를 붙여서, 재작성 대상 파일이 중간에 바뀌면 stale 처리하는 규칙을 달아두면 이 논문의 축소판이 됨. 지금은 작업 리스트 기준으로만 돌아가서 이 보험 하나로 원본-산출물 불일치 사고를 줄일 수 있음.

8. 문제제기. 그레이더가 최종 결과물만 채점해서 중간 동기화 성공 여부를 직접 검증 못 함. 그리고 APEX 452개 과제 중 188개가 모든 조건에서 0점 — 계획·도메인 추론·루브릭 준수 실패는 상태 관리로 못 푼다는 정직한 한계 고백임. 상태 계약은 필요조건이지 충분조건이 아님.

9. 남는 결론. 문서 작업 에이전트의 성능 하한은 워크스페이스 버전 계약이 결정함. 검색 캐시와 수정 대상을 해시로 묶는 건 하루면 달 수 있는 장치고, 약한 모델일수록 이득이 크다는 게 도입 우선순위를 정해주는 근거임.
