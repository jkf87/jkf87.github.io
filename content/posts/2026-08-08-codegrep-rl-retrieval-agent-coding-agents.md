코딩 에이전트가 코드를 고치기 전에 파일을 뒤지며 태우는 토큰이 생각보다 큼. 이 탐색 단계만 전담하는 작은 검색 에이전트를 RL로 훈련시킨 논문이 나와서 정리함. 원문은 [arXiv:2608.05886](https://arxiv.org/abs/2608.05886).

1. 배경 숫자부터. 30B급 OpenHands 에이전트가 SWE-Bench 이슈 하나를 풀 때 평균 23라운드, 631K 토큰이 드는데 상당 부분이 grep, glob, view_file 호출임. 그래서 두 가설을 검증함. 더 나은 파일 검색이 해결률을 올리는가, 같은 이슈를 더 적은 토큰으로 푸는가.

2. 구조가 깔끔함. Qwen3-14B 기반 검색 에이전트가 읽기 전용 도구(grep/glob/read)만 들고 다중 턴 탐색을 하고, 후보 파일 목록을 JSON으로 반환하면 이걸 수정하지 않은 기존 에이전트 프롬프트에 주입함. 메인 에이전트는 그대로 두고 검색만 대체하는 것임. 턴당 최대 8개 도구 병렬 호출, 3턴 탐색 + 1턴 답변으로 제한돼 있어서 비용이 통제됨.

3. 훈련 환경 설계가 실무적임. SWE-Bench Docker 이미지로 훈련하면 이미지당 1~3GB라 비현실적이라서, git worktree 기반 샌드박스를 만듦. 저장소당 bare clone 한 번, 커밋마다 worktree 추가해서 롤아웃당 셋업을 밀리초 단위로 줄임. 8×B200 단일 장비에서 훈련 가능해짐. 대규모 에이전트 RL 환경 구축 고민이 있는 팀이 그대로 베낄 만한 패턴임.

4. 데이터도 영리하게 뽑음. 67K OpenHands 궤적에서 파일 읽기 호출을 추출하고 LLM judge로 관련성을 분류하는 CATM 파이프라인. 패치된 파일뿐 아니라 에이전트가 이해하려고 읽은 파일도 관련 파일로 쳐서 31,977개 유효 샘플을 만듦. 남이 버린 실행 로그에서 훈련 라벨을 캐낸다는 발상이 좋음.

5. 보상 설계 3번의 반복이 하우스키스퍼 교훈임. v1은 Fβ 점수에 도구 호출 페널티를 보상 레이어에서 곱했더니 정책 드리프트 발생. v2는 효율 신호를 어드밴티지 레이어로 옮겨서 KL 드리프트가 0.31→0.09로 감소. v3은 다운스트림이 안 쓰는 라인 범위 점수를 제거해서 안정성과 효율 둘 다 개선. 목표 신호와 효율 신호를 어느 레이어에서 섞을지가 RL 안정성을 좌우한다는 실례임.

6. 결과는 해결률 27.0% vs 25.8%에 라운드 15%, 토큰 19% 절감. 근데 제일 값진 발견은 정밀도 임계점임. BM25(정밀도 0.375)를 주면 성능이 오히려 저하되고, Jina(0.445)는 중립, CodeGrep(0.677)부터 효율 개선이 시작됨. 검색기가 도움이 되려면 정확도 문턱이 있다는 것 — 이건 그냥 검색 증강을 붙이는 모든 파이프라인에 적용되는 원리임. 나쁜 검색은 안 넣느니만 못함.

7. 필자 적용 포인트. 파일 탐색이 비용의 큰 덩어리인 작업(대량 문서 처리, 마이그레이션)은 탐색을 전담하는 작은 모델로 분리하고 결과만 메인 에이전트에 주입하는 구조가 이김. 그리고 검색 게이트를 달 때 정밀도를 먼저 재고, 임계점 아래면 게이트를 안 거는 게 이득임.

8. 문제제기. 검색 품질 평가가 SWE-Bench 중심이라 다른 도메인 임계점은 다를 수 있음. 그리고 해결률 향상이 +1.2pp로 작아서 이 방법의 가치는 기본적으로 비용 절감 쪽임.

9. 남는 결론. 에이전트 파이프라인 비용 최적화는 전체를 바꾸는 게 아니라 가장 비싼 단계를 작은 전담 모델로 교체하는 것에서 나옴. 모델·파이프라인·RL 환경이 전부 공개돼 있어서 재현 가능성도 높은 작업임.
