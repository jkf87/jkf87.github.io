긴 호라이즌 태스크에서 에이전트 메모리 설계는 "뭘 버릴까"의 문제로 접근해 왔음. Duke 연구진의 PRO-LONG은 "버리지 말고 전부 쌓아서 코드로 찾아라"로 뒤집었음. 원문은 [arXiv:2607.20064](https://arxiv.org/abs/2607.20064).

1. 배경. 수천 수만 번 행동에 걸쳐 일관된 추론을 유지해야 하는 환경(ARC-AGI-3 게임 등)에서 메모리 시스템은 딜레마에 걸림. 쓰기 시점에 요약하면 나중에 필요한 정보가 사라지고, 전부 보존하면 검색이 어려워짐. 임베딩 검색, 요약 노트, 스크래치패드가 각각 다른 지점을 타협해옴.

2. 기존 하네스들의 무게가 제일 흥미로움. WorldModeler, Arcgentica 같은 선행 연구는 600줄짜리 프롬프트, 서브에이전트 분할, 커스텀 도구 12개를 동원함. PRO-LONG은 약 30줄의 프롬프트로 이걸 대체함. 복잡도가 성능을 만들지 않는다는 반례임.

3. 설계 원칙은 세 개임. 단순성(하네스가 모든 관찰·행동·결과를 logs.txt에 append), 무손실(압축·요약 없이 환경 상태의 충실한 기록 유지), 코딩 에이전트 호환성(grep·정규식·Python 스크립트로 검색하는 건 Codex나 Claude Code가 이미 잘하는 일)임.

4. 실제 케이스가 생생함. PRO-LONG 에이전트가 regress.py를 직접 작성해서 logs.txt의 모든 행동을 리플레이하며 자기가 코딩한 게임 모델이 로그된 보드 상태를 정확히 예측하는지 검증했음. 메모리를 "저장소"가 아니라 "검증 가능한 데이터셋"으로 쓰는 관점임.

5. 성과. ARC-AGI-3에서 GPT-5.5 41.2%, Opus 4.6 42.4%로 기존 최고 성능과 동등하거나 능가함. 특히 Opus는 기존 최고가 9.1%였는데 42.4%까지 오름. 토큰은 4.2-5.8배 적게 씀. 베이스 대비 평균 +18.0%p.

6. 도구 사다리 실험이 결정적임. 로깅만 추가해도 큰 향상, grep 추가로 추가 향상, Python 실행으로 더 큰 향상. 근데 영구 워크스페이스나 노트 도구는 효과가 미미했음. 무손실 로깅 + 프로그래밍 가능한 검색이 핵심이고 그 위의 추상화는 도움이 안 된다는 것임. "도구가 많을수록 좋은 에이전트"라는 믿음에 대한 데이터 반례임.

7. 이득이 컸던 게임은 현재 보드만으로 규칙을 알 수 없는 경우였음. 터렛 행동 패턴을 과거 경험에서 역추론해야 하는 미로라든가, 과거 경로의 유령이 현재 보드에 영향을 주는 되감기 게임 같은 것들. 과거 기록 검색이 결정적인 상황에서 프로그래밍 메모리가 빛을 냄.

8. 내 업무 자동화에 바로 적용함. 실패한 실험 로그까지 전부 텍스트 파일로 append하고, 다음 세션에서 grep·Python으로 회귀 분석하는 구조임. 중간에 요약본만 남기면 "그때 왜 실패했더라"를 다시는 못 찾음. 무손실 로그가 디스크 비용을 좀 쓰지만 토큰 비용은 오히려 줄어듦. 검색을 모델의 기억에 의존하지 않고 도구에 위임하는 게 핵심임.

9. 문제제기. 100k+ 줄 로그에서 grep이 실용적이라고는 하지만, 환경이 텍스트로 직렬화되지 않는 도메인(연속 제어, 대용량 멀티모달)에선 그대로 안 됨. 그리고 코딩 에이전트가 검색 스크립트를 잘못 짜면 조용히 오답을 찾아오는 리스크도 있어서, 중요한 결론은 재검증을 붙이는 게 안전함.

10. 결론. "무엇을 버릴 것인가"에서 "모두 보존하고 효율적으로 검색할 것인가"로의 전환임. 코딩 에이전트의 프로그래밍 능력이 충분히 강력해진 지금, 메모리의 정답이 단순해졌다는 게 이 논문의 메시지임. 코드와 로그는 [GitHub](https://github.com/alexisfox7/PRO-LONG)에 공개돼 있음.
