에이전트를 오래 굴리면 같은 도구 호출 시퀀스가 계속 반복됨. 그걸 그대로 두면 매번 추론 비용을 다시 지불하는 것. EvoSOP는 이 반복을 SOP(표준 작업 절차) 도구로 뽑아내서 압축함. 내 에이전트 운영에 그대로 적용할 수 있는 구조라 정리함.

1. 배경. 대부분의 에이전트 프레임워크는 파일 읽기, 검색, API 호출 같은 원자적 도구만 줌. 그러니 에이전트는 매번 저수준 도구를 조합해 같은 워크플로우를 처음부터 다시 구성함. 추론 오버헤드도 커지고 장기 작업에서 오류가 누적됨.

2. 문제는 추상화 부재임. 인간은 반복되는 하위 작업을 SOP로 묶어서 매번 저수준 논리를 안 짜도 됨. 도구 증강 에이전트엔 그 계층이 없었다는 것. 게다가 도구를 계속 추가만 하면 도구셋이 비대해져 오히려 의사결정에 노이즈가 생김.

3. [논문](https://arxiv.org/abs/2607.07321)의 조치는 4단계 라이프사이클임. Constructor가 실행 궤적에서 자주 공동 출현하는 도구 호출 시퀀스를 찾아 조건 분기·에러 처리 포함 함수로 재작성. Merger가 기능 중복을 통합. Evaluator가 실제 환경에서 성능 검증. Reviewer가 저성능·중복 SOP를 가지치기함.

4. 핵심은 매크로가 아니라는 점임. 예시 SOP를 보면 "메시지 전송 → 실패 시 최신 ID 조회 → 삭제 → 재전송"이라는 4단계 분기 로직이 하나의 함수로 캡슐화됨. 에이전트는 이제 한 번의 호출로 처리함. 재시도 로직이 도구 안으로 들어간 것.

5. 가중치를 건드리지 않는 것도 포인트임. 모델 업데이트 없이 도구셋이라는 외부 구조만 최적화하는 비모수적 접근. 모델 교체 주기와 무관하게 기존 에이전트 시스템에 붙일 수 있음.

6. 결과. ACEBench(에이전트의 도구 활용 능력을 측정하는 벤치마크), Tau2Bench(통신사 고객 응대를 시뮬레이션해서 정책 준수와 도구 사용을 채점하는 에이전트 벤치마크)에서 모든 백본에서 성공률 유의미하게 상승. 특히 멀티스텝·멀티턴 서브셋에서 두드러짐. 동시에 작업 완료에 필요한 상호작용 라운드 수가 크게 감소. SOP 호출 한 번이 여러 단계를 처리하니 당연한 결과임. GPT-4o, Gemini, Qwen 모두에서 동일 개선으로 모델 무관성도 확인됨.

7. 절제 연구가 구조의 존재 이유를 보여줌. Constructor 빼면 SOP 자체가 안 생겨 성공률 급감. Merger 빼면 중복 SOP가 누적돼 성능 저하. Reviewer 빼면 저성능 SOP가 방치돼 노이즈 증가. 생성만큼 정리가 중요하다는 것.

8. 도구셋 수렴 패턴이 흥미로움. 초기 에포크엔 탐색하며 빠르게 확장되다가 Merger와 Reviewer가 정리하면서 전형적으로 10개 이하로 수렴. 그 10개 미만 SOP로 ~80% 성공률. 적은 수의 잘 정제된 고차원 도구가 수십 개의 원자적 도구보다 낫다는 것.

9. 여기서 문제제기. "SOP 추출"을 자동으로 돌리려면 평가(Evaluator)가 같이 따라와야 함. 검증 없이 궤적에서 패턴만 뽑으면 문맥 의존적인 나쁜 습관까지 코드화됨. 실패 궤적에서 나온 패턴을 SOP로 굳히면 오류가 영구화됨. 이 논문이 Evaluator를 라이프사이클에 강제로 넣은 이유임.

10. 실무 적용은 이미 반쯤 하고 있는 사람이 많음. 자동화 에이전트의 실행 로그를 뒤져서 반복되는 호출 시퀀스를 찾고, 그걸 스크립트나 커스텀 도구로 묶는 작업. EvoSOP는 이걸 사람이 하지 말고 Constructor-Merger-Evaluator-Reviewer 루프로 하라는 것. 수동으로 해도 라운드 절감 효과는 동일함.

11. 우선순위 계산도 간단함. 도구 호출 수가 줄면 토큰 소비도 줄고 중간 단계 오류 확률도 줄어듦. 호출당 비용이 큰 MCP(모델이 외부 도구·데이터 소스를 표준 규격으로 연결해 쓰게 한 프로토콜) 도구나 지연이 큰 외부 API를 많이 쓰는 파이프라인일수록 SOP 압축의 회수 기간이 짧음.

12. 주의점. SOP는 환경이 바뀌면 낡음. API 스펙이 바뀌거나 UI가 바뀌면 캡슐화된 로직이 조용히 실패함. Reviewer의 가지치기를 주기적으로 돌리거나 최소한 SOP별 성공률 모니터링은 붙여야 함.

13. 결론. 모델을 바꾸지 않고 도구셋만 진화시켜서 성공률과 효율을 동시에 올릴 수 있음. 반복 패턴 추출 → 검증 → 통합 → 가지치기. 근데 검증 단계를 빼면 이건 그냥 나쁜 습관의 자동화라는 것까지가 요점임.
