GUI 에이전트 벤치마크가 전부 단일 디바이스 관행에 맞춰 있다는 문제의식에서 만들어진 벤치마크가 나옴. 결과의 낙차가 극단적이라 정리함. 원문은 [arXiv:2609.10451](https://arxiv.org/abs/2609.10451)(EMNLP 2026 Main).

1. 구성 방식부터가 공학적임. 원자 과제 118개를 입력 슬롯, 출력 슬롯, 템플릿, 평가 함수, 대상 플랫폼으로 정의하고, 타입 시스템의 서브타입 부분 순서 아래 과제들을 방향 그래프로 자동 조합해 크로스 디바이스 워크플로 150개를 만듦. 대표 예시가 실감나는 품질임 — 폰으로 사진을 찍고 클라우드에 올리고 Ubuntu에서 내려받아 흑백 변환한 뒤 다시 폰의 특정 경로에 저장하는 7서브태스크 워크플로.

![JarvisGUI 구성](/images/2026-09-10-jarvisgui-cross-device-gui-agents/fig-1-p2.png)

2. 품질 관리도 단단함. 원자 과제는 사람이 20스텝 이내 완수 가능하도록 설계했고 평가 함수를 실행 전후로 돌려 상태 변화를 확인함. 조합 과제는 LLM 재판관이 현실성·일관성·평가가능성 세 축 만점만 남기고, 사람 검증과의 Cohen's Kappa가 약 0.92임. 평가는 최종 환경 상태 검사 — 파일 내용, DOM 등을 보는 거라 에이전트 자기 선언이 아니라 실제 결과로 채점함.

3. 환경도 실용적임. Docker + KVM으로 세 OS를 병렬 실행하는 4계층 구조. GUI 벤치마크 재현의 큰 장벽인 환경 문제를 가상화로 해결했다는 것.

![환경 구조](/images/2026-09-10-jarvisgui-cross-device-gui-agents/fig-2-p4.png)

4. 결과의 낙차가 이 논문의 본체임. 원자 과제 최고가 HOLO2-30B의 Overall TSR 42.4%. 근데 멀티 디바이스 의존(MD) 과제는 최고 2%, 대부분 모델 0%. 서브태스크 4개 이상 조합 과제는 전 모델 0% 부근. 단일 디바이스에서 되는 것들이 디바이스 경계를 넘는 순간 완전히 무너진다는 것.

5. 실패 원인 분석이 세 가지로 정리돼 있음. 첫째, 상태 추론 병목 — 다른 디바이스의 실행 기록만으로 대상 디바이스의 현재 상태를 추론하지 못함. 둘째, 장기 임계 경로 — 순차 단계에서 중간 한 단계 실패가 전체 체인을 끊음. 셋째, 화면 세 개 동시 처리가 그라운딩 정확도를 떨어뜨리고 암시적 지시의 플랫폼 매핑이 실패함. 특히 실행되지 않은 의존 단계를 완료로 가정하는 캐스케이드 오류가 서브태스크 수 증가에 따른 급감의 원인이라는 것.

![디바이스별 성능](/images/2026-09-10-jarvisgui-cross-device-gui-agents/fig-4-p9.png)

6. 이건 앞서 정리한 LHTB·OmniaBench 결과와 정확히 같은 패턴임. 장기 실행에서 계획 유지와 제약 유지가 깨지는 것, 그리고 완료 판정을 에이전트 자기 선언에 맡기면 안 된다는 것. JarvisGUI는 이걸 크로스 디바이스 설정에서 재확인함. 대응도 같음 — 의존 단계별 외부 상태 검증, 체인 중간 게이트, 완료 선언 전 실제 파일·DOM 확인.

7. 필자 적용 포인트. 필자 파이프라인도 브라우저-셸-파일시스템을 넘나드는 멀티 디바이스의 축소판임. 지금 파일 기반 진행 로그가 상태 전달을 담당하고 있는데, JarvisGUI의 실패 분석은 이 설계가 왜 필요한지 보여줌 — 다른 환경의 실행 기록만으로 현재 상태 추론은 실패하니까 상태를 명시적 외부 매체로 공유해야 한다는 것. 그리고 서브태스크 체인이 길어질수록 중간 검증 게이트를 늘리는 게 성공률을 지키는 유일한 길임.

8. 플랫폼별 편차도 참고할 만함. 전 모델이 Windows에서 상대적으로 약했는데 사전학습 데이터에서 고품질 Windows GUI 데이터가 부족해서라는 분석임. GUI 에이전트를 도입할 때는 자기 환경이 학습 데이터에 풍부했는지부터 확인하는 게 순서임.

9. 문제제기. KVM 미지원 환경에서 재현에 제약이 있음. Planner-Grounder 구조로 중앙 플래너(Qwen3-VL-Plus)를 쓰는데 이 구조 자체가 성능 상한을 만들 수 있어서, 다른 오케스트레이션 설계에서 MD 과제 성적이 어떻게 나오는지는 열린 질문임.

10. 남는 결론. 크로스 디바이스는 GUI 에이전트의 다음 전선이고 지금은 전 모델이 사실상 0임. 단일 디바이스 스코어로 에이전트를 골라서 크로스 디바이스 워크플로를 맡기면 실패하는 게 당연하다는 것 — 상태 전달 설계와 중간 게이트 없이는 접근 자체가 성급하다는 게 이 벤치마크의 실무 교훈임.
