스킬 후보의 성능을 알아보려면 타깃 에이전트로 실제 실행해야 하는데 이 실행이 비쌈. 그러면 실행할 후보를 고르는 것 자체가 최적화 문제가 됨 — [COBRA-Skills](https://arxiv.org/abs/2609.11682)가 이 선택을 밴딧으로 품. 스킬 최적화 비용에 고생하는 사람에게 직결이라 정리함.

1. 배경. 스킬은 작업 절차, 추론 전략, 도구 사용법을 텍스트로 정리해 컨텍스트에 주입하는 형태. 근데 generate-evaluate-refine 루프에서 후보의 실제 효용은 타깃 에이전트 실행으로만 알 수 있음. 저품질 후보를 걸러내기 전에 예산이 먼저 소진됨. 트랙토리 반복 분석과 스킬 반복 수정에도 LLM 호출이 계속 듦.

2. 조치는 두 루프임. 컨텍스트 밴딧(각 선택지를 골라볼 때마다 결과를 관찰하며 최선을 배우는 순차 선택 프레임워크) 우선순위 — 각 후보 스킬을 하나의 팔로 취급하고 신경망 보상 예측(2층 MLP)에 LinearUCB(아직 불확실한 선택지에 탐색 보너스를 주는 밴딧 알고리즘) 탐색 보너스를 더한 점수로 매 라운드 스킬 하나만 실제 평가. 증거 기반 스킬 진화 — 주기적으로 저우선순위 스킬 3개를 잘라내고 regeneration(다양성), rollout mutation(성공/실패 트랙토리 근거 국소 수정), crossover(고성능 스킬 재조합)로 채움.

3. 진화를 매 라운드가 아니라 예약된 시점(d=3)에만 돌리는 게 비용 절감의 핵심이었음. 티칭 모델 토큰이 SkillOpt 대비 67-80% 감소. 트랙토리 재분석을 줄였는데 성능은 오히려 더 높아짐 — 같은 실행 예산을 밴딧이 더 잘 배분한 것.

4. 숫자. Qwen3.6-35B 기준 무스킬 60.4 → SkillOpt 69.6 → COBRA 73.5. GPT-5.4-Nano에서는 30.0 → 56.9(+26.9pp)로 약한 모델일수록 향상 폭이 큼. 비용은 Qwen 기준 SkillOpt $121.02 → $54.10, 비용당 개선점은 13.15 → 4.13.

5. 최적화 예제가 벤치마크당 50개뿐이라는 것도 실무적임. 비교 대상들은 더 큰 풀을 썼는데도 이김. 인구 크기 10, 라운드 30이라는 소규모 설정이라 이식 난이도가 낮음.

6. 하네스 일반화도 확인됨. Claude Code, Codex로 타깃 환경을 바꿔도 최고 성능 유지 — 특정 하네스 과적합 없이 일반화된 스킬을 만든다는 것.

7. 여기서 문제제기. 이 구조는 스킬 영역을 넘음. "평가가 API 호출로 귀결되는" 워크로드 전반 — 프롬프트 후보 선별, 도구 구성 탐색, 평가 세트 선택 — 에 같은 설계가 들어맞음. 실무에서 제일 아픈 지점이 스킬 생성이 아니라 스킬 검증이니까.

8. 적용 원칙. (1) 후보를 전부 실행하지 말 것 — 보상 예측+불확실성 보너스로 우선순위를 매기고 최상위만 평가. (2) 정비(진화)를 매번 돌리지 말 것 — 주기적으로 배치로 돌리는 것만으로 비용이 크게 줌. (3) 탐색 보너스를 넣을 것 — 안 그러면 이미 좋았던 스킬의 변형만 계속 시도하게 됨.

9. Skill-α, WikiSkill과 비교하면 방향이 다름. Skill-α는 편집 하나의 롤백 비교, WikiSkill은 지식 축적 층. COBRA는 어떤 후보를 실행할지의 샘플링 문제. 스킬 최적화의 병목이 점점 "무엇을 시도할지"로 이동하고 있다는 것.

10. 한계. 임베딩 공간의 거리가 스킬 호환성을 잘 표현한다는 가정이 조용히 깔려 있음. SocialMaze에서는 SkillOpt가 오히려 0.8pp 높은 등 과제별 편차 존재. 도메인에 따라 50개 예제 확보 자체가 어려울 수 있음.

11. 결론. 비싼 평가 환경에서는 샘플링 전략이 곧 최적화 성능임. 근데 밴딧이 잘 작동하려면 보상 이력이 쌓여야 하니까 결국 "실행 기록을 재활용하는 구조"가 전제라는 것 — 이것도 결국 기록 자산의 문제로 귀결된다는 결론임.
