에이전트에 스킬 문서를 넣어줘도 실행이 흔들리는 문제를 [SkillSentry](https://arxiv.org/abs/2608.09253)가 푸는 방향이 남다름. 모델도 에이전트도 스킬 문서도 수정하지 않고 런타임 훅으로 실행을 감시하고 보정하는 것. SkillsBench 기반 15개 스킬, Claude Code(Haiku-4.5, Opus-4.6)와 Codex(GPT-5.2, GPT-5.4) 네 조합에서 평균 과제 성공률이 24.1% 올랐고 반복 실행 편차도 줄었음. 스킬 문서를 계속 다시 쓰는 방식에 익숙했던 나에게 방향 전환을 알려준 논문이라 정리함.

1. 배경. 같은 스킬로 비슷한 과제를 반복 실행해도 결과가 계속 흔들림. 논문이 잡은 실패 원인은 두 가지. 스킬이 정한 스텝을 건너뛰거나 순서를 바꿔서 실행하는 절차 이탈, 개별 스텝을 틀리게 수행하는 스텝 오류(잘못된 인자, 잘못된 도구 호출). 대표 스킬 하나도 설정별로 0.613에서 0.833까지 갈림. 같은 스킬 문서를 쓰는데 실행 환경에 따라 성공이 왔다 갔다 하는 것. 문서를 아무리 다듬어도 실행 시점의 문제는 안 잡힌다는 뜻임.

![스킬 실행 실패 사례](/images/2026-08-16-skillsentry-skill-runtime-assurance/fig2-failures.png)

2. 재료가 좋음. 스킬 문서를 그대로 컨텍스트에 안 넣음. 대신 문서에서 명세를 뽑고 과거 성공/실패 트레이스에서 실행 경험을 캐서 합침. 이걸 런타임 가이던스라 부르는데 전용 DSL로 표현됨. 스킬 이름과 목표, 스텝별 논리적 액션 패턴, 스텝 진입 시 제안과 경고(on_enter), 실패와 연관된 액션 패턴(failure_patterns), 정상 종료 조건(termination). on_enter와 failure_patterns는 트레이스에서 자동으로 채워짐. 즉 가이던스는 고정 문서가 아니라 실행 통계가 축적되는 산 물체임.

3. 실행 루프를 훅으로 감싸서 검사함. Claude Code와 Codex는 실행 루프의 라이프사이클 훅을 제공하는데, SkillSentry는 이 훅에 붙어서 에이전트가 계획한 액션을 실행 전에 검사함. 에이전트 구현은 한 줄도 수정하지 않음. 절차 체커는 액션이 현재 스텝의 논리 패턴과 맞는지 FSM으로 추적하고 이탈이나 위험 패턴 매치가 보이면 재계획 힌트를 줌. 종료 체커는 종료 조건이 채워지기 전에 조기 종료하려 들면 경고함.

![접근 개요](/images/2026-08-16-skillsentry-skill-runtime-assurance/fig3-overview.png)

4. 설계 디테일이 신중함. 패턴에 안 맞는 액션을 무조건 막지 않음. 유효한 탐색일 수 있어서 실행은 허용하고 FSM 진행만 안 시킴. 영구 차단을 피한 설계라는 게 저자들의 강조점인데 맞는 판단임. 감시자가 탐색을 죽이면 정밀한 절차 과제 외에 다 못 쓰는 물건이 됨.

5. 결과. 네 조합 평균이 Claude Code+Haiku 0.572→0.741, Claude Code+Opus 0.661→0.811, Codex+GPT-5.2 0.604→0.752, Codex+GPT-5.4 0.668→0.805. 개별 스킬 단위로는 excitation-signal-design이 Haiku 기준 0.120에서 0.373으로 세 배 가까이 오름. 약한 모델일수록 감시의 효과가 크다는 패턴이 다시 나옴.

6. 비용이 실무적 포인트임. 추론 턴은 7.8% 증가(Haiku 기준 20.2→22.2), 토큰 비용은 8.7% 증가(796K→886K). 원인은 스텝 가이던스 전달과 이탈 감지 시 재계획 요청. 성공률 개선 대비 비용 증가가 10% 미만이라 바로 쓸 만함.

7. 절제 실험의 해석이 중요함. on_enter를 제거하면 −19.0%, failure_patterns를 제거하면 −13.6%, 그리고 가이던스를 시스템 프롬프트에 통째로 넣으면 −5.8%임. 같은 정보라도 실행 시점에 해당 스텝만 전달하는 게 효과의 상당 부분이라는 것. 즉 "정보를 주는 것"이 아니라 "맞는 타이밍에 맞는 조각만 주는 것"이 효과의 본체임. 이건 앞서 정리한 선택적 개입(메모리 에이전트) 연구와 정확히 같은 결론이 다른 영역에서 재현된 것임.

8. 축적도 됨. 가이던스는 새 트레이스가 쌓일 때마다 갱신되는데 10회 반복 진화하면 테스트 성공률이 약 58.2% 상대 상승. 개선은 초반에 크고 후반에 수렴하며 반복 실행 표준편차도 줄어듦. 크로스 모델 일반화도 확인돼서 다른 모델에서 진화한 가이던스를 가져다 써도 base 대비 +17.2%, 자체 진화 대비 94.2% 효율을 유지함.

9. 내 적용. Claude Code나 OpenClaw류의 훅 인터페이스로 외부 감시 레이어를 붙이는 패턴 자체를 가져감. 스킬 문서를 계속 다시 쓰는 대신 성공/실패 트레이스에서 "이 스텝에서 이런 액션은 경고"와 위험 패턴을 축적하는 편이 쌓이는 자산이 됨. 그리고 재현 실험을 반복 돌릴 때 성공률 편차를 잡는 용도로도 쓸 수 있음. 시작은 간단함. 훅부터 붙이는 것.

10. 한계. 15개 스킬, 두 에이전트, 30분 실행 제한 설정이고 절차형 스킬에 특화된 평가라 자유 탐색형 과제에서 FSM 추적이 어떻게 동작할지 확인이 필요함. 그래도 결론은 유효함. 스킬의 품질 관리는 쓰기 전(문서 최적화)과 실행 중(런타임 보증)으로 나뉘고, 후자가 비용 대비 효과가 더 좋다는 예다는 것.
