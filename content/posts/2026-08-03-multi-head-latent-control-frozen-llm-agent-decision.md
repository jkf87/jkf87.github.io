작은 모델로 돌리다 막히면 큰 모델에 넘기는 라우팅은 자연스러운 전략임. 근데 "언제 넘길까"가 어려움. Huawei와 University of Alberta가 은닉 상태에서 그 신호를 읽어냈음. 원문은 [arXiv:2607.14277](https://arxiv.org/abs/2607.14277).

1. 기존 접근의 한계. 프롬프트 수준 라우팅은 모델이 실제로 그 인스턴스를 풀 수 있는지를 안 봄. 외부 오케스트레이터는 비용과 지연을 추가함. 모델 파인튜닝은 새 모델 나올 때마다 반복해야 함.

2. 핵심 발상은 네 번째 길임. 동결된 백본의 은닉 상태 궤적에서 가벼운 제어 신호를 직접 읽는 것. 백본은 얼려두고 헤드만 16GB GPU에서 하루 이내로 훈련 가능함.

3. 헤드는 두 개임. Capability Head는 최종층 은닉 상태에서 "내가 이걸 풀 수 있나"를 0-1 점수로 냄. 낮으면 큰 모델에 제어권을 넘김. Resolution Head는 "그럼 어떤 개입이 필요한가"를 판단해서 추가 정보 요청, 도구 호출, 정중한 포기 중 하나를 고름.

4. 훈련 데이터 교훈이 중요함. 좁은 도메인(시각-수학만)으로 학습한 헤드는 다른 도메인에서 ROC-AUC 0.62로 급락하는데 120K 혼합 데이터로 학습하면 0.84까지 오름. "모델이 충분한가"라는 질문에 답하려면 광범위한 훈련 분포가 필수라는 것임.

5. 왜 토큰 확률로는 안 되는지가 제일 큰 교훈임. 생성 토큰의 평균 확률은 confident-wrong인 경우를 구분 못 함. 은닉 상태 기반 점수는 정답과 오답 사이에 명확한 분리를 보임. 그리고 "확실하지 않으면 답하지 마"라고 프롬프트로 지시하면 1581건 중 4건만 이양함. 모델은 자기 불확실성을 텍스트로 표현하는 데 극도로 서툴고, 자기 인식은 표면이 아니라 내부 표현 깊은 곳에 인코딩돼 있다는 뜻임.

6. 층 선택도 흥미로움. Capability Head는 최종층에서, Resolution Head는 중간층에서 가장 강한 신호를 얻음. 모델 적절성 평가와 개입 결정이 은닉 상태의 서로 다른 깊이에서 최적화됨. 표면 행동과 내부 표현이 일치하지 않는다는 방증이기도 함.

7. 접두부 평가가 실무적 핵심임. 200 토큰 접두부만 관찰해도 ROC-AUC 0.80(전체는 0.86)으로 조기 판단이 가능함. 불필요한 생성을 중간에 끊고 큰 모델에 넘기는 인터럽트 라우팅의 근거가 됨.

8. 결과. AndroidWorld에서 Qwen3-VL-4B 단독 0.47, 32B 단독 0.58인데 라우팅하면 0.60이면서 대형 모델 비용은 90.7% 감소함. 작은 모델만 쓸 때보다 점수가 오히려 높음. TriviaQA에서 4B는 도구 결정 개선으로 상대 +158.9%, 필요한 검색 놓친 게 464건이나 줄음. When2Call에서도 F1이 37.3에서 49.0으로 오름.

9. 내 라우팅 설계에 반영한 것. 모델 응답의 자기 보고("확실함")를 라우팅 근거로 쓰는 걸 중단함. 대신 은닉 상태 접근이 안 되는 API 환경에선 접두부 200 토큰 수준의 조기 중단 + 과제 난이도 사전 분류로 근사함. 그리고 "도구를 써야 하나, 정보를 물어봐야 하나, 포기해야 하나"를 별도 분류 문제로 분리한 구조가 프롬프트 하나에 다 우겨넣는 것보다 낫다는 걸 여기서 확인했음.

10. 문제제기. 헤드 품질이 전체 효율을 직접 결정해서 헤드가 나쁘면 잘못된 라우팅이 오히려 비용을 늘림. 롱호라이즌에서는 작은 판단 오류가 누적됨. 그리고 은닉 상태 접근은 오픈웨이트 모델에 한정되고, 프론틐어 API 모델에는 적용이 안 된다는 게 현실적 제약임. 그래도 "언제 넘길까" 문제의 정답 방향을 보여줬다는 데 의미가 있음.

11. 결론. 동결된 모델을 쓰면서도 배포 시점 제어가 가능함. 비용 90% 절감은 최적화가 아니라 상용 배포 가능성의 문제이고, 은닉 상태 궤적은 안전 필터링·에스컬레이션으로 확장 가능한 재사용 제어 기반임.
