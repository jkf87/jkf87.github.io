에이전트 프레임워크가 난립함. LangChain, OpenAI Agents SDK, Claude Agent SDK, smolagents, OpenClaw까지. 저마다 도구와 메모리와 트레이스를 주는데, 공통점은 에이전트 코드를 프롬프트 템플릿, 스키마, 콜백, 설정 파일로 쪼개놓는다는 것. [NVIDIA의 NOOA](https://arxiv.org/abs/2607.20709)는 여기에 단순한 질문을 던짐. "파이썬에 이미 추상화가 있으면 그걸 그대로 쓰면 안 되는가." 결론부터 말하면 253줄짜리 일반 파이썬 코드로 SWE-bench Verified(실제 GitHub 저장소의 이슈를 해결하는 코드를 작성하게 하는 코딩 벤치마크) 82.2%를 찍으며 오픈소스 하네스를 전부 이김. 왜 이런 게 되는지와 내가 가져갈 지점을 정리함.

1. 설계 원칙은 다섯 개인데 요약하면 하나임. 에이전트를 파이썬 클래스로 쓰는 것. 클래스가 에이전트, 메서드가 액션, 필드가 상태, 독스트링이 프롬프트, 타입 어노테이션이 계약임. 새 DSL을 안 만들고 LLM이 이미 학습한 파이썬 코드 분포에 가장 가까운 형태를 쓰는 게 핵심임. 모델은 이미 파이썬을 알고 있어서 루프, 조건문, asyncio, DB 클라이언트까지 그냥 쓸 수 있음. 프롬프트 언어를 새로 가르칠 필요가 없다는 것.

![NOOA의 간단한 에이전트 구현](/images/2026-07-24-nooa-nvidia-object-oriented-agents/fig-1-p2.png)

2. 두 번째 원칙이 실무적으로 제일 큼. 정확한 규칙, 산술, 파싱, 상태 전이는 LLM 루프 밖의 결정적 메서드로 빼는 것. 코드 바디가 `...`(ellipsis)면 에이전트 메서드, 실제 구현이 있으면 그냥 파이썬 메서드. 즉 같은 클래스 안에 "LLM이 판단하는 부분"과 "그냥 코드로 돌아가는 부분"이 나란히 있음. 에이전트가 더럽게 비싸고 느려지는 지점이 대부분 정확한 계산을 LLM한테 시키는 구조 때문인데, 이 원칙을 코드 컨벤션 레벨로 못 박은 것임.

3. 세 번째는 참조 전달(pass by reference)임. 메서드 인자가 살아 있는 파이썬 객체로 전달되고, 프롬프트에는 타입, 길이, head/tail 샘플만 보여줌. 100개짜리 리스트를 넘기면 `numbers: list[int] (len=100) [42, 17, 93, ..., 56]` 식으로만 뜨고, 모델은 코드 안에서 `numbers[0:50]`처럼 전체에 접근함. 컨텍스트 윈도우가 아니라 실행 환경이 처리 한계를 정하는 구조임. 도구 출력을 트랜스크립트에 통째로 직렬화하는 기존 방식과의 차이가 토큰 비용 그래프에 바로 나타남.

4. 실제 성적. SWE-bench Verified에서 GPT-5.5 xhigh 기준 82.2%로 OpenCode 78.6%, PI 78.2%를 앞서고 Claude Code(80.8%)와 동급, Codex(88.7%)에 접근함. Terminal-Bench 2.0(실제 터미널에서 명령을 내려 과제를 완수하는 능력을 재는 벤치마크)은 추론 꺼진 설정에서 OpenCode를 11.3포인트 앞짐. ARC-AGI-3(ARC-AGI 시리즈의 3판으로, 추상 추론 퍼즐로 일반 지능을 재는 벤치마크)에서는 기존 6개 전문 에이전트 협업 시스템을 NOOA 1개 + 50줄 스킬로 대체해서 RHAE 50.2%, 동일 모델 raw 13.3% 대비 6.4배 하네스 효과를 냄. 하네스가 모델을 바꾸하는 만큼 성적을 바꾼다는 증거임.

![SWE-bench Verified 패스율](/images/2026-07-24-nooa-nvidia-object-oriented-agents/table-3-p14.png)

5. 토큰 효율도 주목할 만함. SWE-bench xhigh에서 NOOA는 약 28회 호출, 약 1.1M 토큰으로 82.2%를 냄. PI는 66회 호출, 약 2.2M 토큰으로 78.2%. 호출 수와 토큰의 절반으로 더 높은 성적. 원인은 위의 참조 전달 구조임. 도구 출력이 살아 있는 파이썬 값으로 유지되고 트랜스크립트에 반복 직렬화되지 않음. 컨텍스트 관리가 성능이 아니라 비용 문제라는 걸 실무에서 체감 중이라면 이 부분이 답의 절반임.

6. 컨텍스트 렌더링도 세 영역으로 정리돼 있음. 한 번 계산해서 재사용하는 정적 블록, append-only인 이벤트 히스토리, 매 턴 재계산되는 동적 블록(라이브 상태). 정적은 불변, 히스토리는 붙이기만, 동적은 꼬리에 배치해서 KV 캐시(이미 계산한 프롬프트 앞부분의 중간 결과를 재사용하는 추론 가속 장치) 재사용을 극대화함. 내 세션 설계에서 "매 턴 전체를 다시 렌더링"하고 있으면 캐시가 계속 무효화돼서 비용이 두 배가 되는 것과 같은 원리임.

7. 메모리 시스템 운영도 배울 만함. ARC-AGI-3에서 3,262개 메모리 작성, 12,654회 자동 주입, 27,115회 의도적 도구 읽기(99% 적중)를 기록했는데, 자동 주입은 턴당 평균 4.1개로 억제돼서 컨텍스트 폭주를 막음. 메모리를 무조건 밀어 넣는 게 아니라 주입 비율에 상한을 둔 것. 앞서 정리한 "선택적 개입" 연구와 정확히 같은 방향임.

8. 근데 비판적으로 보자. 이 논문의 부록에서 14개 프레임워크를 비교하는데, OpenAI 샌드박스 에이전트, Microsoft CodeMode, PydanticAI 코드 모드처럼 NOOA 평가 기간 중 유사 실험이 우후죽순 나옴. 저자들은 "분야가 여섯 가지 아이디어로 수렴 중"이라 해석하는데, 수렴이라는 건 이 설계가 정답이라는 뜻이 아니라 아직 누구도 검증 못 한 미지영역이 남아 있다는 뜻이기도 함. 그리고 치명적인 트레이드오프가 있음. 모델이 쓴 코드를 에이전트 프로세스 안에서 실행하니까 샌드박싱은 전부 외부에서 해야 하고, 그러려면 참조 전달을 포기하고 직렬화 복사를 받아들여야 하는 딜레마가 생김. 편의성과 격리의 양립이 아직 안 된 것.

9. 그래도 내가 가져갈 것은 명확함. 첫째, 정확한 계산은 LLM한테 안 시키고 결정적 코드로 빼기. 둘째, 큰 데이터는 프롬프트에 통째로 직렬화하지 말고 요약 + 코드 접근으로 바꾸기. 셋째, 프롬프트와 도구와 상태를 분리된 파일로 흩뿌리지 말고 하나의 모듈로 모아서 소프트웨어처럼 다루기. 전부 특정 프레임워크 없이 오늘 적용 가능한 원칙들임.
