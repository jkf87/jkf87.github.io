컴퓨터 사용 에이전트 개선책은 죄다 "더 잘 보게 만드는 것"이었음. StateAct는 반대로 스크린샷을 버리고 프로그램 내부 상태를 코드로 직접 읽음. 같은 모델로 성공률을 올리고 비용은 9분의 1로 줄임. 화면 자동화를 실무에서 쓰는 사람에게 직결되서 정리함.

1. 배경. 데스크톱 작업의 진짜 산출물은 화면이 아니라 프로그램 상태의 변화임. 근데 스크린샷은 손실 압축임. 셀에 42가 보일 때 리터럴 42인지 =SUM(B1:B6)의 결과인지 알 수 없고, 숨겨진 행은 렌더링 자체가 안 되고, 파일이 제대로 저장됐는지도 화면으로는 안 보임.

2. 형식적으로 렌더링 함수는 단사(injective, 서로 다른 입력이 항상 서로 다른 출력을 내는 성질)가 아님. 서로 다른 상태가 같은 픽셀을 만듦. 그러니 완벽한 인식 모델도 픽셀로 원래 상태를 복원할 수 없음. 반면 코드 기반 채널(load_workbook(...)["B7"].value)은 정확한 값을 직접 읽음.

3. [StateAct](https://arxiv.org/abs/2607.22798)의 조치는 행동 공간 재설계임. 메인 에이전트는 코드와 구조적 조작만 함 — bash 세션, 파일 에디터, 계획 체크리스트. 마우스·키보드 조작은 메인 에이전트에게 아예 노출 안 함. GUI가 필요하면 전용 서브에이전트에 위임하는데, 108개 작업 중 28개, 메인 스텝의 1.1%에서만 호출됨.

4. 상태 발견 과정이 재밌음. 에이전트는 사전 지식("메일은 보통 sqlite에", "엑셀은 OOXML")과 find, ls, grep, sqlite3 탐색을 결합해서 상태가 어디 저장됐는지 찾음. 근데 "어디에"만 찾지 "정답값"을 찾지 않음 — 그건 작업 수행의 몫.

5. 검증도 같은 원칙임. finish가 호출되면 독립 finish gate가 새 컨텍스트에서 실행됨. 이 게이트는 에이전트의 메시지 히스토리, 계획, finish 사유를 못 봄(내레이션 블라인드). 작업 지시문과 머신 접근 권한만 받아서 실제 파일, 앱 백엔드, 셀 수식을 직접 확인함. 자기 반성과 반대 — 에이전트 주장을 보지도 않고 독립 검증하는 것.

6. 숫자. OSWorld 2.0(실제 운영체제 안에서 파일·앱 조작 과제를 시키는 컴퓨터 사용 벤치마크)에서 Claude Opus 4.8 기준 스크린샷 베이스라인 20.6% → StateAct 26.9% 바이너리 성공. 비용은 작업당 약 $72 → $7.8로 9배 절감. 출력 토큰도 224K → 100K. 공개 시스템 중 유일하게 프론티어를 넘음.

7. 제거 실험의 교훈. 상태 기반 행동 제거가 제일 큰 하락. 근데 GUI 서브에이전트 없는 bash-only는 베이스라인보다도 낮은 45.9%였음. 코드만으로는 안 되고 GUI가 안전망으로 있어야 상태 우선 접근이 완성된다는 것. 극단으로 밀지 말 것.

8. 실패 분석이 진짜 인사트임. 상태 기반 행동이 인식 실패를 대부분 없애버렸음. 남은 실패의 지배 유형은 추론 오류(79개 중 38개). 벽이 사라진 게 아니라 인식에서 추론으로 이동한 것. 하네스로 풀 수 있는 영역에 한계가 있다는 솔직한 진단.

9. finish gate도 완벽하지 않음. 구조 결함(잘못된 경로, 미저장)은 잘 잡지만 값의 정확성은 못 잡음 — 게이트가 같은 소스를 같은 방식으로 해석하면 같은 오류를 재생산하는 공통 모드 실패(검증자가 원래 검증 대상과 같은 방식으로 틀려 중복 검증이 무의미해지는 상황). 검증자를 늘리는 게 아니라 해석을 다르게 만들어야 한다는 과제.

10. GUI 서브에이전트는 강할 필요가 없다는 것도 절감 포인트임. 31B 경량 모델로 바꿔도 짧은 호라이즌 4개 벤치마크에선 차이가 없음. 근데 가장 긴 OSWorld 2.0에선 61.6% → 43.2%로 급락. 긴 작업일수록 프론티어급이 필요함.

11. 여기서 실무 적용. 화면 자동화를 짤 때 "무조건 스크린샷+클릭"이 아니라 순서를 정할 것. (1) 앱의 상태 저장소나 파일, API로 직접 읽고 쓸 수 있는가. (2) 안 되는 부분만 GUI 조작으로. 엑셀은 openpyxl로, 브라우저는 DOM으로, 메일은 DB로 — 이미 우리가 아는 사실을 에이전트 설계에 다시 적용하는 것.

12. 검증 설계도 베낄 것. 완료 판정을 수행한 에이전트에게 맡기지 말고, 에이전트 주장을 차단한 채 실제 파일 상태를 확인하는 독립 게이트로. 이건 StructAgent의 검증자 상태 확정이나 진행의 신기루 연구와 같은 방향임 — 이번 시즌 에이전트 설계의 공통분모.

13. 한계. 오디오·비디오 같은 비텍스트 상태는 커버 안 됨. 상태 저장소를 찾는 탐색에 실패하는 앱에서는 GUI 폴백 비용이 커짐. 그리고 "프로그램 상태"에 접근 권한이 있다는 전제 자체가 실무 환경에선 안 맞을 수 있음(권한, 난독화).

14. 결론. 에이전트가 어디를 보는지 바꾸는 게 모델 교체보다 쌈. 스크린샷은 손실 압축이고 코드는 정확한 값이라는 관찰 하나로 성능과 비용을 동시에 잡음. 근데 상태 접근이 안 되는 화면은 여전히 GUI로 가야 하고, 그 안전망 없이는 전체가 무너진다는 것까지가 설계의 전부임.
