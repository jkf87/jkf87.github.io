코딩 에이전트에게 데이터 파이프라인을 시키면 대부분 일회성 파이썬 스크립트를 내놓음. 실행은 되지만 관리도 검수도 재사용도 안 됨. 여기서 DAG는 방향성 비순환 그래프를 뜻하는데, 데이터 처리 단계들을 화살표로 연결해 앞 단계가 끝나야 뒤 단계가 실행되는 순서 구조로 파이프라인을 표현하는 방식임. DataFlow-Harness 연구는 이 간극에 NL2Pipeline gap이라는 이름을 붙이고, 에이전트가 플랫폼 네이티브 DAG를 직접 조립하게 만듦. 자동화 파이프라인을 에이전트로 짜는 사람에게 실무 교훈이 많은 구조임.

1. 문제 정의가 먼저다. 워크플로우는 의도된 데이터 처리 절차, 파이프라인 표현은 플랫폼에 영속되는 객체, DAG는 실행 의존성 그래프임. 코드 생성 정확도가 아무리 높아도 산출물이 가시적이고 편집 가능하며 재사용 가능한 객체가 아니면 산업 환경에서 못 씀. 그래서 구축 과정 자체를 플랫폼 시맨틱에 접지(grounded)시켜야 한다는 게 출발점임.

![DataFlow-Harness architecture](/images/2026-07-23-dataflow-harness-grounded-code-agent-pipelines/fig-1-p4.png)

2. 첫 번째 구성 요소는 DataFlow-Skills임. "어떤 순서로 오퍼레이터를 고르고 조립할지"라는 절차적 지식을 에이전트에 주입함. 스키마 추론 → 오퍼레이터 선택 → 파라미터 설정 → 서빙 검증의 권장 시퀀스와 호환성 규칙임. MCP는 모델 컨텍스트 프로토콜로, LLM이 외부 도구와 데이터 소스에 표준화된 방식으로 접속하게 해주는 인터페이스임. MCP가 "무엇이 가능한가"를 알려준다면 Skills는 "어떻게 해야 하는가"를 알려줌. 이 구분이 뒤에 나올 실험 결과에서 결정적임.

3. 두 번째는 MCP 도구 레이어임. 에이전트가 라이브 오퍼레이터 레지스트리와 현재 파이프라인 상태에 접근함. 모든 변경은 Request-Validate-Commit 프로토콜을 거침. 매 턴 시작 때 최신 상태를 다시 가져오고(사람이 수동 편집한 것도 반영), 에이전트는 타입화된 구조적 변이로만 의도를 표현함. 임의 파이썬 코드가 아니라 오퍼레이터 추가·제거, 파라미터 업데이트, 엣지 연결만 허용됨. 그래프가 비순환인지, 인접 오퍼레이터 간 스키마가 호환되는지 검증하고 통과 시 커밋함.

![DataFlow-WebUI dual-modality interface](/images/2026-07-23-dataflow-harness-grounded-code-agent-pipelines/fig-2-p5.png)

4. 세 번째는 듀얼 모달리티 UI임. 대화형 에이전트 인터페이스와 시각적 DAG 에디터가 하나의 백엔드를 공유함. 대화로 만들면 실시간 시각화되고, 사람이 에디터에서 노드를 드래그해서 고치면 그 변경이 다음 에이전트 턴에 반영됨. 사람과 에이전트가 같은 객체를 편집하는 구조. 자동화 도구 설계에서 늘 부족하던 "사람 개입 지점"을 이렇게 풀었음.

5. 실험 결과에서 제일 중요한 대비는 이것임. MCP 도구 접근만 준 설정은 통과율이 83.3%로 오히려 떨어짐. 근데 Skills를 더하니 93.3%로 회복됨. 도구에 접근할 수만 있고 어떻게 써야 할지 모르면 자유도가 성능을 해친다는 것. 그리고 DataFlow-Harness의 비용은 일회성 스크립트를 내놓는 바닐라 Claude Code 대비 72.5% 절감, 지연은 49.9% 단축임. 관리 가능한 산출물이 오히려 싸고 빠르다는 결과. 거버넌스와 효율이 양립됨.

6. 다운스트림 결과가 의외였음. 에이전트가 만든 파이프라인의 출력 데이터로 Qwen2.5-7B를 파인튜닝했더니 수학에서 25.1 → 35.9(AIME24@32), 코드 64.6 → 75.4(MBPP). AIME24는 수학 경시 문제 벤치마크이고 @32는 문제당 32번 답을 뽑아 하나라도 맞으면 통과로 세는 채점 방식, MBPP는 초급 파이썬 프로그래밍 문제 모음 벤치마크임. 접지된 파이프라인이 검증을 거치니 더 깨끗한 데이터가 나온다는 것. 파이프라인 품질이 그대로 학습 데이터 품질로 이어지는 구조임. 합성 데이터 만드는 사람에게 그대로 적용되는 교훈임.

7. 내 실무 결론은 네 가지임. 첫째, 에이전트가 만드는 자동화 산출물을 일회성 스크립트가 아니라 영속적·편집 가능한 객체로 강제할 것. 둘째, 도구 접근(MCP)만 주지 말고 절차적 가이드(Skills)를 세트로 줄 것. 하나만 주면 성능이 떨어지는 게 숫자로 증명됨. 셋째, 에이전트의 변경을 임의 코드가 아니라 타입화된 변이로 제한하고 검증 후 커밋할 것. 넷째, 사람 개입은 별도 리뷰 단계가 아니라 같은 객체를 공유하는 동시 편집으로 설계할 것.

근데 한계는 존재함. 단일 에이전트(Claude Code), 단일 모델(Opus 4.7), 12개 태스크 평가라 일반화에 제약이 있음. 스키마 검증은 구조적 유효성만 보장하고 시말틱 정확성은 별개임. 그래도 "MCP만 있으면 된다"는 통념을 깨는 데이터로서 가치가 큼.
