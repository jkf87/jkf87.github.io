스킬 진화 연구 대부분은 검증 데이터셋이 있다고 가정하는데 실제 배포 환경엔 없음. 에이전트에게 주어지는 건 이진 종료 보상뿐이고 시도 횟수도 제한적임. 이 희소 보상 설정에서 매번 최선 수정을 커밋하는 탐욕적 방식은 초기 진단이 틀리면 이후 전부를 낭비하는 착취 함정에 빠짐. [SkillHEX](https://arxiv.org/abs/2608.05628)(가설을 세워 자기검증하고 수정 이력을 트리로 보관하는 스킬 진화 프레임)가 두 가지 구조로 이걸 풂. 가설 기반 자기검증과 증거 기반 트리 탐색. 시도 예산 안에서 기존 대비 최대 9.5pp 높은 통과율을 냄.

1. 배경. 기존 스킬 진화는 두 패러다임으로 나뉘었음. 스킬 지시문을 매개변수로 보고 언어 모델 피드백으로 기울기를 계산하는 텍스트 공간 최적화(TextGrad, GEPA — 스킬 문구를 매개변수처럼 보고 피드백으로 개선하는 방법들), 실행 궤적에서 휴리스틱을 증류하는 경험 기반 접근(Trace2Skill, CoEvoSkills). 둘 다 검증 데이터를 가정함. SkillsBench에서 기존 방법들이 2-3회 반복 후 정체되는 것도 이 때문임. 예산이 부족한 환경에서 그리디하게 커밋하다 막히는 것.

![기존 방법의 정체 vs SkillHEX](/images/2026-08-12-skillhex-hypothesis-driven-agent-skill-evolution/fig-1-p1.png)

2. 첫 번째 구조, 가설 기반 자기검증. 실패 시 세 단계를 돎. 실행 궤적과 현재 스킬을 분석해서 검증 가능한 실패 원인 가설을 만들고 Add/Refine/Refute 연산으로 가설을 동적 관리함. 각 가설에 대해 실행 가능한 테스트 케이스를 생성해서 규칙 기반 검증기로 구문 정확성을 보장함. 그리고 테스트 결과를 증거 행렬로 누적하는데, 핵심은 캐시된 출력에 대해 테스트를 재실행한다는 것. 추가 환경 호출 없이 밀집 진단 신호를 만들어서 시도 예산을 안 태움. 희소한 보상을 가설 검증으로 밀도 있게 바꾸는 게 아이디어의 본질임.

3. 두 번째 구조, 증거 기반 트리 탐색. 스킬 수정을 in-place가 아니라 트리로 관리함. 각 노드가 스킬 버전과 캐시된 출력, 보상을 보관하고 PUCT(이미 좋은 노드와 아직 덜 탐색한 노드 사이 균형을 잡는 트리 탐색 선택 규칙) 방식으로 노드를 골라서 증거가 지지하는 수정과 미탐색 대안 사이의 균형을 유지함. 한 경로가 실패해도 트리에 보존된 다른 후보로 회귀할 수 있음. 앞서 정리한 누적 개선 연구들과 같은 맥락인데, 여기선 희소 보상 + 제한 예산 조건에서 트리가 회복 가능성을 줌.

![프레임워크 구조](/images/2026-08-12-skillhex-hypothesis-driven-agent-skill-evolution/fig-2-p4.png)

4. 결과. SkillsBench(에이전트 스킬 활용 능력을 재는 87개 작업 벤치마크) 87개 작업, 반복 예산 5회 기준으로 GPT-5.3-Codex에서 기존 최강 CoEvoSkills 46.4% 대비 SkillHEX 55.9%, Claude Opus 4.7에서 49.4% 대비 57.9%. 사람이 쓴 스킬(43.0%, 44.3%)도 크게 앞섬. 토큰 효율도 좋아서 CoEvoSkills 대비 18.0% 적은 토큰으로 더 높은 통과율. 트리 탐색이 in-place 수정보다 토큰을 절약한다는 게 직관에 반하는 결과인데, 실패 경로를 반복 탐색하지 않아서로 읽힘. 초기 스킬 없이 시작해도 LLM 생성 스킬로 시작한 것과 유사한 성능이라 진입 장벽도 낮음.

5. 케이스 스터디가 이 논문의 차이를 잘 보여줌. 전력 시장 가격 책정 문제에서 첫 가설(LMP 듀얼 스케일링 오류)을 따라 세 번 수정했으나 공식 검증이 실패함. SkillHEX는 트리에 보존된 대안(V2)으로 회귀한 뒤 MATPOWER 데이터 의미론 수정을 적용해서 마지막 시도에 성공함. in-place 방식이었다면 첫 진단이 틀린 순간 끝났을 경로임. 진단이 틀릴 수 있다는 전제를 구조에 넣는 게 설계의 출발점이라는 것.

6. 한계가 정직하고 중요함. 지식 집약적 도메인(자연과학, 금융)에서는 실행 궤적만으로 메꿀 수 없는 사실적 지식 결손이 있다는 것. 가설 검증으로 해결되는 건 절차적 정밀도지 지식 획득이 아님. 스킬 진화가 만능이 아니라는 경계선을 명확히 그은 것. 도메인 지식이 부족한 실패는 스킬을 아무리 고쳐도 안 풀리고, 그럴 땐 자료를 가져다줘야 함.

7. 내 적용은 이렇게임. 첫째, 프롬프트·스킬 수정을 시도할 때 매번 현재 버전을 덮어쓰지 말고 이전 버전을 보존해서 실패 시 회귀 가능하게 만들기. git 브랜치나 파일 버전으로 하면 됨. 둘째, 실패 원인을 "그럴듯한 설명"으로 커밋하지 말고 검증 가능한 가설로 변환해서 테스트하기. 셋째, 환경 호출 없이 캐시된 출력을 재분석하는 습관. 이미 뽑아둔 로그로 진단 가능한 걸 새 실행으로 확인하느라 예산을 태우는 게 얼마나 많은지 돌아보게 됨.
