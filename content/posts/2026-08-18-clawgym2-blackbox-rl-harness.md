Claude Code, Codex, OpenClaw 같은 프로덕션 하네스는 롱호라이즌 과제 성능을 크게 올려줌. 근데 이 하네스를 RL(강화학습, 보상 신호를 받으며 시행착오로 정책을 개선하는 학습 방식) 학습에 쓰는 건 막혀 있었음. 내부가 블랙박스라 무슨 호출이 일어나는지 정리가 안 되고, 롱호라이즌 과제의 상태ful 환경에서 대규모 동시 롤아웃이 인프라를 무너뜨리고, 중간 한 번의 실패로 배치 전체가 날아가고, 호출 로그는 잘리고 갈라져서 그냥 독립 학습시키면 공유 히스토리를 반복 학습함. ClawGym II는 이 벽을 넘음. 하네스 내부를 안 고치고 겉에서 도는 RL로 안정적으로 에이전트를 최적화한 것.

1. 구조가 세 층임. 첫째, 샌드박스 실행 인프라. 태스크 환경과 하네스를 임시 샌드박스에 격리해서 대규모 동시 롤아웃을 돌림. 실패가 누적돼도 전체 배치가 안 무너지게 하는 게 목적. 둘째, 서빙 프록시. 모델 호출 경계에 프록시를 두고 하네스가 모델을 부를 때마다 입력-출력 쌍을 캡처함. 하네스 코드를 안 열어도 학습에 필요한 기록이 모델 쪽에서 확보됨. 이게 블랙박스 문제의 해답. 내부를 못 보면 경계에서 가로채면 됨. 셋째, prefix tree 재구성. 캡처된 호출들이 잘리고 갈라지고 중복되니 롤아웃 단위 prefix tree로 조립해서 공유 히스토리 구조를 복원함. PPO(근접 정책 최적화, 한 번의 업데이트로 정책이 크게 바뀌지 않게 제한하는 대표 강화학습 알고리즘)와 GRPO(같은 문제의 여러 롤아웃을 한 그룹으로 묶어 상대 비교로 학습 신호를 만드는 그룹 강화학습 알고리즘)가 이 트리에서 최적화되도록 고쳤고 학습 시점과 추론 시점의 컨텍스트 구성 일관성도 유지함.

![Figure 1. 블랙박스 RL 프레임워크 개요](/images/2026-08-18-clawgym2-blackbox-rl-harness/fig-1-p6.png)

2. mix-harness 학습이 마지막 조각임. 하나의 모델을 OpenClaw와 Claude Code라는 이질적 하네스로 동시에 최적화함. 결과가 흥미로움. mix-harness로 학습한 모델이 단일 하네스로만 학습한 모델과 맞먹거나 더 좋았음. 파이프라인이 하네스 종류를 가리지 않는다는 뜻. 새 하네스가 나와도 같은 파이프라인에 붙일 수 있다는 실무적 의미임.

![Figure 4. 단일 하네스 vs mix-harness 학습 비교](/images/2026-08-18-clawgym2-blackbox-rl-harness/fig-4-p13.png)

3. 숫자. Qwen3-30A3B 시작으로 OpenClaw 경로 ClawII-OC가 ClawGym-Bench(하네스 환경에서 에이전트 과제 수행을 측정하는 벤치마크) Pass@1(첫 시도 만에 과제를 푸는 비율) +9.98p, PinchBench +11.71p. Claude Code 경로 ClawII-CC는 +14.81p, +17.28p. Claude Code 쪽이 더 크게 올랐는데 저자들은 하네스가 성숙할수록 학습 시그널이 커진다고 읽음. 그리고 최적화 200~400스텝 동안 학습이 안정적으로 유지됐다는 게 그 자체로 결과임. 긴 롱호라이즌 RL에서 안정성은 흔치 않으니까. JobBench, OfficeQA 같은 더 어려운 과제에서도 일관된 개선이 있었고 평가는 코드 검증과 루브릭 판정을 0.7/0.3으로 가중합하는 하이브리드 프로토콜을 썼음.

![Table 1. ClawGym-Bench / PinchBench 성능 비교](/images/2026-08-18-clawgym2-blackbox-rl-harness/table-1-p11.png)

4. 내 해석을 원문 근거와 구분해서 적음. 원문이 증명한 건 두 가지. 하네스 내부를 수정하지 않고 모델 호출 경계의 프록시 기록과 prefix tree 재구성만으로 PPO/GRPO 학습이 되고, 이질적 하네스를 하나의 학습 루프에 묶는 mix-harness가 단일 학습보다 뒤지지 않는다는 것. 여기서 내 해석은 이렇게임. 하네스를 자체 구축하지 않는 팀에게 이미 검증된 상용·오픈소스 하네스를 그대로 학습 환경으로 쓰는 길이 열렸다는 게 실질적 의미. 그리고 prefix tree 재구성은 에이전트 RL에서 반복되는 "잘린 로그를 멀티턴 궤적으로 어떻게 맞추느냐" 문제의 깔끔한 답 중 하나. 트레이스 기반 디버깅에도 같은 구조가 재사용 가능해 보임.

![Figure 2. OpenClaw 롤아웃 하네스에서의 PPO/GRPO 학습 곡선](/images/2026-08-18-clawgym2-blackbox-rl-harness/fig-2-p12.png)

5. 주의할 점도 분명함. 이건 개인이 바로 돌려볼 규모가 아님. 샌드박스 대규모 동시 롤아웃, 서빙 프록시, 트리 기반 최적화까지 갖추는 전제 조건이 필요함. 다만 개념 이식은 가능함. 첫째, 에이전트 로그를 쌓을 때 호출 경계(입력, 출력) 쌍을 온전히 남길 것. 내부를 몰라도 경계 기록이 있으면 나중에 재구성이 됨. 둘째, 잘린 로그를 그냥 독립 샘플로 쓰지 말 것. prefix tree로 조립해야 공유 히스토리를 반복 학습하는 오류를 피함. 셋째, 모델 성능을 올리고 싶을 때 하네스 교체만 반복할 게 아니라 현재 하네스를 학습 환경으로 삼는 선택지가 생겼다는 것. 넷째, 학습-추론 일관성, 학습 때의 컨텍스트 구성과 실제 하네스 추론 시점이 어긋나면 학습이 헛돈다는 원칙을 기억할 것.
