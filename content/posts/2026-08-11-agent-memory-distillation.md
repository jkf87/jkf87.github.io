작은 LLM 에이전트는 성공률이 낮아서 성공 궤적 자체를 못 만듦. 그래서 자기 경험에서 뽑은 메모리도 실패 투성이가 됨. KAIST의 AMD는 선생 에이전트의 성공 궤적에서 3단계 메모리를 뽑아 학생에게 주입함. 원문은 [arXiv:2608.07169](https://arxiv.org/abs/2608.07169).

1. 문제는 메모리 전송의 두 함정임. 첫째, 학생(4B)은 AppWorld에서 성공률 15% 수준이라 성공 궤적이 거의 없음. 둘째, 선생(GPT-5-mini) 메모리를 그대로 줘도 능력 차이 때문에 고수준 전략("먼저 로그인하라")을 4B가 이해 못 함. 단순 전송은 zero-shot과 거의 차이가 없었음.

2. 해법은 3단계 계층 메모리임. Workflow(태스크 전략·관련 도구·검증 단서, 시작 시 자연어로 주입), Subtask(서브태스크별 구체 행동 예시, 시작 시 코드 블록으로), Function(함수별 호출 규약·실패 패턴, 에러 발생 시 반응형으로)임. 고수준 계획은 prose, 저수준 실행은 코드로 준다는 형태 선택이 중요한 설계임.

3. 결과. 파인튜닝 없이 메모리 주입만으로 Qwen3-4B가 AppWorld 14.88%에서 49.40%로 오름(+34.5%p), BFCL V3도 29.13%에서 40.38%로 오름. Gemma4-E4B와 Qwen3-8B는 AppWorld에서 선생(50.00%)을 넘김. 작은 모델에 맞게 정제된 메모리가 원본 선생 능력보다 효율적일 수 있다는 뜻임.

4. 어블레이션의 교훈이 제일 값짐. Subtask 메모리 추가가 AppWorld에서 +25.0%p로 가장 큰 기여를 함. 구체적인 코드 예시가 있어야 4B가 실제로 행동을 바꿈. 자연어 설명만으론 부족함. 내가 소형 모델 에이전트에 가이드를 줄 때 추상 원칙을 늘어놓는 습관을 고쳐야겠다는 대목임.

5. 검색 수 k의 발견도 반 직관적이고 중요함. k=1이 최선이고 Subtask 메모리는 k가 커질수록 정확도가 떨어짐(49.40% → 33.34%). 작은 모델에게 추가 컨텍스트는 노이즈가 됨. 정밀한 주입 하나가 다수 주입보다 낫다는 것임. 내 프롬프트에서 "관련 있을 것 같은 예시 전부"를 붙이는 관행을 k=1 원칙으로 바꿨음.

6. 상호작용 효율도 전달됨. AMD를 쓰면 학생의 턴 수가 선생에 가까워짐. Qwen3-4B 기준 AppWorld에서 23.8턴 → 14.9턴(선생 10.1턴). 메모리가 "무엇을 할까"뿐 아니라 "얼마나 효율적으로 할까"까지 물려줌. 토큰 비용 관점에서도 이득이라는 계산이 나옴.

7. 내 워크플로우에 적용한 구조. 첫째, 강한 모델로 선생 궤적을 만들고 그걸 (a) 자연어 전략 노트, (b) 서브태스크별 코드 예시, (c) 에러 대응 규약 셋으로 분리 정리함. 둘째, 에러 시에만 Function 메모리를 반응형으로 끼워넣어 상시 컨텍스트를 늘리지 않음. 셋째, 예시는 항상 1개만, 가장 유사한 것만 골라 넣음.

8. 문제제기. 선생 궤적을 도메인별로 미리 뽑아둬야 해서 새로운 업무에는 준비 비용이 들음. 그리고 선생 메모리 품질이 상한선이라 선생이 실패하는 태스크는 커버가 안 됨. 벤치마크 3종 한정 검증이라 일반 문서 작업 등 다른 영역의 재현은 직접 해봐야 함.

9. 결론. 능력 차이는 메모리 계층으로 좁힐 수 있음. 전략은 자연어로, 실행은 코드로, 에러 교정은 반응형으로, 주입은 k=1로. 이 네 원칙이 파인튜닝 없이 4B를 선생급으로 올리는 조합임.
