MCP 기반 에이전트를 운영하면 짜증 나는 순간이 하나 있음. 모델이 "도구를 쓰겠다"고 결정한 뒤 샌드박스가 뜨길 기다리는 몇 초. 그동안 GPU는 놀고 있음. SpecBox는 이 콜드 스타트를 추측적 사전 할당으로 공략함. 토큰이 생성되는 도중에 다음 도구를 예측해서 샌드박스를 미리 켜두는 것. P99 지연 2.9배 단축, 상시 대기 방식 대비 메모리 45.9% 절감. 에이전트 인프라 실무자에게 바로 와닿는 결과임.

1. 문제 정의가 명확함. 에이전트 1스텝의 지연은 T_context + T_generation + T_env_prep + T_data_io + T_sandbox_exec으로 분해됨. LLM 추론 쪽은 계속 최적화돼 왔는데 환경 준비와 데이터 입출력은 여전히 순차 처리. AutoGen, LangGraph, AgentScope 모두 LLM이 도구 호출을 확정한 뒤에야 샌드박스를 준비하는 반응형 모델임. 32개 MCP 샌드박스의 콜드 스타트는 대부분 2~4초, 일부는 20초에 육박함. 모델이 빨라져도 이 병목은 그대로 남는다는 것.

![Figure 1: 순차 실행(vanilla)과 SpecBox의 사전 준비(overlapped) 실행 비교](/images/2026-08-03-specbox-speculative-sandbox-scheduling-llm-agent/fig-1-p1.png)

2. 관찰이 세 개임. 첫째, 단계 내에서도 미리 시작 가능함. 토큰을 스트리밍하는 도중 부분 토큰만으로 호출 도구를 짐작할 수 있음. 둘째, 단계 간에도 앞당길 수 있음. 에이전트 워크플로엔 시간적 국소성이 있어서 논문 검색 다음에 문서 읽기가 오고 분석 다음에 차트가 옴. 셋째, 중복 실행과 데이터 재전송이 많음. 같은 문서를 다시 조회하고 같은 분석을 반복함. 세 관찰이 각각 최적화 하나로 대응되는 깔끔한 구조임.

3. 첫 번째 메커니즘, 의도 인식 예열. 두 개의 비동기 라우터가 토큰 스트림을 감시함. 키워드 라우터는 도구 특화 키워드 2개 매치 시 후보로 선정. 마이크로초 단위지만 "read" 같은 범용 동사 때문에 위양성이 있음. 시맨틱 라우터는 TF-IDF 희소 검출으로 문맥과 도구 의도를 비교. 정확하지만 토큰이 누적돼야 해서 느림. 두 후보의 합집합, 즉 하나라도 히트하면 즉시 예열을 시작함. 합집합이 평균 대기 124ms에 콜드 스타트 5.0%를 기록한 반면 교집합은 콜드 스타트 0%지만 대기가 393ms로 3.16배 느렸음. "완벽한 예측보다 빠른 시작"이라는 트레이드오프 판단이 실무적임.

4. 두 번째, 확률적 프리페칭. 샌드박스 의존성 그래프 위에 1차 마르코프 모델을 구축함. 과거 트레이스에서 단계 간 전이 빈도를 세고 라플라스 평활화로 다음 샌드박스 출현 확률을 추정. 확률 0.6 이상이고 콜드 스타트 비용이 큰 후보만, 스텝당 예산 1개만 미리 켬. 단순한데 효과가 큼. 프리페칭을 켠 버전이 10턴 기준 평균 대기 97ms, 없는 버전은 583ms로 6배 차이. "현재 도구가 실행 중일 때 다음 도구 환경을 백그라운드로 준비한다"는 원칙 자체가 에이전트 파이프라인 어디에나 적용 가능함.

5. 세 번째, 재사용 인식 전송. 시맨틱 캐시는 도구가 같고 정규화된 호출의 의미 유사도 0.8 이상이면 이전 결과를 재사용함. 적중률 37.4%, 대기 2.91배 단축. 그리고 대역 외 전송은 JSON-RPC는 제어 신호만 남기고 큰 결과물은 공유 메모리로 전달함. 1GB 페이로드에서 JSON-RPC 1873ms, 대역 외 5.97ms. 313배 차이. MCP 도구와 호환성을 유지하면서 데이터 경로만 갈아끼우는 설계임. 에이전트에서 큰 파일을 도구 결과로 주고받는다면 전송 경로 점검이 최적화 1순위라는 뜻임.

6. 전체 성능. 200개 다중 턴 트레이스, 32개 MCP 서버, Qwen3.5-Max 환경에서 온디맨드 P99 257.2초 → SpecBox 88.7초. 상시 대기(Reserved)와 성능이 비슷한데 메모리는 49.4 vs 80.6GiB로 절반 가까이 아낌. CPU도 22~23% 덜 씀. "항상 켜두는 것과 비슷한 성능을 훨씬 적은 자원으로"라는 지점이 인프라 비용 관점에서 핵심임.

![Figure 9: 다중 턴 에이전트 세션에서의 누적 샌드박스 프로비저닝 지연 시간 분포](/images/2026-08-03-specbox-speculative-sandbox-scheduling-llm-agent/fig-9-p8.png)

7. 핵심 통찰은 "에이전트 루프의 병목은 LLM 추론이 아니라 환경 준비에 있다"는 것. 그리고 그 병목을 토큰 생성 시간 뒤에 숨길 수 있다는 것. CPU 파이프라인의 분기 예측을 샌드박스 스케줄링으로 옮긴 셈임. 내 이식 결론은 이렇게임. 첫째, 에이전트 지연을 디버깅할 때 모델 시간과 환경 준비 시간을 분리 측정할 것. 둘째, 도구 호출 로그를 모아 다음 도구 전이 확률을 계산해보고 상위 전이만 프리페치할 것. 셋째, 큰 페이로드는 채널을 분리할 것. 넷째, 반복 호출이 잦은 도구엔 의미 기반 캐시를 검토할 것. 한계는 있음. 1차 마르코프는 긴 호라이즌에서 정확도가 떨어지고, 공유 메모리는 같은 호스트로 제한되며, 부작용 있는 도구의 캐시 안전성은 추가 검증이 필요함. 그래도 원칙은 유효함. 기다리는 시간은 예측으로 지운다는 것.
