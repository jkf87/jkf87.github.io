LG CNS가 공개한 논문(arXiv 2609.05395)은 두 가지를 함께 제시함. 하나는 실제 한국 공공 API 위에서 돌아가는 다단계 tool-calling 벤치마크 KOPA-Bench(145과제)이고 다른 하나는 라이브 실행으로 검증된 의존성 그래프를 순회해 학습 데이터를 만드는 EDGE 프레임워크임. Qwen3.5-9B를 EDGE 데이터로 GRPO(같은 프롬프트에서 여러 응답을 뽑아 서로 비교해 업데이트하는 그룹 기반 RL 알고리즘) 파인튜닝하자 pass@1(한 번 시도로 과제를 성공할 확률)이 0.33에서 0.43으로 오르며 같은 계열 untuned 27B(0.4482)에 근접했음. 데이터를 잘 만드는 9B가 모델을 키우는 27B를 거의 따라잡은 셈임.

1. 배경부터. 데이터 주권 규제 때문에 공공기관은 오픈소스 모델을 온프레미스로 돌려야 함. 근데 기존 tool-calling 벤치마크는 에뮬레이트된 서비스나 LLM 사용자 시뮬레이터 기반이라 실제 API 응답의 지저분함을 담지 못함. 그래서 실공공 API 위의 벤치마크가 필요했던 것임.

2. KOPA-Bench 설계 조건. 교통/금융/교육/법/정치/행정 6개 도메인 커버리지, 체인형 다단계 추론이 가능한 API 상호연결성, KOGL 라이선스 허용으로 플랫폼 10개를 골랐음. 규모는 과제 145개, 도구 2,318개, 과제당 평균 5회 tool-call(최대 14회), 병렬 실행 포함 과제 59%임. 공식 문서를 파싱해 MCP(AI 에이전트가 외부 도구에 표준 방식으로 접속하게 하는 연결 규약) 서버로 구현해서 인증·세션·재시도 로직을 서버가 흡수하게 했음.

3. 한국 공공 API 특유의 함정이 과제에 그대로 들어 있음. "2021년 제주 중학교 특수교육 학생 수"를 물으려면 먼저 get_education_api_key()로 API 키를 발급받은 뒤 그 키를 다음 호출에 넘겨야 함. 키를 건너뛰면 Invalid API-key 에러가 돌아옴. 법령 코드, 기관 코드 같은 코드-룩업을 먼저 해야 하는 과제가 많다는 것도 특징임. 실무 데이터의 난이도가 여기서 나옴.

![트라젝토리 비교](/images/2026-09-07-edge-kopa-bench-korean-public-api/fig1-trajectory-comparison.png)

4. 평가 설계가 잘 돼 있음. RESPONSE, ENVIRONMENT, ACTION 세 축으로 나눔. ACTION 하나로 평가하면 정답 액션을 포함했는데 시스템 상태가 틀어지는 경우와 우회 경로로 정답 상태에 도달하는 경우가 섞여서 구분이 안 됨. 결과와 과정을 나눠 측정한 것임.

5. 과제 검증도 이중임. 저자 아닌 전문가 감사에서 7개 과제(4.8%) 오류를 잡았고, 골든 트라젝토리 실행 결과를 Claude Sonnet 4.6에 줘서 타깃 답변과 비교하는 실행 검증에서 첫 시도 80% 통과, 전 과제 통과까지 수정을 반복했음. 벤치마크 만드는 절차의 정직함이 벤치마킹할 만함.

6. EDGE의 핵심은 Phase A임. 도구 간 의존성 그래프를 만들 때 어떤 도구의 출력이 다른 도구의 입력으로 흘러갈 수 있는지 후보 엣지를 세우고 실제 라이브 API를 호출해보고 성공한 엣지만 남김. 문서상 가능해 보이는데 실제로는 실패하는 연결은 그래프에서 잘려나감.

![EDGE 개요](/images/2026-09-07-edge-kopa-bench-korean-public-api/fig2-edge-overview.png)

7. Phase B는 이 검증된 그래프 위에서 트라젝토리를 조립함. 각 분기점을 응답 카디널리티(일대일/일대다)로 타입을 붙이고 그래프를 순회하면서 한국어 질의와 정답을 생성함. 이렇게 1,781개 학습 데이터를 만듦. 핵심 통찰은 프루닝이 문서 말고 실행 결과에 지배된다는 것. 신뢰할 수 없는 엣지가 잘릴수록 실행 성공률이 올라감.

![프루닝과 실행 성공률](/images/2026-09-07-edge-kopa-bench-korean-public-api/fig7-pruning-execution.png)

8. 결과. Qwen3.5-9B base 0.3275 → EDGE+GRPO 0.4310(+10pp). pass@4는 0.5517로 untuned 27B의 0.5655와 사실상 동급임. 4B도 0.18→0.31로 올랐음. 개선이 in-distribution에만 국한되지 않아서 영어 범용 벤치마크 BFCL(도구 호출 정확도를 평가하는 대표 벤치마크)에서도 4B +4.04pp, 9B +5.87pp 올랐음.

9. 내 해석. 이 논문의 진짜 자산은 벤치마크보다 데이터 합성 파이프라인 쪽임. "실제로 호출해보고 성공한 엣지만 남긴다"는 규칙은 도구 생태계에 상관없이 적용할 수 있는 일반 레시피임. 사내 내부 API, MCP 서버 묶음에도 그대로 옮길 수 있음.

10. 실무 채점. 첫째, 도구 의존성 그래프를 문서 기준 말고 실행 성공 여부로 구축할 것. 둘째, tool-call 평가를 ACTION/RESPONSE/ENVIRONMENT로 분리해 볼 것. 셋째, 도구 문서를 파싱해 MCP로 래핑하는 작업을 자동화하면 도구 인벤토리 구축 비용이 크게 내려감. 2,318개 도구 래핑이 수작업이었다는 점이 그 기회를 보여줌.

11. 그리고 작은 모델 + 좋은 데이터 전략의 실증임. 온프레미스 제약이 있는 조건이라면 모델을 키우는 대신 데이터 합성 품질로 격차를 메우는 루트가 실제로 통한다는 숫자임.

12. 한계. 같은 계열 모델 내 비교라는 조건이 붙고, 공공 API 도메인 특수성이 있음. 그래도 EDGE 방법 자체는 범용이라는 게 BFCL 개선으로 확인됐음.
