이 논문의 핵심 주장은 명확함. LLM 기반 루트 코즈 분석(RCA, 장애가 발생한 근본 원인을 데이터로 역추적하는 작업)의 성능 격차는 에이전트 바깥의 하네스 레이어에서 발생한다는 것. CUHK와 ByteDance의 OpsHarness는 Claude Code나 Codex 같은 범용 에이전트를 그대로 재사용하면서 바깥에 자가진화하는 하네스를 얹었음. 4개 백본 평균 top-1 정확도 59.0%, 맨살 범용 에이전트 대비 +63.4%, 전용 RCA 에이전트 대비 4.02배임.

1. 출발점이 흥미로움. OpenRCA와 RCAEval(둘 다 장애 주입 시나리오로 근본 원인을 맞히는지 채점하는 RCA 벤치마크)에서 GPT-5.5, Claude Sonnet 4.6, GLM-5.2, DeepSeek-V4 네 모델로 비교했더니 RCA 전용 에이전트(RCA-Agent 17.9%, mABC 5.6%)보다 그냥 Codex/Claude Code 범용 에이전트(36.1%)가 전 백본에서 앞섰음. GPT-5.5 기준 bare Codex가 OpenRCA 질의의 45%를 맞히고 RCA-Agent는 32%에 그침. 전용 설계가 이미 범용을 못 따라잡은 상태였던 것임.

2. 근데 범용 에이전트도 51.2%가 최대라 프로덕션 요구엔 못 미침. 저자들의 분석은 실패 원인이 추론 능력 부족이 아니라 시스템 특화 진단 지식 부족이라는 것. 새로 합류한 유능한 엔지니어가 팀의 노이즈 프로필을 모르는 상황과 같음. 실제 실패 사례로 절대값이 크게 튀는 노이즈 카운터를 원인으로 오판하고 baseline이 0 근처라 상대적으로 작은 컨테이너 CPU 포화를 놓친 케이스가 나왔음.

![핵심 메시지](/images/2026-08-28-opsharness-self-evolving-rca-harness/fig-1-p1.png)

3. 구조는 데이터 플레인과 컨트롤 플레인으로 나뉨. 데이터 플레인은 계층화된 운영 지식 저장소(K0 시스템 프로필, K1 텔레메트리 스키마, K2/K3 진단 지식)와 아이디어카드 형태의 도구 라이브러리임. 컨트롤 플레인은 4개 워크플로임.

4. 네 워크플로의 역할 분담이 깔끔함. setup은 시스템 텔레메트리를 샘플링해 스키마를 추론하고 초기 하네스를 작성함. diagnose는 지식과 도구로 Top-N 원인 리스트를 반환함. evolve는 진단 트랙토리에서 성공/실패 패턴을 원자적 제안으로 증류함. verify는 듀얼 게이트 샌드박스 검증을 통과할 때만 승격함.

![전체 설계](/images/2026-08-28-opsharness-self-evolving-rca-harness/fig-3-p5.png)

5. 검증이 이 논문의 묘미임. inner 게이트에서 진화된 하네스가 제안이 나온 원본 케이스에서 정확도 하락이 없어야 하고(ΔA ≥ 0), 비용 증가가 max(0.05·C, 1) 토큰 이내여야 하고, 정확도든 비용이든 하나는 엄격히 개선돼야 함. outer 게이트에서는 별도 보류 배치에서도 회귀가 없어야 통과함. 이 듀얼 게이트가 과적합과 회귀를 막는 장치임.

![자기진화 루프](/images/2026-08-28-opsharness-self-evolving-rca-harness/fig-4-p7.png)

6. Ablation이 게이트의 가치를 증명함. 12개 연속 진화 윈도우에서 게이트가 있으면 정확도가 지속 상승하는데 no-verify 변형은 초반 상승 후 하락함. 검증 없이 진화만 켜면 오히려 나빠진다는 것. "쓸수록 좋아진다"는 경험은 게이트 없이는 과적합으로 되돌아온다는 교훈임.

![12 윈도우 변화](/images/2026-08-28-opsharness-self-evolving-rca-harness/fig-5-p9.png)

7. 산업 배포 결과도 강력함. Company A 변경 이상 데이터셋에서 6개 설정 전부 Direct 대비 개선돼서 평균 0.74 vs 0.24 A@1(첫 번째로 제시한 원인이 정답인 비율)임. 오픈소스 스택(OpenCode + GLM-5.2)에서도 0.73으로 유지됨. 특정 상용 모델 의존이 아니라는 것임.

![산업 결과](/images/2026-08-28-opsharness-self-evolving-rca-harness/fig-8-p10.png)

8. 비용 구조가 실무적으로 결정적임. 케이스당 약 106k 토큰, 325초로 Direct(112k, 317s), ICL(106k, 308s)과 동급임. 전용 에이전트들은 토큰 1.7~2.7배, 시간 2.3~3.5배를 씀. 하네스 전체 온디스크 크기는 약 228KB(도구 106KB, 스킬 95KB, 진화 지식 27KB)임.

9. 실무 채점. 도메인 에이전트를 새로 만들 계획이라면 범용 에이전트 + 외부 하네스 조합을 먼저 베이스라인으로 잡는 게 순서임. 논문 데이터상 전용 에이전트가 이 베이스라인을 이기기 어려움. 그리고 진단 트랙토리에서 자동 증류되는 경험 자산은 듀얼 게이트가 없으면 무의미함.

10. 특히 graceful degradation도 확인할 만함. 시스템이 바뀌어도 콜드스타트(41.4%)가 Direct(36.1%)보다 높음. 진화된 지식이 시스템 변화에 오히려 발목을 잡지 않는다는 것. 지식 노후화 리스크가 실무 채택의 최대 걸림돌인데 그 지점을 데이터로 보여준 것임.

11. 베낄 것 두 개. 첫째, 계층화된 지식 저장소 구조(K0~K3). 시스템 프로필, 텔레메트리 스키마, 진단 지식을 분리해두면 시스템 변경 시 교체 범위가 최소화됨. 둘째, inner/outer 듀얼 게이트. 자동 개선 루프에 원본 케이스 회귀 검사와 보류 배치 검사를 둘 다 두는 원칙임.

12. 한계. RCA라는 검증기가 명확한 도메인의 결과라서 정성 판단이 섞인 운영 업무로의 확장은 별도 검증이 필요함. 그리고 setup/evolution/verification의 초기 비용(각 0.82M, 0.75M, 1.55M 토큰)이 있어서 케이스 수가 적은 시스템에선 상각이 어려움.

13. 그래도 결론은 남음. 에이전트 능력의 병목은 모델이 아니라 도메인 지식의 주입과 검증 구조였다는 것. 그리고 그 지식은 사람이 손으로 쓰는 문서가 아니라 진단 트랙토리에서 자동 증류되는 게 저렴하고 안전하다는 것임.
