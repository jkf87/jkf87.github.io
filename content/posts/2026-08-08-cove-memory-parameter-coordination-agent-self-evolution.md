에이전트가 배포 후 경험을 축적할 때 저장 위치가 문제임. 외부 메모리에 넣을지 모델 가중치에 박을지. COVE는 이 판단을 자동으로 하는 라우터와 스케줄러를 제안함. 하네스 진화와 파라미터 진화를 하나로 조율하는 프레임워크임.

1. 배경. 에이전트는 API 변경, 새 라이브러리, 바뀐 사용자 요구에 계속 직면함. 기존 자가진화는 둘로 나뉘었음. 하네스 기반은 피드백을 외부 메모리나 스킬로 저장함. 빠르지만 모델 역량이 부족하면 쓸모없는 경험이 쌓임. 파라미터 기반은 경험을 가중치에 내재화함. 깊지만 비싸고 표면 형식이 바뀌면 부서짐.

2. 왜 둘 중 하나만으론 안 되는지 증거가 명확함. Lean 정리 증명(MiniF2F, 수학 문제를 Lean이라는 형식 증명 언어로 증명하는 벤치마크)에서 하네스 메모리를 늘려도 성공률이 거의 안 변함. 에피소드 50→250, 검색 메모리 2→8개를 늘려도 컴파일 에러가 안 줄어듦. 메모리가 힌트를 줘도 모델이 실행할 역량이 없는 것임.

3. 반대 방향 실패도 있음. WikiTableQuestions(위키피디아 표를 보고 질문에 답하는 벤치마크)에서 파라미터 학습 후 API 이름을 바꾸면 성공률이 40.5%→16.5%로 추락하고 API 정답률도 96.5%→54.0%로 내려감. 표면 지식을 가중치에 박아넣었기 때문임. API 이름 같은 건 가중치가 아니라 메모리에 있어야 한다는 뜻임.

![하네스 진화의 한계](/images/2026-08-08-cove-memory-parameter-coordination-agent-self-evolution/fig-2-p3.png)

4. COVE의 첫 메커니즘은 Task-aware Router임. 피드백을 읽고 어느 채널로 보낼지 정함. 실패 원인이 추론 역량 부족이면 파라미터 채널, 표면 지식 부족이면 하네스 채널임. MATH는 이미 추론 능력이 충분해 대부분 하네스로 가고 TableQA는 반복 패턴이 많아 파라미터 비중이 높아짐.

5. 두 번째는 Stage-aware Scheduler임. 하네스 탐색이 plateau에 도달하면 파라미터 학습을 트리거함. 항상 파라미터 학습을 켜는 것보다 plateau에서만 켜는 게 더 높은 성공률을 냄. "메모리로 안 늘면 그때 가중치"라는 순서가 효율의 핵심임.

![plateau 트리거](/images/2026-08-08-cove-memory-parameter-coordination-agent-self-evolution/fig-4-p3.png)

6. 세 번째는 KnowledgePO임. 지식을 세 등급으로 분류함. 휘발성(API 이름, 스키마)은 메모리에만 저장하고 파라미터 학습 시 anti-recitation 페널티로 내재화를 차단함. 안정성(알고리즘 패턴, 도메인 추론)은 파라미터로 내재화함. 전략성(디버깅 계획)은 메모리로 유지하다 반복 증거가 쌓이면 내재화함.

7. 결과. 하이브리드 지표에서 COVE 24.1로 Parametric-only 21.3, Harness-only 20.8을 앞섬. MATH 91.7, Lean4 7.0, HotpotQA(여러 위키피디아 문서를 건너 찾아야 답이 나오는 멀티홉 질의응답 벤치마크) 69.6임. 파라미터 단독 대비 학습 토큰을 86% 줄이면서 전반적으로 나음.

![메인 결과](/images/2026-08-08-cove-memory-parameter-coordination-agent-self-evolution/table-2-p7.png)

8. 라우터 ablation이 효율의 핵심을 보여줌. COVE는 Always-Both 대비 토큰의 16%만 쓰면서 65.0 vs 69.0의 성능을 냄. 효율(성능/토큰)은 28.83 vs 4.89임. 아무거나 다 학습시키는 것보다 고르는 게 압도적으로 싸다는 것임.

9. Anti-recitation 효과도 검증됨. API 이름을 바꿔서 테스트하면 일반 fine-tuning은 성공률이 급락하고 API 오류가 주요 실패 모드가 됨. 근데 anti-recitation 모델은 안정적으로 현재 프롬프트의 API를 따라감. 가중치에 표면 형식을 못 박게 막는 것의 가치가 실험으로 증명된 것임.

![두 진화 경로](/images/2026-08-08-cove-memory-parameter-coordination-agent-self-evolution/fig-1-p2.png)

10. 실무 채점. 우리 자동화 에이전트의 개선 루프에 바로 묻는 질문임. 첫째, 모든 교훈을 프롬프트나 메모리에만 쌓고 있진 않은가. 역량 문제는 메모리로 안 풀림. 둘째, 반복 패턴은 파인튜닝 자산으로 분류하고 표면 지식은 메모리로 분류할 것. 셋째, 파라미터 학습은 메모리 개선이 정체됐을 때만 트리거하는 게 비용상 이득임.

11. 특히 휘발성 지식의 anti-recitation 원칙이 중요함. API 이름이나 스키마 같은 건 바뀔 때마다 가중치를 다시 학습해야 하는 부채가 됨. 이건 메모리로 두고 프롬프트에서 주는 게 정답이라는 걸 수치로 보여준 케이스임.

12. 한계. 베이스가 Qwen3-8B로만 실험돼서 더 큰 모델에서 라우팅 일관성 확인이 필요함. 5개 태스크 평가라 웹·터미널·코딩 에이전트 같은 다양한 환경 검증이 부족함. 두 채널 사이 지식 이전의 완전한 통제도 여전히 어려움.

13. 그래도 프레임워크는 남음. 경험 저장은 단일 채널이 아니라 지식 성격에 따른 라우팅 문제라는 것. 휘발성/안정성/전략성의 3분류는 자체 에이전트 개선 파이프라인 설계의 체크리스트로 바로 쓸 수 있음.
