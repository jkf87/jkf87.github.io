프롬프트 최적화, 프로그램 진화, ML 워크플로 최적화는 지금까지 LLM을 변이 연산자로 쓰고 외부 알고리즘(진화 연산, 밴딧, MCTS(몬테카를로 트리 탐색, 가능한 선택지를 트리로 펼치고 시뮬레이션으로 유망한 가지를 골라 파고드는 알고리즘))이 검색 정책을 맡는 분업 구조였음. ReASearch는 이 분업을 없애고 단일 에이전트 루프가 검색 정책 전체를 수행하게 만듦. 14개 태스크에서 도메인 특화 시스템과 동등 이상이었고 Circle Packing에선 인간 최고 기록도 넘었음.

1. 문제 정의는 이렇음. 태스크 인스턴스와 아티팩트 z(프롬프트, 프로그램, 학습 설정)가 주어졌을 때 출력의 기대 보상을 최대화하는 z*를 찾는 것. 기존엔 LLM이 후보를 제안하고 외부 알고리즘이 무엇을 시도할지 결정했음. ReASearch는 그 결정 권한을 에이전트에게 통째로 넘김.

![기존 방법과의 비교](/images/2026-08-11-reasearch-optimizer-is-the-agent/fig-1-p2.png)

2. 아키텍처는 화려하지 않음. 파일 I/O, Python/Bash 실행, 컨텍스트 압축, 지속적 메모리(lessons.md)를 갖춘 코드 에이전트임. 태스크별로 도구 세트와 시스템 프롬프트만 바꿔서 세 영역에 같은 루프를 적용함. 평가 도구, 수정 도구, 분석용 python_exec, 메모리의 네 범주가 도구 설계의 전부임.

3. 핵심 도구는 python_exec임. 에이전트를 텍스트 추론기에서 계산적 추론기로 바꾸는 지점임. 평가 로그 파싱, 실패 패턴 분류, 통계 계산, 검증 전 가설 테스트가 가능해짐. 이거 하나로 외부 분석 코드가 필요 없어짐.

![아키텍처 비교](/images/2026-08-11-reasearch-optimizer-is-the-agent/fig-2-p3.png)

4. 컨텍스트 관리도 단순함. 90,000 토큰 임계치를 넘으면 compact()가 전체 기록을 요약하는데 lessons.md 내용은 보존함. 압축 후에도 핵심 교훈이 남는 구조임.

5. 제일 베낄 만한 설계는 시스템 프롬프트 재주입임. 매 턴 현재 최고 점수, 최근 20개 실험 결과, 정체 경고를 시스템 프롬프트에 다시 넣음. 상태를 에이전트가 "볼 수 있게" 두는 것과 "반드시 보게" 만드는 것의 차이라는 게 저자들의 설명임.

6. 관찰된 검색 행동이 이 논문의 뼈대임. 하드코딩 없이 다섯 패턴이 자연 출현했음. 첫째, 태스크 구조화. HotpotQA(여러 문서를 묶어야 답할 수 있는 다단계 질의응답 벤치마크)에서 baseline 실패 126건을 python_exec로 범주화해서(verbosity 57, wrong-reasoning 68, 오염 8) 수정 방향을 정함.

7. 둘째, 사전 검증. 비싼 검증 세트 평가 전에 트레이닝 배치에서 개선 신뢰성을 먼저 확인함. 셋째, 자발적 백트래킹. Candidate #4가 #3보다 3점 낮으면 원인 분석 후 #3으로 회귀해서 단일 문장 추가로 최고점을 냄.

8. 넷째, 오버피팅 탐지. AIME(수학 경시 대회 문제로 구성된 벤치마크)에서 트레이닝 정확도 상승(60%→66.7%)이 검증 하락으로 이어지자 "도메인 특화 추가는 검증을 해친다"고 lessons.md에 기록하고 방향을 전환함. 다섯째, 전략적 최종 선택. 검증 최고점 후보 대신 전체 이력 기반 합성 프롬프트를 제출해서 테스트 52.0%로 검증 최고점 49.3%를 넘김.

![궤적 예시](/images/2026-08-11-reasearch-optimizer-is-the-agent/fig-3-p4.png)

9. 결과 숫자. 프롬프트 최적화에서 HotpotQA 44.6%→66.0%, GSM8K(초등 수준 수학 문제 벤치마크) 84.7%→88.4%, Terminal-Bench 2.0 58.5%→63.6%. 프로그램 진화에선 Circle Packing(주어진 공간에 원을 겹치지 않게 최대한 채우는 조합 문제)의 n=23-32 일부 인스턴스에서 인간 최고 기록 초과. ML 워크플로에선 NanoGPT(소형 GPT 학습용 오픈소스 스크립트) 최적화로 0.969 bpb(bits per byte, 다음 글자를 예측하는 데 드는 정보량, 낮을수록 좋음)로 AutoResearch를 앞섬.

![프로그램 진화 결과](/images/2026-08-11-reasearch-optimizer-is-the-agent/table-2-p7.png)

10. Claude Code와의 비교가 설득력 있음. 동일 지시문, 동일 모델(Claude Sonnet 4.6), 동일 예산에서 ReASearch가 이겼는데 원인은 매 터 상태 재주입임. Claude Code는 시스템 프롬프트가 세션 시작 시 고정이고 실험 이력을 에이전트가 자발적으로 조회해야 하고 정체 대응도 에이전트가 알아서 해야 함. 상태 노출을 구조화하는 것만으로 같은 모델의 성적이 달라진다는 것임.

![도구 호출 통계](/images/2026-08-11-reasearch-optimizer-is-the-agent/fig-5-p6.png)

11. Ablation도 실무 감각에 맞음. lessons.md 제거는 프롬프트 최적화에서, python_exec 제거는 프로그램 진화에서 더 큰 타격을 줌. 두 컴포넌트가 서로 다른 검색 측면을 지원한다는 뜻임. 도메인에 따라 메모리와 실행 환경 중 뭘 먼저 단단히 할지 정하는 기준이 됨.

12. 오픈소스 백본(GLM-5, Kimi-2.5)에서도 작동함. AIME/HotpotQA에선 Claude에 근접하고 Terminal-Bench 2.0에선 baseline 대비 유의미한 개선임. 특정 상용 모델 전용 트릭이 아니라는 것임.

13. 실무 채점. 우리가 프롬프트나 설정을 자동 튜닝하는 루프를 돌린다면 세 가지를 베낄 것임. 첫째, 매 터 최고 점수와 최근 결과와 정체 경고를 상태로 재주입할 것. 둘째, python 실행 도구를 붙여서 로그 분석을 계산으로 하게 할 것. 셋째, 교훈 파일을 압축에서 보존할 것. 이 세 개가 하네스 차원의 개선이라 모델 교체에도 살아남음.

14. 그리고 큰 그림의 교훈. 후보 선택, 예산 배분, 백트래킹, 탐색-활용 트레이드오프 같은 검색 정책의 핵심이 외부 알고리즘 없이 에이전트 추론에서 자연 출현한다는 것임. 최적화 인프라를 따로 짜는 대신 에이전트 루프를 잘 설계하는 쪽이 적용 범위가 넓다는 시사임.
