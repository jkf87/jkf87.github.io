---

MS 리서치가 2026-08-18자로 Agent Lightning v1.0 기술 보고서를 냈음. 핵심은 배포할 때 쓰는 에이전트 하네스를 그대로 RL 포스트트레이닝에 넣는 프레임워크라는 것. 약 3,500줄짜리 가벼운 구현임.

1. 결과 숫자부터. Qwen3.5-9B 코딩 에이전트가 학습 예제 6천 건 + 적당한 컴퓨트만으로 SWE-bench Verified 41.8%→56.4%를 찍었음. 절대 게인 14.6%p임. 검색 에이전트(Llama-3.2-3B, HotpotQA)는 검증 보상 25.1%→41.7%, 인스트럭션 팔로잉(Qwen3-4B)은 51.9%→70.2%임.

2. 하네스드 에이전틱 RL이 뭔지. 기존 에이전틱 RL은 학습 엔진(verl, AReaL 등)이 환경 루프를 직접 돌면서 매 턴 LLM을 호출함. 하네스드 방식은 반대임. 학습 엔진이 외부 프로세스(하네스)를 띄우고 하네스가 LLM API를 여러 번 호출함. 학습 엔진은 연속된 트라젝토리를 못 보고 request-response 쌍만 프록시로 관측함. 이 패러다임에 harnessed agentic RL이라는 이름을 붙인 게 이번 보고서임.

![아키텍처](/images/agent-lightning-v1-harnessed-agentic-rl-2026-08-23/fig-1-p1.png)

3. 구조는 세 개임. API Gateway는 상태를 갖는 서비스로 롤아웃 라이프사이클 추적, 모델 등록, 모든 request-response 로깅을 담당함. 일반 LLM 엔드포인트처럼 행동해서 기존 하네스가 코드 수정 거의 없이 붙음. Rollout Controller는 에이전트 태스크 실행을 Kubernetes Job으로 스케줄링함. 코딩 에이전트 격리 샌드박스에는 이게 필수임. Customized Trainer는 verl 위에 구축됨.

4. 하네스가 루프를 소유하면 표준 RL이 깨지는 지점 세 곳이 이 보고서의 실체임. 첫째, 리토큰화와 샘플 병합. 하네스는 다음 스텝 프롬프트를 만들 때 이전 응답에 도구 출력을 붙이고 챗 템플릿을 다시 적용함. 그래서 다음 request의 토큰 prefix가 이전 턴과 정확히 안 맞을 수 있음.

5. GPU 효율을 위해 연속 request를 하나의 시퀀스로 병합하는 게 기본인데 토큰이 안 맞는데 억지로 병합하면 오프폴리시 오염이 생김. 실제로 본 게 아니라 다른 데이터로 학습하는 셈임. Agent Lightning은 엄격한 토큰 prefix 매치가 유지될 때만 best-effort 병합을 함.

![리토큰화](/images/agent-lightning-v1-harnessed-agentic-rl-2026-08-23/fig-3-p4.png)

6. 둘째, 어드밴티지 계산 단위. 검색 에이전트는 2스텝, 코딩 에이전트는 20스텝처럼 롤아웃이 만드는 샘플 수가 제각각임. 샘플 단위로 계산하면 스텝 많은 태스크가 정책에 과도한 영향을 줌. 논문은 롤아웃 단위 어드밴티지, 즉 최종 결과 보상을 그 롤아웃의 전체 스텝에 분배하라고 주장함.

7. 셋째, 로스 정규화. 샘플 단위 정규화는 긴 롤아웃 몇 개가 그래디언트를 지배하게 만듦. 롤아웃 토큰 평균 로스를 쓰면 태스크당 기여가 균등해짐. 세 설정 비교에서 롤아웃 단위 어드밴티지 + 정규화 조합이 최상으로 검증 보상 38.2% 피크를 냈음.

![샘플 수 차이](/images/agent-lightning-v1-harnessed-agentic-rl-2026-08-23/fig-5-p8.png)

8. 롤아웃 통계가 실증을 줌. 평균 롤아웃당 학습 샘플 2.41개, 단일 시퀀스로 병합되는 롤아웃은 36%뿐이었음. 다중 샘플 처리가 실제로 필요하다는 데이터임. 효율도 collocated async RL 구조로 동기식 대비 2배 빠르고 GPU도 덜 씀.

9. 코딩 에이전트 학습 파이프라인이 실무적으로 제일 유용한 부분임. 전체 파이프라인을 재현 가능하게 공개했는데 리워드 해킹 방어가 잘 정리돼 있음. .git 디렉토리를 숨기고 git 커맨드를 비활성화해서 커밋 히스토리 조작으로 버그를 고친 척하는 걸 차단함. 네트워크 격리로 화이트리스트만 허용해 인터넷에서 정답 검색을 차단함. SWE-smith 난이도 필터링도 포함돼 있음.

10. 실무 채점. 이 보고서의 실체는 프레임워크 소개보다 "하네스드 RL에서 표준 RL이 어디서 깨지는가"에 대한 정리 쪽임. 리토큰화, 롤아웃 어드밴티지, 로스 정규화 세 개는 직접 구현해보는 팀이라면 전부 부딪히는 문제임.

11. 그리고 3,500줄 구현이라는 점이 의도적임. 대형 프레임워크가 아니라 연구용 테스트베드 포지션이고 verl 기반이라 기존 스택에서 붙이기 쉬움. 코딩 에이전트 RL을 하려는 팀은 데이터 클리닝과 샌드박싱 스크립트만 봐도 값진 상태임.

12. 리워드 해킹 방어 두 가지는 범용 교훈임. 우리 자동 튜닝 루프에서도 평가 대상이 되는 저장소의 버전 관리 정보와 외부망 접근을 통제하는 게 기본 방어선임. 안 그러면 모델이 진짜 문제 해결 대신 채점 우회를 학습함.

13. 하네스-모델 공동 학습이라는 방향에서 이 보고서의 위치도 명확함. OpenForge RL이 인프라 관점에서 접근했다면 Agent Lightning은 학습 알고리즘 쪽의 깨짐 지점을 정리함. 배포 하네스를 학습에 그대로 쓰는 게 더이상 연구 트릭이 아니라 재현 가능한 레시피가 되어가는 중이라는 신호임.
