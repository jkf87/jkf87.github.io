에이전트 강화학습은 각 작업을 독립 에피소드로 취급해서 경험이 사라짐. 비슷한 작업에 공통 해결 패턴이 있는데도 무시됨. SkillRise가 "작업을 풀면서 동시에 다음 작업에 쓸 스킬을 정리하는 단일 정책"을 제안했음. 원문은 [arXiv:2607.26784](https://arxiv.org/abs/2607.26784).

1. 기존 접근의 문제. LaMer는 같은 인스턴스를 반복하며 reflection을 개선하지만 스킬이 인스턴스 특화에 머물러 전이가 안 됨. RetroAgent·SkillRL은 추출-저장-검색-실행 파이프라인을 거치는데 어느 단계에서 실패했는지 귀인이 어렵고, 외부 티처(Gemini-2.5-Pro)에 의존하며 런타임이 4-6배임.

2. SkillRise의 설계는 세 조각임. 첫째, 관련 작업을 하나의 시퀀스로 묶음(예: 청바지 검색 2속성 → 3속성 → 4속성). 둘째, 단일 정책이 task solving(현재 작업 해결)과 skill curation(궤적으로 스킬 문서 개정)을 번갈아 수행. 개정된 스킬 문서만 다음 작업으로 넘어가고 이전 궤적은 안 넘어감. 스킬 문서가 작업 간 유일한 정보 채널임.

3. 셋째가 핵심 통찰인 분리 크레딧 할당임. Task solving은 현재 작업 보상으로, skill curation은 후속 작업 보상의 할인합(γ=0.6)으로 평가함. 그룹 내 비교도 같은 역할·같은 위치끼리만 해서 "푸는 능력"과 "정리하는 능력"이 서로의 베이스라인을 오염시키지 않게 함. 스킬 정리의 성패를 "다음 작업이 잘 풀리는가"로 측정하는 게 자연스러운 검증이라는 점이 내 방식과 같아서 공감이 갔음.

4. 결과. Qwen3-4B 백본으로 ALFWorld 85.9%, WebShop 84.4%, ScienceWorld 54.6%로 전 벤치마크 최고임. 최강 베이스라인 GiGPO 대비 ScienceWorld +8.5pp가 제일 큰데, 과학 주제가 가장 다양해서 크로스태스크 전이 효과가 크게 나온 것임.

5. 제일 흥미로운 발견은 테스트 타임 크로스태스크 스케일링임. 훈련은 K=3 시퀀스로 했는데 테스트에서 시퀀스를 늘리면 성능이 계속 오름. 에이전트가 특정 스킬을 암기한 게 아니라 "스킬을 정리하는 방법" 자체를 배웠다는 증거임. 같은 작업 반복형 베이스라인은 이런 경향이 전혀 없음.

6. 효율도 좋음. RetroAgent와 동등한 성공률을 런타임 1/6으로 냄. SkillRL보다 12.5pp 높으면서 4.3배 빠름. 외부 티처도 메모리 모듈도 검색 컴포넌트도 필요 없음. 파이프라인 분리가 오류 합성과 귀인 난해함을 만든다는 걸 역으로 보여주는 셈임.

7. 스킬 문서가 실제로 뭘 담는지가 실무 포인트임. "첫 객체를 찾으면 즉시 집지 말고 두 번째 위치를 먼저 확인하라" 같은 절차적 지식, "냉장고 객체를 countertop부터 확인해야 할 때가 있다" 같은 실패 모드, "탐색 순서는 지시문 전치사구 순서를 따르라" 같은 일반화 전략임. 인스턴스 메모가 아니라 이전 가능한 절차 지식으로 정제되는 게 관건임.

8. 내 자동화에 적용한 것. 작업 종료 후 궤적을 그대로 다음 컨텍스트에 넣는 대신, "다음 비슷한 작업에 도움될 교훈만 3-5줄로 정리"하는 큐레이션 스텝을 루프에 박아넣음. 그리고 스킬 문서는 후속 작업 성공률로 평가해서 실패한 문서는 자동 폐기함. γ가 0.3-0.7에서 결과가 1pp 이내로 강건했다는 것도 미세조정 안 해도 된다는 실무적 편의임.

9. 문제제기. 시퀀스 구성에 환경이 주는 작업 패밀리 메타데이터가 필요해서 오픈 환경에서 관련 작업을 자동 발견하는 건 미해결임. 검증이 4B 모델·텍스트 환경 한정이라 멀티모달·대규모에서는 미확인임. 그래도 "정책이 직접 스킬을 편집하라"는 설계 원칙은 모델 크기와 무관하게 유효해 보임.

10. 결론. 스킬 학습은 파이프라인이 아니라 정책의 일부여야 하고, 테스트 타임 스케일링이 스킬 품질의 리트머스임. 코드는 [github.com/Within-yao/SkillRise](https://github.com/Within-yao/SkillRise)에 공개돼 있음.
