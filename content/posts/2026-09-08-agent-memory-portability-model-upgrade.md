업그레이드 배포 다음 날 에이전트가 지난 몇 달 쌓은 기억을 잊기 시작하는 상상. 저장소 파일은 한 글자도 안 바뀌었고 바뀐 건 읽는 모델 하나뿐임. [arXiv 2609.05339](https://arxiv.org/abs/2609.05339)는 이 지점을 4가지 메모리 포맷으로 측정함. 포맷 선택이 곧 업그레이드 내성이라는 결론이라 정리함.

1. 실험 설계가 분리가 깔끔함. writer가 히스토리를 메모리로 저장하고 reader가 그 저장소로 질문에 답함. 업그레이드 후에는 A가 쓴 저장소를 B가 읽게 하고 B가 자기 저장소를 읽을 때와 비교 — 이동 손실만 분리됨. 답 코드를 무작위화해서 사전학습 암기 차단, 4개 본실험을 Git 태그로 선등록한 절차적 신뢰성도 갖춤.

2. 결과가 포맷별로 완전히 갈림. 원본 히스토리 전체(LC-RAW)와 청크+벡터(RAG, 문서를 잘라 임베딩으로 색인해 두고 유사한 것을 가져오는 검색 증강 구조)는 모델 교체 후 ±0.1pp로 작성자 영향 없음. 고정 스키마 지식그래프(KG-fixed, 엔티티와 관계를 정해진 형식의 그래프로 저장하는 구조)는 +0.0004±0.0020로 사실상 완벽. 근데 모델이 요약한 노트(NOTES)는 -13.3pp에서 +9.9pp까지 출렁임.

3. NOTES의 함정은 평균에 있음. Llama 노트를 Qwen이 읽으면 -13.3pp, Qwen 노트를 Llama가 읽으면 +9.9pp. 평균은 0에 가까워서 "이전 잘 됨"처럼 보이는 것 — 방향별로 테스트 안 하면 못 보는 손실임.

4. 원인은 요약 품질 차이. 같은 160KiB 예산에서 Qwen은 필요 증거의 85.6%를 143KiB로 담고 Llama는 64.5%를 159KiB로 담음. 바이트 예산이 같아도 남기는 정보량이 다른 것. 그리고 손실의 80%는 저장 시점에 이미 발생 — 쓰는 시점에 없어진 사실은 읽는 모델이 아무리 좋아도 복구가 안 됨.

5. 재작성 수리도 안 됨. 스타일만 새 모델에 맞게 다시 써도 회복이 없었고 Llama는 재작성의 46%에서 식별자를 그냥 떨어뜨림. 저장소만 가지고 노트를 다시 쓰는 수리는 48건 전부 90% 회복에 실패 — 사라진 증거는 저장소에 없으니까.

6. RAG의 문제는 업그레이드가 아니라 검색임. 원본 전체 읽기가 0.712~0.911인데 RAG는 0.535~0.565. 결손의 81%가 검색 단계이고 청크 자체 손실은 0.005. 저장은 멀쩡한데 꺼내는 데서 깨지는 것 — 그리고 이건 업그레이드 전에도 그랬다는 점이 포인트. 새 reader 탓으로 돌리기 전에 검색 품질부터 따로 재야 함.

7. 임베딩 혼합 인덱스가 제일 무서운 함정임. 임베더를 v1.0에서 v1.5로 올릴 때 전부 재임베딩하면 +11.90pp인데 이전 벡터를 절반 섞으면 +4.96pp — 이득의 약 60%를 잃음. 두 버전 모두 1024차원이라 차원 에러가 안 나고 서비스는 멀쩡히 돌아감. 시스템이 알려주지 않는 실패라는 것.

8. 해법은 단순함. 새 임베더로 별도 인덱스를 통째로 만들고 검증 후 컷오버. 점진 전환이 필요하면 벡터 공간을 격리하고 인덱스 버전별로 질의를 라우팅할 것.

9. 수리 실험의 결론이 원본 보존의 근거임. NOTES 재구성은 원본 히스토리를 보관한 경우에만 34/48을 90%로 복구. RAG 재임베딩은 96건 전부 약 $0.013에 끝나고 KG 스키마 재구축은 사실상 공짜. 원본을 버리는 순간 수리 옵션이 사라짐.

10. 실무 체크리스트로 정리함. (1) 마이그레이션은 방향별로 테스트 — A→B와 B→A가 다름. (2) 임베딩 업그레이드는 혼합 금지, 별도 인덱스 컷오버. (3) 압축 노트만 저장하지 말 것, 원본 히스토리는 수리용으로 보관. (4) 이상한 답이 나오면 reader 모델부터 의심하지 말고 저장·검색 단계를 분해할 것 — 손실은 대부분 업스트림에서 남. (5) 저장소 메타데이터에 writer 모델, 임베더 버전, 스키마 버전을 기록할 것.

11. 이건 CAPTURE, 파일시스템 메모리 연구와 이어짐. 메모리의 위험은 읽는 시점만이 아니라 쓰는 시점에 이미 결정된다는 것 — 저장 손실 80%가 그 증거. 메모리 포맷 설계는 "무엇을 남기느냐"가 아니라 "나중에 누가 읽느냐"까지 포함하는 문제임.

12. 한계. 7~8B급 모델 2개, 단일 교차, 합성 히스토리 48개. 절대치보다 설계 원칙으로 가져가는 게 맞음.

13. 결론. 모델을 바꿀 계획이 있다면 메모리 포맷부터 점검할 것 — 스키마 고정 구조는 이식되고 모델 산물은 이식이 안 됨. 근데 결국 원본을 버리지 않는 것이 모든 수리의 전제라는 것 — 압축은 편리하지만 되돌릴 수 없다는 결론임.
