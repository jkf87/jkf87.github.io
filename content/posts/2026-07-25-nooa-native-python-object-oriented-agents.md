에이전트 프레임워크가 너무 많아서 각자 DSL을 배우는 비용이 크잖음. NVIDIA가 "에이전트가 그냥 파이썬 객체면 되지 않나"로 접근한 프레임워크를 봤음. 원문은 [arXiv:2607.20709](https://arxiv.org/abs/2607.20709).

1. 발상은 단순함. 에이전트를 하나의 파이썬 클래스로 보는 것. 메서드가 액션, 필드가 상태, 독스트링이 프롬프트, 타입 애너테이션이 입출력 계약임. 바디가 `...`면 LLM이 채우는 에이전틱 메서드, 일반 코드면 결정론적 메서드. 같은 클래스에 둘이 공존함.

![NOOA: 에이전트=파이썬 클래스](/images/2026-07-25-nooa-native-python-object-oriented-agents/fig-1-p2.png)

2. 이게 왜 좋은가. 에이전트 소스코드가 원래 프롬프트 템플릿, 툴 스키마, 콜백, 설정 파일로 찢겨 있음. NOOA는 그 전부를 하나의 클래스로 합쳐서 일반 소프트웨어처럼 테스트·디버그·리팩터·버전관리가 되게 함. 프롬프트 엔지니어링을 소프트웨어 엔지니어링으로 흡수하는 것임.

![](/images/2026-07-25-nooa-native-python-object-oriented-agents/gifs/code-typing-screen.gif)

3. 여섯 가지 모델 대면 인터페이스가 설계의 핵심임. 타입 입출력(하네스가 렌더링·검증), 참조 전달(100만 행 테이블도 타입·길이·샘플 프리뷰만 컨텍스트에 노출하고 실제 데이터는 변수로 존재), 코드가 곧 액션(JSON 툴콜 대신 파이썬 코드), 프로그래밍 가능한 루프(별도 워크플로 언어 없음), 객체 상태(대화 기록이 아니라 필드가 상태), 하네스 API 노출(컨텍스트·이벤트가 모델이 호출하는 파이썬 API).

![여섯 가지 대면 인터페이스](/images/2026-07-25-nooa-native-python-object-oriented-agents/fig-2-p5.png)

![](/images/2026-07-25-nooa-native-python-object-oriented-agents/gifs/programming-green-code.gif)

4. 참조 전달이 실무적으로 제일 큼. 컨텍스트 창에 데이터 전체를 밀어넣는 대신 변수 이름과 프리뷰만 보여주고 모델이 코드로 조작함. 컨텍스트 비용 문제를 인터페이스 차원에서 해결하는 것이라 긴 문서 처리 파이프라인에 바로 참조할 만함.

5. 14개 프레임워크 비교표에서 대부분이 여섯 가지 중 일부만 지원함. NOOA가 전부를 하나의 표면에 결합한 첫 사례라고 주장하는데, 설득력이 있음. 그리고 현재 모델들이 이 인터페이스를 학습한 적 없는데도 잘 씀. 파이썬 클래스와 타입 애너테이션이 학습 데이터에 이미 넘치게 있어서임. 새 DSL을 가르칠 필요가 없다는 게 강점임.

![14개 프레임워크 비교](/images/2026-07-25-nooa-native-python-object-oriented-agents/fig-4-p6.png)

6. 성능도 확인됨. SWE-bench Verified(실제 GitHub 이슈를 해결하는 능력을 재는 코딩 벤치마크의 사람 검증 서브셋)와 Terminal-Bench 2.0(터미널 명령 과제 수행 벤치마크)에서 여러 모델로 검증했고, ARC-AGI-3(추론·에이전트 과제 벤치마크)에선 멀티에이전트 시스템을 단일 에이전트 + 1페이지 스킬로 압축하면서 스코어-비용 프론티어를 밀었음. 인터페이스가 심플해져서 시스템이 심플해지고, 심플해진 시스템이 더 싸게 돌아가는 구조임.

7. 필자가 빌릴 것 두 가지. 첫째, 상태를 대화 기록이 아니라 명시적 필드·파일로 두는 원칙 — 이건 어떤 프레임워크 쓰든 적용됨. 컨텍스트 압축에도 살아남는 상태 설계가 장기 작업 신뢰성의 기본임. 둘째, 컨텍스트 구성을 정적 블록 + 이벤트 히스토리 + 휘발성 동적 블록 순으로 배치하는 것. KV-cache(이전 토큰의 계산 결과를 저장해 재사용하는 추론 캐시) 재사용을 극대화하는 이 배치는 비용 절감으로 직결됨.

8. 문제제기. 클래스 안에 모든 걸 넣으면 에이전틱 메서드와 결정론 코드의 경계가 커지면서 디버깅 지점이 흐려질 수 있음. 그리고 REPL 기반 실행은 샌드박싱과 권한 제어가 전제여야 하는데 논문에서 그 지점이 얇음. 프로덕션 도입은 보안 검토가 먼저임.

9. 남는 결론. 에이전트 개발의 수렴점은 특수 프레임워크가 아니라 익숙한 소프트웨어 인터페이스임. 진전은 더 큰 모델이나 더 좋은 프롬프트뿐 아니라 모델-하네스 공동 개발에서 오고, 그 장소가 인터페이스라는 논문의 주장에 동의함.
