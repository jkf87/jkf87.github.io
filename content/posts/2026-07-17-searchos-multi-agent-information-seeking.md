검색 에이전트가 긴 작업에서 길을 잃는 건 모델 능력 문제가 아니라 상태 관리 문제라는 관점의 논문이 나왔음. 계획·증거·실패 기록이 대화 이력이라는 휘발성 매체에만 있으니 잃어버린다는 것. 원문은 [arXiv:2607.15257](https://arxiv.org/abs/2607.15257).

1. 실패 양상은 익숙함. 대화가 길어지면 뭘 찾았고 뭘 못 찾았는지 추적이 무너지고, 검색 실패 시 같은 쿼리를 반복하며, 에이전트를 늘리면 늘린 대로 동일 작업을 중복하거나 가장 는 워커를 기다리며 놀게 됨.

2. SearchOS의 첫 발상은 정보 탐색을 관계형 스키마 완성으로 보는 것임. 요청을 엔티티 테이블과 속성으로 세우고, 각 셀을 채우되 모든 값에 출처 URL과 발췌문을 인용으로 묶음. 진행 상황이 커버리지 맵으로 측정 가능해지니 "다 됐나?"가 감이 아니라 빈 셀 개수가 됨.

3. 두 번째 발상은 외부 상태 네 개임. 의존성 있는 작업 큐(Frontier Task), 원자 단위 증거 노드의 Evidence Graph, 셀별 filled/missing/uncertain 상태의 Coverage Map, 그리고 실패 메모리. 실패 메모리가 없으면 에이전트 그룹이 같은 막다른 경로를 여러 번 탐색한다는 걸 실험에서 확인했다는 게 인상적임.

4. 세 번째는 파이프라인 병렬임. 동기식 배치로 모든 워커를 기다리는 대신, 작업 끝난 에이전트에게 즉시 다음 빈 셀을 주는 이벤트 기반 연속 디스패치. GPU 학습의 파이프라인 병렬과 같은 활용도 논리임.

5. 네 번째가 제일 실무적임. 제어를 프롬프트가 아니라 미들웨어로 옮김. 모델 호출 전에 역할별로 상태를 주입하고, 도구 실행 후에 증거를 추출해 그래프에 커밋하고, 상태 업데이트 후에 반복·예산 초과를 감지해 continue/correct/stop을 반환함. 프롬프트 수준 안전장치는 이기종 post-trained 모델에서 신뢰할 수 없다는 판단인데, 이건 필자 경험과도 일치함.

6. 스킬 시스템도 차등이 있음. 검색 전략 스킬과 사이트별 접근 스킬을 분리하고 성공/실패 궤적에서 정제해 세션 간 재사용함. 스킬 쓰면 GISA에서 검색 호출 39.1%, 페이지 호출 42.7%, 세션 시간 36.6% 감소. 품질과 효율이 동시에 오름. 시행착오가 줄어서 품질이 올라가는 구조임.

![](/images/2026-07-17-searchos-multi-agent-information-seeking/fig-2-p4.png)

7. 필자 작업에 바로 이식할 것 두 가지. 첫째, 반복 조사 에이전트에 실패 메모리를 파일로 달아주는 것. 스크래핑 실패한 URL·막힌 접근 경로를 세션 넘어 공유하면 재시도 낭비가 사라짐. 둘째, 조사 과제를 "채울 표"로 정의하고 빈 셀을 워커에게 나눠주는 방식. 프롬프트로 "빠짐없이 조사해라"라고 하는 것보다 커버리지가 명시적인 쪽이 완성 판정이 기계적으로 됨.

8. 문제제기. 평가가 텍스트 웹 검색에 한정됨. 그리고 스키마 설계를 오케스트레이터가 하는데, 이 스키마 품질이 전체 성능의 병목이 될 수 있음. 표를 잘못 세우면 아무리 채워도 답이 안 나오는 구조라서, 스키마 구축 단계의 견고성 검증이 다음 관문임.

9. 남는 결론. 다중 에이전트가 자꾸 같은 데서 넘어지면 프롬프트를 고칠 게 아니라 상태를 시스템으로 빼내야 함. 검색 에이전트 인프라를 데이터베이스처럼 설계하자는 방향은 재현해볼 가치가 큼.
