같은 모델, 같은 태스크인데 하네스만 바꿨더니 점수 차이가 23.8점이 나왔다는 [Harness-Bench](https://arxiv.org/abs/2605.27922)(베이징대·Qihoo360)가 나옴. Agent = Model + Harness라는 주장의 실측 데이터라 정리함.

1. 배경. 기존 벤치마크(SWE-bench(깃허브 이슈 수정 과제 코딩 벤치마크), WebArena(실제 웹사이트에서 과제를 수행시키는 웹 에이전트 벤치마크), GAIA(웹 검색·도구 사용이 필요한 범용 어시스턴트 과제 벤치마크))는 하네스를 고정하거나 통째로 추상화해서 실행 레이어 차이를 못 잼. Harness-Bench는 반대로 접근 — 태스크, 예산, 타임아웃, 평가자를 고정하고 하네스 설정만 바꿔가며 실행. 각 하네스의 네이티브 동작은 그대로 유지함.

2. 구성. 106개 샌드박스 오프라인 태스크를 8개 워크플로 카테고리(소프트웨어 엔지니어링, 데이터 분석, 워크스페이스/도구 조작, 근거 기반 지식작업 등)로 구성. 점수는 Security × Completion × Process 곱 구조 — 보안 위반이 하나라도 있으면 0점으로 날아가는 보수적 설계. 프로세스 평가는 claude-sonnet-4.6 고정 심판.

3. 숫자. 6개 설정 가능 하네스 × 8개 API 모델 완전요인설계로 5,088개 트레이토리(+Codex 106개). 최고 NanoBot 76.2점, 최저 OpenClaw 52.4점 — 격차 23.8점. 모델 바운드 참조로 Codex(GPT-5.4)가 80.4점.

4. 재밌는 디테일. NanoBot이 최고점을 받으면서도 Hermes, ZeroClaw, NullClaw, Moltis보다 토큰을 적게 씀. 긴 트레이토리가 곧 성능이 아니라는 것 — A²E의 토큰 격차 데이터와 함께 보면 하네스의 효율 설계가 독립 변수라는 게 확실해짐.

5. 제일 실무적인 발견. 강한 모델일수록 하네스 간 분산이 작음 — GPT-5.4, Claude-Sonnet-4.6은 프롬프트·도구 인터페이스·상태관리 차이에 잘 버팀. 약한 백엔드는 편차가 큼. 예산이 부족해서 약한 모델을 쓴다면 하네스 설계에 더 공을 들여야 한다는 결론이 나오는 것.

6. 카테고리별로는 구조화된 데이터 분석, 도구 시퀀싱, 워크스페이스 조작에서 하네스 의존성이 더 컸음. 정형화된 절차가 있는 작업일수록 실행 레이어의 표현이 성적을 좌우한다는 것.

7. 실패 패턴 분석이 값진 부분임. 실패 트레이토리를 뜯어보니 모델이 그럴듯하게 추론은 하는데 그 추론이 도구 피드백·워크스페이스 상태·검증 가능한 산출물과 분리되는 패턴이 반복됨. 대표 증상 — 출력 스키마 위반, 필수 산출물 누락(이해한 것처럼 보이는데 기계 검증 형태로 못 만듦), 부분 진행 후 회복 실패(피드백을 다음 행동에 반영 안 하고 커밋 없이 끝남).

8. 하네스는 '무엇이 미완료 의무인지, 무엇이 관측된 증거인지, 무엇이 복구 가능한 실패인지'에 대한 표현을 암묵적으로 정의한다는 해석이 좋음. 이 표현이 약하면 그럴듯한 추론이 평가 조건에서 떠내려간다는 것 — StructAgent, PolicyGuide의 검증 명시화와 같은 방향.

9. 여기서 문제제기. "모델만 바꿔 끼우는" 에이전트 도입은 절반만 한 선택임. 동일 예산이면 하네스 튜닝이 더 싸게 먹히는 경우가 많음. 그리고 강한 모델이 하네스 영향을 덜 받는다는 결과는 강한 모델의 가격 프리미엄과 하네스 엔지니어링 인건비가 대체재 관계라는 뜻이기도 함 — 모델 업그레이드와 하네스 개선 중 어느 쪽이 싼지 계산해보라는 것.

10. 보안 게이트를 0/1 곱으로 넣는 설계도 실무 벤치마크에서 바로 벤치마킹할 만함. 위반이 있으면 다른 점수가 무의미해지는 구조 — E-Commerce Bench의 다축 평가와 함께 보안 축의 극단적 가중치 버전임.

11. 한계. 샌드박스 오프라인이라 라이브 서비스·장기 상태는 커버 못 함. 프로세스 점수에 LLM 심판이 개입하므로 진단 용도로 읽어야 함. 코드·데이터는 github.com/Qihoo360/harness-bench에 공개돼 있어서 내부 회귀 테스트로 쓸 수 있음.

12. 결론. 에이전트 성능은 베이스 모델만으로 보고하면 안 되고 모델+하네스 조합 단위로 봐야 함. 근데 약한 모델일수록 하네스가 성적을 좌우한다는 것 — 비용 절감을 위해 약한 모델을 쓰는 사람일수록 하네스가 진짜 작업이라는 결론임.
