에이전트 성능의 상당 부분은 모델이 아니라 하네스에서 나옴. 근데 오픈소스 RL 프레임워크는 단순 롤아웃을 가정해서 Claude Code·OpenClaw 같은 복잡한 하네스를 훈련 루프에 못 올림. 그래서 연구자들은 훈련용으로 단순화한 하네스를 다시 짜고, 그 순간 배포 환경과 다른 훈련-배포 불일치가 생김. [OpenForge RL](https://arxiv.org/abs/2607.21557)이 이 문제를 프록시 하나로 풀었음. 나아가서 어떤 하네스로 훈련하느냐가 성능을 얼마나 바꾸는지 처음으로 데이터로 보여줌.

1. 구조는 단순함. 훈련 루프 안에서 롤아웃을 직접 돌리는 대신 원격 컨테이너로 오프로드함. Kubernetes 오케스트레이터가 롤아웃 파드를 만들고 관리함. 컨테이너 안에서 하네스가 추론을 하다가 모델을 호출하면 **프록시**가 그 호출을 가로채서 RL 프레임워크의 추론 엔진(vLLM 등)으로 라우팅함. 프록시는 모든 프롬프트-응답 쌍을 기록하고, 롤아웃이 끝나면 궤적을 재구성해 훈련 샘플로 만듦. 하네스 코드를 한 줄도 수정할 필요가 없다는 게 핵심임.

![OpenForge RL 시스템 구조](/images/2026-07-25-openforge-rl-train-harness-native-agents/fig2-html.png)

2. 이 "호출을 가로채서 기록한다"는 발상은 RL이 아니어도 쓸 데가 많음. 내가 이미 운영 중인 에이전트 하네스의 모델 호출을 프록시로 한 겹 감싸면, 그동안 손으로 모으기 어려웠던 실전 프롬프트-응답 로그가 구조화된 궤적으로 쌓임. 이건 곧 바로 SFT 데이터, 실패 분석 코퍼스, A/B 비교 기반이 됨. 훈련 인프라가 없어도 프록시 로깅만으로 에이전트 개선 사이클의 원재료가 생기는 것.

3. 운영 디테일도 실무적임. 복잡한 환경에선 하나의 롤아웃이 응답 없으면 전체 배치가 멈춤. 그래서 턴 수 제한 대신 wall-clock 타임아웃(실제 경과 시간 기준 제한)을 걸어서 초과하면 해당 롤아웃만 종료하고 나머지는 계속 진행함. 그리고 네트워크 문제나 크래시로 끝난 궤적의 샘플은 전부 폐기함. 부분 롤아웃이 잘못된 훈련 신호를 주기 때문. 이 원칙은 내 자동화 파이프라인의 로그 수집에도 그대로 적용됨. 실패한 실행의 로그를 "그냥 버려야 할 오염"과 "분석해야 할 실패"로 나누지 않고 섞어두면 나중에 통계가 전부 오염됨.

![태스크 합성 파이프라인](/images/2026-07-25-openforge-rl-train-harness-native-agents/fig3-html.png)

4. 성과. Qwen3-30B-A3B 백본으로 ClawEval pass@3 55.9, QwenClawBench 33.7, MCPAtlas 28.1로 RL이 SFT 위에 모든 벤치마크에서 추가 개선을 냄. ClawEval pass³(3회 시도 모두 성공)이 28.2에서 31.7로 오른 게 의미 있음. RL이 운 좋은 샘플을 뽑는 게 아니라 신뢰성 자체를 높였다는 증거임. GUI 쪽은 Qwen3-VL-8B로 OSWorld-Verified(실제 컴퓨터 화면을 보며 파일·앱 조작 과제를 수행하게 하는 벤치마크) 37.7, Online-Mind2Web(실제 웹사이트에서 검색·내비게이션으로 과제를 끝내게 하는 벤치마크) 63.0, WebVoyager(웹 탐색으로 실제 사이트에서 과제를 완수하는 벤치마크) 72.3. 특히 MolmoWeb은 20만 태스크로 훈련했는데 OpenForge-GUI는 2,500개로 이를 능가함. 태스크의 질과 환경의 진짜함이 개수를 이긴다는 것.

5. 제일 흥미로운 발견은 하네스별 학습 효과 차이임. 같은 모델을 하네스만 바꿔서 훈련했더니 ReACT는 +15.0, ZeroClaw는 +25.4, Codex는 +20.3, OpenClaw는 +9.5였음. 단순하고 도구 추가가 쉬운 하네스에서 가장 크게 개선되고, 프롬프트와 컨텍스트가 긴 정교한 하네스는 학습이 더 어려움. 즉 "더 정교한 하네스가 항상 더 낫다"는 통념의 반례임. 배포 시점 성능은 정교한 하네스가 좋을 수 있지만, 학습 가능성은 단순함이 이기는 지점이 있다는 것.

6. 일반화 결과도 있음. ZeroClaw 하나로만 훈련한 모델을 못 본 OpenClaw와 Codex로 평가해도 베이스 대비 +3.3, +4.6이 나옴. 그리고 세 하네스로 섞어 훈련하면 전부에서 최고 성능. 다양한 환경에서 훈련할수록 일반화가 좋다는 건 모델 훈련뿐 아니라 내 에이전트 튜닝에도 적용됨. 하나의 워크플로우에 과적합된 프롬프트는 다른 워크플로우에서 무너진다는 것과 같은 구조임.

7. RL이 에이전트 행동을 어떻게 바꾸는지도 분석돼 있음. RL을 거치면 generic shell 사용이 줄고 전용 서비스 도구(email, calendar 등) 사용이 늘어남. 작업 완료 후 자기 검증 빈도가 크게 늘고, 긴 계획을 끝까지 수행하는 비율이 올라감. 근데 에러 복구는 여전히 약함. 즉 RL이 가르치는 건 "도구를 알고, 확인하고, 끝까지 가는 것"이지 "넘어져서 일어나는 것"이 아님. 실패 복구는 여전히 하네스의 재시도 설계와 사람의 개입 영역이라는 뜻임.

![RL이 도구 사용 패턴을 바꾸는 방식](/images/2026-07-25-openforge-rl-train-harness-native-agents/fig-5-p10.png)

8. 한계도 솔직함. 에러 복구가 약하고, 부분 롤아웃의 크레딧 할당(성공·실패의 공을 어느 행동 단계에 돌릴지 정하는 문제) 문제가 남았고, GUI 환경의 실시간 웹사이트 의존성(사이트가 바뀌면 검증이 깨짐)은 실용적 과제임. 코드·데이터·모델 공개 예정이라고 함.

9. 돌아보면 이 논문의 진짜 기여는 도구 자체보다 질문임. "하네스를 배포용 래퍼가 아니라 학습 대상으로 다루면 무엇이 보이는가." 하네스별 학습 난이도 차이, 다중 하네스 훈련의 일반화, RL의 행동 변화 프로파일이 전부 그 관점 전환에서 나온 결과임. 하네스를 고르는 일이 모델을 고르는 일만큼 중요하다는 걸 이제는 실험으로 말할 수 있게 된 것. 내 에이전트 스택을 볼 때도 "어떤 하네스 위에서 굴러가는가"를 첫 번째 질문으로 올려야 함.
