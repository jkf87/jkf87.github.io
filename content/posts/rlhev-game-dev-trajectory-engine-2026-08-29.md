코드 에이전트가 강한 이유는 컴파일러와 런타임이 실행 결과를 그대로 돌려주기 때문임. 반면 공간 생성은 CLIP 점수 같은 모델 기반 프록시에 기대고 있는데 이 신호는 편향과 노이즈가 커서 RL 보상으로 부적합함. [RLHEV](https://arxiv.org/abs/2608.25518)의 핵심 주장은 여기서 나옴. 월드모델 스케일링은 영상을 더 모으는 것보다 실행 가능한 검증 신호를 돌려주는 데이터 엔진이 먼저라는 것. 그리고 그 데이터 엔진으로 게임 개발을 쓰겠다는 발상임.

1. 구조가 코드 에이전트의 직역임. 게임 엔진으로 인코딩된 장면은 실행 가능한 월드 명세라서 엔진이 충돌, 물리, 내비게이션 가능성, 유한 플레이 가능성을 검사하는 정밀한 지역 신호를 줌. 그리고 개발자가 그 장면을 수용할지 판정하는 전역 검증 신호를 줌. 이 둘을 결합한 게 RLHEV. 컴파일러-사람 루프를 공간 지능으로 옮긴 것으로 이해하면 됨. 앞서 정리한 TRACE(검증자가 없으면 검증자가 있는 문제를 제조)와 정확히 같은 방향인데 여기선 검증자가 게임 엔진이라는 게 차이임.

![검증 루프 비교](/images/rlhev-game-dev-trajectory-engine-2026-08-29/fig_verification_loop.png)

2. AWoMo라는 워크플로가 데이터 엔진의 실체임. 단일 신경망이 아니라 모델, 에이전트, 엔진 검증기, 인간 리뷰어가 묶인 커플드 워크플로인데 프롬프트, 장면 프로그램, 렌더 상태, 실패, 수정, 엔진 체크, 사람 판정까지 통째로 멀티모달 궤적으로 저장함. 수용된 종료 상태는 지도 학습 타깃이 되고 실패-수정 페어는 다음 편집 예측 페어가 됨. 성공만이 아니라 실패-수정 과정이 자산이 된다는 건 Living-Harness의 에피소드 기억과 같은 원칙임.

![보상 비교](/images/rlhev-game-dev-trajectory-engine-2026-08-29/fig_reward_comparison.png)

3. 결과. UnitySceneBench(200 예제, 메서드당 8 시드)에서 640 인스턴스 구간 생성 품질 0.8106, 720 풀 예산에서 0.8197. 최강 비-풀 베이스라인 대비 best-of-eight +0.098. 사전학습 데이터는 수용 87,745 / 기각 504 샘플의 규모. 엠바디드 진단에서는 AWoMo 증강 데이터로 정책을 학습했을 때 D4RL Gym-MuJoCo +48.43%, MuJoCo 리턴 +9.96%, R2R 성공률 +0.79%. 게임 개발 궤적으로 만든 데이터가 로봇 정책 학습까지 이전된다는 것이 이 논문의 도박이고 첫 숫자는 나온 상태임.

![장면 프로그램 표현](/images/rlhev-game-dev-trajectory-engine-2026-08-29/fig_scene_program.png)

4. 제가 주목하는 지점 두 가지. 첫째, 재귀적 개선이 AI-to-AI 현상만이 아니라 사람 실무 + 실행 환경 + 학습 시스템의 생태계 속성이라는 논문의 프레임. 개발자의 수용 판정이라는 사람 신호가 루프 안에 정식 구성요로 들어 있다는 것. 둘째, 스스로 반증 조건을 명시했다는 것. "개발 궤적 + 인간-엔진 보상이 OOD 일반화를 개선 못 하면 게임 개발은 월드모델의 데이터 엔진이 아니다"라고 못 박아둠. 이런 반증 가능성 선언은 연구의 신뢰도를 올려줌.

5. 한계도 분명함. 사람 수용 판정이 여전히 병목이고 R2R 개선 +0.79%는 절대 크기가 작아 과대 해석하면 안 됨. 그래도 내 적용 결론은 이것임. 내 업무 도메인의 "컴파일러"를 찾는 문제에서 게임 엔진은 좋은 영감임. 스키마 검증, 실행 시뮬레이션, 렌더 테스트처럼 기계가 정밀하게 지역 검사를 하고 사람은 수용/기각만 하는 이중 신호 구조. 모델 기반 프록시 점수에 의존하는 검증이 있다면 그걸 실행 기반 검증 + 사람 게이트로 바꾸는 게 이 논문이 주는 레시피임.
