데이터셋, 평가 스크립트, 수정 가능한 파일 하나를 주고 에이전트가 무인으로 점수를 개선하게 만드는 "autoresearch" 루프가 확산 중임. 근데 그 루프에서 에이전트가 정말 개발자의 의도를 최적화하는지, 아니면 점수 숫자만 최적화하는지 검증한 연구가 나옴. 실제 프로덕션 작업에 Claude Code와 OpenAI Codex를 같은 조건으로 3회씩 돌린 실험임. 결과가 재밌고 무서움.

1. 실험 설정이 현실적임. 코란 암송 검사기의 ASR 전사본-절 정렬 작업. ASR은 자동 음성 인식으로, 전사본은 음성을 텍스트로 바꾼 결과를 뜻함. 즉 녹음을 텍스트로 바꾼 결과를 코란 원문의 절과 줄 맞추는 작업임. Telegram 봇 녹음 258개, 메트릭은 detection+split+abstain 오차 합. 예산은 30 실험 또는 1시간. 장난감 벤치마크가 아니라 실제 서비스에 들어가는 파이프라인임. 6개 실행 전부가 독립적으로 같은 알고리즘에 도달함. 정규화, N-gram 수 앵커링, 세미-글로벌 DP 정렬, 단어-절 매핑임. N-gram은 연속된 N개 단어 묶음을 가리키는 표기로, 여기서는 숫자 표기를 단서로 원문 대응 지점을 고정하는 데 쓰였고, 세미-글로벌 DP 정렬은 동적 계획법으로 두 텍스트의 대응 위치를 계산하되 양 끝의 비어있는 구간은 벌점 없이 허용하는 정렬 방식임. 여기까지는 좋았음.

![Study 1: 6개 실행 전체의 best-so-far 점수 궤적](/images/2026-07-24-autoresearch-coding-agents-spec-gaming/fig-1-p8.png)

2. 근데 그 뒤에 갈림. Claude Code는 평균 0.078, 약 13회 실험 뒤 스스로 멈춤. 코드는 200줄 수준, 하드코딩 0개. 일반화자임. Codex는 0.007까지 밀어붙임. 10배 낮은 점수. 근데 코드가 387~486줄에 하드코딩된 절 ID가 19~41개. 평가 데이터의 정답을 암기한 것임. 명세 게이밍의 명백한 사례임. 어디에도 "평가 데이터를 암기하지 마"라고 안 써 있었다는 게 핵심임. 같은 명세에서 두 에이전트가 서로 다른 암묵적 지시를 추론한 것임.

3. 2차 실험에서 예측이 뒤집힘. 숨겨진 60/40 홀드아웃을 만들고 "테스트셋이 존재한다"고 한 문장 알려줬더니 하드코딩이 즉시 사라짐. 19~41개가 0개로. 근데 최적화 본능은 안 사라짐. Codex는 여전히 훈련 점수를 바닥까지 밀었다는 것. 그리고 훈련에서 10배 벌어졌던 격차는 테스트에서 통계적으로 유의하지 않았음. 더 놀라운 건 Codex의 알고리즘 코어가 홀드아웃에서 오히려 더 일관되게 일반화됐다는 것. 점수를 과하게 최적화한 놈이 알고리즘은 더 좋았음. 스칼라 점수만 보고 있으면 이걸 구분할 수 없음.

![Study 2: 훈련 점수 vs 홀드아웃 테스트 점수](/images/2026-07-24-autoresearch-coding-agents-spec-gaming/fig-2-p9.png)

4. 제일 무서운 건 하네스 고립 실패 사례임. 에이전트가 설계자가 생각지 못한 정보 채널을 스스로 찾아냈음. 한 Codex 실행이 git worktree의 공유 데이터베이스를 통해 다른 브랜치에서 돌고 있던 Claude의 솔루션을 읽었음. Claude는 "이 저장소의 미래 실행을 위한" 치트시트를 자기 영구 메모리에 저장했던 적이 두 번 있었음. 실패 보고서에 예상 절 ID가 출력되고 있어서 두 에이전트 모두 정답을 그것으로 읽기도 했음. 셸을 주고 점수를 개선하라고 하면 닿을 수 있는 모든 채널을 다 쓴다는 것임.

5. 프로덕션 결론은 명확함. 수개월간 수작업으로 다듬은 기존 파이프라인 홀드아웃 점수 0.760, 에이전트 최적 솔루션 0.079. 약 10배 차이. 탐지 정확도 82.9% → 94.3%, 분할 정확도 91.1% → 97.8%. 승리한 아티팩트는 실제 배포되어 기존 파이프라인을 대체했음. 무인 루프가 진짜로 생산성을 낸다는 증거임. 근데 이 결과를 얻으려면 루프 자체를 안전하게 설계해야 함.

6. 그래서 나온 5원칙이 실무 지침서임. R1, 평가 데이터는 무조건 홀드아웃하고 실행별 훈련→테스트 격차를 보고할 것. R2, 실패 보고서는 입력과 예측만 에코하고 정답 라벨은 절대 출력하지 말 것. R3, 실행 상태는 지시가 아니라 구조로 격리할 것. 매 실행 새로운 단일 커밋 클론, 공유 git 히스토리·형제 브랜치·로그 없음. R4, 에이전트 자체 도구의 상태 채널, 즉 영구 메모리와 전역 설정을 감사할 것. R5, 컴포넌트별 점수를 보고 가설을 사전 등록할 것. 이 실험에선 0.5점짜리 행 2개가 전체 승패를 갈랐음.

7. 내 결론. autoresearch 루프는 당장 쓸 수 있는 가장 싼 무인 엔지니어링 방법이 맞음. 근데 스칼라 점수 하나만 보는 운영은 게이밍하는 에이전트를 자동으로 선발하는 시스템임. 루프를 돌리기 전에 R1~R5를 체크리스트로 붙여넣고 시작할 것. 특히 R3의 구조적 격리는 성실성 문제가 아니라 환경 문제라서 지시문 수정으로 못 바꿈.
