에이전트가 실행 중 자기 하네스를 고치는 자기진화가 늘어나면서 새로운 안전 문제가 생김. 능력은 올라가는데 나중에 안전하게 되돌릴 수 없는 변형이 생기는 것. EvoUndo(Sah et al., arXiv:2608.28363)는 이 문제를 복구 가능성 제약으로 formalize함. 핵심 설계는 한 줄. 능력을 개선하는 변형이라도 복구 검증을 통과하지 못하면 영구 적용하지 않는다는 것.

1. 증거가 먼저임. 600개 자기진화 태스크(6계열×100)에서 능력은 개선됐지만 복구 검증에 실패한 변형이 197개였음. 이걸 기존의 반복적 수리 방식, 그러니까 더 열심히 프롬프트해서 고치는 방식으로 복구하려 하면 0/197 전멸. 원인이 모델 능력이 아니었다는 게 핵심 발견임. 상태 주소 정보 부족(grounding)과 복구 언어의 표현력 부족이 원인이어서, 더 잘 프롬프트해도 해결되는 종류의 실패가 아니었음.

2. 문제 정의가 정확함. 올바른 복구 절차는 상태 의존적이고 필요한 정보는 변형 이전 상태에만 존재함. 그래서 증인 캡처 w(변형 전 사전 상태에서 필요한 정보를 뽑아두는 것)와 복구 프로그램 u를 짝으로 준비해야 함. 그리고 복구 가능성은 변형을 만든 상태에서만이 아니라 반사실(counterfactual) 상태 분포에서도 성립해야 한다는 조건이 붙음. 내 상태가 우연히 복구됐다고 끝이 아니라 다른 상태에서도 왕복이 될 때 진짜 복구 가능이라는 것.

3. 게이트 설계가 fail-closed로 되어 있음. 효과 계약 감사에서 런타임이 SnapshotDiff와 실행 트레이스로 실제 효과를 독립 계산하고, 관측된 효과를 계약에서 빼먹으면 탈락. 반사실 왕복 검증은 개발 상태 10개, 숨김 상태 40개(IID 20+OOD 20)에서 s→w→m→u→ŝ 왕복을 검사. 입장 기준은 Wilson 95% 하한 신뢰구간 ≥ 0.85. 구문 오류나 예외는 즉시 거부. 그리고 수리 제한. 정방향 변형 m은 불변으로 잠기고 (w,u,Ce)만 수정 가능함. 변형을 no-op으로 약화해서 회피하는 길을 막은 것.

4. 복구 실험 결과가 이 논문의 뼈대임. 197개 실패를 두 층으로 나눠 보면 S0층 48개는 정확한 주소 grounding을 주기만 해도 0/48 → 38/48(79.2%)로 회복. S1층 143개는 복구 언어를 L1으로 확장하니 142/143(99.3%) 회복. L1은 미들웨어 순서, 이벤트 리스너, 샌드박스 파일, 관리 소켓, 순서 있는 복구 합성까지 다루는 언어임. 오라클 기준 복구 가능 범위가 48/197 → 191/197로 늘어남. 즉 실패의 대부분이 "언어가 못 표현해서"였다는 것.

5. 반전도 있음. 진단 피드백을 세밀하게 주는 게 항상 좋지 않다는 것. gpt-oss-120b에서 정확한 주소 피드백이 확장 언어와 결합하면 오히려 성능이 -25.89pp 낮아졌음. Qwen3.8-27B 재현에서는 유의하지 않아서 모델 의존적이지만, 거친 진단 + 표현력 좋은 복구 언어 조합이 최고 효율(94.2%)이었다는 건 실무적으로 흥미로움. "피드백을 더 자세히"가 아니라 "복구 도구를 더 강하게"가 답일 수 있다는 것.

6. 비용도 측정됨. 평균 저장 393.6B, 지연 0.050ms로 풀 스냅샷(1165.0B, 0.084ms)보다 가벼움. 개발 반사실 다양성을 Q2→Q20으로 늘리면 오탐이 16.8% → 0.0%로 사라지는 대신 수확이 49.7% → 35.0%으로 내려감. 정밀도-커버리지 트레이드오프가 명시적으로 드러나서 운영 시 자기 지점을 골라야 함.

7. 실무 이식은 두 가지가 바로 가능함. 첫째, 자기진화 파이프라인에 undo 검증 게이트를 앞단에 붙이는 설계. 변형 제출 시점에 사전 상태 증인 캡처와 복구 프로그램을 함께 요구하는 방식. 오늘 바로 적용 가능한 패턴임. 둘째, 진단 피드백 세밀화를 무조건 최대화하지 말 것. 이 논문에서는 거친 진단 + 표현력 좋은 복구 언어가 최고였음. 한계도 명확히 둘 것. L0/L1 계산의 완전성 보장이 없고, 분산 상태·외부 API는 미커버, 불가역 물리·금융 효과는 복구 대신 보상 의미론이 필요하며 모델 규모 다양성도 부족함. "되돌릴 수 없는 변경은 애초에 받지 않는다"는 원칙 자체가 git이 시스템 설계에도 적용돼야 한다는 결론임.
