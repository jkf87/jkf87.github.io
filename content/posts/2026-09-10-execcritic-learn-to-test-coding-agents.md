코딩 에이전트의 실행 피드백 루프에서 가장 위험한 지점을 찌른 논문이 나옴. 패치와 그 패치를 검증하는 테스트를 같은 에이전트가 같은 트라젝토리에서 만들면 두 오류가 서로 공명해서 가짜 확신이 생긴다는 것. ExecCritic(arXiv 2609.09133, Microsoft Research·UW-Madison·Georgia Tech)이 이 문제를 역할 분리로 풀어서 SWE-bench Verified 72.6%, 베이스라인 대비 +11.4포인트를 냈음. 평가 시점에 stronger model도 Oracle 피드백도 안 쓰고.

1. 동기가 되는 대비가 핵심임. 같은 Qwen-3.5-35B-A3B Repair 에이전트를 고정하고 피드백 소스만 바꿨더니 테스트 없음 61.2%, 학습 안 된 Qwen이 만든 테스트 57.3%(-3.9p), GPT-5.6이 만든 테스트 65.3%(+4.1p), Oracle 테스트 69.4%(+8.2p). 같은 실행 피드백 메커니즘인데 테스트 소스에 따라 -3.9p에서 +8.2p까지 갈림. "실행 피드백을 넣으면 좋아진다"는 통념이 테스트가 틀리면 피드백이 독이 된다는 반례로 교정된 것. 문제의 정식화도 직관적임. 관습적 루프에서는 패치와 검증 근거가 같은 정책에서 나와서 같은 오해가 패치와 근거와 중단 결정을 함께 오염시킴.

2. 구조가 두 단계임. Learn to Test에서 Test 에이전트는 이슈와 버그 상태 리포지토리만 보고 테스트 패치, 실행 커맨드, JSON 행동 계약을 산출함. 하네스가 이 묶음을 검증해서 버그 상태에서 깨끗하게 실패하는지 확인함(Base-gate). 그리고 학습 신호로 Base-to-Gold 성공, 즉 버그 상태에서 실패하고 정답 패치 상태에서 통과하는지를 측정함. 진짜 판별 테스트의 조건임. Test to Improve에서 동결된 테스트가 Repair 에이전트의 각 패치 후보에 실행되고 실패하면 bounded 실행 피드백이 다음 수정을 조건화함. 통과하면 즉시 종료, 최대 5회 수정 후에도 안 되면 마지막 후보를 강제 제출. Repair 에이전트는 테스트를 고칠 수 없고 소스만 고침. 독립성이 구조로 강제된 것.

![Figure 1 전체 구조](/images/2026-09-10-execcritic-learn-to-test-coding-agents/fig-1-p1.png)

3. 학습 레시피도 베낄 만함. Test 보상은 Base 실패 + Gold 통과 시 후보 패치들에 대한 balanced accuracy에 따라 계단식 상승. 올바른 패치는 통과시키고 잘못된 패치는 실패시켜야 최고점이라는 판별 보상임. Repair 보상은 Round-0 직접 성공 1.5, 수정 후 성공 1.0, 테스트 통과·공식 실패 0.2. Round-0 보너스를 크게 둬서 직접 해결 능력을 유지하면서 피드백 활용을 가르침. 그리고 Repair 학습을 Round-0 정확도 0.4 미만 이슈로 제한해서 수정 신호가 있는 데이터만 씀. 학습 데이터 필터링의 실무적 교훈임.

![Figure 4 Test/Repair 보상 구조](/images/2026-09-10-execcritic-learn-to-test-coding-agents/fig-4-p6.png)

4. 결과. Test 에이전트 Base-to-Gold가 22.2% → 62.2%(+40.0p)로 Codex-5.3(61.0%) 수준에 도달. Repair 에이전트 Round-0가 61.2% → 68.3%. 두 학습된 에이전트 조합이 72.6%. 그리고 학습된 조합에 Oracle 피드백을 주면 77.6%까지 오르니 남은 격차가 테스트 품질을 올리면 더 딸 수 있다는 뜻임. 오버헤드도 작아서 수정에 진입한 트랙토리는 평균 13턴 추가로 해결. 테스트 생성은 이슈당 1회의 일회성 비용이고 Repair 실행 3회에서 재사용됨.

![Figure 5 테스트 소스별 효과](/images/2026-09-10-execcritic-learn-to-test-coding-agents/fig-5-p9.png)

5. 내 해석. 이 논문의 진짜 기여는 진단 쪽임. 검증자와 실행자의 독립성을 명시적으로 설계해야 한다는 교훈은 코딩 외 도메인에도 적용됨. 내 에이전트 시스템에서도 "평가 기준을 만드는 주체"와 "그 기준으로 수정하는 주체"가 같은 컨텍스트에 있으면 안 됨. 다만 한계도 읽어야 함. SWE-bench Pro에서는 생성 테스트가 +0.7p에 그침. Pro 인스턴스는 평균 14.43개 F2P 테스트(Verified는 3.03개)를 요구해서 하나의 테스트 묶음이 커버리지에 한계가 있음. 테스트 하나에 하나의 행동만 검증하는 설계는 넓은 스펙 태스크에서 상한이 낮다는 것. 언어 일반화 편차도 큼. Python 62.2%, Rust 66.7%, C++ 58.3%, C 26.1%, Java 2.4%. 레포지토리 네이티브 테스트 인프라 발견이 언어마다 난이도가 다름.

6. 실무 이식은 이렇게임. 첫째, 자기 채점 루프가 있다면 채점 기준 생성과 수정 실행을 분리할 것. 기준은 수정 중 동결하고 수정자가 기준을 못 고치게 할 것. 둘째, 생성된 검증 기준에 자격 게이트를 둘 것. "버그 상태에서 실패, 정답 상태에서 통과" 같은 판별 조건을 통과해야 기준으로 쓰게 하는 것. 셋째, 검증 기준의 품질을 시스템 성능의 병목으로 취급할 것. 피드백 방향을 정하는 게 기준이라서 기준이 나쁘면 기준 없는 게 나았음. 넷째, 검증 커버리지가 넓은 태스크는 단일 기준에 의존하지 말 것. 상한이 낮다는 게 측정돼 있음.
