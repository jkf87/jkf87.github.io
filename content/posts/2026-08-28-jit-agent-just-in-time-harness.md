하네스 최적화 연구는 지금까지 크게 두 갈래였음. 사람이 수작업으로 다듬거나 실행 트레이스로 오프라인 개선하거나. JIT-Agent(arXiv 2608.25593)는 제3의 길을 엶. 하네스를 태스크가 들어올 때 그 자리에서 생성하는 것. 컴파일 언어의 AOT vs JIT 비유를 논문 스스로 씀. 그리고 하네스 인텔리전스라는 개념을 내세워 모델 스케일링과 직교하는 별도의 훈련 가능한 능력이라고 주장함.

1. 표기 정리가 먼저임. 하네스 h를 네 튜플로 정의함. M(메모리)은 히스토리 컨텍스트·증거 저장·상태 압축. P(계획)은 목표 분해와 개정. A(액션)은 실행 루프·제어 흐름·검증. F(역량)은 태스크 레지스트리 기반 도구·스킬 배치. 실행 프로토콜 아래에서 정보는 M→P→F→A로 흐름. ReAct 같은 고정 스캐폴드도 이 표기로 변환돼서 비교 대상이 됨. 이 정형화가 있어야 "생성"이 무엇을 만드는지가 정의됨.

![](/images/2026-08-28-jit-agent-just-in-time-harness/gifs/3d-printing-on-demand.gif)

2. 훈련이 세 단계로 쌓임. Stage I 생성. 교사 모델이 ReAct, Plan-and-Execute 같은 시드 뱅크를 보고 태스크에 맞게 하네스를 다시 짜고 그 데이터로 SFT와 선호 학습을 돌림. 성능이 오르면서 비용을 희생하지 않는 하네스를 선호하도록 가중치를 줌. Stage II 수리. 생성한 코드는 인터페이스 불일치와 런타임 예외로 깨짐. 컴파일 에러와 스택 트레이스 같은 진단 리포트를 입력으로 넣고 로컬 패치를 생성하도록 훈련함. 개발자가 디버깅하듯 실행 가능해질 때까지 고치는 것. Stage III 진화. Evo-GDPO로 후보 하네스 그룹을 병렬 실행하고 성과·지연·비용 보상으로 하네스 뱅크를 갱신함. 테스트 타임에도 생성 전략이 계속 좋아지는 구조임.

![](/images/2026-08-28-jit-agent-just-in-time-harness/gifs/repair-technicians.gif)

3. 숫자. DeepSearchQA에서 DeepSeek-V4-Flash + JIT-Agent가 GPT-5.6 대비 +9.1. OdysseyBench +4.3. 태스크당 API 비용 평균 36% 감소. xBench-DS에서는 표준 ReAct 대비 토큰 절반 이하로 더 높은 정확도. 저비용·고성능 파레토 프론티어에 위치한다는 게 논문의 프레임임. 작은 모델이 하네스로 큰 모델을 넘는다는 결과는 하네스 인텔리전스가 스케일링과 직교한다는 주장의 근거가 됨.

![4개 벤치마크 리더보드](/images/2026-08-28-jit-agent-just-in-time-harness/four_benchmark_leaderboard.png)

4. 생성된 하네스 구조 시각화가 제일 흥미로웠음. 프롬프트 수정 수준을 넘어서 에이전트 로직이 다시 배선됨. 아티팩트 생산엔 태스크를 DAG로 변환해 병렬 실행하는 구조, 딥 리서치엔 경계 있는 재귀 위임으로 개인 메모리를 가진 서브에이전트가 단서를 해결하는 구조, 다중 출처 증거 수집엔 후보×단서 매트릭스를 채워야 검증이 트리거되는 구조가 나옴. 여행 계획엔 체크리스트 통과 후 답하는 구조, 데이터 분석엔 코드 기반 상태 관리 우선 구조가 나왔다고 함. 태스크에 따라 최적 하네스 구조가 달라진다는 실증 포인트임.

![비용-성능 프론티어](/images/2026-08-28-jit-agent-just-in-time-harness/jit_training_pipeline_frontier.png)

5. 내 해석을 원문 주장과 구분해서 적음. 원문 주장은 하네스 인텔리전스가 훈련 가능하고 전이 가능하며 복리로 쌓이는 능력이라는 것. 벤치마크 숫자가 이걸 뒷받침함. 내가 주목하는 건 다른 지점. Stage II의 진단 기반 수리가 실무에서 가장 먼저 써먹을 수 있는 부분임. 하네스 생성 코드가 깨졌을 때 스택 트레이스를 보고 패치하는 훈련 데이터를 만드는 일은 개인도 따라 할 수 있음. 생성→수리→진화 순서도 그대로 벤치마킹 가능한 설계 원칙임. 반면 Stage III의 Evo-GDPO는 보상 설계, 성과·지연·비용의 가중치가 숨은 설계 결정이라 재현하려면 이 가중치를 먼저 고정해야 함.

6. 한계도 적을 것. 하네스 뱅크가 커질수록 평가 비용이 함께 커지는 구조라 오프라인 트레이스 기반 방법(AutoSaddler 계열)과 어느 쪽이 싼지 비교가 아직 없음. 생성 하네스의 안전성 검증도 숙제로 남음. 실무 이식은 이렇게임. 첫째, 하네스를 네 모듈로 문서화해서 태스크 유형별로 어떤 배선이 좋았는지 기록할 것. 둘째, 실패한 하네스 코드와 진단 리포트를 짝지어 수리 데이터를 쌓을 것. 셋째, 비용·지연·성과를 같이 재는 보상 구조를 미리 정의할 것. 넷째, 태스크 유형이 다양하다면 고정 하네스 하나를 유지하기보다 유형별 하네스 생성을 실험해볼 것.
