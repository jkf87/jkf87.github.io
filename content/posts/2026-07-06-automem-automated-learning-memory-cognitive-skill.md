장기 과제를 맡긴 에이전트는 대부분 메모리 문제로 무너짐. Stanford의 AutoMem은 메모리를 고정된 모듈이 아니라 훈련 가능한 기술로 취급해서, Qwen2.5-32B 하나를 Claude Opus 4.5급으로 끌어올렸음. 구조가 실무에 그대로 벤치마킹할 만해서 정리함.

1. 배경부터. 에피소드가 수만~십만 스텝에 이르는 작업은 컨텍스트 윈도우로 다 담을 수 없음. 그래서 보통 RAG를 붙이거나 요약 버퍼를 얹는데, 이건 메모리를 파이프라인 부품으로 취급하는 방식임. 모델은 메모리를 잘 쓰는 법을 배우지 못하고, 설계자가 일일이 스키마를 짜야 함.

2. 문제는 사람이 그 설계를 검증할 수 없다는 데 있음. 한 에피소드가 수만 스텝이면 인간 리뷰로 메모리 실수를 찾는 건 물리적으로 불가능함. 그래서 메모리 설계는 대부분 손대감(手勘)으로 유지되고, 실패해도 원인을 못 찾음.

3. AutoMem의 첫 조치는 파일 시스템 연산(read, write, search, append)을 태스크 액션과 같은 공간에 넣는 것임. 매 스텝 LOG 루틴(기록할 것을 골라 파일에 쓰기)과 PLAN 루틴(필요한 걸 검색해서 읽고 행동)을 돌림. 모든 메모리 결정이 추적 가능한 액션 로그가 되는 게 포인트임.

![AutoMem 프레임워크](/images/2026-07-06-automem-automated-learning-memory-cognitive-skill/fig-p3.png)

4. 그 위에 자동 루프 두 개를 얹음. 루프 1은 구조 최적화. 메타-LLM이 전체 에피소드 트레이스를 리뷰해서 메모리 실패 패턴을 진단하고, 프롬프트·파일 스키마·액션 어휘를 반복 개정함. 숙련된 리뷰어가 실행 로그 읽고 버그 잡는 일의 자동화임.

5. 루프 2는 숙련도 훈련. 구조 개선이 한계에 오르면, 메타-LLM이 좋은 메모리 결정을 골라 SFT 데이터로 만들고 태스크 액션 모델은 동결한 채 메모리 전용 LoRA 스페셜리스트만 학습시킴. 기존 역량을 안 깨면서 메모리 실력만 올리는 안전한 경로임.

6. 결과. Crafter·MiniHack·NetHack 세 환경에서 32B+AutoMem이 51.4%, 30.0%, 1.9%를 기록. 미최적화 72B를 전 환경에서 압도하고 Claude Opus 4.5(49.5%, 27.5%, 2.0%)와 대등함. 스케일보다 메모리 관리가 더 큰 변수였다는 증거임.

7. 정성 변화도 확인할 만함. 루프 1만으로 무효 액션 32~65% 감소, 중복 기록 68~83% 감소, 스텝당 입력 컨텍스트 3~30% 축소. 루프 2를 거치면 writes/search 비율이 Crafter 0.84→0.39, NetHack 4.66→1.31로 내려감. 쓰기 전에 먼저 검색하는 습관이 가중치에 박힘.

8. 여기서 내 실무 해석. 우리가 돌리는 장기 자동화 작업(멀티세션 리서치, 코드베이스 유지보수, 반복 분석)도 결국 같은 구조임. 컨텍스트 관리를 모델에게 맡기든 프롬프트로 강제하든, 메모리 액션을 로그로 남기지 않으면 개선 자체가 불가능함.

9. 그래서 당장 베낄 수 있는 건 세 가지. 첫째, 에이전트에 파일 기반 메모리를 1급 액션으로 달고 모든 읽기·쓰기를 로깅할 것. 둘째, 주기적으로 메타-LLM에게 트레이스를 리뷰시켜 스키마와 프롬프트를 개정하는 루프를 만들 것. 셋째, 좋은 메모리 결정 예시를 따로 축적해서 프롬프트나 파인튜닝 자산으로 쓸 것.

10. 근데 한계는 분명히 봐야 함. 검증 환경이 게임(Crafter, MiniHack, NetHack)이라 실무 도메인 일반화는 미검증임. 외부 루프가 Gemini 3.1 Pro급 메타-LLM을 전제로 하고, 에피소드를 여러 번 돌려야 해서 비용도 만만치 않음.

11. 그래도 방향은 유효함. 개인 비서, 다중 세션 작업, 장기 추론 같은 곳에서 메모리 최적화가 모델 스케일보다 저렴한 경쟁력이 될 가능성이 높음. 비싼 모델로 올리기 전에 메모리 설계부터 점검하라는 결론임.
