Claude Code, Codex, OpenClaw 같은 하네스 없이 에이전트는 제 역량을 못 냄. 근데 그 하네스가 RL 기반 end-to-end 훈련을 극도로 어렵게 만든다는 사실은 잘 안 알려져 있음. OpenForge RL은 이 문제를 프록시 + 오케스트레이터 두 개의 가벼운 컴포넌트로 푼 최초의 오픈소스 프레임워크임.

1. 문제 구조부터. 실사용 환경의 하네스는 단순 API 래퍼가 아니라 서브에이전트를 spawn하고 MCP 서버와 통신하고 GUI를 제어하는 상태를 가진 다중 프로세스 시스템임. 근데 veRL, Slime, OpenRLHF 같은 기존 RL 프레임워크는 단일 모델 호출이나 간단한 코드 실행을 가정함.

2. 그래서 연구자들은 훈련용으로 하네스를 단순화해 재구현해왔음. 결과는 훈련-배포 불일치. 모델은 단순화된 훈련 환경에선 잘하는데 실제 배포 하네스에서 성능이 떨어짐. 클로즈드 시스템(GPT-4+Codex, Claude+Claude Code)만이 실 하네스 훈련을 보유한 격차가 계속 벌어졌음.

![OpenForge RL 개요](/images/2026-07-27-openforge-rl-harness-native-agent-training/fig-1-p1.png)

3. 해법의 첫 조각은 경량 프록시임. 하네스가 LLM에 보내는 호출을 가로챔. 하네스의 자체 추론 로직은 그대로 돌게 놔두고, prompt-response 쌍을 기록해서 표준 RL 훈련 샘플로 변환함. 하네스 내부를 수정할 필요가 없으니 어떤 하네스든 그대로 씀.

4. 두 번째 조각은 Kubernetes 오케스트레이터임. 각 롤아웃을 자체 컨테이너에서 실행함. 훈련 노드와 롤아웃 환경이 분리되니 스케일링 문제가 풀리고, 클라우드에서 탄력 확장이 되고, 도구·브라우저·데스크톱 같은 서로 다른 환경을 동시에 지원함.

![프록시 + 오케스트레이터](/images/2026-07-27-openforge-rl-harness-native-agent-training/fig-2-p4.png)

5. 설계의 요점은 훈련과 추론의 분리임. 하네스를 바꾸지 않고 LLM 호출 경로만 가로채서 RL 엔진으로 라우팅하는 것. any harness × any environment × 표준 RL 코드베이스 조합이 성립함.

6. 결과. 도구 에이전트 OpenForge-Claw(30B-A3B MoE)가 ClawEval pass@3 55.9, MCPAtlas 28.1. GUI 에이전트 OpenForge-GUI(8B)는 OSWorld-Verified 37.7, WebVoyager 72.3으로 몇 배 큰 모델과 맞먹거나 능가함. 훈련 데이터는 수백~수천 태스크에 불과했음.

7. 제일 흥미로운 발견은 하네스 선택이 에이전트 행동을 결정한다는 것임. ZeroClaw, OpenClaw, Codex 세 하네스로 같은 모델을 훈련해 비교함. 더 단순하고 정렬된 하네스일수록 학습이 쉬움. 복잡한 하네스는 탐색 공간을 넓혀 RL 수렴을 어렵게 만듦.

8. RL의 효과 방향도 명확함. 자기 검증, 도구 커버리지, 다단계 계획 완료율이 전반 개선됨. 근데 에러 복구는 여전히 약함. RL로 학습하기 가장 어려운 능력 중 하나라는 게 저자들의 판단임.

![SFT vs SFT+RL](/images/2026-07-27-openforge-rl-harness-native-agent-training/fig-5-p10.png)

9. 실무 채점. 이 발견은 하네스 설계에 바로 적용됨. 에이전트 훈련을 염두에 둔다면 하네스를 단순하고 일관되게 유지할 것. 복잡도는 탐색 공간을 늘려 학습을 방해함. 그리고 에러 복구 능력은 RL에 맡기지 말고 별도 타겟(재시도 로직, 복구 스킬 주입)으로 다룰 것.

10. 데이터 문제도 함께 풀었음. 도구/GUI 영역은 코딩과 달리 훈련 태스크가 부족함. 그래서 자동 태스크 합성 파이프라인을 제공함. 웹/X API에서 시나리오 후보 생성, 품질 필터링, Docker 환경과 검증 스크립트 자동 구축, 오픈 LLM/VLM으로 태스크 테스트, 결함 패치 순임. GUI 태스크까지 Xvfb 가상 디스플레이로 확장됨.

![데이터 합성 파이프라인](/images/2026-07-27-openforge-rl-harness-native-agent-training/fig-3-p5.png)

11. 이 파이프라인 자체가 재사용 가치가 큼. 자동화 에이전트를 자체 훈련하려면 태스크와 검증 스크립트가 같이 생산되는 구조가 필요한데, 그 틀을 그대로 베낄 수 있음. 태스크 후보 → 필터 → 환경 구축 → 테스트 → 정제의 5단계임.

12. 한계. GUI 점수가 절대값으로 높은 건 아니고 벤치마크 의존 검증임. 그리고 하네스별 행동 차이가 좋은 쪽인지 나쁜 쪽인지 판단하는 기준은 아직 연구 과제로 남아 있음.

13. 그래도 의미는 큼. 오픈소스 연구자도 자기가 쓰는 하네스에서 end-to-end 훈련이 가능해진 것. 하네스-모델 공동 최적화가 대기업 전용이 아니게 된 첫 인프라라는 점에서 격차를 좁히는 출발점임.
