메모리 기반 자기개선 에이전트가 실제로는 취약하다는 재평가가 나왔음. 실행 분산이 24개 케이스 중 17개(71%)에서 오히려 커졌고, 태스크 순서만 섞어도 +1.5% 개선이 -4.5% 하락으로 뒤집힘. 내 자기개선 루프 평가 방식을 고치게 되는 논문이라 정리함.

1. 배경. AWM(Agent Workflow Memory)과 RBank(ReasoningBank)라는 대표적 메모리 기반 자기개선 방법을 Salesforce가 GPT-5-mini로 다시 돌림. WebArena 812, VisualWebArena 910, SCUBA 267 태스크. 근데 시작점이 이미 다름 — 메모리 없는 기본 에이전트가 WebArena 55.3%로 리더보드 최고 성적급. 예전 논문들의 이득이 약한 모델 기준이었다는 것.

2. 발견 1. 자기개선 루프가 분산을 키움. 메모리 없는 에이전트도 3회 반복에 최고/최저 격차가 4.4~6.7%까기 벌어지는데, 자기개선을 얹으면 71% 케이스에서 분산이 더 커짐. GitLab 격차가 4.4% → 7.8%. 이유는 구조적 — 메모리 생성이 이전 태스크에 조건화돼 있고 샘플링도 확률적이라 초반 무작위성이 누적되어 실행마다 다른 메모리 상태로 수렴함.

3. RBank의 평균 +1.5% 개선은 3회 실행 기준 p-value 0.23. 통계적으로 유의하다고 말하기 어려움. 단일 실행 리더보드가 얼마나 위험한지의 수치화임.

4. 발견 2. 태스크 순서에 함정이 있었음. 기본 순서(작은 ID부터)의 통과율 이동평균이 초반 75%에서 ID 150 넘으며 40% 아래로 떨어짐 — 어노테이터가 쉬운 태스크부터 만든 부작용으로 사실상 easy-to-hard 커리큘럼이 순서에 박혀 있었던 것. 자기개선 방법은 쉬운 태스크에서 성공 경험을 먼저 쌓으니 이 순서가 은밀한 성공 전제였음.

5. 셔플하면 무너짐. 기본 순서 54.8%가 Shuffle-1 + AWM 49.1%, RBank 49.8%. "메모리가 있으면 최악에도 기본 수준은 유지할 것"이라는 상식이 깨짐. 실사용 환경에서 요청이 커리큘럼 순서로 들어오는 일은 없다는 게 이 결과의 무게임.

6. 원인 분석이 제일 흥미로움. 에이전트가 실제로 쓴 메모리를 수작업으로 뜯어봤더니 — 브라우저만 가능한 환경인데 API를 쓰라는 메모리가 계속 생성돼 있었음. 실행 불가능한 전략인데 그럴듯해서 뱅크에 쌓이고 검색되고 에이전트를 흔듦. "사용자에게 확인 요청" 메모리도 환경이 지원 안 해서 타임아웃까지 반복함.

7. 메모리의 전염이 특히 위험함. 지도 태스크에서 하버사인 공식으로 직접 거리를 계산하는 우회 전략이 한 번 메모리에 들어가면, 가끔 정답을 맞추기 때문에 점점 더 자주 검색되고 재사용됨. 가끔 맞는 나쁜 전략이 스스로 증식하는 구조. 논문 표현 그대로 "검증되지 않은 가설(unverified hypotheses)이지 진짜 교훈이 아님".

8. 완화 실험. 메모리 생성 단계에 태스크 루브릭(+Rub), 환경 피드백(+Env), API·사용자 확인 금지 프롬프트(+PMod)를 추가했더니 셋 다 쓰면 Shuffle-1에서 49.8% → 52.7%. 하락분의 약 31% 회복. 근데 여전히 기본 에이전트보다 낮음 — 나머지 69%는 열린 문제.

9. 여기서 내 평가 관행 점검. 내 자동화 개선 보고는 몇 번의 실행인가. 1회 실행으로 A안이 B안보다 낫다는 결론을 내고 있으면 그 차이는 노이즈일 확률이 높음. 최소 3회 실행 + 태스크 순서 셔플은 이제 기본. 그리고 개선이 커리큘럼 순서(쉬운 것부터) 덕이 아닌지 확인할 것.

10. 메모리 검증 레이어의 필요성이 실무 교훈임. RAG에 넣는 문서는 검수하면서 에이전트가 스스로 쓰는 메모리는 검수 없이 재사용함. 가끔 맞는 나쁜 전략이 제일 위험하니 메모리에 "실행 가능성" 필터와 "성공률 추적"을 붙일 것. 하버사인처럼 가끔 성공하는 메모리를 정리하는 게 Skill-α의 Merge/Prune 교훈과 같은 맥락임.

11. 환경 제약을 명시하는 것만으로 실패 메모리가 줄어듬. "이 환경은 브라우저만 된다", "API 호출 불가" 같은 제약을 메모리·반성 프롬프트에 박아넣는 것 — 논문의 +PMod에 해당하는 저비용 조치임.

12. 결론. "스스로 좋아지는 에이전트"를 믿기 전에 물어볼 것 세 개. 몇 번의 실행인가, 어떤 순서로 태스크가 들어왔나, 메모리에 실행 불가능한 가설이 쌓여 있지 않은가. 근데 이 검증 부담이 자기개선의 이득보다 클 수도 있다는 것 — 그 계산까지가 도입 판단이라는 결론임.
