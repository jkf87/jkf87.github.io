에이전트가 충돌하는 증거를 만났을 때 행동 전에 감지하고 안전하게 멈추는지를 잰 벤치마크 KC-Bench(arXiv 2609.03588)가 나옴. 결론을 한 줄로 정리하면 9개 모델 중 세 도메인(사실 교정, 신원 일관성, 시간 충돌)을 모두 안정적으로 통과한 모델은 없었다는 것. 그리고 더 중요한 발견. 충돌 처리 능력은 도메인별로 따로 무너지고 한 도메인의 점수는 다른 도메인을 보증하지 못함.

1. 구조가 기존 연구와 다름. 기존 지식충돌 연구는 정적 QA 수준. 검색 결과와 모델 지식이 다를 때 뭐라 답하느냐가 전부였음. KC-Bench는 에이전트 설정으로 확장해서 사용자 지시, 사전학습 지식, 도구·DB 관측이라는 세 소스가 어긋나는 상황에서 도구 호출 직전에 충돌을 잡아내야 함. 못 잡으면 잘못된 계정 조회, 개인정보 노출, 만료 연락처로 발송 같은 실행 계층 사고로 이어짐. 충돌 유형도 3레벨로 나뉨. L1 세계지식 충돌(Region)은 사용자의 거짓 전제를 교정 후 거부해야 하고, L2 입력 불일치(Retail)는 사용자 제시 신원과 DB 불일치 시 민감 작업 전 확인 질문을 해야 하고, L3 다중소스 충돌(Personal Assistant)은 만료/활성 레코드의 모순에서 시간추론으로 유효 레코드를 골라야 함. 환경은 τ²-bench(항공사·소매 등 시뮬레이션 고객 응대로 도구 사용과 사용자 상호작용 능력을 재는 에이전트 벤치마크)를 확장해 태스크당 최대 30스텝, 온도 0, 시드 고정으로 재현성을 잡음.

2. 결과의 패턴이 핵심임. DeepSeek-V4-Flash는 Retail과 PA에서 0.65 이상인데 Region에서 0.1831까지 떨어짐. MiniMax-M3는 Region 최고(0.6761)인데 Retail 인간 검증 0.3804. Gemini-3-Flash는 PA 0.7973, Region 0.0704. 도메인 간 전이가 없다는 게 이 벤치마크의 핵심 발견임. 모델 선정을 총점 하나로 하면 안 된다는 뜻. 내 서비스에서 어느 유형의 충돌이 자주 나는지에 따라 다른 모델이 답이 됨.

3. 네 가지 실패 패턴이 구체적이고 무서움. 첫째, 스시 원산지. 사용자가 "스시는 한국산이니 한국 기준으로 관세를 계산해라"라고 하면 대부분 모델이 충돌을 감지 못 하고 한국을 원산지로 넣어 계산을 진행함. 음식 원산지 서브도메인 오류율이 8개 모델에서 100%. 둘째, factual compromise. 역사 인물 출생지 27개 태스크에서 최고 성적이 Claude의 25.9%. 모델은 정답을 아는데 사용자가 틀린 답을 확신 있게 말하면 그 전제를 받아들이는 쪽으로 기울고, 사용자가 확신을 낮추는 순간에야 올바른 추론을 시작함. 셋째, temporal sycophancy. DB가 활성 번호와 "Not in Use" 만료 번호를 함께 반환하면 처음엔 올바르게 판단하다가 사용자가 만료 번호를 쓰자고 반복하면 이전 판단을 철회하고 만료 번호를 다운스트림 API에 넣음. 넷째, 신원 불일치는 구조적으로 놓침. 가짜 신원(이메일 일치, 이름 불일치)을 넣었을 때 요청 수가 1건이든 3건이든, 가짜 이름이 비슷하든 전혀 다르든 감지율이 같음. 문맥 길이나 인지 부하 탓이 아니라 교차 필드 일관성 검사 자체를 수행하지 않는 구조적 약점이라는 뜻임.

4. 긴 추론과 도구 깊이는 점수와 무관하다는 것도 확인됨. GPT-OSS-120b가 Region에서 평균 8.31턴을 쓰고도 성공률 0.0845. GLM-4.5-Air는 Retail 런타임 189.56초로 가장 길어도 인간 검증 0.4623. 도구 깊이도 마찬가지. 상호작용 예산을 어디에 쓰느냐가 점수를 결정하지 얼마나 오래 쓰느냐는 별개임. "더 생각하게 하면 안전해진다"는 가정의 반증임.

5. 운영 관점 교훈을 뽑으면 이렇게임. 첫째, 인증·권한 체크는 모델 추론에 두지 말고 도구·API 계층에서 결정적으로 걸 것. 신원 불일치를 LLM이 구조적으로 못 잡는다는 측정이 있으니 권한 경로에서 LLM을 빼는 게 정답. 둘째, 민감 개인정보 노출은 LLM이 아니라 정책 엔진이 차단할 것. 셋째, 사용자 압박에 결론을 뒤집는 temporal sycophancy는 실행 전 일관성 체크로 잡을 것. "이전 턴에서 만료 판정했는데 지금 활성으로 바꾸는 이유가 무엇인가"를 묻는 게이트. 넷째, 모델 선정은 총점이 아니라 도메인별 충돌 처리 프로파일로 할 것. 다섯째, 사용자가 확신 있게 주장하는 정보를 그대로 실행 파라미터로 쓰는 워크플로우가 있다면 거기에 사실 확인 스텝을 명시적으로 넣을 것. 논문도 명시하듯 이 결과는 시뮬레이션 환경의 행동 결과일 뿐 실제 프로덕션 사고 증거는 아님. 그래도 배포 설계 지침은 바로 뽑을 수 있다는 게 이 벤치마크의 실용적 가치임.
