긴 에이전트 작업을 돌리면 워크스페이스 히스토리가 컨텍스트 창을 넘음. 지금 대부분의 에이전트 시스템은 컴팩션(요약)이나 텍스트 검색으로 대응하는데 [KVMem](https://arxiv.org/abs/2609.04852)은 문제 정의 자체를 바꿈. 히스토리가 실행 뷰를 벗어날 때 이미 KV 상태로 인코딩돼 있으니 버리는 게 아니라 페이징해두고 필요할 때 복원하면 된다는 것. 운영체제의 가상 메모리를 KV 캐시에 적용한 발상임. 이 질문은 한번 들으면 당연해 보여서 정리함.

1. 기존 방식의 문제가 명확하게 정리돼 있음. 컴팩션은 나중에 뭘이 중요해질지 모르는 시점에 미리 버리는 결정이라 초기 파일의 한 문장이나 툴 출력의 값 하나가 나중에 크리티컬이 되면 복구할 방법이 없음. 서로 다른 두 히스토리가 같은 요약으로 매핑되면 구분 자체가 불가능하다는 논증도 깔끔함. 그리고 Compact+RAG는 빠진 증거를 원문으로 복구하는데 그 텍스트는 이미 한 번 prefill해서 KV를 만들어둔 내용이라 매번 재계산 비용을 다시 지불함. 1M 토큰 설정에서 pre-answer latency가 416초나 나오는 이유가 이것.

![세 가지 핵심 설계](/images/2026-09-07-kvmem-gpu-agent-workspace-virtualization/fig-1-p6.png)

2. 관측이 설계를 받침함. 실제 에이전트 롤아웃의 어텐션을 분석했더니 같은 스텝 안의 인접 윈도우 KL 발산은 평균 0.070비트인데 스텝 경계를 가로지르는 윈도우는 평균 2.59비트로 37.3배 높음. 모델의 과거 어텐션은 한 스텝 안에서 안정적이고 스텝이 바뀔 때 급변한다는 것. 그래서 워킹셋을 스텝당 한 번, prefill 직후에 갱신하고 디코딩 중에는 고정함. 그리고 어텐션이 희소해서 윈도우당 top-8 블록이 전체 과거 어텐션의 66.5%, top-16이 77.0%를 차지함. 전체를 상주시킬 필요 없이 작은 세트만 잘 고르면 된다는 것.

![스텝 경계 어텐션 관측](/images/2026-09-07-kvmem-gpu-agent-workspace-virtualization/fig-2-p7.png)

3. 검색 인덱스도 재치있음. 백만 토큰의 모든 KV를 스캔하면 안 되니 32토큰 블록 단위로 나누고 각 블록을 K 벡터의 평균(Mean-K) 하나로 요약한 인덱스를 만듦. RoPE 위치 인코딩을 제거한 position-independent K를 쓰고 검색 시점에는 현재 쿼리 벡터와 후보 블록의 Mean-K를 어텐션 공간에서 직접 스코어링함. 별도 임베딩 모델이 아니라 서빙 모델 자신의 어텐션 신호로 랭킹하는 게 포인트임. 인덱스는 호스트 메모리에 두고 고정 크기 타일만 GPU로 올려서 워크스페이스가 커져도 검색의 GPU 풋프린트가 일정함.

4. 복원이 단순 페이지 로드가 아닌 것도 핵심임. RoPE가 박힌 K는 위치가 바뀌면 무효라서 position-independent raw K를 원천으로 유지하다가 새 논리 위치에 맞춰 re-RoPE함. 매 스텝 바뀌는 쿼리 의존 서브셋을 새 컴팩트 위치로 재매핑하는 실행 모델은 vLLM·LMCache·CacheBlend 어느 추상화에도 없어서 저자들이 C++/CUDA 네이티브 엔진을 직접 구현했다는 것. 선행 stage-out, 워킹셋 겹침 활용 페이지 재사용, 블록 패킹과 3단계 파이프라인 같은 구현 디테일도 견고함.

![패킹+파이프라인](/images/2026-09-07-kvmem-gpu-agent-workspace-virtualization/fig-3-p9.png)

5. 결과. AgentLongBench 1M 토큰에서 KVMem의 지연시간이 0.73초인데 Compact+RAG는 416.38초. fresh prefill이 0.08K 토큰인데 RAG는 31.00K 토큰. 텍스트로 다시 집어넣는 경로를 아예 안 타서 나오는 숫자임. 그리고 눈에 띄는 관측 하나. ≤256K 설정에서 KVMem이 60.87%로 Full Context(59.54%)보다 오히려 높음. 전체 컨텍스트를 다 보여주면 롱컨텍스트 성능 저하가 생기는데 쿼리 관련 서브셋만 노출하면 그 저하가 부분 완화된다는 것. 전부 보여주는 게 최선은 아니라는 관점의 시스템 레벨 근거임.

6. 실전 평가도 있음. DeepSWE 첫 16과제 × 4샘플에서 Qwen3.8-27B + Claude Code 하네스로 Pass@1 43.8%→48.4%, Pass@4 81.3%→93.8%. 평균 prefill 시간이 211.5초에서 95.0초로 2.23배 단축되고 디코딩 토큰도 18.7% 감소함. 그리고 노트북에서 1M 토큰. 24GB RTX 5090 Laptop에서 vLLM은 약 10K, llama.cpp는 약 80K가 한계인데 KVMem은 실행 뷰 80K는 llama.cpp와 동일한 채로 가상 워크스페이스를 1M 토큰까지 키우면서 약 50 tokens/s를 유지함.

7. 한계도 솔직함. 가상화되는 건 주소 가능한 워크스페이스지 한 번의 모델 호출이 attend하는 토큰 수가 아니고, 재사용한 과거 KV는 원래 자기 인과 컨텍스트에서 계산된 것이라 새 컨텍스트 재계산과 수학적으로 동등하지 않음. KV 상태는 텍스트보다 훨씬 커서 스토리지 용량과 재사용 가능한 모델 상태를 바꾸는 트레이드오프임. 그리고 저수준 제어가 필요해서 블랙박스 API 위에는 얹을 수 없고 클라우드 서빙 통합은 남은 과제임.

8. 내 해석. 긴 컨텍스트 논의는 대부분 프롬프트/요약 레이어에서 일어났는데 KVMem은 그 아래 시스템 레이어에서 문제를 다시 정의함. 당장 API 기반 에이전트에는 못 쓰지만 "컨텍스트가 넘치면 요약"이라는 디폴트 가정을 다시 보게 한다는 점에서 의미가 있음. 로컬 추진파이프라인을 운영하는 사람이라면 눈여겨볼 방향임. 코드는 [GitHub](https://github.com/kvmem/kvmem-qw3)에 공개돼 있음.
