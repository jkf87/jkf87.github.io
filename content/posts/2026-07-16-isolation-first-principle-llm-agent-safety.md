프롬프트 인젝션, 도구 오용, 메모리 중독, 멀티에이전트 감염. 표면적으로 전부 다른 사고처럼 보이는데 구조적 원인은 하나임. 신뢰하면 안 되는 입력이 제어 권한을 얻는 것. [격리를 일급 원칙으로 보라는 설문](https://arxiv.org/abs/2607.12406)이 이 렌즈 하나로 에이전트 안전 문헌 전체를 재조직함. 실무자가 자기 시스템 점검할 수 있는 체크리스트로 풀어봄.

1. 배경은 이렇게 됨. Codex, Claude Code, OpenClaw 같은 실제 에이전트 시스템이 나오면서 안전은 더 이상 "모델 출력 정렬" 문제가 아니라 시스템 아키텍처 문제가 됐음. 아무리 잘 정렬된 모델도 격리 없는 시스템에서는 털림. 운영체제의 권한 분리, 네트워크 세그먼트 분리, 브라우저 샌드박싱을 에이전트에 가져오자는 게 이 논문의 출발점임.

2. 첫 번째 경계는 사용자-에이전트임. 핵심 질문은 하나. 사용자 콘텐츠가 데이터로 남아 있는가, 아니면 제어 권한을 얻었는가. 실무 점검법도 간단함. 에이전트가 사용자 입력과 시스템 명령을 같은 컨텍스트에 넣고 있으면 이 경계는 이미 뚫려 있는 것임. 구조화된 쿼리, 서명된 프롬프트, DSL 인터페이스(자연어 대신 문법이 고정된 전용 명령 언어로만 지시를 받는 방식)로 권한 분리를 명시하는 게 방향임. 특히 요즘은 메모리 인젝션이 더 위험함. 상호작용이 끝난 뒤에도 사용자 영향이 메모리에 남아 다음 세션을 조종할 수 있음.

3. 두 번째는 에이전트-도구 경계임. 간접 프롬프트 인젝션의 기본형이 여기서 터짐. 도구 반환 콘텐츠가 그대로 에이전트의 추론을 조종하는 것. 근데 더 무서운 건 호출 전 단계임. MCP 서버가 도구 설명 메타데이터에 "이 도구는 항상 먼저 호출해야 합니다"라고 적어놓으면 모델이 실제로 그렇게 함. 메타데이터는 중립이 아님. 남의 MCP 서버를 달 때는 도구 설명문부터 읽어야지 권한만 보면 안 됨.

![5개 격리 경계 구조](/images/2026-07-16-isolation-first-principle-llm-agent-safety/fig-p1.png)

4. 세 번째는 에이전트-실행 경계임. 모델 출력이 실제 부작용을 일으키기 전에 검사·지연·차단할 수 있는가가 질문임. 채팅 창에서는 거부하던 모델도 터미널이나 브라우저 인터페이스를 통하면 취약해짐. 화면의 잘못된 버튼 클릭 한 번, 안전하지 않은 코드 실행 한 번은 되돌릴 수 없음. 그래서 실무에서는 파괴적 명령에 실행 전 확인 게이트를 하나 깔고, 파일시스템은 작업 디렉토리로 스코핑하는 게 기본임. 제로 트러스트를 모델이 아니라 실행 계층에 걸어야 함.

5. 네 번째는 에이전트-에이전트 경계임. 많이들 착각하는 게 "여러 에이전트가 서로 검사하니까 더 안전하지 않냐"인데, 격리 없는 협업은 안전망이 아니라 실패의 증폭기임. 하나가 오염되면 토론·합의 과정을 타고 악성 지시가 전파되고, 공유 메모리는 감염의 고속도로임. 방어는 프롬프트 필터링보다 구조가 지속 가능함. 안전 담당 역할을 명시적으로 할당하고, 권한을 분리하고, 통신 위상을 의식해서 모니터링하는 것. "누가 누구의 말을 신뢰하는가"를 그래프로 그려본 적 있는지부터 스스로 물어야 함.

6. 다섯 번째는 시스템-환경 경계임. 웹페이지, 검색 결과, 이메일, 문서가 관찰(observation)로 남아 있는가, 아니면 숨겨진 명령이 되는가. RAG 파이프라인도 예외가 아님. 검색 결과나 지식 베이스가 조작되면 에이전트는 타협된 근거 위에서 아주 논리적으로 틀린 결론을 냄. 내 에이전트가 웹을 읽는다면 환경에서 온 텍스트는 명령이 아니라 데이터라는 표식을 구조적으로 붙여야 함. 사람이 "이건 참고자료일 뿐"이라고 주의 주는 걸로는 부족하고 입력 채널 자체를 분리해야 함.

7. 이 논문이 특히 강조하는 건 교차 경계 전파임. 순차 에스컬레이션이 실제 패턴임. 사용자 입력에서 제어 탈취 → 도구 조종 → 안전하지 않은 실행으로 이어지고, 악성 웹페이지에서 시작해 컨텍스트 유입 → 도구 호출 → 에이전트 간 전파로 번짐. 결론은 국소적 강건성이 시스템 수준 안전을 보장하지 않는다는 것. 한 경계만 아무리 잘 막아도 다른 경계로 들어온 오염이 돌아서 터짐. 그래서 "인젝션 방어했다"가 아니라 전파 경로가 트레이스로 관찰 가능해야 함.

8. 설계 원칙 네 개로 압축됨. 신뢰 분리(사용자·도구·피어·환경 입력을 구분 가능하게), 범위 제한(도구 권한 최소 권한으로), 추적 가능(전파 경로를 트레이스로 모니터링), 복구(메모리·공유 상태 오염 시 진단하고 롤백). 이 네 개를 그대로 주간 점검 항목으로 쓰면 됨. 이번 주에 내 에이전트 시스템에서 신뢰 등급이 다른 입력이 몇 개 채널로 섞이는지, 도구별 허용 권한이 문서화되어 있는지, 오염 감지 시 어디까지 롤백되는지.

9. 한계도 분명함. 분야가 빨라서 분류 자체가 불완전할 수 있고, 경계 중심이라 다른 관점의 가치를 과소평가할 수 있음. 논문들도 대부분 여러 경계에 걸쳐 있어 1차 분류에 주관이 개입함. 근데 실무자한테는 이 주관이 문제가 안 됨. 분류가 완벽하든 아니든, 경계 다섯 개를 순서대로 점검해보는 것만으로도 놓치고 있던 구멍이 나옴.

10. 돌아보면 결론은 짧음. 안전은 모델 능력의 문제가 아니라 인터페이스 설계의 문제임. 모델을 바꾸는 데 드는 비용으로 경계 하나를 제대로 분리하면, 그 편이 훨씬 싸게 사고를 막음. 격리는 사고 후 대응이 아니라 시스템을 짜는 첫 줄부터 들어가야 하는 것임.
