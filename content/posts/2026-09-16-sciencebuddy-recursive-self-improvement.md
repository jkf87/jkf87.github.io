과학 연구 에이전트의 문제의식은 이것임. 대화 안에서 답을 고치는 것과 다음 작업에서 실제로 더 잘하는 것은 다름. [ScienceBuddy](https://arxiv.org/abs/2609.17523)는 협업 기록을 지속 가능한 개선으로 바꾸는 구조를 제안하는데 핵심은 하네스 개선과 모델 강화학습을 중첩 루프로 묶었다는 것. 하네스만 바꿔도 검증 정확도가 31.1%에서 51.1%로 올라갔고 모델 RL만으로도 커버리지가 48.3%에서 67.8%로 늘었다는 분리 측정이 이 논문의 뼈대임. 앞서 정리한 Co-Harness와 같은 문제의식을 4B 소형 모델로 검증했다는 점이 의미 있어 정리함.

1. 재료 추출이 먼저임. 협업 기록에서 두 가지를 뽑음. 요청·실행 기록·산출물을 재구성해서 instruction, 입력 자산, 실행 환경을 갖춘 태스크로 패키징하는 것. 그리고 작업 범위, 방법론 요구, 근거, 산출물 기준을 항목별 가중치로 구성한 평가 루브릭. 루브릭은 대화에서 자동 구성되지만 연구자 승인을 정답 레이블로 쓰지 않는다는 원칙을 지킴. 채점은 실행 가능한 체크와 고정 판정 모델이 담당함. 앞서 정리한 PARL과 이어지는 원칙인데, 사용자 피드백은 루브릭 재료이지 정답이 아니라는 것.

![전체 구조](/images/2026-09-16-sciencebuddy-recursive-self-improvement/fig-2-p2.png)

2. 내부 루프, 하네스 진화가 설계의 정수임. 작업 모델을 고정하고 고정 보조 모델이 최근 궤적과 루브릭 평가를 진단한 뒤 하네스에 한 항목씩 bounded edit을 제안함. 스킬 하나 추가/삭제/수정, 명령 수정, 컨텍스트 설정 변경 중 하나만. 그리고 부모-후보를 동일한 개발 태스크·시드·예산에서 짝 평가해서 유효하고 점수 차가 양수일 때만 수용하고 동점이면 부모를 유지함. 한 번에 한 항목만 바꾸고 짝 평가로 가리니 무엇이 시스템을 좋게 만들었는지 추적 가능함. 프롬프트 전체를 통째로 재작성하는 방식과의 결정적 차이임.

3. 외부 루프, 모델 RL. 선택된 하네스를 고정하고 환경 난이도를 파일럿 실행으로 보정한 뒤 루브릭 기반 보상으로 GRPO 업데이트를 수행함. 새 모델이 나오면 상속된 하네스를 새 모델로 재평가 후 배포함. 각 사이클은 내부 탐색 10스텝 + RL 20업데이트이고 논문은 3사이클을 실행했으며 도구와 실행 인프라, 루브릭, 평가기는 루프 중에 바뀌지 않음. 무엇을 고정하고 무엇을 움직일지 명시한 것 자체가 좋은 설계의 조건이라는 걸 다시 보여줌.

4. 숫자. 하네스만 바꿨을 때 검증 정확도 31.1%→51.1%(+20.0pp), 적응 배치 24회 동안 최고 배치 정확도 75.0%. 선택된 하네스에 남은 것은 명령 4개와 scoped 스킬 9개로 Python 실행·스키마 검사·기록 조회·명시적 답 제출 절차였음. 진짜 필요한 게 몇 개 안 된다는 것. 모델 RL만 적용했을 때는 약 2시간 만에 커버리지 48.3%→67.8%. 두 루프를 3사이클 돌면 훈련 전후 비교에서 정답 42.2%가 73.3%로 이동하고 새로 풀게 된 문제가 33.3%, 더 이상 맞추지 못한 문제는 2.2%에 불과함. 회귀가 거의 없는 개선이라는 것.

![3사이클 학습 동향](/images/2026-09-16-sciencebuddy-recursive-self-improvement/fig-1-p1.png)

5. 내 해석. 하네스 개선과 모델 RL이 직교하는 이득을 낸다는 게 분리 측정으로 명확해진 논문인데, 실질적 장점은 개선 단위가 명시적이고 평가 가능하다는 점임. 주의할 점도 분명함. 진단·편집에 GPT-6 Astra라는 별도 보조 모델이 필요하고 루프마다 짝 평가와 RL 예산이 듦. 개인 규모 하네스에 바로 적용하기엔 비용이 만만치 않음.

6. 내 적용. 파인튜닝 없이 가져갈 것은 내부 루프의 형태임. 하네스(내 경우엔 스킬과 명령) 수정은 한 번에 한 항목만, 짝 평가로 수용/기각, 동점이면 현행 유지. 이 세 규칙만 코드화해도 "뭘 고쳤는데 좋아진 건지 모르는" 개선 사고에서 벗어날 수 있음. 그리고 최종 하네스가 명령 4개 + 스킬 9개였다는 결과는 자극적임. 내 스킬 뱅크가 몇 개인지 생각하면 정리의 기준이 되는 숫자임.
