ReAct 에이전트에서 실질 추론은 Thought 단계에서만 일어남. Action 직렬화와 Observation 대기 동안엔 추론이 정지함. Second Thought(arXiv 2608.13667, SMU)는 이 반복 구간을 reasoning idle window로 formalize하고 거기에 미래 턴을 위한 보조 추론을 병렬로 돌림. 결론부터. 정확도를 유지하면서 추가 추론을 임계경로 밖으로 이동시켜 턴 수와 지연시간을 줄이는 학습 불필요 프레임워크임.

1. 왜 기존 병렬 추론과 다른가가 설계의 출발점임. 셀프컨시스턴시, Tree-of-Thought 같은 방법은 Thought 내부에서 경쟁 후보를 수평으로 샘플링해서 병합 시 투표·정렬이 필요함. 반면 이 윈도의 보조 추론은 두 제약 아래 있음. 이미 결정된 행동은 바꿀 수 없어서 트라젝토리에 조건화되어야 하고, Observation 도착이라는 외부 데드라인 때문에 중단에 강해야 함. 이 두 제약이 설계를 결정했다는 게 논문의 논리임.

2. 구조가 단순함. Thought가 끝나는 순간 같은 모델이 트라젝토리 스냅샷을 이어받아 네 개의 보조 브랜치를 fork함. Observation이 도착하면 브랜치를 전부 종료하고 생성된 생각을 다음 턴 컨텍스트 끝에 병합함. 네 브랜치의 역할이 정해져 있음. Check는 현재 계획의 전제 검증, Recall은 트라젝토리 초반의 제약·맥락 재소환, Rehearse는 다음 단계 예행, Alternative는 현재 계획 실패 시 대안 초안. 경쟁 후보가 아니라 같은 트라젝토리를 보는 보조 관점이라서 이어붙이는 것으로 병합이 끝남. 프리픽스 KV 캐시를 메인 스레드와 공유해서 비용 효율도 확보됨.

![Second Thought 전체 워크플로우](/images/2026-09-05-second-thought-idle-window-parallel-reasoning/fig-2-p3.png)

3. 원자적 사고 설계가 중단 강건성을 만듦. 윈도 길이는 Observation 도착 시점에 따라 결정돼서 예측 불가능함. 그래서 각 브랜치는 서로 의존하지 않는 원자적 사고 단위로 출력함. 임의 시점에서 중단돼도 진행 중인 단 하나만 버리고 완료된 사고는 그대로 씀. 데드라인이 불확실한 병렬 작업의 표준 패턴을 LLM 추론에 이식한 것임. Figure 1 예시가 직관적임. vanilla ReAct는 하위 호환 제약을 위반해서 되돌리기 비용을 지불하는데 Second Thought는 대기 시간에 생성된 제약 회상과 대안 준비가 그 실수를 사전에 차단함.

![버그 수정 태스크 비교](/images/2026-09-05-second-thought-idle-window-parallel-reasoning/fig-1-p2.png)

4. 결과. 턴 수는 9개 모델-벤치마크 조합 전부에서 감소. 메인 스레드 디코딩은 6개 조합에서 유의하게 감소했고 최대 43%(36.5k → 20.8k 토큰). Pass@1은 7개 조합에서 유의차 없음, 2개에서 +12.4점과 +10.2점 상승. 유일한 하락은 150개 중 1문제 차이로 유의하지 않음. 그리고 결정적인 대조가 있음. 같은 계산 예산을 메인 스레드 추론에 배치하는 대조군(budget forcing)과 비교하면 적용 4개 설정 전부에서 Second Thought가 더 높은 Pass@1을 기록하면서 순차 디코딩은 1.3~3.2배 적게 씀. 같은 예산이라면 메인 라인에 넣기보다 윈도에 분산하는 편이 낫다는 해석이 가능함.

5. ablation이 네 브랜치의 역할 분해를 줌. 검증 없는 맥락 회상만으로는 부족하고(only-recall 46.0% 하락), 과거 제약의 재소환이 같은 실수 반복을 방지하고(w/o-recall 최대 하락), Rehearse는 다음 단계 고민을 미리 끝내는 역할(w/o-rehearse 시 토큰 +10%). 전체 구성이 파레토 최적. 더 적은 토큰을 쓰는 변형은 정확도를 희생함. 커버리지도 측정됐는데 수확 턴이 전체의 28.7%지만 그 턴이 아이들 타임의 86.7%를 차지하고 96.5%의 태스크가 최소 1회 세컨드 사고를 받음.

![절제 실험](/images/2026-09-05-second-thought-idle-window-parallel-reasoning/fig-3-p6.png)

6. 지연시간 검증이 성실함. 토큰 절약이 실제 시간으로 이어지는지 SWE-Bench Pro 50개 인스턴스를 동일 엔드포인트, 동시성 4, 3회 반복의 페어 프로토콜로 재생했더니 과제당 중간 지연이 256.9초 → 229.0초(-10.9%). 메인 디코딩 -13.4%, 도구 실행 -6.0%. 임계경로 자체가 단축됐다는 것.

7. 실무 적용 결론. 첫째, 이건 training-free라서 프롬프트와 오케스트레이션 수준으로 오늘 적용 가능함. 도구 응답을 기다리는 에이전트가 있다면 그 대기 시간에 "제약 회상, 전제 검증, 다음 단계 예행, 대안 초안" 네 가지를 병렬로 돌리는 컨텍스트 추가를 실험할 것. 둘째, 추론 예산을 늘릴 때 순차 디코딩에 쏟지 말고 idle window에 분산할 것. 같은 예산으로 정확도와 지연을 같이 잡는 길임. 셋째, 중단 가능성이 있는 병렬 작업은 원자적 단위로 출력하게 설계할 것. 넷째, 비용 인식은 필수. 보조 브랜치 4개가 병렬 디코딩하므로 API 토큰 비용과 동시성은 늘어나고 도구 응답이 빠른 환경에선 윈도 자체가 짧아서 효과가 제한될 수 있음. 도구 지연이 긴 환경일수록 이 구조의 이득이 큼.
