에이전트 하나 배포하면 공격 표면이 네 층으로 늘어남. 인프라, 도구 프로토콜, 에이전트 동작, 모델. 근데 대부분 팀은 이걸 한 가지 방법으로 전부 점검하려다 실패함. Tencent Zhuque Lab이 이 문제를 레이어별로 검증 방법을 다르게 매칭하는 방식으로 풀었고, 도구를 오픈소스로 풀었음. [논문](https://arxiv.org/abs/2606.31227)과 [AI-Infra-Guard 저장소](https://github.com/Tencent/AI-Infra-Guard)를 실무 적용 관점으로 정리함.

1. 배경부터. Ollama, vLLM, Dify, ComfyUI, MCP 서버까지 AI 인프라가 사무실 네트워크에 난립하는데 기존 웹 취약점 스캐너는 이 컴포넌트들을 카탈로그에조차 안 올림. 스캐너가 "무엇인지" 인식을 못 하니 취약점 판정은 꿈도 못 꿈. 게다가 llama.cpp처럼 b7824 같은 빌드 번호, 2.3.dev 같은 개발 스냅샷, latest 롤링 태그를 쓰는 비정규 버전 체계 때문에 semver 가정 비교기는 에러를 내거나 조용히 잘못된 판정을 냄.

2. 위협 모델 자체도 달라짐. SQL 인젝션이 아니라 인증 없는 GPU 접근으로 인한 비용 탈취, 설정 파일 노출로 인한 API 키 유출, 프롬프트 인젝션으로 에이전트 목표 하이재킹, 도구 남용이 새로운 주범임. 그래서 AI-Infra-Guard는 75개 이상 AI 컴포넌트 핑거프린트와 1,400개 이상 취약점 규칙을 갖춘 결정론적 매칭 엔진부터 깔았음. 발견 결과도 Verified, Version-based, Inferred 세 단계로 정밀도를 나눠서 "스캐너가 확신하는 것"과 "추정인 것"을 구분해 줌. 이 구분이 실무 보고서 작성할 때 거짓 양성 파이프라인을 크게 줄여줌.

![인프라 스캐닝 개요](/images/2026-07-07-ai-infra-guard-multi-layer-agent-red-teaming/fig2-infra-scan.png)

3. 두 번째 레이어는 MCP 서버 감사임. MCP 서버는 에이전트에게 파일 읽기, DB 쿼리, 명령 실행 권한을 주는 구조라, 도구 설명문이 모델의 신뢰 컨텍스트로 직접 주입됨. 도구 포이즈닝, 합법 도구를 가로채는 도구 섀도잉, 초기엔 안전하다가 나중에 악성으로 바뀌는 래그 풀까지, 전형적인 웹해킹과는 전혀 다른 위협이 있음. 여기에 정규식 규칙을 끼워맞추는 건 불가능하니, AI-Infra-Guard는 취약점 지식을 자연어 감지 기준으로 선언하는 Prompt-as-Rule 패러디임을 쓰고 LLM 에이전트 하네스가 정적 분석과 동적 테스트로 감사를 수행함.

4. 실무 포인트 하나. 감사 대상 MCP 코드 자체를 신뢰할 수 없는 입력으로 취급해서, 감사 도구가 간접 프롬프트 인젝션에 당하지 않게 설계했다는 점임. 내가 코드 리뷰용 에이전트를 돌릴 때도 마찬가지임. 남의 저장소를 읽는 에이전트는 그 내용에 조작이 들어 있을 수 있다는 전제로 격리 실행해야 함. 이 논문이 스캐너 자체 보호를 설계에 넣었다는 건 그 위협이 이론이 아니라 실제 터진다는 뜻임.

![MCP 서버 감사](/images/2026-07-07-ai-infra-guard-multi-layer-agent-red-teaming/fig3-mcp-scan.png)

5. 세 번째 레이어는 에이전트 스킬 공급망임. npm의 악성 패키지처럼, 에이전트 스킬 패키지에도 포이즈닝과 과도한 권한 요구, 임베디드 프롬프트 인젝션이 숨을 수 있음. 스킬 설치는 곧 권한 부여라는 인식부터 가져야 함. 남이 만든 스킬을 설치하기 전에 패키지 내용을 한 번 열어보는 것, 그게 새로운 npm audit임.

6. 네 번째 레이어는 배포된 에이전트의 런타임 동작임. 이건 코드를 뜯어봐야 알 수 없고 오직 다중턴 대화로 프로빙해야 드러남. AI-Infra-Guard는 4개 위험 패밀리 페이로드와 에스컬레이션 래더를 돌리고, 카나리 토큰으로 공격 성공을 검증하며, 정지 규칙으로 비용을 통제함. 내 에이전트를 배포 전에 직접 대화로 괴롭혀 보는 셈임. 이 과정을 자동화해두지 않으면 릴리즈마다 사람이 일일이 프로빙하게 됨.

![에이전트 레드팀](/images/2026-07-07-ai-infra-guard-multi-layer-agent-red-teaming/fig4-agent-scan.png)

7. 마지막 모델 레이어는 탈옥 평가 하네스임. 26개 이상 공격 오퍼레이터와 16개 데이터셋을 붙여서 단일턴·다중턴 공격을 모두 돌리고 모델 기반 판단으로 성공 여부를 결정함. 모델을 갈아끼울 때마다 이 평가를 도구 체인으로 돌리면, "새 모델이 더 똑똑해졌는데 더 쉽게 탈옥되는 건 아닌가"를 숫자로 확인할 수 있음.

8. 근데 이 전체를 한 도구로 하겠다는 발상 자체를 다시 보게 됨. 정규식으로 탈옥을 판정할 수 없고, 코드 분석만으로 인증 없는 접근 노출을 증명할 수도 없음. 레이어마다 필요한 증거 클래스가 다르니 검증 패러다임도 달라야 한다는 게 이 프레임워크의 핵심 주장임. 내 조직의 에이전트 보안 체크리스트를 짤 때도 "스캔/감사/레드팀/평가" 네 종류의 활동으로 나눠서 배정하는 게 맞음. 하나의 도구나 한 사람에게 전부 맡기는 순간 특정 레이어는 무조건 빈틈이 됨.

9. 적용 순서는 명확함. 먼저 인프라 스캔을 돌려서 노출된 AI 컴포넌트부터 찾음. 그다음 운영 중인 MCP 서버를 감사하고, 스킬 패키지를 검사하고, 배포 전 에이전트에 다중턴 레드팀을 돌리고, 모델 교체 시점마다 탈옥 평가를 반복함. Go 백엔드가 서버를 잡고 Python 모듈이 스캐닝을 하는 구조라 셀프호스팅으로 띄워서 주기 점검에 넣기도 어렵지 않음.

10. 돌아보면 핵심은 단순함. 에이전트 보안은 "한다/안한다"가 아니라 레이어별로 다른 질문을 던지는 일임. 내 인프라가 노출되어 있는가, 내 도구가 오염되어 있는가, 내 에이전트가 조종당하는가, 내 모델이 우회되는가. 질문 네 개에 점검 도구 네 개를 매핑해두면, 다음 사고 때 어느 레이어가 뚫렸는지 답할 수 있음.
