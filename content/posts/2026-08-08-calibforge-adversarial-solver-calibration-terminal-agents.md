터미널 에이전트 훈련용 태스크를 자동으로 만드는 시스템이 여럿 나왔음. TermiGen, Endless Terminals 같은 것들. 공통 검증법은 구조 검사와 자가 풀기. 근데 이 검증이 "풀 수 있는가"만 알려줄 뿐 "적절한 난이도인가"는 못 알려줌. 너무 쉬워서 전부 통과하거나 너무 어려워서 전부 실패하거나 검증 코드가 깨져 있어도 통과함. CalibForge의 출발점은 단순하고 정확함. 태스크의 학습 가치는 솔버 행동으로만 판단할 수 있다는 것.

1. 1단계는 기존과 비슷함. 웹 검색으로 버전 호환성, 의존성 충돌, 설정 함정 같은 구체적 엔지니어링 문제를 찾아 태스크 명령문, Dockerfile, 검증 테스트를 함께 만듦. 구조 검사에서는 필수 파일, 빌드, 초기 상태에서 테스트 전부 실패를 확인함. 자가 풀기로 작성 에이전트가 직접 풀어보고 통과시킴. 여기까지는 "실행 가능한 태스크"를 만드는 수준임.

![CalibForge 전체 파이프라인](/images/2026-08-08-calibforge-adversarial-solver-calibration-terminal-agents/fig-1-p1.png)

2. 2단계가 이 논문의 핵심임. 검증 통과 태스크를 솔버 에이전트들에게 풀게 하고 pass/fail 패턴으로 캘리브레이션함. 멀티 솔버 전략은 서로 다른 모델 3개가 독립적으로 풀어서 최소 하나는 통과, 최소 하나는 실패해야 유지함. 전부 통과면 너무 쉬운 거고 전부 실패하면 너무 어렵거나 깨진 태스크. 대조 솔버 전략은 강한 솔버는 통과, 약한 솔버는 실패해야 함. 조건이 안 맞으면 작성 에이전트가 솔버 결과와 궤적 전체를 피드백으로 받아 태스크를 수정하고 재검증함. 최대 50라운드까지 돌아감.

3. 수정 사례가 왜 이게 필터링이 아니라 개선인지 보여줌. 두 솔버가 다 통과한 태스크는 명령문이 해결 경로를 너무 직접적으로 알려주고 있었음. 힌트를 제거하니 강한 솔버만 통과. 전부 실패한 태스크는 비교 기준이 모호했음. 의미를 명확히 하니 부분 통과. 역전(약한 놈 통과, 강한 놈 실패)은 검증 코드가 경직되어 있었음. 검증을 일반화하니 정상 패턴. 솔버 행동이 태스크의 어떤 부분을 고쳐야 하는지 진단해주는 구조임.

![CalibForge 파이프라인 상세](/images/2026-08-08-calibforge-adversarial-solver-calibration-terminal-agents/fig-2-p3.png)

4. 효과 숫자가 설득력 있음. 솔버 피드백 없으면 TB2 정확도 22.47%. 단일 솔버 24.34%. 멀티 솔버 캘리브레이션 29.21%. 대조 솔버 캘리브레이션 31.09%. 단일 대비 +6.75pp. 근데 이 격차는 궤적 수로 설명이 안 됨. 멀티 솔버가 no-solver보다 SFT(정답 예시로 모델을 미세조정하는 지도 학습) 궤적이 더 적은데도 성능이 높음. 데이터 양이 아니라 데이터 질, 정확히는 난이도 분포가 성능을 만든다는 증거임. 그리고 첫 솔버 프로브에서 대조 조건을 만족하는 태스크는 19%뿐이었는데 수정 루프를 거치면 96%가 통과. "검증 통과 = 학습 가능"이 아니라는 것.

5. 메인 결과. CalibForge-35B-A3B가 Terminal-Bench 2.0에서 47.57%, SWE-bench Pro 44.32%(SWE-bench Pro는 실제 GitHub 저장소의 버그를 고치는 코딩 벤치마크의 난이도 높은 버전), Doc2Repo 48.77%. 같은 백본에 같은 티처로 증류했을 때 태스크 소스만 바꿔도 최강 베이스라인 대비 +6.75pp가 남. 태스크 5,431개는 태스크당 평균 검증 함수 7개, 환경 의존성 2개, 초기 파일 362개가 들어간 실제 엔지니어링 환경임. 커맨드라인 퍼즐 수준이 아님.

![메인 결과 표](/images/2026-08-08-calibforge-adversarial-solver-calibration-terminal-agents/table-1-p7.png)

6. 내 실무 이식은 이렇게임. 이 논문의 원칙은 에이전트 훈련뿐 아니라 평가 세트 설계에도 그대로 적용됨. 첫째, 합성 태스크를 "실행 가능"으로만 검증하지 말 것. 서로 다른 모델 몇 개를 돌려서 pass/fail 패턴을 볼 것. 전부 통과하거나 전부 실패하면 학습·평가 가치가 없음. 둘째, 태스크의 정답률 분포를 데이터 셋 차원에서 관리할 것. 강한 모델은 풀고 약한 모델은 못 푸는 대역이 실제로 모델을 가르치고 구분함. 셋째, 솔버 실패 궤적은 버리지 말고 태스크 수정 피드백으로 쓸 것. 문제 출제 자동화에서 궤적이 곧 개선 신호임. 코드와 데이터셋이 공개되어 있어서 도입 장벽도 낮음.
