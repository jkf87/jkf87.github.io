에이전트 디버깅이 어려운 이유는 하나임. 에러가 보이는 지점과 에러를 만든 지점이 다르다는 것. 최종 답변이 틀렸어도 진짜 원인은 수십 단계 앞의 누락된 제약 조건이나 잘못된 핸드오프일 수 있음. AgentDebugX는 이 간극을 메우는 폐루프 디버깅 프레임워크임.

1. 구조는 4단계 루프임. Detect는 도구 호출 포맷 오류, 진행 없는 루프, 조기 성공 선언 같은 기계적 실패를 규칙과 LLM 판사로 찾음. 19개 시드 실패 모드가 기본 제공되고 계획·메모리·도구·검증·조정 카테고리를 덮음.

2. Attribute가 핵심임. 증상을 진짜 원인 스텝으로 추적하는 단계. 휴리스틱부터 전체 궤적 단일 패스, 이진 탐색, 스텝별 검사까지 비용-정확도 트레이드오프 전략을 골라 쓰고, 각 귀인기는 순위화된 가설과 신뢰도·출처를 반환함. 모호하면 DeepDebug로 에스컬레이션함.

![AgentDebugX 파이프라인](/images/2026-07-22-agentdebugx-agent-failure-debugging/fig-1-p3.png)

3. Recover와 Rerun이 루프를 닫음. 근본 원인을 실행 가능한 재시도 지시문으로 변환하고, 원본과 복구본 궤적을 나란히 비교함. 성공한 브랜치는 해결 사례로 저장되고 실패한 브랜치는 다시 탐지로 들어감. 모든 수정은 인간 또는 정책 게이트 뒤에서만 적용됨.

4. DeepDebug가 기술적 핵심임. 단일 패스 귀인의 두 맹점을 해결함. 전역 읽기는 눈에 띄는 다운스트림 증상에 고착하고, 좁은 스텝 스캔은 목표를 잃어버림. 그래서 4스테이지로 나눔. 전역 읽기로 초기 후보 지정, 구조 기반 조사(멀티 에이전트면 핸드오프 캐스케이드 상향 추적, 단일이면 이분 탐색)로 두 번째 후보 확보, 교차 검증, 진단 보고서 출력.

5. 교차 검증 아이디어가 좋음. 두 패스가 일치하면 채택하고 불일치하면 두 가설을 나란히 놓고 더 강한 인과 설명을 고름. 전체 궤적 탐색 문제를 두 가설 사이의 집중된 판단으로 환원시킴. 검사가 전부 기록돼서 감사 추적도 남음.

![웹 콘솔](/images/2026-07-22-agentdebugx-agent-failure-debugging/fig-2-p5.png)

6. 결과. Who&When(멀티 에이전트 실패에서 어떤 에이전트의 어느 스텝이 원인인지 맞히는 귀인 벤치마크)에서 qwen3.5-9b 백본으로 strict agent-and-step 정확도 28.8%. 최강 단일 패스 baseline의 21.7%를 크게 앞섬. GAIA(웹 검색·도구 사용을 요구하는 범용 어시스턴트 벤치마크)에서는 실패했던 73개 작업 중 13개를 단 한 번의 재실행으로 복구, 전체 정확도 55.8%→63.6%임. 자기수정 baseline들은 각각 4~6개만 복구했음.

7. 여기서 나오는 실무 교훈이 이 글의 반임. 에러 위치를 알려주면 모델은 훨씬 잘 고침. 모델이 스스로 추론 에러를 찾긴 어렵지만 위치를 알려주면 고칠 수 있다는 건 자기수정 연구에서 반복된 결론임. 그래서 귀인 인프라가 곧 복구율임.

8. 분류 체계도 확장형임. 판사가 시드에 없는 실패를 만나면 novel-mode 후보로 기록하고, 유도기가 클러스터링해서 새 실패 모드를 제안함. 여러 실행에서 에이전트들이 서로를 무한 대기하면 "multi-agent deadlock" 모드가 제안되는 식임. 제안이 큐레이션된 분류를 덮어쓰진 않음.

9. 통합이 실용적임. `pip install agentdebugx`로 시작하고 LangGraph, CrewAI, OpenAI Agents SDK, OpenTelemetry, raw ReAct 궤적을 전부 같은 AgentTrajectory 표현으로 변환함. 진단은 원본 프레임워크와 무관하게 돌아감. Error Hub는 진단 번들 공유 시 자격 증명과 PII를 스트리핑함.

10. 실무 채점. 우리 자동화 파이프라인에 바로 대입할 지점은 귀인 단계임. 실패 로그를 통째로 모델에게 주고 "뭐가 문제야"라고 하는 건 전역 읽기 고착을 재현하는 것임. 대신 두 경로(전역 요약 후보 + 좁힌 탐색 후보)를 따로 뽑아서 교차 검증시키는 구조가 DeepDebug의 요령이고, 프레임워크 없이도 프롬프트 루프로 흉내 낼 수 있음.

11. 그리고 재시도 지시문을 게이트 뒤에 두는 원칙. 자동 복구가 무분별하게 재실행되면 비용과 부작용이 터짐. 진단-체크포인트-지시문을 패키징해서 승인 후 돌리는 구조는 그대로 베낄 만함. 성공 브랜치를 해결 사례로 쌓는 것도 재사용 자산이 됨.

12. 한계. 귀인 정확도 28.8%라는 건 아직 근접하고 있을 뿐이라는 뜻이기도 함. 복구도 13/73임. 벤치마크가 검증 세트 중심이니 실 운영 롱테일에선 수치가 달라질 수 있음.

13. 그래도 방향은 분명함. Langfuse, LangSmith 같은 관측 도구가 트레이스를 보여주는 데 그쳤다면, AgentDebugX는 근본 원인 특정→수정안 제안→재실행 검증까지 감. "무엇이 잘못됐나"에서 "어디서 잘못되기 시작했나"로 질문을 옮기는 게 에이전트 운영의 다음 단계임.
