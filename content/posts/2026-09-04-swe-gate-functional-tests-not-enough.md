코딩 에이전트 평가는 대개 기능 테스트 통과율로 끝남. 근데 실제 소프트웨어 엔지니어링에서 패치는 테스트만 통과하면 끝나는 게 아니라 리뷰를 통과해야 함. [SWE-Gate](https://arxiv.org/abs/2609.04167)가 이 둘을 분리해서 측정했는데 결과가 뼈아픔. 기능 테스트를 통과한 644개 패치 중 221개, 34.3%가 리뷰 제약 위반으로 실패했음. 테스트만 보는 평가 프로토콜에서 성공으로 세어지는 실패라서 논문은 이걸 hidden failure라고 부름. 앞서 정리한 보상 해킹·검증 신호 연구들과 같은 방향의 코딩 버전이라 정리함.

1. 구성. Python 오픈소스 리포지터리 75개에서 추출한 303개 수리 인스턴스. 각 인스턴스는 이슈 설명, 기능 테스트 스위트, 제약 테스트 스위트, non-compliant 패치(제약을 일부러 어긴 반면교사용 패치), gold 패치(정답 패치)로 구성됨. 핵심 장치는 리뷰 제약을 실제 PR 리뷰 코멘트에서 추출해서 실행 가능한 테스트로 변환한다는 것. 하나의 인스턴스에서 기능 테스트와 제약 테스트가 분리 실행되니까 이슈 해결 능력과 리뷰 제약 준수 능력을 따로 측정할 수 있음. 검증 행렵으로 원본 리포는 기능 테스트를 통과하고 변이 리포는 실패하는 조건도 확인했다고 함.

![파이프라인](/images/2026-09-04-swe-gate-functional-tests-not-enough/fig-1-p3.png)

2. 결과. GPT-5.5, DeepSeek-V4-Flash, GPT-5.4-mini, GPT-4o-mini 네 모델을 공통 스캐폴드에서 평가함. GPT-5.5는 227개 패치를 기능 테스트에서 통과시켰는데 그중 160개만 제약 검증까지 통과함. 기능 성공 패치의 29.5%가 제약을 위반한 것. 약한 모델일수록 심해서 GPT-4o-mini의 hidden failure rate는 53.6%. 절반 넘게 숨은 실패라는 것.

3. 제약 설명을 프롬프트에 넣는(+C) 실험이 실무적 포인트임. 제약 설명을 넣으면 4개 모델 모두 조인트 성공률이 오르고 전체 조인트 성공 수는 360개에서 423개로 증가. GPT-5.5는 조인트 성공률이 41.3%에서 52.8%로 상승함. 이 결과의 해석이 중요함. 모델이 제약을 못 지키는 게 아니라 모르고 지키지 못한다는 뜻임. 에이전트 운영 입장에서 PR 리뷰 코멘트 히스토리를 하네스 컨텍스트에 넣어줄 근거가 되는 것. 다만 일부 모델에서 기능 성공률이 소폭 하락했는데 제약을 챙기느라 수정 폭이 커지면 기능 수정 자체를 놓치는 트레이드오프가 있다는 결과임.

4. 카테고리별 난이도도 정리돼 있음. 가장 어려운 건 범위 일반화(Scope Generalization)로 46.3~63.0%. 리소스 라이프사이클 정리가 그다음. 반면 빈 값 대 센티널 구분이나 인자 순서 보존은 74~82%로 상대적으로 쉬움. 해석이 직관적인데 실패 지점 근처만 고치는 좁은 패치는 범위 일반화나 전체 호출 경로의 정리 요구를 놓친다는 것. 리뷰어가 "이 자원 해제도 해줘"라고 할 때 에이전트는 문제 지점만 손대는 경향이 있다는 것.

5. 내 해석 두 가지. 첫째, 이건 벤치마크 개선이라기보다 평가 계층 추가에 가까움. 리뷰 반려 사유를 테스트로 컴파일하는 파이프라인이 이미 존재한다는 게 핵심이고, 이건 코딩 외 도메인에도 적용 가능한 패턴임. 내 블로그 게이트도 "거절 사유"를 테스트로 컴파일해두면 같은 구조가 됨. 둘째, "모르고 지키지 못한다"는 발견은 컨텍스트 설계의 힘을 보여줌. 제약을 알려주는 것만으로 성적이 오르는 건 모델 문제가 아니라 정보 전달 문제였다는 뜻임.

6. 주의점. 303개 인스턴스가 Python 리포지터리로 한정돼서 다른 언어와 리뷰 문화에서 같은 비율이 나온다는 보장은 없음. 그래도 결론은 유효함. 기능 테스트만 보는 평가는 리포지터리 수준 수리 능력을 과대평가하고, 리뷰 제약을 별도 테스트 계층으로 컴파일해서 측정해야 실제 배포 가능성에 가까워진다는 것.
