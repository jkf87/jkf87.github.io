GPQA(전문가 수준의 과학 문제로 모델 지식을 재는 벤치마크)든 MATH(수학 경시 문제 모음 벤치마크)든 프론티어 모델들이 90% 이상을 받는 시대임. 근데 한 프롬프트 안에 수학·코딩·검색·데이터 분석을 연쇄로 묶은 [Relay-Bench](https://arxiv.org/abs/2607.18438)에서는 GPT-5.5가 43.3%, Gemini 3.1 Pro가 40.0%, Claude Opus 4.7이 16.7%에 그침. 모델을 고르거나 에이전트를 설계하는 사람이 이 격차를 이해 안 하면 비용만 쓰고 일을 못 시킴. 왜 이런 벌어짐이 생기는지와 실무 교훈을 정리함.

1. 배경. 2025~2026년 벤치마크는 포화 상태임. Humanity's Last Exam(초난도 학술 문제로 모델 성능 상한을 재는 벤치마크)조차 출시 1년 만에 최고 점수가 4배 올랐음. 그래서 최근 벤치마크들은 입력 모달리티를 늘리거나, 도구 호출을 평가하거나, LLM 판관제를 도입하는 방향으로 갔음. Relay-Bench는 정반대로 감. 텍스트만 쓰고 도구는 전부 허용한 채, 문제 내부 구조를 바꿈.

2. 설계는 세 가지 원칙임. 첫째, 의존성 연쇄. 2~13개의 서브문제를 묶어서 한 서브문제의 정답이 다음 서브문제의 입력이 되게 함. 둘째, 도메인 혼합. 수학, 코딩, 정보 추출, 시각 추론, 일반 지식, 데이터 분석, 문제 해결 7개 영역을 한 문제에 섞음. 셋째, 컨텍스트 부풀리기. 약 7,813자의 무관한 설정 텍스트를 넣고 단어를 3글자 암호로 치환함. 단일 도메인에선 쉬운 문제들이 연쇄로 엮이면 실패를 유발하는 구조임.

![합성 문제의 의존성 그래프 구조](/images/2026-07-23-relay-bench-multi-domain-reasoning/fig-1-p1.png)

3. 이 구조가 실무의 어디냐 하면, 그대로 실제 업무임. "이 보고서의 수치를 검증하고(수학), 관련 데이터를 크롤링해서(검색), 스크립트로 정제하고(코딩), 요약 문단을 쓰는(작문)" 작업은 의존성 연쇄에 도메인 혼합에 장문 컨텍스트까지 전부 해당함. 즉 Relay-Bench는 인위적인 시험이 아니라 실무 작업의 압축판에 가까움. 단일 벤치마크 점수가 높다고 이런 작업이 잘 되는 건 아니라는 게 숫자로 증명된 셈임.

4. 결과의 대비가 극명함. 같은 모델들이 HLE(Humanity's Last Exam) 40~44%, ARC-AGI-2(추상 추론 퍼즐로 일반 지능을 재는 벤치마크) 39~77%, τ²-Bench(항공·소매 등 고객 응대 시나리오로 도구 사용·정책 준수를 측정하는 벤치마크) 85~95%를 받는데 Relay-Bench 평균은 33.3%. 도구를 전부 허용했는데도 점수가 안 오르는 구조적 한계가 있다는 게 핵심임. 즉 문제는 모델이 도구가 없어서가 아니라, 도메인 전환과 연쇄 의존성 관리 자체임. 이건 모델 교체로 풀리는 게 아니라 하네스가 풀어야 할 영역임.

![주요 벤치마크 간 성능 비교](/images/2026-07-23-relay-bench-multi-domain-reasoning/fig-2-p1.png)

5. 모델별 실패 방식이 다른 게 제일 재밌는 발견임. Claude Opus 4.7은 답을 제출한 것 중 오답이 단 하나였고 환각률 50.0%로 가장 낮음. 대신 파싱 가능한 답변 자체가 적고, 암호화된 문제를 만나면 `stop_reason=refusal`로 응답을 아예 중단함. GPT-5.5는 정답은 가장 많지만 환각률도 33.3%로 가장 높음. Gemini는 그 중간. 즉 "틀리는 방식"이 세 갈래임. 거부형, 추측형, 중단형. 에이전트 운영자는 자기 모델의 실패 방식을 알아야 대응이 나옴. 추측형엔 검증 게이트를, 거부형엔 입력 전처리를, 중단형엔 재시도 로직을.

![모델별 파싱 가능한 응답 및 정답 수](/images/2026-07-23-relay-bench-multi-domain-reasoning/fig-4-p4.png)

6. 비용 데이터도 실무적임. 전체 벤치마크 개발·실행 비용이 $163.29에 불과했음. 모델별로는 Claude $33.76, Gemini $32.99, GPT-5.5 $22.44. Claude는 한 문제에서 370만 입력 토큰과 41회 도구 호출을 기록함. 반복 재시도로 토큰을 태우는 패턴이 그대로 보임. Gemini는 단가는 싼데 캐시 적중률이 0.6%에 불과해 실질 비용이 올라감. GPT-5.5는 더 싸면서 더 정확해서 비용-성능 프론티어에서 둘을 지배함. 모델 선택은 단가표가 아니라 실제 워크로드에서의 총비용으로 해야 한다는 표본임.

![비용 대비 정확도](/images/2026-07-23-relay-bench-multi-domain-reasoning/fig-6-p5.png)

7. 컨텍스트가 길어질수록 정확도가 하락하는 것도 별도 연구와 일치함. 완벽한 검색이 보장돼도 컨텍스트 길이 자체가 성능을 깎는다는 이미 알려진 결과임. 그래서 실무의 답은 컨텍스트를 채우는 게 아니라 쪼개는 것. 도메인이 바뀌는 지점에서 세션을 분리하고, 앞 단계의 결과물만 다음 단계에 넘기는 릴레이 구조가 단일 롱컨텍스트보다 강함. 벤치마크가 보여준 것도 결국 "연쇄를 하나의 머리가 다 들고 가면 무너진다"임.

8. 한계는 분명함. 문제 30개라 신뢰구간이 넓어서 특히 Claude 점수는 구간 폭이 점수보다 큼. 저자도 더 큰 문제 셋과 검색·코드 실행을 제외한 개정판을 후속으로 제시함. 숫자 자체를 등급표로 쓰는 건 무리고, 방향성을 읽는 도구로 쓰는 게 맞음.

9. 결론은 세 줄임. 첫째, 여러 도메인이 얽히는 실제 작업에서 단일 도메인 벤치마크 점수는 무의미할 수 있음. 둘째, 모델마다 실패 방식이 다르니 내 워크로드에서 어떻게 실패하는지 직접 측정할 것. 셋째, 도메인 간 전환은 하네스가 관리해야지 모델한테 맡기면 안 됨. 모델 능력의 문제라고 여겼던 것의 절반이 사실은 설계의 문제임.
