에이전트가 도구를 부를지 말지를 프롬프트나 파인튜닝 없이 모델 내부에 벡터 하나를 더하는 걸로 추론 시점에 조절하는 연구가 나왔음. 원문은 [arXiv:2608.25198](https://arxiv.org/abs/2608.25198), 코드는 [GitHub](https://github.com/YuqiChen4188/Steering-Tool-Use-Propensity)에 공개돼 있음.

1. 문제. 도구 호출은 비쌈. 안 해도 되는 호출은 지연과 비용을 늘리고 이메일 발송 같은 되돌릴 수 없는 부작용을 낳을 수 있음. 반대로 안 부르면 자기 지식으로 못 푸는 문제를 자신만만하게 틀림. 실제 측정에서 PopQA에서 스티어링 전 모델은 29%만 맞히면서도 검색을 거의 안 부르는 과소 호출 쪽이었고, 어떤 모델은 기본 호출률 0.83의 과다 호출 쪽이었음. 기존 해법인 파인튜닝·프롬프트 수정은 비싸고 추론 시점 조정이 어려움.

![표현 스티어링으로 도구 사용 양방향 제어(논문 Figure 1)](/images/2026-08-29-tool-call-steering/fig-1-p1.png)

2. 방법은 세 단계임. 첫째, 성향 프록시로 모델 고유의 도구 호출 오프닝 토큰 첫 로그확률을 측정함. 생성 없이 forward pass 한 번이면 됨. 둘째, 그 값의 상하위 10% 쿼리들로 잔여 스트림 평균 차이(difference-of-means)를 구해 방향 벡터를 추출함. 라벨·그래디언트·SAE가 전부 불필요하고 몇천 개 쿼리면 충분함. 셋째, 추론 시 지정 레이어에 h' = h + αv를 더함. α=0이면 원래 모델, 음수는 억제, 양수는 유도임.

3. 작동 레이어가 중후반(실험 모델 기준 L21-24, 운영 L22)이라는 것도 기억할 만함. 초반 레이어는 거의 무반응이고 마지막 레이어는 효과는 커도 단조성이 깨짐. 이진 결정이 읽히는 위치가 정해져 있다는 뜻임.

4. 결과 1. α를 -2에서 +3까지 올리면 호출률이 거의 0에서 0.79-1.00까지 단조 증가하고 호출 포맷도 유지됨. α=+3부터는 malformed 콜이 나오기 시작해 이게 운용 범위의 끝이라고 저자가 표시해둠.

5. 결과 2가 제일 눈에 띔. α를 올려서 새로 생긴 호출은 모델이 파라미터 지식으로 못 푸는 롱테일 질문 쪽에 집중됨. 인기 많은 상식 문제에는 그대로 안 두고 PopQA 인기도 하위 쪽으로 쏠림. 억지로 호출을 늘린 게 아니라 "몰라서 부르는" 올바른 호출이 늘어난다는 것임.

6. 결과 3. 실제 검색 API를 붙이고 α를 스윕하면 비용-정확도 파레토 프론티어가 그려짐. 검색 0회면 0.29이던 정확도가 질문당 약 1.1회 검색에서 0.56까지 오르고, 검색 장려 프롬프트와 조합하면 0.58까지 감. 프롬프트 엔지니어링과 충돌하지 않고 합성됨.

![비용-정확도 트레이드오프 개선(논문 Figure 2)](/images/2026-08-29-tool-call-steering/fig-2-p4.png)

7. 일반성도 확인됨. Qwen3 4B/8B/30B-A3B(MoE), Gemma-4-E4B, gpt-oss-20b 전부에서 같은 레시피가 먹혔고 기본 호출률이 0.07에서 0.83까지 갈려도 α로 전부 조절됐음. 실검색에서도 무검색 대비 1.5-2.5배 게인이 다섯 모델 전부에서 확인됐음. 그리고 "부를지 말지"만 바꾸고 "어떤 도구를 부를지" 라우팅은 모델 고유 패턴을 유지함.

![5개 모델 교차 재현성(논문 Figure 3)](/images/2026-08-29-tool-call-steering/fig-3-p5.png)

8. 홀드아웃 전이도 흥미로움. 추출에 안 쓴 6개 도구(번역, 날씨, SQL, 주가 등)에 같은 벡터를 적용해도 억제 효과가 도구별 벡터와 비슷하거나 더 셌음. "부를지 말지" 방향이 도구 공통 성분을 담고 있다는 증거임.

![홀드아웃 도구 억제 강도(논문 Table 1)](/images/2026-08-29-tool-call-steering/table-1-p5.png)

9. 내 업무 관점 해석. 이건 배포 시점 비용 다이얼임. 트래픽이 몰릴 때 α를 내려 호출 비용을 줄이고 정확도가 중요한 시점엔 올리는 식으로 씀. 클램핑 실험에서 호출률이 0.01에서 0.16에 그친 것까지 보면 가산 스티어링이 아니면 전체 조절 범위가 안 나옴. 다만 잔여 스트림 접근은 오픈웨이트 모델에서만 가능해서 프론티어 API 에이전트에는 못 쓰는 제약이 있음. 그래서 나는 이 논문을 직접 적용보다는 "호출 성향이 읽히고 조절 가능한 양"이라는 사실 자체를 라우팅 설계 근거로 씀. 과소·과다 호출 모델을 만나면 프롬프트를 다듬는 것보다 호출 오프닝 로그확률 프록시를 먼저 측정해서 어느 쪽 병목인지 진단함.

10. 문제제기. 도구를 부르기로 한 뒤의 실행 품질은 통제하지 못하고, reasoning-first 모델은 결정이 읽히기 전에 추론 구간을 우회해야 해서 추가 비용이 있음. 그리고 정확도는 검색 약 1회/질문에서 정점을 찍고 그 뒤로는 비용만 늘어나므로 "100%로 밀면 좋다"가 아니라 최적 α를 찾는 문제임.

11. 결론. "도구를 부른다/안 부른다"는 이진 결정이 모델 내부에서 선형 방향 하나로 읽히고 그 방향을 더하거나 빼는 것만으로 연속 조절됨. 학습 0, 프롬프트 변경 0으로 호출률 0-90% 이상을 다루고 정확도를 2배 가까이 올린 사례로서, 에이전트 비용-정확도 튜닝의 새 레버를 보여준 논문임.
