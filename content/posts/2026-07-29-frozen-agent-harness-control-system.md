모델은 못 바꾸는데 하네스는 고칠 수 있는 게 프로덕션의 현실임. 그럼 하네스를 어떻게 최적화해야 하나를 실험한 논문이 나왔는데, 결과가 예상을 깜. 원문은 [arXiv:2607.25415](https://arxiv.org/abs/2607.25415).

1. 전제는 이해가 쉬움. 2026년 프로덕션 에이전트는 대부분 동결된 모델 + 하네스 구조임. 그리고 하네스 구성이 모델 선택보다 성능 분산을 더 크게 설명한다는 연구가 이미 있음. 그래서 이 논문은 하네스를 작고 고정된 이산 행동 공간으로 정의하고 그 위에서 고전 RL로 정책을 학습함.

2. 하네스를 6개 레버로 쪼갠 게 설계의 백미임. 프롬프트 스타일(direct/structured/reflective), 도구 정책(never/when_needed/always), 메모리 정책 3종, 계획 정책 3종, 검증 정책 3종, 최대 스텝(2/4/6). 729가지 구성. 각 구성에 사람이 검토한 이름이 붙어 있어서 회귀가 나면 어느 레버 탓인지 즉시 알 수 있음. 임의 코드 생성 방식과의 근본적 차이임.

3. 보상 함수도 실용적임. 성공률에 검증 점수, 정책 준수, 근거 없는 주장 페널티, 토큰 비용, 지연시간을 함께 넣음. 단일 메트릭만 최적화하면 비용 폭주나 환각을 못 잡으니까 당연한 설계인데, 이걸 실제로 다 계측한 게 공들인 부분임.

4. 근데 결과가 반전임. 4개 최적화기 × 3도메인 × 2모델 실험에서 DSPy 정적 기준선이 모든 도메인, 모든 모델에서 온라인 적응형 컨트롤러와 일치하거나 능가함. 도구 사용 도메인 Haiku 기준으로 정적 기준선이 96% 성공률에 에피소드당 285 토큰, REINFORCE가 62%에 680 토큰. 저자가 스스로 예상 못 한 결과라고 함.

![최적화기별 신뢰성-비용 파레토(논문 Figure 1)](/images/2026-07-29-frozen-agent-harness-control-system/fig2-pareto.png)

5. 원인 진단이 이론으로 연결됨. 729차원 이산 공간에서 밀집 정책이 샘플 효율적이려면 최소 729 에피소드가 필요한데 실제 예산은 25~60. 반면 DSPy BootstrapFewShot은 지표 가이드 검색이라 처음부터 그럴듯한 영역에서 시작함. 균등 탐색이 못 이길 수밖에 없는 구조라는 것.

![최적화기 간 성공률·토큰 비용 비교](/images/2026-07-29-frozen-agent-harness-control-system/results-comparison.png)

6. 함정 보고 세 개가 실무자에게 제일 값짐. 콜드스타트에서 Q값 전부 0 초기화로 argmax가 항상 index 0을 골라 도구 없는 구성에 갇힌 것. 한 에피소드 크래시가 잡 전체 39개를 죽인 것. DSPy 캐시 히트가 비용 0으로 계측돼 정적 기준선 비용을 과소 평가한 것. 셋 다 겪기 쉬운 함정이고 해결책도 표준적임. 낙관적 초기화, 에피소드 격리, usage 폴백.

7. 필자가 바로 쓰는 교훈. 파이프라인 프롬프트를 온라인 실험으로 계속 바꾸는 것보다, 검증기가 있는 상태에서 지표 가이드로 한 번 최적화한 정적 구성을 먼저 박아두는 게 이김. "온라인 적응은 정적 기준선으로 부트스트랩한 뒤, 작업 분포가 이동했을 때, 에피소드 예산이 729 이상일 때"라는 세 조건이 갖춰야만 가치가 있다는 결론에 동의함. 이건 배포 첫날 체크리스트로 쓸 수 있음.

8. 문제제기. 도메인이 세 개(가상 CRM, HumanEval, HotpotQA)로 좁고 로컬 소형 모델 포함이라 대형 모델 일반화는 스팟 체크 수준임. 그리고 하네스를 6레버로 고정하는 것 자체가 가정이라, 레버 밖의 개입(도구 자체를 바꾼다든지)은 이 프레임 밖임.

9. 남는 결론. 하네스 최적화는 모델을 못 고치는 환경에서 가성비 제일 높은 레버인데, 어떻게 최적화하느냐가 무엇을 최적화하느냐만큼 중요함. 적은 예산에서는 좁은 영역을 지표로 집중 파는 쪽이 균등 탐색을 이긴다는 단순한 교훈이 숫자로 증명된 작업임.
