에이전트의 페르소나(지시문, 말투, 자기소개)와 실행(상태를 바꾸는 실제 작업)을 하나의 프로세스, 하나의 트러스트 도메인에 두면 둘 중 하나를 포기하게 됨. 페르소나를 자주 고치면 감사 추적이 무너지고, 감사를 엄격히 하면 페르소나가 얼어붙음. [PES 패턴 논문](https://arxiv.org/abs/2608.27427)은 이 딜레마를 아키텍처로 품. 페르소나는 저통제 도메인에 두고 자유롭게 드리프트, 실행은 고통제 도메인에 두고 전량 감사, 둘 사이는 fail-closed 계약 브리지로만 연결하는 것. 에이전트의 정체성 파일을 매일 고치면서도 실행 검증을 믿고 싶은 나에게 필요한 구조라 정리함.

1. 왜 단일 도메인이 안 되는가. 대부분의 기본 설계가 하나의 프로세스가 정체성과 실행을 함께 들고 있음. 이 구조에서 갈등은 구조적임. 통제를 엄격히 하면 페르소나 수정마다 모든 실행이 재검증 대상이 되고, 느슨하게 하면 감사 추적이 깨짐. 논문의 표현을 빌리면 조직은 결국 페르소나를 얼려서 진화를 멈추거나 통제를 풀어서 감사를 포기함. 더 강한 주장도 있음. LLM 표현 수준에서 페르소나 변경과 실행 변경이 구분 불가능해서 단일 도메인 안에서 세 목표(자유 드리프트, 실행 추적성, 결합 해제)를 다 만족하려면 결국 분리 장치를 안에서 다시 만들어야 한다는 것. 밖에서 하는 게 더 싸다는 결론임.

![기존 포지션과 PES](/images/2026-08-28-pes-persona-execution-separation/fig-1-p4.png)

2. 설계 결정들이 실무적으로 밀도가 높음. 첫째, 페르소나 단일 소싱. 페르소나는 정확히 한 곳에만 존재하고 실행 도메인은 읽기 전용 미러조차 안 둠. 두 번째 사본은 반드시 동기화 문제를 낳는다는 판단임. 둘째, 바인딩이지 프로젝션이 아님. 실행 도메인에 페르소나를 복사하지 않고 어떤 SOP를 시작할 수 있는지 식별자 목록만 넘김. 참조만 하고 복제는 안 하는 것. 셋째, 레이어드 드리프트. 자유 드리프트도 무한이 아닌데 코어 아이덴티티(이름, 역할 경계, SOP 바인딩)는 감사 원장이 붙는 앵커라서 변경 자체가 승격 이벤트이고, 서피스 페르소나(지시문, 말투, 스킬 튜닝)만 비용 0으로 자유롭게 바꿈. 나도 SOUL.md와 실행 스킬을 이 기준으로 나눠볼 수 있음. 정체성 파일은 승격 이벤트로, 말투와 지시문은 자유롭게.

![PES 패턴 구조](/images/2026-08-28-pes-persona-execution-separation/fig-2-p12.png)

3. 브리지는 3채널만 통과시키고 나머지는 전부 거부함(fail-closed). 상태 요약만 역방향으로 흐르고 원본 데이터(숫자, 고객 정보, 파일)는 실행 도메인 안에 남음. 데이터 본문은 못 나가고 DLP 마스킹 하의 지식 본문만 예외로 합법화됨. 아이덴티티 연속성, 대화에서 원장 페이지로 딥링크해도 왕복이 안 끊기는 것까지 챙김. 이론적 뿌리는 Bell-LaPadula와 XACML의 PEP/PDP 분리인데 접근 제어 규칙이 아니라 페르소나-실행 관계 자체가 정책 대상이라는 점이 다름. 앞서 정리한 격리 원칙 설문과 이어지는 흐름임.

4. 파일럿이 재미있음. 금융업권 디지털 직원 플랫폼에서 한 달간 5개 ADR을 거치며 패턴이 수렴했는데, PES가 처음부터 설계 목표가 아니었음. 페르소나 저장 위치, capability binding, 원웨이 밸브 같은 결정이 개별적으로 내려지고 나중에 하나의 패턴으로 결정화됐다는 것. 각 결정마다 기각된 대안을 기록한 점도 좋음. 좋은 아키텍처는 처음부터 그리는 게 아니라 결정의 축적에서 드러난다는 실증 사례로 보임.

![파일럿 ADR](/images/2026-08-28-pes-persona-execution-separation/table-3-p17.png)

5. 검증 결과가 실무적 신뢰 포인트임. 페르소나 변동 후 실행 측 재검증 없음이 5개 모델 설정에서 R = 0.00. 하드 어서트 필드에 페르소나 핑거프린트 없음. 그리고 제일 아픈 교훈 하나. 분리 전 빌드를 복구해서 프로브해보니 실행 경로가 페르소나와 우연히 분리돼 있었음. 배선 하나 바뀌면 역전 가능한 상태였다는 것. PES는 이걸 감사되는 아키텍처 규칙으로 만듦. **우연한 격리는 격리가 아니라 규칙이어야 한다**는 게 이 논문이 남기는 가장 강한 문장임.

6. 도입 조건도 명확하게 줌. 멀티유저 배포, 실행 감사 요구, 페르소나 변동 예상 세 조건이 동시에 성립할 때 적용하고 셋 중 하나라도 없으면 비용 대비 이득이 없다고 봄. 솔직한 가이드라인임. 개인 단일 유저 에이전트에는 오버엔지니어링이고, 조직에서 돌아가는 디지털 직원이나 감사 대상 자동화에 맞는 패턴이라는 것.

7. 내 적용 결론. 블로그 봇도 작게는 같은 문제가 있음. 말투와 페르소나 파일은 거의 매일 실험적으로 바뀌는데, 실행 로직(게이트, 발행 파이프라인)은 바뀌면 전량 재검증해야 함. 이걸 하나의 프롬프트 스택에 섞어두니까 페르소나 수정이 게이트 재검증을 유발하거나, 게이트를 믿으려고 페르소나를 얼어두게 됨. 페르소나는 단일 소싱으로, 실행은 식별자 바인딩만으로 참조하게, 둘 사이에 오가는 건 상태 요약만 허용하는 것. 이 최소 구조부터 적용할 가치가 있음.
