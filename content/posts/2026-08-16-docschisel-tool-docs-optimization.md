에이전트가 도구를 못 쓰면 모델 탓부터 하게 되는데, 원인의 상당 부분이 도구 문서에 있다는 걸 보여준 논문이 나옴. 도구 설명 자체를 최적화 대상으로 다뤘다는 게 신선해서 정리함. 원문은 [arXiv:2608.10037](https://arxiv.org/abs/2608.10037).

1. 출발점이 데이터 조사임. 14개 도구 사용 데이터셋에서 도구 문서 24,955개를 모아 17개 정보 필드로 정리했는데, 전 데이터셋 공통 필드는 도구 이름과 기능 설명 두 개뿐. 사용 안내나 호출 제약을 주는 데이터셋은 14개 중 2개뿐이었음. 문서가 "고정 입력" 취급받으며 방치돼 왔다는 증거임.

![](/images/2026-08-16-docschisel-tool-docs-optimization/gifs/read-the-instructions.gif)

2. 필드 효과 측정 결과가 실무적으로 제일 아픔. 필드 하나를 넣거나 빼면 과제 성공률이 평균 6.34%p씩 움직임. 근데 17개 중 방향이 일관된 건 6개뿐. 호출 제약(IC)을 넣으면 일관되게 상승, 과제 도메인(TD)을 빼면 최대 13.75%p 하락. 그리고 백본마다 효과가 갈림 — 선택 인자 표시 제거가 GPT-4o·GLM-5에선 손해인데 Claude Haiku에선 오히려 7.5%p 이득. ReAct에서 Multi-Agent로 바꾸면 효과가 뒤집히는 필드도 나옴. 고정 문서 규격이 모든 에이전트 설정에 안 통한다는 결론임.

![DocsChisel 접근 개요](/images/2026-08-16-docschisel-tool-docs-optimization/fig2-approach-overview.png)

![](/images/2026-08-16-docschisel-tool-docs-optimization/gifs/pottery-carving-refine.gif)

3. DocsChisel 루프가 네 단계임. 원본 문서로 최적화 세트를 돌려 실패 트레이스에서 "문서 때문에 실패한 케이스"를 진단하고, 진단을 필드 추가/제거/정제 연산으로 계획하고, 원본을 시맨틱 앵커로 둔 채 계획만 적용해 새 문서를 생성하고, 검증 세트에서 회귀까지 잡아 채점함. TS가 원본 이상일 때만 후보에 넣는 조건이 보수적이고 좋음. 도메인 단위 메모리가 쌓여서 같은 도메인의 다른 도구 최적화에 재사용됨.

![진단 프롬프트 설계](/images/2026-08-16-docschisel-tool-docs-optimization/fig4-diagnosis-prompt.png)

4. 결과는 원본 문서 대비 과제 성공률 평균 +95.89%, 기존 최고 기법 대비 +75.15%. 9개 도메인 전체로는 +194.22%. 반복 분산도 기존 기법 대비 크게 줄어서 안정적임. 이메일·CRM·스마트홈처럼 절차성이 강한 도메인에서 특히 컸음.

![원본 대비 효과](/images/2026-08-16-docschisel-tool-docs-optimization/fig8-effectiveness.png)

5. 왜 기존 기법을 이기는지 설명이 설득력 있음. EasyTool은 같은 템플릿을 전 설정에 강제해서 특정 에이전트에 필요한 필드를 지우거나 못 넣음. DRAFT는 고립된 도구 실행 피드백이라 에이전트 전체 실행 실패를 못 고침. DocsChisel은 에이전트 실패 트레이스에서 출발해 필드 단위로 고치니 차이가 난다는 것.

![반복 최적화 수렵](/images/2026-08-16-docschisel-tool-docs-optimization/fig9-iterations.png)

6. 비용 구조가 합리적임. 도구당 12.65분, 문서 길이는 원본보다 24% 길어지지만 최적화는 한 번 하면 재사용하는 오프라인 비용임. 반복은 5회까지가 효율 고점이고 그 뒤로 수렴. 메모리를 빼면 TS가 -76.47%로 무너지니 도메인 경험 재사용이 실질 엔진임.

7. 필자가 바로 적용할 것 세 가지. 첫째, MCP 도구 설명은 사실상 프롬프트라는 관점 — 도구 많은 하네스에서 설명 최적화는 모델 교체와 별개로 남는 투자임. 둘째, 호출 제약 추가가 일관된 이득이었다는 점 — 제 도구 설명부터 "언제 쓰면 안 되는지" 한 줄씩 추가하는 것으로 시작함. 셋째, 백본별 효과 차이 — 도구 설명에 버전을 붙이고 백본별로 관리하는 게 정당해짐. 지금은 하나의 설명을 모든 모델에 쓰고 있어서 이게 곧 개선 과제임.

8. 문제제기. 과제 분해 오류, 확률적 추론, 불완전한 쿼리 같은 문서 밖 요인은 못 고침. 도구 수천 개짜리 대형 레지스트리에는 도구당 13분짜리 최적화에 우선순위 매기기가 필요함. 통계 처리는 Mann-Whitney U + Holm 보정에 분류 일치도 κ=0.862로 단단하지만, 최적화 모델 의존도가 커서 Claude Haiku가 93.75%인데 GPT-4o는 47.50%로 갈림.

9. 남는 결론. 도구 설명은 한 번 쓰고 버리는 부속이 아니라 백본별로 버전 관리하는 자산임. 실패 트레이스에서 진단해 필드 단위로 고치는 루프를 도구 레지스트리에 달아두는 게 모델 업그레이드보다 싸고 확실한 개선이라는 게 이 논문의 실무 메시지임.
