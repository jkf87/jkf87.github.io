에이전트에게 도구를 주는 건 이제 상식임. 근데 그 도구 사용 경험이 모델 안에 축적되는 설계는 드묾. SpatialCLI는 이 질문을 정면으로 다룸. 도구를 쓰는 능력을 모델 안으로 밀어넣을 수 있는가. 8B 모델이 도구를 쓸 때 GPT-5.6을 크게 앞서고, 도구를 뺏어도 성능의 대부분을 유지한다는 결과를 냄. 도구를 런타임 보조 수단이 아니라 학습 데이터로 보는 패러다임 전환임.

1. 출발은 능력의 비대칭임. "저 이미지에서 가장 먼 곰인형을 찾아라"는 지시를 VLM이 이해는 함. 근데 정답에 필요한 건 세 단계의 세밀한 지각. 곰인형 segmentation(이미지에서 곰인형 영역을 픽셀 단위로 분리하는 작업), 각각의 depth 측정, 가장 먼 것 localization. 일반 VLM은 이 중 신뢰할 수 있게 수행하는 게 0개. 반대로 SAM 3(Meta가 만든 범용 이미지 분할 모델) 같은 전문 모델은 segmentation은 완벽한데 "뭘 세그먼트해야 하는지"를 스스로 못 정함. 이 비대칭이 도구 조합 에이전트의 존재 이유이자 병목임. GPT-5.6이 이런 조합 벤치마크에서 48.8%에 그치는 건 개별 능력이 아니라 능력 간 조정이 진짜 병목이라는 증거임.

![SpatialCLI 개념도](/images/2026-08-02-spatialcli-spatial-tool-internalization/fig-1-p2.png)

2. 파이프라인이 3단계로 깔끔함. Call 단계에서는 Locate, Segment, Depth, Pose 네 도구를 ReAct 루프(생각-행동-관찰을 번갈아 기록하며 다음 행동을 정하는 에이전트 실행 방식)에 노출함. 남은 호출 예산을 매 턴 보여줘서 "더 쓸지 답을 낼지"를 모델이 결정함. 이것만으로 Qwen3-VL-8B가 35.3%에서 66.5%로 오름. Learn 단계에서는 교사 모델 궤적으로 콜드스타트 SFT(정답 예시로 모델을 미세조정하는 지도 학습)를 하고 GRPO(같은 문제의 여러 롤아웃을 비교해 상대적으로 나은 행동을 강화하는 강화학습 알고리즘)로 도구 호출 정책을 강화함. 여기서 중요한 발견이 있음. SFT 없이 RL만 하면 도구 호출 수가 3.36 → 6.74로 폭주함. SFT를 먼저 하면 2.56회로 안정됨. 그리고 도구만 쓰고 RL이 없으면 도구 의존성이 모델 고유 능력을 잠식해서 도구 없는 성능이 하락하기 시작함.

3. Internalize 단계가 혁신의 핵심임. 성공한 도구 호출 궤적을 텍스트 추론 체인으로 번역해서 도구 없이도 같은 추론을 하도록 훈련함. 이때 두 가지 설계가 필수였음. 첫째, 점진적 증거 기반 궤적 언어화. 전체를 한 번에 번역하지 않고 도구 호출 턴마다 증거를 정리한 뒤 전역 통합함. 한 번에 하면 긴 컨텍스트에서 정보가 묻혀서 8.2점을 잃음. 둘째, 듀얼뷰 훈련. 내재화 뷰(도구 없이 답하기)와 도구 사용 뷰를 동시에 훈련함. 하나만 남기면 나머지 능력이 무너져서 도구를 쓸 줄 알면서 없이도 푸는 두 능력의 공존이 안 됨.

![SpatialCLI 전체 파이프라인](/images/2026-08-02-spatialcli-spatial-tool-internalization/fig-2-p3.png)

4. 결과 숫자. SpatialCLI-8B가 도구 사용 시 SpatialCLI-Bench 91.3%. GPT-5.6 Sol 48.8%의 거의 두 배. 그리고 GPT-5.6에 같은 도구를 붙여도 54.9%까지만 오름. 학습된 도구 정책이 도구 자체보다 중요하다는 뜻임. 도구를 뺀 상태에서도 72.7%. 원래 35.3%에서 37.4점 오른 것. MindCube(3D 장면 이해 벤치마크)에서는 29.3% → 84.6%(도구 사용), 73.8%(도구 없음). 8B의 내재화된 능력이 50배 큰 모델을 넘는다는 결과임.

![전체 성능 비교](/images/2026-08-02-spatialcli-spatial-tool-internalization/table-1-p7.png)

5. 스케일링 분석이 패러다임을 바꿈. 도구 사용 성능은 8B, 27B, 35B에서 거의 같음(±1점). 도구 호출 정책이 한 번 학습되면 전문가 모델이 나머지를 처리하기 때문. 반면 도구 없는 성능은 모델 용량에 따라 계속 오름. 내재화는 전문가 능력을 자기 파라미터에 인코딩하는 과정이라 더 큰 모델일수록 더 많이 흡수함. 그래서 큰 모델의 이점은 도구 성공률이 아니라 흡수 용량에 있다는 결론. "도구 성공 = 문제 해결"이 아니라 "도구 성공 = 학습 기회"로 보라는 것임.

![내재화 스케일링 분석](/images/2026-08-02-spatialcli-spatial-tool-internalization/fig-4-p7.png)

6. 도구 인터페이스 설계 교훈도 큼. 도구 출력을 이미지 annotation이 아니라 구조화된 텍스트(좌표, 폴리곤, depth 값)로 반환하니 성능이 더 높음. 이유는 두 개. VLM이 텍스트 좌표를 직접 추론에 쓰기 쉽고, 텍스트는 후속 내재화 단계에서 그대로 감독 신호로 변환됨. 이미지 annotation은 내재화가 어려움. 도구 인터페이스 설계가 런타임 성능뿐 아니라 학습 파이프라인 전체를 좌우한다는 것. 도구를 만들 때 반환 형식부터 학습 관점으로 정하라는 교훈임.

7. 내 실무 이식은 이렇게임. 첫째, 에이전트의 성공한 도구 호출 궤적을 버리지 말고 구조화된 로그로 쌓을 것. 그게 곧 증류 데이터임. 둘째, 도구 출력은 인간이 읽을 수 있는 구조화 텍스트로 정규화할 것. 셋째, 능력을 잃지 않으려면 도구 사용 루프와 무도구 추론을 번갈아 훈련·평가할 것. 도구 의존이 고유 능력을 잠식한다는 게 이 논문의 측정 결과임. 넷째, 큰 모델로 갈아탈 때 기대할 것은 도구 성공률이 아니라 경험 흡수 용량임. 한계도 있음. 비전-공간 도메인의 결과라 다른 도메인 일반화는 미검증이고, 내재화 데이터 구축 비용이 만만치 않음. 그래도 도구 경험을 자산으로 축적하는 설계 방향은 그대로 취할 가치가 있음.
