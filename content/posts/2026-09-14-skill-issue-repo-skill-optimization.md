레포지토리 하나에 붙는 SKILL.md, 그러니까 에이전트에게 읽히는 .md 문서를 자동 최적화하는 실험 결과가 나옴. 결론부터. GEPA(실행 피드백을 받아 프롬프트·지시문을 후보 여러 개로 유지하며 통째로 재작성을 반복하는 진화형 최적화기)가 만든 문서는 테스트 점수를 평균 4.9pp 올렸지만 20~26개짜리 홀드아웃에서는 에이전트 실행 분산과 통계적으로 구분이 안 됐음(최고 p=0.29). SkillOpt(기존 문서 하나에 add/delete/replace 증분 편집을 누적하는 최적화기) 문서는 사실상 제자리. 대신 정성 평가에서 차이가 명확했음. 실제 레포 메인테이너는 GEPA 문서를 "초안으로 받아서 다듬겠다"고 했고 SkillOpt 문서는 "일반론이 많다"고 평가 절반을 덜어냈음.

1. 배경이 실무적임. 에이전트 메모리 연구는 임베딩 스토어, 검색 서비스, LLM-as-a-judge 갱신 루프 같은 레포 바깥 인프라를 요구하는 경우가 많았음. 반면 SKILL 방식은 .md 파일이 코드와 함께 버전 관리되고 PR로 리뷰되고 그냥 머지됨. 규모도 이미 커서 AGENTS.md 포맷은 오픈소스 6만 개 프로젝트 이상에서 쓰이고 SKILL 스펙은 45개 이상 에이전트 도구에서 지원됨. 문제는 이 문서를 사람이 손으로 쓴다는 것. 그래서 "실행 로그에서 자동 합성하자"는 라인이 나왔고 이 논문은 단일 레포 특화 케이스를 다룸.

2. 태스크 생성의 교훈이 핵심임. 기존 SWE-smith 스타일은 결함을 심어 "고쳐라"를 만드는데 이렇게 만든 태스크는 대부분 단일 파일 수준이라 유능한 에이전트가 SKILL 없이도 거의 다 풀어버림. 점수에 움직일 여지가 없었다는 것. 저자들은 Kotlin/JVM을 타깃으로 PR mirroring을 재구현함. 머지된 PR을 단일 고정 베이스 커밋에서 되돌려서 태스크를 만드는 방식. 부모 커밋 방식은 태스크마다 다른 시점의 레포를 붙잡아서 의존 PR 때문에 컴파일이 안 되는 태스크가 생기고, 최적화된 SKILL이 존재하지 않는 모듈 구조를 단정하는 낡은 지식을 담는 문제도 나왔다고 함. 수율은 대략 5개 중 1개. koog 660개 PR → 119 태스크, ktor 452 → 131, kotest 100.

3. 최적화기 비교. GEPA는 Pareto frontier(비용-성능 곡선에서 더 개선할 수 없는 후보들의 집합)에서 샘플링해 전체 재작성을 하고 SkillOpt는 단일 진화 문서에 add/delete/replace 증분 편집을 하며 홀드아웃 엄격 개선 게이트와 감쇠하는 edit budget을 씀. 결과는 GEPA가 세 레포 전부에서 시드 대비 상승(kotest 0.554, ktor 0.567, koog 0.525), SkillOpt는 들쭉날쭉(ktor는 하락). 근데 부호 검정(각 태스크에서 오른 내림 부호만 세서 우연인지 판정하는 검정)으로는 어떤 실행도 p=0.05를 못 넘김. 20~26개 규모에서 유의해지려면 다섯 번 중 네 번을 이겨야 함. 그리고 이 논문의 정직한 지적. 이 라인의 선행 연구 보고 효과도 전부 이 선 아래에 있다는 것.

4. 메인테이너 리뷰가 유일하게 확실하게 갈린 지표임. GEPA 문서에서 건질 만하다고 표시된 부분은 전부 프로젝트에 몸담지 않으면 얻을 수 없는 지식이었음. 멀티플랫폼 소스셋("우리가 여기서 많이 고생했다"), 소스셋 경계를 넘지 말라는 규칙, 모듈 간 의존성 방향. 빠진 것도 구체적. @Tool 어노테이션이 빠진 건 "very strange"라는 반응. SkillOpt 문서는 "새 모듈 등록이 3파일 변경" 하나만 살아남고 나머지는 일반론으로 잘림. 메인테이너의 원칙이 인상적임. 일반 베스트 프랙티스는 글로벌 스킬로, 레포 특화 조각만 레포에 남겨라. 전체 재작성이 증분 편집을 이긴 이유도 여기서 읽힘. 증분 편집은 일반론을 붙이기 쉽고 전체 재작성은 실행 로그의 특이한 사례를 반영하기 쉬운 것.

5. 실무자가 가져갈 것 세 가지. 첫째, SKILL 자동 최적화를 돌리기 전에 태스크 난이도부터 확인할 것. 시드 상태 통과율이 이미 높으면 최적화가 붙일 게 없음. 둘째, 작은 홀드아웃에서 몇 pp 오른 건 런-to-런 분산일 가능성이 큼. 부호 검정 한 번은 돌려볼 것. 셋째, 문서 품질 평가는 pass rate보다 레포를 아는 사람의 리뷰가 낫고, 이 논문 기준 합리적인 쓰임은 "자동 생성 초안 + 사람이 다듬기" 워크플로우임. 비용도 참고할 것. 3레포 × 2최적화기에 총 $2,013.98, 69.2시간. 그리고 레포 채굴이 항상 태스크 풀을 보장하지 않음. tracy는 패키지 개명 때문에 역적용이 전부 실패(203개 중 5개 생존). 내 AGENTS.md 운영에 바로 적용할 원칙은 하나. 내가 프로젝트에서 고생해서 아는 비관습 지식만 남기고 에이전트가 스스로 아는 일반론은 지울 것.
