하네스 진화 연구는 대부분 중앙 집중식임. 모든 워크로드와 궤적을 단일 옵티마이저가 처리하는 방식. 근데 현실에서 데이터는 조직, 사용자, 환경에 걸쳐 분산되어 있고 워크로드를 중앙으로 못 옮기는 경우가 많음. [EvolveNet](https://arxiv.org/abs/2608.04968)이 이 조건에서 하네스 진화를 하는 최초의 프레임워크임. 나아가서 "각자 고친 코드를 어떻게 합치는가"라는 프로그래밍의 오래된 질문에 행동 증거 기반의 답을 줌. 여러 에이전트 인스턴스를 운영하는 사람에게 바로 닿는 이야기라 정리함.

1. 구조는 라운드 기반임. 서버가 공유 하네스를 모든 클라이언트에 방송하고, 각 클라이언트는 로컬 워크로드에서 자기 하네스를 진화시키고, 서버가 클라이언트별 프로그램 델타를 집계해서 새 공유 하네스를 만들고, 검증 슬라이스에서 행동 비교 후 채택하거나 롤백함. 모델 가중치는 고정이고 하네스 코드만 적응의 대상임.

2. 기술적으로 어려운 건 집계임. 모델 가중치는 벡터라서 평균 내면 되지만 소스 코드는 벡터 공간에 없어서 좌표별 산술로 합칠 수 없음. EvolveNet의 해법은 두 단계임. 각 클라이언트의 델타를 mechanism 단위로 분해하고, 각 mechanism에 global 또는 home(domain) 스코프를 할당하는 것. global mechanism은 모든 입력에 적용되고 home mechanism은 해당 도메인 조건에서만 활성화됨. 즉 "전체에 좋은 것은 승격하고, 특정 도메인에만 좋은 것은 조건부로 살린다"는 규칙을 코드 집계에 적용한 것.

![순차 진화와 분산 진화 비교](/images/2026-08-07-evolvenet-collaborative-harness-evolution/fig-1-p5.png)

3. 게이트가 회귀를 막음. 각 클라이언트는 로컬 진화 시 새로 해결한 문제 집합과 망가뜨린 문제 집합을 보고함. 서버의 집계 후보도 동일하게 검증됨. 고친 아이템 수가 망가뜨린 수보다 적으면 롤백. 한 번 리비전을 허용하고 그래도 실패하면 이전 하네스로 복원됨. 누적 개선의 세금(회귀)을 게이트로 걸러내는 구조. 앞서 정리한 회귀 제어 원칙의 분산 버전임.

4. 결과. 다섯 벤치마크에서 전부 유의미한 개선을 냄. BIRD(텍스트-투-SQL, 즉 자연어 질문을 SQL 쿼리로 바꿔 정확도를 재는 벤치마크) +13.4, DS-1000(판다스·넘파이 같은 데이터사이언스 라이브러리 코드 생성 벤치마크) +13.0, LiveCodeBench(최신 코딩 대회 문제를 계속 갱신해 학습 데이터 오염을 막는 벤치마크) +33.4, SWE-bench Verified(실제 GitHub 이슈 해결 벤치마크 중 사람이 검증한 서브셋) +20.0, ClawEval +8.3. 전부 Holm 보정(여러 비교를 동시에 할 때 유의성 판정을 보수적으로 낮추는 통계 교정) 후에도 통계적으로 유의함. 특히 LiveCodeBench 33.3%에서 66.7%로 두 배는 인상적임.

5. 제일 흥미로운 비교는 라우팅과 합병의 구분임. "분산된 전문가를 도메인별로 dispatch하는 것과 뭐가 다른가"라는 당연한 질문에 DS-1000에서 네 가지 집계 규칙을 동일한 스냅샷에 적용해서 답함. 최고 것 선택(집계 없음)이 59.5%, 도메인별 위임이 64.0%, global 메커니즘만 합병하면 66.5%, 스코프 타입 합병(EvolveNet)이 68.5%. 합병이 순수 라우팅을 4.5점 앞섬. 즉 도메인 전문가를 골라 보내는 것보다, 좋은 수정을 뽑아서 하나의 하네스에 녹이는 게 더 낫다는 것. 전역 메커니즘 승격이 주된 이익이었다는 분석도 있음.

![집계 규칙 비교](/images/2026-08-07-evolvenet-collaborative-harness-evolution/table-2-p12.png)

6. 경험 축적 측정도 검증됨. DS-1000에서 클라이언트 5개가 새로 푼 문제의 합집합 20개 중 합쳐진 하네스가 18개를 유지. 90% 보존율. 한 클라이언트만 푼 문제도 합병 후에 살아남음. 그리고 동일 예산의 중앙 집중식(병렬 5브랜치) 67.3% 대비 EvolveNet 70.7%로 분산 탐색이 더 효율적이었음. 모델을 deepseek-v4-flash에서 MiMo-V2.5로 통째로 바꿔서 파이프라인을 반복해도 정성적 패턴이 재현됨. 모델 독립적이라는 것.

7. 한계가 솔직하고 실무에 유용함. 라운드 3회, 클라이언트 7개 범위에서만 검증됐고, 라벨 있는 검증 데이터가 필요해서 완전 라벨 프리가 아님. 그리고 하네스가 3라운드 만에 14줄에서 409줄로 부풀었는데 이를 제어하는 사이즈 게이트가 없음. 데이터 국소성은 보장하지만 프라이버시 보장은 아님, 코드에 클라이언트 정보가 인코딩될 수 있음. 하네스 진화의 숨은 비용이 코드 비대화라는 지적은 운영자에게 그대로 해당함. 내 스킬과 프롬프트도 진화를 거듭할수록 부풀어서 컨텍스트 비용을 잡아먹음. 크기 게이트를 상시 두는 게 필요함.

8. 내 적용 결론. 여러 에이전트 인스턴스가 각자 다른 프로젝트에서 쌓은 개선(스킬, 프롬프트 수정)을 주기적으로 합칠 때 이 패턴을 씀. 수정을 mechanism 단위로 분해하고, 공통으로 좋은 건 글로벌 스킬로 승격, 특정 프로젝트에만 좋은 건 조건부로 유지. 그리고 합칠 때마다 기존 작업 회귀 테스트를 돌려서 고친 게 망가뜨린 것보다 많을 때만 채택. 도메인별로 나눠 쓰는 것보다 합쳐 쓰는 쪽이 이겼다는 게 이 논문의 실험적 결론임.
