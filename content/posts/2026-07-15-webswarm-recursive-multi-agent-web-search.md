딥 리서치 에이전트를 만들다 보면 항상 같은 벽에 부딪힘. 단일 ReAct 에이전트(생각-행동-관찰을 한 스텝씩 반복하며 도구를 부르는 표준 에이전트 루프)는 컨텍스트가 길어지면서 탐색이 얕아지고, 무작정 병렬로 나누면 이번엔 깊이를 못 파고. WebSwarm이라는 프레임워크가 이 "깊이냐 넓이냐" 딜레마를 재귀 위임으로 풀었음. 오케스트레이션 설계를 고민 중이라면 참고할 게 많은 구조임.

1. 출발은 문제 진단임. 기존 멀티에이전트 검색은 세 가지로 얕았음. 첫째, 재귀 깊이. "연도 → 브랜드 → 모델 → 속성" 같은 다단계 탐색에서 루트에서 한 번만 분해하고 끝냄. 나머지는 결국 단일 에이전트의 긴 궤적으로 떨어짐. 둘째, 협업 적응성. 팩트 조회는 빠르게, 넓은 탐색은 커버리지로, 깊은 탐색은 반복 검증으로 가야 하는데 하나의 전역 패러다임만 씀. 셋째, 증거 기반 확장 부재. 웹 정보가 집계 페이지에 몰려 있는지 시간축으로 흩어져 있는지 모르고 자르니 검색 효율이 떨어짐.

2. WebSwarm의 답은 실행 중에 만들어지는 위임 트리임. 루트가 과제를 받고, 각 노드는 지역 목표와 검색 모드를 부여받음. 해결 못 하겠으면 스스로 하위 노드를 더 위임함. 핵심은 과제만 나누는 게 아니라 "목표-모드 쌍"을 생성한다는 점임. 분해와 협업 구조가 같이 내려가는 것임.

![WebSwarm은 기존 멀티에이전트 오케스트레이션 패러다임들을 통합하고 재귀적 위임으로 발전시킨다. 좌측부터 병렬 분할정복, 직렬 핸드오프, 다중 샘플 집계를 보여주고, 우측이 WebSwarm의 재귀적 위임 구조다.](/images/2026-07-15-webswarm-recursive-multi-agent-web-search/fig-p1.png)

3. 검색 모드가 네 개임. atom은 원자적 팩트 조회로 ReAct가 직접 도구를 부름. deep은 searcher와 verifier를 붙인 직렬 탐색·검증 구조. wide는 독립 자식 노드를 동시에 뿌렸다가 병합하는 병렬 분할정복. entity_collect는 미지 집합을 여러 경로로 수집하고 중복을 제거함. 내가 이 구조를 쓸만하다고 보는 이유는, 실무 과제도 이 네 부류로 거의 다 분류되기 때문임. 검색 자동화 파이프라인을 짤 때 모드를 미리 정의해두는 설계 패턴 자체가 가져올 것임.

4. 두 번째 설계가 트릭임. wide 노드가 확장할 때 Web-Probing Agent가 경량 탐색을 먼저 함. 정보가 소수 집계 페이지에 몰려 있는지, 여러 소스에 시간·이벤트·엔티티 축으로 흩어져 있는지 파악한 뒤 확장 방향을 결정함. 분해 축을 실제 웹 구조에 맞추자는 것. 데이터 소스 구조를 먼저 보고 작업 분배를 정하는 건 에이전트뿐 아니라 사람 팀 오케스트레이션에서도 기본이었음. 이걸 자동화했다는 점이 의미 있음.

![WebSwarm 전체 아키텍처 개요. DeepWideSearch 벤치마크의 실제 실행 예시로, 루트 노드가 하위 검색 노드들을 재귀적으로 생성하고 각 노드가 atom/deep/wide/entity_collect 모드를 가진다.](/images/2026-07-15-webswarm-recursive-multi-agent-web-search/fig-p3.png)

5. 세 번째는 경험 전이임. wide 노드가 동종 자식을 여러 개 만들 때 소수의 scout 노드를 먼저 돌림. 그 궤적에서 신뢰할 만한 쿼리 패턴, 유용한 소스, 실패 경로를 뽑아 subtask experience로 정제하고 나머지 형제 노드에 주입함. 반복 시행착오가 줄어듦. 중요한 건 전이가 같은 인스턴스 내 동일 부모의 동종 노드 사이에만 일어난다는 것. 샘플 간 독립성을 안 깨는 설계임. "몇 개만 먼저 돌려서 교훈을 뽑고 나머지에 심는다"는 패턴은 멀티에이전트 비용 절감에 바로 써먹을 수 있음.

6. 성능은 GLM-4.5 백본(에이전트 두뇌 역할을 하는 기반 LLM) 기준으로 BrowseComp-Plus 68.00(단일 ReAct 50.50)임. BrowseComp-Plus는 여러 번 검색·교차 확인해야 풀리는 어려운 웹 탐색 질문으로 구성된 벤치마크임. WideSearch-EN Row F1 44.14(기존 최고 39.98)은 폭 넓은 다중 정답 검색 과제에서 표 행 단위로 정확도·재현율을 함께 반영한 F1 점수를 매긴 것임. DeepWideSearch-EN SR 6.58(기존 최고 5.26)은 깊이와 넓이를 동시에 요구하는 과제의 성공률(SR, success rate)임. 네 벤치마크에서 단일 에이전트는 물론 InfoSeeker, ROMA 같은 멀티에이전트 기준선까지 일관되게 앞섬. Kimi-K2, Qwen 계열 백본에서도 향상이 일관됐음. 개선이 모델 능력이 아니라 오케스트레이션 구조에서 온다는 게 핵심임. 백본을 바꿔도 살아있는 설계라는 뜻임.

![주요 실험 결과 표. WebSwarm이 모든 벤치마크에서 단일 에이전트 및 멀티에이전트 기준선을 일관되게 능가한다.](/images/2026-07-15-webswarm-recursive-multi-agent-web-search/fig-p5.png)

7. 내 결론은 이렇게임. 분해와 협업 구조를 사전에 고정해선 안 되고, 탐색 증거가 쌓이는 대로 공동으로 진화시켜야 함. 실무 파이프라인에 바로 이식할 세 가지는 모드 네 개 정의, 프로빙 후 확장, scout 경험 전이임. 근데 비용은 계산해봐야 함. 재귀 위임은 노드 수가 늘면 호출 비용도 재귀적으로 늘어남. 과제 하나에 트리가 얼마나 커지는지 상한을 걸어두는 게 운영의 관건임.
