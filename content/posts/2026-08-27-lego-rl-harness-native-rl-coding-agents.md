코딩 에이전트 하네스를 RL 훈련에 올리려면 보통 하네스 코드를 훈련용로 뜯어고쳤음. [LEGO-RL](https://arxiv.org/abs/2608.17393)은 반대로 훈련 엔진 쪽에서 하네스의 LLM 호출을 프록시로 가로채서 토큰 단위 정렬을 맞춤. 하네스 내부 제어 흐름을 거의 건드리지 않고 OpenHands SDK, Claude Code, OpenCode를 그대로 정책경사 RL(GSPO, 시퀀스 단위로 어드밴티지를 정규화하는 정책경사 알고리즘) 훈련에 연결함. Qwen3.5-35B-A3B 기준 SWE-bench Verified(실제 GitHub 이슈와 정답 패치를 모은 코딩 벤치마크 중 사람이 검증한 서브셋)에서 하네스별로 4~9.4%p 상승. 앞서 정리한 OpenForge RL과 같은 방향의 후속으로 볼 수 있어 정리함.

1. 문제. 코딩 에이전트 RL은 이제 실제 하네스 없이는 말이 안 되는데 툴 통합, 리포지토리 컨텍스트, 실행 피드백을 전부 하네스가 관리하기 때문임. 근데 하네스의 네이티브 실행 환경은 정책경사 훈련과 충돌함. 환경 크래시와 보상 해킹이 결과 보상 신호를 오염시키고, 훈련-추론 불일치가 롤아웃 행동과 정책 업데이트를 분리시킴. 특히 성가신 게 컴팩션과 재직렬화. 하네스가 컨텍스트를 줄이려고 히스토리를 다시 쓰면 훈련기가 계산한 로그확률과 실제 생성 스트림이 어긋남.

![훈련 인프라 개요](/images/2026-08-27-lego-rl-harness-native-rl-coding-agents/fig-1-p2.png)

2. 세 가지 기둥으로 해결함. 첫째, in-process LLM 프록시. 하네스 내부 LLM 호출을 가로채서 원시 생성 스트림을 캡처하고 트레이너 쪽에서 로그확률을 재계산함. 하네스가 히스토리를 다시 직렬화해도 정렬이 안 깨짐. 롤아웃-훈련 확률 상관 0.99 이상이 이 장치의 검증 결과임. 둘째, 샌드박스 오케스트레이션. 이미지 캐싱과 단계별 방어로 보상 해킹을 완화함. 테스트 통과만 요령껏 만드는 궤적에 대해 실행 단계마다 검증을 끼워 넣는 것. 셋째, 플러그인과 Live UI. 훈련이 관찰 가능해야 디버깅이 된다는 관점인데 에이전트 RL에서 이게 생각보다 큰 문제라 동의함.

3. 구조적 차이가 중요함. 전통적 agentic RL은 훈련 엔진이 환경 루프를 소유함. LEGO-RL은 하네스가 루프를 소유하고 훈련 엔진이 관찰하는 건 LLM 요청-응답 쌍의 시퀀스뿐임. 환경 루프 소유권이 훈련 엔진에서 하네스로 넘어갔을 때 생기는 새 문제 세트를 다루는 논문이라는 것. 훈련용 모조 환경을 따로 만들면 거기서 생긴 실력이 실제 하네스로 옮겨가는지가 항상 의문이었는데, 배포되는 하네스 그대로 훈련하니 그 질문 자체가 사라짐.

![운영 워크플로](/images/2026-08-27-lego-rl-harness-native-rl-coding-agents/fig-2-p7.png)

4. 결과. 같은 모델, 같은 알고리즘인데 하네스마다 다름. 베이스 성능은 OpenHands SDK 64.0% > Claude Code 62.4% > OpenCode 57.2%였고 훈련 후에는 70.4% / 68.2% / 66.6%로 격차가 줄어듦. OpenCode가 9.4%p로 가장 크게 오름. 약한 하네스일수록 훈련 이득이 크다는 패턴 읽기는 세 점에서 나온 추정이지만, 하네스가 곧 훈련 환경이라는 걸 숫자로 보여준다는 점은 논문 보고값 그대로임.

![훈련 곡선](/images/2026-08-27-lego-rl-harness-native-rl-coding-agents/fig-3-p9.png)

5. 파인튜닝을 안 하는 입장에서 가져갈 것. 첫째, 확률 상관 0.99라는 숫자는 컴팩션 있는 하네스에서 RL을 돌리는 사람에게 실질적 체크리스트임. 내 작업은 아니지만 내 에이전트 로그 분석에도 같은 질문이 적용됨. 기록된 궤적과 실제 실행이 같은 것인가. 컨텍스트가 재작성된 로그는 분석 대상이 아니라 오염된 대상이라는 것. 둘째, 보상 해킹 방어를 단계별로 끼워 넣는 구조는 그대로 벤치마킹 가능함. 최종 결과만 보지 말고 실행 단계마다 검증을 거치면 통과만 요령껏 만드는 궤적이 걸러짐.

6. 한계. 세 하네스 전부 코딩 에이전트라는 점, 단계별 보상 해킹 방어가 특정 벤치마크에 과적합됐을 가능성을 원문도 완전히 배제하지 않음. 그래도 "하네스 무수정 + 프록시 정렬"이라는 접근의 실현 가능성을 숫자로 보였다는 게 의미임. 하네스 진화와 하네스 훈련이 같은 기반 위에서 논의되는 흐름이 이제 완성 단계에 들어온 것으로 보임.
