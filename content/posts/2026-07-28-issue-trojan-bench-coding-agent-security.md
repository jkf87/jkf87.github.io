GitHub 이슈만으로 코딩 에이전트를 뚫는 실험 결과가 나옴. Cursor·Claude Code·Codex Desktop에 악성 이슈 4,176회를 던져서 2,776회, 즉 66.5%가 모든 방어선을 통과했음. 원문은 [arXiv:2607.20759](https://arxiv.org/abs/2607.20759).

1. 실험 설계가 현실적임. 정상 미해결 이슈 6개(SymPy·requests)를 시드로 4가지 공격 카테고리 × 6가지 전달 벡터로 696개 악성 아티팩트를 자동 생성함. 개발 워크플로에서 자연스러워 보이게 컨텍스트 정렬된 것들이라 실제 공격면과 가까움.

![공격 범주와 전달 벡터 설계](/images/2026-07-28-issue-trojan-bench-coding-agent-security/fig-1-p2.png)

2. 가장 치명적인 건 공급망 공격임. "재현하려면 이 패키지를 설치하라"는 식으로 존재하지 않는 PyPI 패키지를 유도했더니 96.6% 성공, 일부 조합은 100% 관통. 이유는 단순함. pip install이 너무 일상적인 개발 행위라 안전성 훈련이 이를 차단하지 않음. 설정 파일 중독(.cursorrules 수정으로 확인 프롬프트 우회)은 84.7%, 숨겨진 지속 훅은 59.8%, 자원 고갈은 24.9%임.

![공급망 공격 성공률](/images/2026-07-28-issue-trojan-bench-coding-agent-security/fig-2-p4.png)

3. 전달 벡터 결과가 충격적임. PDF, 웹사이트, 소스코드 주석, 이슈 코멘트, 이슈 본문 다섯 벡터가 전부 동일한 72.2% 성공률. 더 이상한 건 페이로드를 숨기나 안 숨기나 결과가 똑같다는 것. 흰 글자, HTML 주석, 1pt 폰트로 숨겨도 72.2%, 그냥 보이게 해도 72.2%. 인간 리뷰어 눈에 안 보이는 페이로드가 에이전트에 의해 실행됨. 인간 감독 모델이 근본적으로 깨졌다는 뜻임.

![전달 벡터별 관통률](/images/2026-07-28-issue-trojan-bench-coding-agent-security/fig-3-p6.png)

4. 그리고 방어선 분석이 핵심임. 1,400회 저항 사례를 분석했더니 모델 수준 명시적 거부가 82.9%, 이미지 alt-text에 대한 신뢰 분류가 17.1%, 그리고 프레임워크 수준 방어가 0건. 샌드박스, 명령 승인, 네트워크 격리 그 어떤 것도 모델이 허용한 작업 공간 내 악성 행위를 못 막았음. 모델이 전부인 구조임.

![방어선 분석 결과](/images/2026-07-28-issue-trojan-bench-coding-agent-security/fig-4-p9.png)

5. Spotlighting 방어도 실패함. 신뢰할 수 없는 콘텐츠를 마커로 감싸는 기법인데 악성 페이로드가 계속 실행됨. 이유는 근본적임. 방어 지시와 주입된 콘텐츠가 같은 자연어 채널에 있어서, 지시 따르기 목표가 안전 경계 준수를 덮어써버림. 자연어 안에서 자연어를 이기려는 설계는 안 됨.

6. 필자 운영 관점에서 결론이 명확함. 외부 이슈·PR·문서를 읽는 에이전트 파이프라인은 모델의 판단을 방어선으로 삼으면 안 됨. 실제로 취할 조치는 세 가지. 외부 콘텐츠 처리 에이전트는 쓰기 권한과 네트워크가 분리된 샌드박스에서만 돌리기, 패키지 설치류 명령은 화이트리스트 기반으로 승인제 처리, 그리고 PR 리뷰를 인간 눈이 아니라 diff 도구로 기계 검수하기. 모델 안전성이 좋아질 때까지 프레임워크 격리가 유일한 실방어임.

7. 문제제기. 벤치마크가 6개 시드 이슈 기반이라 공격 다양성이 제한적이고, 실제 오픈소스 프로젝트에서 대규모 재현이 필요함. 그래도 GitHub 프로젝트의 22~29%가 이미 코딩 에이전트를 쓰고 있다는 채택률 숫자 앞에서 위험은 이론적이지 않음.

8. 남는 결론. 코딩 에이전트 보안은 지금 모델 안전성 훈련이라는 얇은 종이 한 장에 의존하고 있음. 신뢰 경계를 자연어가 아니라 시스템 권한으로 그어야 하고, 그 전제 없이 외부 입력을 받는 에이전트는 사고 대기 상태로 보는 게 맞음.
