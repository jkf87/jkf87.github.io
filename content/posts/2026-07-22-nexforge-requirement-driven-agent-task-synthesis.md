에이전트를 훈련시키거나 평가하려면 실행 가능한 환경과 고품질 궤적(에이전트가 작업을 수행하며 남긴 단계별 실행 기록)이 필요한데, 이걸 만드는 기존 방식은 전부 "미리 마련된 도구·저장소·스킬 그래프"에 매여 있었음. [NexForge](https://arxiv.org/abs/2607.14186)는 사용자 요구사항 한 줄에서 출발해서 실제 수요를 조사하고, 분포를 제어하고, 실행 환경과 전문가 궤적까지 자동 합성하는 파이프라인임. 직접 파인튜닝을 안 하더라도, 이 구조는 내 업무자동화 에이전트의 테스트 케이스를 만드는 방법에 그대로 이식할 수 있어 정리함.

1. 배경. SkillSynth는 미리 정의된 스킬 그래프, Terminal-World는 스킬 기반 환경, R2E-Gym이나 SWE-smith는 특정 코드 저장소에 의존함. 이렇게 되면 세 가지 문제가 생김. 입력 substrate 크기가 데이터 크기의 상한이 되는 확장 한계, 새 도메인마다 파이프라인을 다시 짜야 하는 비용, 그리고 실제 수요가 아니라 substrate의 편향이 태스크 분포를 결정하는 왜곡. 훈련 데이터가 실제 사용 패턴을 반영해야 한다는 건 모델 훈련이든 내 자동화 도구의 회귀 테스트든 똑같이 중요한 문제임.

![기존 substrate-bound 방식과 NexForge 비교](/images/2026-07-22-nexforge-requirement-driven-agent-task-synthesis/fig-2-p2.png)

2. 핵심 통찰은 분리임. "무엇을 연습할지"와 "어떻게 실행 가능하게 만들지"를 나누는 것. 요구사항이 들어오면 먼저 웹 검색이 되는 리서치 에이전트가 실제 전문가 워크플로와 기술 문서, 역할 기술서를 조사함. 결과물은 둘임. 태스크 형태·산출물·소스 전략·런타임·언어·난이도에 대한 가중 분포인 태스크 수요 프로파일과, 조직·직무·워크플로 같은 맥락 정보인 시나리오 저수지. 시나리오는 태스크 형태를 명시하지 않고 맥락만 기술하니까 분포를 독립적으로 오염시키지 않음.

3. 두 번째 단계가 분포 인식 컴파일임. 시나리오마다 순차적 호환성 검사를 돌림. 시나리오 → 태스크 타입 → 산출물 → 소스 전략 → 런타임 → 언어 → 난이도 순서로, 각 단계에서 이전 선택과 호환되는 옵션만 남기고 프로파일 가중치로 샘플링함. 이 필터를 적용하니 디렉티브-시나리오 호환률이 7%에서 81%로 뜀. "무작위로 조합하면 아홉 개 중 여덟 개는 말이 안 되는 작업"이라는 뜻이고, 그걸 구조적으로 걸러낸 것임.

![NexForge 전체 파이프라인](/images/2026-07-22-nexforge-requirement-driven-agent-task-synthesis/fig-3-p4.png)

4. 세 번째 단계가 실행 환경 구축임. 디렉티브가 정해지면 공개 저장소와 문서에서 자료를 채굴하고, 워크스페이스 구조를 설계하고, 실제 돌아가는 환경을 만들고, 교사 모델(GPT-5.5)로 궤적을 수집하고, 오류 전용 출력과 중복을 정제함. 이 흐름을 실무 테스트 데이터로 옮기면 이렇게 됨. "이 자동화가 잘 되는지 확인하고 싶다"가 아니라, 리서치로 내 업무의 실제 작업 유형 분포를 만들고, 거기서 케이스를 뽑고, 각 케이스를 실제로 돌려볼 수 있는 입력 상태를 구축하는 것. 사람이 샘플 케이스를 감으로 고르는 것보다 편향이 훨씬 덜함.

5. 성과가 인상적임. Qwen3.5-35B-A3B에 NexForge 데이터를 3.6K개만 줘도 Terminal-Bench 2.0에서 52.0%, 43.2K로 스케일하면 58.4%로 Terminal-Bench 2.0(실제 터미널에서 명령을 내려 과제를 완수하는 능력을 재는 벤치마크) 기준 Claude Opus 4.6 + Claude Code(58.0%)와 동급이 됨. 같은 32B급 베이스에서 기존 최고였던 Terminal-World(31.5%)를 크게 앞지름. 데이터가 늘수록 일관되게 오르는 스케일링 곡선도 확인됐고, 오피스 도메인 GDPval(전문가의 실제 업무 과제를 AI가 수행하는지 재는 오피스 작업 벤치마크)에서도 813 → 1384 Elo(상대 실력을 점수로 환산해 비교하는 평점 척도)로 꾸준히 상승함. 공개된 Nex-N2-Pro는 Terminal-Bench 2.1에서 75.3%로 GPT-5.5(83.4%)에 근접한 오픈 모델 SOTA(최고 성능 기록)임.

![Terminal-Bench 2.0 스케일링 결과](/images/2026-07-22-nexforge-requirement-driven-agent-task-synthesis/fig-1-p1.png)

6. 왜 잘 되는지 ablation이 설명함. 프로파일을 빼면 태스크 타입이 24개에서 3개 수준으로 무너지고 top-1 시그니처 커버리지가 78.5%로 몰림. 시나리오를 빼면 궤적이 짧아지고 도구 호출이 줄어듦. 즉 "무엇을 연습할지"(프로파일)와 "현실감"(시나리오)이 상호 보완적이며, 둘 다 있어야 다양하면서 실제 같은 데이터가 됨. 내 테스트 케이스 설계에서도 유형 다양성과 맥락 현실성은 따로 관리해야 한다는 교훈임.

7. 크로스 도메인 적응도 확인됨. 같은 코어 파이프라인으로 터미널(소프트웨어 엔지니어링 54%, 시스템 관리 12% 등 24개 타입)과 오피스(데이터 분석 21%, 문서 리뷰 17% 등 15개 타입)을 커버함. 요구사항 명세만 바꾸면 도메인이 바뀜. 도메인별 인프라를 다시 짜지 않아도 된다는 게 이 구조의 실용적 가치임.

8. 근데 냉정하게 볼 지점. 교사 모델이 GPT-5.5라 비용이 만만치 않음. 그리고 정답 검증자 없이 궤적을 필터링해서 불완전한 궤적이 섞일 수 있다고 저자들이 인정함. 검증자 없는 궤적 수집은 결국 교사의 실수까지 학습된다는 구조적 리스크가 있고, 다음 버전에서 머신 체크 가능한 검증자를 넣겠다고 함. 이 부분은 AHA류의 "반증 가능한 성공 판정"과 연결되는 문제임.

9. 실무 적용 요점 세 개. 첫째, 내 에이전트 회귀 테스트 케이스를 감으로 고르지 말고 수요 프로파일을 만들어서 분포 기반으로 뽑기. 둘째, 케이스 유형과 시나리오 맥락을 분리 관리해서 다양성과 현실성을 같이 확보하기. 셋째, 합성된 케이스는 호환성 필터를 돌려서 말이 안 되는 조합을 만들자마자 걸러내기. 전부 오늘 할 수 있는 일들이고, 파이프라인 자체가 리서치 에이전트 + 생성 에이전트 조합이라 그대로 조립 가능함.
