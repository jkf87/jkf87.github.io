에이전트 운영 중 반드시 만나는 장면을 통제 실험으로 재현한 벤치마크가 나옴. 모델이 분명 정답을 아는데 API 결과가 다르게 내려오면 조용히 자기 답을 버린다는 것. 원문은 [arXiv:2608.26295](https://arxiv.org/abs/2608.26295).

1. 설계가 이 벤치마크의 차별점임. 542개 검증된 사실 질문에서 모델별 클로즈드북 답을 먼저 유도하고, 정답/오답이 통제된 도구 결과를 삽입함. 실행 가능한 도구를 썼고 7-9B 오픈웨이트 모델 5종에 6,504개 에피소드를 돌림. 기존 평가가 "도구와 기억 중 뭘 선호하나"만 쟀다면 이건 정답 조건별 판단을 측정한 것임.

![출처 정확성 4조건 설계(논문 Figure 1)](/images/2026-08-28-memtoc-memory-tool-conflict/fig-1-p2.png)

2. 핵심 숫자. 정답을 가진 모델이 틀린 도구 결과를 만나면 6.5~17.1%만 자기 답을 지킴. 올바른 도구는 86.0~93.1%로 잘 따르는데 틀린 도구도 비슷하게 따름. 둘 다 틀린 경우엔 78.4~86.0%로 도구 답을 그대로 반복함. 판단해서 고르는 수준이 아니라 복사에 가깝다는 것.

![MemToC 구성 개요(논문 Figure 2)](/images/2026-08-28-memtoc-memory-tool-conflict/fig-2-p3.png)

![도구를 무조건 믿으면 안 됨](/images/2026-08-28-memtoc-memory-tool-conflict/gifs/believing-everything.gif)

3. 왜 문제냐. 도구는 항상 옳지 않음. API는 실패하고 검색 결과는 오래되고 계산기도 버그가 있음. 모델이 도구 결과를 무조건 복사하면 도구 에러가 그대로 최종 답이 되는 경로가 만들어지고 파이프라인이 길수록 오염이 증폭됨. 앞서 정리한 도구 결과 권위 연구와 정확히 같은 실패 구조가 정답 통제 조건에서도 재현된 셈임.

![도구 관찰 조건별 에피소드 예시(논문 Figure 3)](/images/2026-08-28-memtoc-memory-tool-conflict/fig-3-p11.png)

4. 추가 발견 하나. 같은 질문과 에피소드에서 지시문 표현만 3가지로 바꾸면 모델 간 순위가 흔들림. 프롬프트 표현 하나로 순위가 바뀐다는 뜻이라 도구 신뢰도 랭킹 해석은 조심해야 한다는 교훈임.

5. 파인튜닝 실험도 냉정함. 체인 레벨 크로스피팅으로 SFT와 DPO를 비교했는데 판정 기준이 비대칭임 — 정답 유지는 오르되 올바른 도구 추종은 줄지 않아야 통과. 그 결과 4개 백본 중 2개에서만 통과. 그리고 20개 조합 중 19개에서 기권(abstention)이 감소함. 도구 에러 후나 답 불가 입력에서 아는 척이 늘어난 것. 개선은 드물게 깨끗하게 온다는 경고임.

6. 필자 적용 포인트. 블로그 파이프라인도 스크래핑 결과·검색 결과가 오염됐을 때 에이전트가 그대로 베껴 쓰는 위험이 있음. 대응은 두 가지. 첫째, 무조건 도구 우선 정책을 버리고 도구 출력에 신뢰도·출처·타임스탬프 메타데이터를 붙여 모델이 판단 재료를 갖게 하는 것. 둘째, 도구 출력과 모델 지식이 충돌하면 양쪽 다 제시하거나 기권하게 하는 규칙을 게이트에 다는 것. 기권은 실패가 아니라 정확도의 일부라는 걸 이 논문의 부작용 결과가 반증함.

7. 문제제기. 대상이 7-9B 오픈웨이트 5종이라 프론티어 모델에서 같은 패턴인지는 미확인임. 그리고 사실형 QA 중심이라 절차형 작업에서의 충돌 해소는 별개 문제임.

![아무도 못 믿는 상황](/images/2026-08-28-memtoc-memory-tool-conflict/gifs/trust-issues.gif)

8. 남는 결론. "도구를 신뢰하라"는 통념을 소스 정확성을 통제해 처음으로 뒤집어 본 측정이라는 게 이 벤치마크의 가치임. 도구 결과는 입력이지 진리가 아니며, 충돌 시 판단 규칙을 시스템에 명시해두는 게 에이전트 파이프라인의 필수 부품이라는 것.
