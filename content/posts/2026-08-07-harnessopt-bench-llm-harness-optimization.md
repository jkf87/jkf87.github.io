LLM이 다른 LLM 에이전트의 하네스(프롬프트, 도구, 제어 흐름, 메모리)를 자동 최적화하는 능력을 재는 벤치마크가 나옴. 하네스 개선을 에이전트에게 맡기는 사람이 늘어나는 시점에 필요한 데이터라 정리함.

1. 배경. 코드 최적화는 단위 테스트로 저렴하게 검증되지만 하네스 변경의 효과는 확률적 에이전트를 여러 케이스에서 반복 실행해야 측정 가능함. 평가 비용이 구조적으로 비쌈. [HarnessOpt-Bench](https://arxiv.org/abs/2608.06301)는 이 특성을 반영한 첫 통합 평가 프로토콜임.

2. 프로토콜 설계가 견고함. 후보 하네스 전체가 수정 대상이고, 모델·환경·검증자는 불변값으로 고정. 개발/검증/테스트 비중첩 분할로 테스트는 검색 중 접근 불가. 예산은 파티션당 100회 평가 호출과 케이스 실행 한도. 목적 함수는 정규화 gain(베이스라인 대비 개선 폭을 0~1 스케일로 조정한 점수).

3. 주요 결과 RQ1. 모델 효과가 하네스 효과의 약 1.8배. 작업·하네스를 고정하고 모델만 바꾸면 gain이 평균 0.142 이동하는데 하네스를 바꾸면 0.079. "누가 하네스를 최적화하는가"가 "어떤 하네스에서 하는가"보다 크다는 것.

4. RQ2. 모델 릴리즈가 거듭될수록 이 능력이 향상되고 있음. GPT 5 시리즈는 +0.03 → +0.49로 단조 증가. 하네스 최적화 능력이 프론티어 경쟁 축으로 편입되고 있다는 것.

5. RQ3. 네이티브 하네스의 일관된 우위는 없음. 공용 하네스 11승, 네이티브 9승. GPT 모델에서만 자사 하네스가 우세했고 Claude와 Kimi는 차이 없음. 어떤 하네스도 모든 모델에서 이기지 못함 — 작업-모델 조합 의존이라는 것.

6. 제일 실용적인 발견은 탐색 행태임. 레버 커버리지(프롬프트, 컨텍스트 관리, 스텝 캡, 재시도, 도구 스키마, 답 추출, 검색 정책, 추론 강도의 8개 축을 얼마나 넓게 건드렸나)와 gain의 상관이 모든 작업에서 양수(Spearman +0.34~+0.88. Spearman은 순위 기반 상관계수). 반면 trace 읽기 비율은 음수(-0.31~-0.64). 넓게 튜닝한 옵티마이저가 이기고, 로그만 깊게 읽는 옵티마이저가 진다는 것.

7. trace 읽기가 부정적이라는 게 흥미로움. 111개 셀 중 상세 trace를 요청한 건 7개뿐. 성공하는 최적화는 실행 로그 파기가 아니라 레버 조합 탐색에서 나온다는 것. 내가 하네스 개선할 때 로그 분석에 매몰되는 습관과 반대 방향임.

8. 예산 소비 패턴도 봐둘 것. 중위 옵티마이저는 평가 호출 8회(4%)만 쓰고 케이스 예산을 82% 소진. 병목은 호출 한도가 아니라 실제 케이스 실행 횟수임. 하네스 개선 실험을 설계할 때 케이스 실행 비용이 진짜 예산이라는 것.

9. 검증-테스트 갭도 확인됨. 대부분의 실행에서 검증 최고 점수가 테스트 점수보다 높음. 하네스 개선을 검증 셋에서만 평가하면 과대평가한다는 것 — 이전에 본 하네스 진화 연구의 과적합 결과와 같은 맥락. 홀드아웃이 필수.

10. 여기서 문제제기. 내 하네스 개선 루프에 적용할 것. (1) 하나의 레버만 반복 조정하지 말고 여덟 개 축을 의식적으로 순회할 것. (2) 로그 정독은 특정 문제 디버깅 때만. (3) 검증 케이스와 보고용 케이스를 분리할 것. (4) 케이스 실행 비용 기준으로 실험 예산을 짤 것.

11. 한계. seed가 "측정 가능한 중간 성능"을 보이도록 골라진 것이라 일반적 시작점과 다름. 단일 타겟 모델 설정이라 멀티모델 하네스엔 그대로 안 적용됨. 중간 순위 모델 간 구분은 해상도 밴드 이내인 경우가 많아서 변별력에 한계.

12. 결론. 하네스 최적화 능력이 재현 가능한 평가 대상이 됐고, 그 능력의 격차는 모델 선택에서 벌어지고 있음. 그리고 잘하는 최적화자의 행태가 명확함 — 넓은 레버 탐색, 적은 로그 소비. 근데 결국 케이스 실행 비용이 예산의 본체라서, 평가 인프라 없이는 이 능력을 쓸 수도 재질 수도 없다는 것까지가 결론임.
